# MIK-7630 — MCP Events: webhook, backend and task events as subscriptions

Status: design and test plan for 4.0.0; no product code yet.
Ticket: MIK-7630 (Linear, milestone v4.0.0). Criteria: `MIK-7630.*` in
`docs/requirements/RELEASE-4.0.0-scope-update.md`.
Companion: `docs/design/2026-10-01-mik-7630-event-sources-4.0.0.md` (the three
sources the 2026-10-01 split deferred and the 2026-10-06 operator decision
moved back into 4.0.0, which plug into the adapter interface in §4).
Fail-fast harness: `scripts/dev/mcp_events_failfast.py`.

## 1. Problem

An MCP client that supports the draft Events extension (ChatGPT today) can ask a
server for `events/list`, subscribe with `events/subscribe` and a callback URL,
and act when the server POSTs a signed event. The gateway sits in front of many
backends and already receives signed inbound webhooks, but it answers none of the
`events/*` methods. The aim: any backend behind the gateway becomes
subscribable, and the backend itself needs no support for the extension.

Three sources ship in 4.0.0:

| Source | What becomes an event | Exists today as |
|---|---|---|
| Inbound webhook | each accepted POST to a configured webhook route | `src/scheduler/mod.rs`, `src/config/features/webhooks.rs` |
| Backend notification | `notifications/resources/updated` and `notifications/{tools,resources,prompts}/list_changed` from any MCP backend | backend notification intake (§3.3) |
| Task settled | a task reaching a terminal state | task store (§3.4) |

Three more are designed to slot in at 4.0.1 without rework (companion doc): REST
capability watch (poll and diff), gateway operational events (budget, health,
kill switch) and scheduler time events.

Out of scope for 4.0.0: poll and push delivery (`events/poll`, `events/stream`),
the `gap` and `terminated` control envelopes, cursor replay (every 4.0.0 event
type is emit-only and returns `cursor: null`), and the optional ed25519 server
identity signature. ChatGPT supports none of these: "Polling, streaming, and the
draft's `gap` and `terminated` control notifications are not supported by this
integration" ([OpenAI, MCP Events](https://developers.openai.com/plugins/build/mcp-events)).

## 2. Sources and the version this design targets

- Draft extension: `modelcontextprotocol/experimental-ext-triggers-events`,
  `docs/design-sketch-proposal.md`, last changed at commit `28ec35e9`
  (2026-09-04); repository head `6682596d` on 2026-10-01. Quotes below are from
  that revision. The extension is a draft; §8 (F13) says what happens if it moves.
- Consumer profile: OpenAI, *MCP Events* (fetched 2026-10-01). It requires
  protocol `2026-07-28`, which the gateway already serves.
- Signature scheme: Standard Webhooks, `v1,` HMAC-SHA256 over
  `webhook-id.webhook-timestamp.body`.
## 3. Architecture

 webhook route ──┐

  task status)    │     queue)       re-check      (§3.6)      store)     sign per attempt)

One new module, `src/events/`, owns everything right of "sources". It has no
dependency on any one source; sources depend on it through the trait in §4.
That one-way dependency is what lets the 4.0.1 sources land without touching
the core.

### 3.2 Event flow

1. A source turns something that happened into a `SourceEvent` (§4) and
   `try_send`s it into one bounded queue (`events.queue_depth`, default 1024).
   Sources never block. A full queue drops the event and counts it per source.
2. The fan-out task takes each `SourceEvent` and finds live subscriptions with
   the same `name`, whose `arguments` the source's `matches` accepts.
3. For each match, fan-out **re-checks access now**, not at subscribe time:
   the subscription's principal must still pass `EventSource::authorize` and
   the visibility predicate (§3.7). On failure the subscription is deleted
   (F9) and nothing is sent.
4. It builds the body and runs the firewall scan (§3.6). On a block the
   occurrence is dead-lettered (F8).
5. (Rate limit and budget are applied per attempt in step 7, not here, so
   a backlog drained later or a retry cannot escape them.)
6. It writes an outbox record (§5) holding the exact body bytes, and wakes
   the delivery worker.
7. Before **every** attempt, including retries and replays, the worker
   re-runs the access re-check of step 3, takes a rate-limit token, and
   checks the budget against current spend. Revoked access cancels every
   pending record of that subscription; no token defers the attempt; a
   refused budget dead-letters it. Only then does it sign and POST (§3.5),
   record an audit entry, and mark the record delivered, schedule a retry or
   dead-letter it.

Steps 2–6 for one occurrence run on one task, so ordering per subscription
follows source order. Delivery is concurrent across subscriptions (at most
`events.max_in_flight`, default 32) and serial within one subscription. That
gives a receiver in-order arrival except after retries, which the draft
allows ("Concurrent deliveries and retries may therefore arrive out of
order").

### 3.3 Backend notifications: what exists and what is new

Facts:

- The gateway already produces `notifications/tools/list_changed` for each
  backend whose tool set changes. `announce_tools_changed(backend)`
  (`src/gateway/router/mod.rs:264`) publishes it into `SubscriptionRegistry`,
  scoped to callers who may access that backend.
- Notifications a backend sends **outside** a request are dropped. The only
  sink is request-scoped (`src/transport/notification_sink.rs`, a
  task-local). Nothing produces `resources/updated`,
  `resources/list_changed` or `prompts/list_changed` from a backend today:
  the registry only matches those methods in its filter
  (`subscription_registry.rs:289-291`).
- `notifications/resources/updated` is only sent for URIs the client
  subscribed to upstream (`resources/subscribe` on pre-2026 backends,
  `subscriptions/listen` with resource URIs on 2026-07-28 backends).

So source (b) is two parts with different costs:

| Part | Event names | Mechanism | Cost |
|---|---|---|---|
| b1 | `backend.<server>.tools_changed` | an internal `Listener` on `SubscriptionRegistry` (`subscribe()`); no new producer | small |
| b2 | `backend.<server>.resource_updated` (argument `uri`), `backend.<server>.resources_changed`, `backend.<server>.prompts_changed` | a new **upstream listener** per backend, opened only while at least one event subscription needs it | the largest piece of 4.0 |

The upstream listener (b2) takes one of three forms, chosen by the backend's
recorded protocol era (`src/backend/era.rs`):

- **2026-07-28 HTTP backend:** a long-lived `subscriptions/listen` POST to
  the backend that names the needed notification kinds and resource URIs.
  Its SSE response is read until it closes, then reopened with backoff.
- **Pre-2026 HTTP backend:** the backend's GET SSE stream, plus
  `resources/subscribe` / `resources/unsubscribe` for each URI.
- **stdio backend:** the reader loop already sees unsolicited lines
  (`src/transport/stdio.rs:508`, `capture_notification`). The change routes
  any notification that arrives outside a request scope to a per-backend
  broadcast instead of dropping it, plus `resources/subscribe` per URI.

Each received notification goes straight to the events hub as a
`SourceEvent`, where the per-subscription `authorize` (including URI-level
read access for `resource_updated`) applies. It is deliberately **not**
republished into `SubscriptionRegistry`: that registry scopes by backend
only, so republishing would show resource URIs to downstream
`subscriptions/listen` clients who may see the backend but not the resource.
Opening that path is a separate decision with its own URI-level filter.

Lifetime is reference-counted through the adapter hooks (§4). The first
event subscription for `(backend, uri)` opens or extends the upstream
subscription, and the last unsubscribe or expiry closes it. If the backend is offline when the
first subscription arrives, the subscribe still succeeds: `on_first_subscriber`
records the need and the reconnect loop opens the upstream subscription when
the backend returns (events in between are lost, emit-only). Only a policy
refusal fails the subscribe. With no event
subscriptions there is no upstream connection, so a gateway with events off,
or with no subscribers, opens nothing new. Upstream disconnects reconnect
with jittered backoff (cap 5 min). An event missed while disconnected is
lost, which is the emit-only contract.

### 3.4 Task settled

The tap is `TaskExecutor::published` (`src/gateway/task_service/execution.rs:466`).
It already publishes `notifications/tasks {taskId, status}` with audience
`Any` (`:483`). The event source does **not** consume that broadcast, for
two reasons: `Any` carries no owner, and the record has no settle time. The
source instead registers a second callback at the same point that receives
the committed task record. It emits `task.settled` only when the record's
status is terminal (`completed`, `failed`, `cancelled`), and the payload
carries `{taskId, status, settledAt}`. The result is never in the payload:
the subscriber fetches it with `tasks/get`, which applies its own ownership
check. Only the task's owning principal can subscribe or receive the event:
`authorize` and the fan-out re-check both compare the task store's owner
with the subscription principal. Argument: optional `taskId`; omitted means
all of the principal's tasks.

### 3.5 Delivery client

One `reqwest::Client` built from `pinned_client_builder()`
(`src/security/ssrf/mod.rs:129`) with `redirect(Policy::none())`, a 5 s
connect timeout, a 10 s total timeout, and a 4 KiB cap on reads of the
response body (the verification echo is the only body the gateway reads).
`PinningResolver` resolves the callback host once per connection, rejects the
connection if any returned address is non-public, and hands reqwest only the
checked addresses. reqwest keeps the original hostname for SNI and
certificate checks, which is the draft's "connects directly to that validated
IP (sending the original hostname in the `Host` header / TLS SNI)". IP-literal
URLs are refused at subscribe time by `validate_url_not_ssrf`. The same client
sends verification POSTs and deliveries, so both get the same checks
(*OpenAI*: "Apply these checks to verification requests as well as event
deliveries").

An operator allowlist `events.callback_allow_private` (a list of CIDRs,
default empty) is the draft's "unless explicitly configured to allow them".
It is meant for a receiver on the same private network and for tests. The
shared resolver has no allowlist today, so the events client is built with
`PinningResolver::with_allowed(cidrs)`, a new constructor that exempts exactly
the configured CIDRs; every other caller is unchanged. The subscribe-time
`validate_url_not_ssrf` call is likewise skipped only for IP literals inside
those CIDRs. An empty list (the default) is byte-for-byte today's policy.

Signing: `webhook-signature = "v1," + base64(HMAC-SHA256(key, id + "." + ts +
"." + body))`, computed per attempt with a fresh `ts`. During a rotation grace
window the header carries two space-separated signatures, new key first.

### 3.6 Payload safety: firewall, provenance, ids

**Firewall.** The body's `data` object goes through
`Firewall::check_response_artifact` (`src/security/firewall/response.rs:20`)
with a new `ResponseArtifactKind::EventPayload` and the event's source as the
policy target. That is the same boundary MIK-7407 made mandatory for tool
results. Redactions apply in place. A redacted field that then fails
`payloadSchema` (for example a required string that was removed) is
dead-lettered, not sent malformed. A block verdict dead-letters the
occurrence. The scan runs once, before the outbox write, so retries and
replays never send unscanned bytes. Replay re-scans (§3.8), because the
policy may have changed since.

**No injected text.** The gateway adds nothing to `data` beyond what the
source produced and the firewall redacted. No preamble, no "treat this as
data" sentence, no wrapper field. The draft puts sanitising on the client
("Clients SHOULD sanitize or sandbox event payloads before presenting them to
an LLM"), and *OpenAI* says "do not add instructions telling the model how to
behave inside the event payload". A test pins the exact key set (row T20).

**Provenance.** `_meta` on `EventOccurrence` is "Reserved for protocol/extension
metadata … Not governed by `payloadSchema`." The gateway puts its receipt
there, under `_meta["io.github.mikkoparkkola/provenance"]`, using the
existing `RuntimeProvenanceReceipt` shape (`src/trust/result_provenance.rs`)
with a new subject kind `event`: source kind, backend id where there is one,
event name, `observed_at`, and the gateway's signature when
`enable_provenance_stamping` is on. Choosing `_meta` over `data` keeps
`payloadSchema` honest. Choosing it over a header keeps the receipt inside
the HMAC-covered body.

**Event ids.** The draft: "when the upstream source provides a stable event
identifier … the server SHOULD use that value as `eventId`". The gateway
derives `eventId = "evt_" + hex(sha256(source_kind ‖ upstream_id ‖
subscription_id))[..32]`, where `upstream_id` is the source's stable id
(the inbound delivery header such as `X-GitHub-Delivery` when configured, the
task id plus terminal status for task events, or a gateway-minted occurrence
id otherwise). Mixing in the subscription id departs from the literal SHOULD.
Without it, one occurrence fanned out to two subscriptions that share a
callback URL would carry one `webhook-id`, and a receiver deduping on
`webhook-id` (which the draft tells it to do) would drop the second. The id
is still stable across retries, gateway restarts and replays, which is the
property the dedupe needs.

**Inbound dedupe.** Webhook routes have no replay window today (the HMAC
covers the body only). The source keeps a 24 h seen-set per route. A route
that configures `delivery_id_header` dedupes on the delivery id only, so an
upstream retry is dropped. A manual redelivery that keeps the id (GitHub's
"redeliver" keeps `X-GitHub-Delivery`) is also dropped within the 24 h
window. A dedupe drop happens before any event exists, so it leaves no
outbox or dead-letter record to replay; re-emission needs a new delivery id
from the provider or the window to pass. A redelivery with a new id arrives. A route without the
header does no dedupe by default, so two identical legitimate occurrences
both arrive. A route may opt in with `dedupe: body`, which keys on the
SHA-256 of the **signed body**, the one key an attacker cannot change without
breaking the HMAC; the operator who opts in accepts that an identical
legitimate body within 24 h is dropped. Replay protection proper needs a
signed timestamp, which these upstream HMAC schemes do not carry; §7.5 states
the limit.

### 3.7 Who may see what: visibility, tenant guard, audit, limits

**Visibility.** One predicate serves `events/list`, `events/subscribe` and
fan-out:

- webhook and backend events: the caller passes `admits_backend` for the
  backend behind the source (`src/gateway/meta_mcp/visibility.rs:135`). A
  caller who cannot see a backend's tools cannot see its events.
- task events: the caller owns the task.

The visibility predicate and `EventSource::authorize` are separate checks:
the first hides the event type, the second judges one subscription's
arguments (for example, a `uri` the caller may not read).

**Tenant guard.** The gateway has no per-principal tenant entitlement to
compare against: MIK-7116's guard limits how many distinct tenants one
principal touches in a window (`TenantGuard::check`,
`src/security/firewall/tenant_guard.rs:108`), and MIN.2 flags or blocks a
principal that read tenant A's sensitive data and then reads tenant B's.
Events reuse exactly those semantics and invent no new ones. Each delivery
is treated as a read by the subscription principal: its `data` is attributed
with `response_tenants` (`:152`) and recorded in the same per-principal
window, and the MIN.2 verdict applies. In observe mode the event is delivered
and the finding is audited; in block mode it is dead-lettered with reason
`tenant`. An events-specific entitlement ("principal P may only receive
tenant T") would be a new policy model and is out of scope; §7.4 records
this limit.

**Audit.** Every delivery attempt writes one record through the MIN.1 writer
`log_invocation_attributed` (`src/security/transparency_log_attributed.rs:60`)
with a new `InvocationTarget::EventDelivery`. The record holds: subscription
id, event name, `eventId`, attempt number, principal, tenant attribution,
callback host (never the full URL), status category, firewall verdict, and
the SHA-256 of the body sent. It never holds the body, the secret or the
callback query string. The record is written before the POST, with status
`sending`: a log that refuses it means no POST, and the record retries. How
the attempt ended (status category, delivered) follows as an
`events.delivery_outcome` record joined on `outcome_of_attempt` (MIK-7784). Subscribe, refresh, unsubscribe, verification outcome,
dead-letter and replay each write one governance record through
`append_event` (`src/security/transparency_log.rs:410`).

**Rate limit and budget.** Each subscription gets a `governor` limiter
(`events.rate_limit_per_subscription`, default 60/min, burst 10). Over the
limit, delivery is delayed, not dropped, and `deliveryStatus.throttled` is
reported. With `cost-governance` on, each delivery is charged through
`BudgetEnforcer::check` / `record_spend` (`src/cost_accounting/enforcer.rs:183,323`)
under the synthetic tool name `events:<event name>` and, as the
`api_key_name` argument, the subscription principal's API-key name when the
principal is an API-key client (otherwise `None`, which the enforcer treats
as the global budget), at a configured cost (`events.cost_per_delivery_usd`,
default 0) per attempt. The principal's existing budgets
and kill switches then govern events with no second mechanism. A refused
budget check dead-letters with reason `budget`.

### 3.8 Dead letters and replay without growing the meta surface

A dead letter is the outbox record moved to `dead/` with a reason
(`gone` 410, `too_large` 413 or oversize, `exhausted`, `firewall_blocked`,
`tenant`, `budget`, `ssrf`, `access_revoked`). Dead letters are kept for
`events.dead_letter_retention` (default 7 days), then swept, and are capped
at `events.dead_letter_max_records` (default 10 000) and
`events.dead_letter_max_bytes` (default 256 MiB); over either cap the oldest
dead letters are evicted first and the eviction is counted and audited
(T49, T50).

Replay is an **admin HTTP route and a CLI command, not a meta-tool**. The
meta-tool count is pinned by `tests/public_claims_validation.rs:336` and
`src/gateway/meta_mcp_tool_defs_tests.rs:598`, and admin meta-tools also count
toward the 9–17 band. The surface:

- `GET /ui/api/events/dead-letters?subscription=&reason=`: list (ids,
  reasons, times, sizes; no bodies, no secrets);
- `POST /ui/api/events/dead-letters/{id}/replay` and `…/replay?all=1&subscription=`;
- `mcp-gateway events dead-letters list|replay` calling the same functions.

All of these sit in the authenticated `/ui/api/*` router (`src/gateway/ui/mod.rs:59`) and require admin standing like its other mutating handlers (`is_admin`, `:54`).
Replay re-runs steps 3–6 of §3.2: access re-check, fresh firewall scan,
limiter, and a new outbox record with the **same** `eventId` signed with the
subscription's **current** secret. Replay into a deleted or expired
subscription is refused.

### 3.9 Discovery through `gateway_search`

`gateway_search` scans backends' cached tool lists live
(`src/gateway/meta_mcp/search.rs:786`). Events join that scan as a second
kind of entry. Each visible descriptor is matched on name and description and
returned with `"kind": "event"` and its `inputSchema`, so a client that only
knows the meta surface finds `webhook.github.push.received` the same way it
finds a tool. Results are filtered by the same visibility predicate as
`events/list`. Nothing about events is added to `tools/list`.

## 4. The source-adapter interface

Every source, in 4.0.0 and later, is one implementation of this trait. The
core (catalogue, subscription service, fan-out, outbox, delivery, dead
letters) knows the trait and nothing else.

```rust
/// What kind of thing produced an event. An enum, not a string, so the audit
/// record and metrics cannot invent a kind the core does not know.
pub enum SourceKind { Webhook, BackendNotification, TaskSettled,
                      // 4.0.1, reserved now so records written by 4.0.0 parse later:
                      RestWatch, GatewayOperational, Schedule }

pub struct EventDescriptor {
    pub name: String,               // stable, namespaced; never reused for another schema
    pub description: String,
    pub input_schema: Value,        // JSON Schema for `arguments`
    pub payload_schema: Value,      // JSON Schema for `data`
    pub scope: Visibility,          // Backend(name) | Owner | Operator
    // (Corrected 2026-10-06: not shipped as a field; see EventSource::charges.)
}

pub struct SourceEvent {
    pub name: String,
    pub occurred_at: DateTime<Utc>,
    pub upstream_id: String,        // stable per occurrence (§3.6)
    pub data: Value,                // already minimal; must satisfy payload_schema
    pub scope: Visibility,          // who may receive this occurrence
    pub lifecycle_key: Option<String>, // set by sources whose upstream work is per key
                                    // (a credentialed watch): the core then matches only
                                    // subscriptions holding this key
}

#[async_trait]
pub trait EventSource: Send + Sync {
    fn kind(&self) -> SourceKind;
    /// Current descriptors. A change is announced via `EventsHub::catalogue_changed`.
    fn descriptors(&self) -> Vec<EventDescriptor>;
    /// May `principal` subscribe to `name` with these `arguments`? Called at subscribe
    /// and again at every fan-out.
    async fn authorize(&self, principal: &Principal, name: &str, arguments: &Value)
        -> Result<(), Refusal>;
    /// Does this occurrence match a subscription's `arguments`?
    fn matches(&self, principal: &Principal, arguments: &Value, event: &SourceEvent) -> bool;
    /// What the core refcounts upstream work on. Default: JCS of (name, arguments),
    /// shared across principals. A source whose upstream work runs under the caller's
    /// own credential (a credentialed 4.0.1 watch) includes the principal.
    fn lifecycle_key(&self, _principal: &Principal, name: &str, arguments: &Value) -> String {
        jcs(&json!([name, arguments]))
    }
    /// First live subscription for this lifecycle key appeared. Sources that must
    /// start something upstream (b2's listener, a 4.0.1 poller or timer) do it here.
    async fn on_first_subscriber(&self, _key: &str, _principal: &Principal, _name: &str,
                                 _arguments: &Value) -> Result<(), Refusal> { Ok(()) }
    /// Last one for this key went away (unsubscribe, expiry, revocation).
    async fn on_last_subscriber(&self, _key: &str) {}
}
```

Sources emit through `EventsHub::emit(SourceEvent)`, the non-blocking queue
of §3.2. The core refcounts subscriptions per `lifecycle_key`; with the
default key that is `(name, canonical arguments)` across all principals. It calls `on_first_subscriber` before it
answers the subscribe that takes the count from 0 to 1; a refusal there
fails that subscribe with the refusal's code. It calls `on_last_subscriber`
after the count reaches 0. On restart the core replays `on_first_subscriber`
once for each distinct live lifecycle key, passing the principal of one
live subscription holding it, so upstream state is rebuilt
from the store, not from memory.

When a `SourceEvent` carries a `lifecycle_key` (the field and its filter
shipped with MIK-7811, not with I4 as this section first implied), the core offers it only to
subscriptions holding that key before calling `matches`; `matches` also
receives the subscription principal. Together these let a credentialed watch
deliver principal A's poll result to A alone even when B subscribed with
identical arguments.

`matches` belongs to the source rather than the core because sources mean
different things by an argument. For a webhook route, `event_type` matches by
glob. For b2, `uri` is an exact match. For a 4.0.1 watch, the arguments are
the poll target itself.

**Fit check against 4.0.1.** Each deferred source written against this trait
(full treatment in the companion doc):

| 4.0.1 source | descriptors | authorize | matches | first/last subscriber | touches core? |
|---|---|---|---|---|---|
| REST capability watch | one per watchable read-only capability | `may_invoke` on that capability | arguments equal the poll target | start or stop a poll-and-diff task keyed by canonical arguments | no |
| Gateway operational | `gateway.budget.*`, `gateway.backend.health_changed`, `gateway.kill_switch.changed` | operator standing (or own budget for `budget.*`) | field equality | none (always-on producers) | no |
| Scheduler time | `schedule.tick` with a cron argument | any authenticated principal, quota-bounded | the subscription's own cron fired | start or stop a timer for that cron | no |

The three reserved `SourceKind` variants and the `Operator` visibility value
exist in 4.0.0 so that a 4.0.1 record or config is not a schema migration.

## 5. Data model

Store root `events.store_dir` (default `~/.mcp-gateway/events`, created with
`create_dir_private`). Same pattern as the task store: one JSON file per
record, an in-memory image that serves reads, and every mutation committed
on a blocking thread under one ordering lock with `replace` + `sync_dir`.
Each file carries `"v": 1`; a loader refuses a version it does not know
(`MAX_LOADABLE_VERSION`, as in `task_service/record.rs`).

| Directory | One file per | Fields | Removed when |
|---|---|---|---|
| `subs/` | subscription (`<id>.json`) | `id`, `principal`, `tenant`, `url`, `name`, `arguments` (canonical), `secret`, `previous_secret` + `previous_until`, `granted_at`, `expires_at` (null = no expiry), `active`, `failed_since`, `last_delivery_at`, `last_error` | unsubscribe, expiry sweep, revocation |
| `verified/` | `(principal, url)` (file name = sha256 of the pair) | `principal`, `url`, `verified_at`, `last_subscription_ended_at` | 24 h after the last subscription for the pair ends |
| `outbox/` | pending delivery (`<eventId>.json`) | `event_id`, `subscription_id`, `body_b64` (exact bytes), `attempt`, `next_attempt_at`, `first_attempt_at`, `state` (`pending`/`in_flight`) | delivered (deleted), or moved to `dead/` |
| `dead/` | dead letter | outbox fields + `reason`, `dead_at`, `last_status` | retention sweep (7 d) or successful replay |
| `seen/` | inbound delivery-id set, one file per route | bounded map `id → seen_at`, trimmed to 24 h | rewritten on trim |

**Secrets at rest.** `secret` and `previous_secret` are the only sensitive
fields. Files are created owner-only (`create_file_private`), the store dir
is `0700`, and the `Debug` impl of the record type redacts both (the
`capability/definition/mod.rs:809` pattern). No log, audit record, dead-letter
listing, admin answer or error message carries a secret or a full callback
URL; callback URLs appear as host only, because a path or query can itself
carry a capability token. Encryption at rest is not added. The task store,
the cost ledger and OAuth token files sit in the same directory under the same
protection, and adding a key-management scheme for this one store would leave
it the odd one out. Recorded as a known limit in §7.

**Bounds.** `events.max_subscriptions` (default 10 000) and
`events.max_subscriptions_per_principal` (default 100) cap `subs/`;
`events.max_outbox` (default 50 000) is a hard cap on `outbox/`, checked
before every insert, and `events.max_outbox_per_subscription` (default 1 000)
stops one dead receiver from taking the whole outbox. A new occurrence over
either cap is dropped and counted; records already pending are never dropped
(F11, T45). `verified/` holds two kinds of record: those with a live subscription,
bounded by `max_subscriptions`, and tail records whose last subscription has
ended (kept 24 h), capped at `events.max_verified_tail` (default 10 000,
per principal 100) with the oldest evicted first, so subscribe/unsubscribe
churn cannot grow it (T46); each route's `seen/` set is
capped at `events.seen_max_per_route` (default 100 000 ids, about 7 MiB),
evicting the oldest.


## 6. Method contracts against the draft

Every quote is from the draft at `28ec35e9` unless marked *OpenAI*. "Gateway"
says what this design does; "Deviation" is empty unless the gateway departs from
a SHOULD.

### 6.1 Capability advertisement

> "Servers advertise event support in their capabilities: `"events": { "listChanged": true }`"

Gateway: `server/discover` (and the legacy `initialize` answer) carries
`capabilities.events = { "listChanged": false }` **only** when `events.enabled`
is true and at least one source is configured. With the feature off the key is
absent, and every `events/*` method answers `-32601 Method not found`, the same
as today. `listChanged` is false (build notes, section 19): the catalogue does change when
backends are added or removed and webhook routes reload, but no notification
carries that to a client, and events have no listen channel for one. A client
re-reads `events/list`. A producer is a separate decision with its own wire
surface; no 4.0 criterion needs it.

### 6.2 `events/list`

> "`delivery` lists the delivery modes this event type supports — any non-empty subset of `"poll"`, `"push"`, `"webhook"`."

> *OpenAI:* "Return only events the connected account is allowed to discover."

> *OpenAI:* "If the catalog spans multiple pages, return `nextCursor` and accept it as `cursor` on the next `events/list` request."

Gateway: the catalogue is the union of every source adapter's descriptors (§4),
filtered by the caller's visibility (§3.7), sorted by name, paginated with the
same opaque cursor helper `tools/list` uses. Every descriptor has
`"delivery": ["webhook"]`. Names are namespaced by source so two backends
cannot collide: `webhook.<capability>.<route>.received`,
`backend.<server>.tools_changed`, `backend.<server>.resources_changed`,
`backend.<server>.prompts_changed`, `backend.<server>.resource_updated`,
`task.settled`. Schemas evolve additively only
(the draft's *Schema evolution* rule), enforced by a snapshot test (row T12).

### 6.3 `events/subscribe`

> "`delivery.secret` is REQUIRED. … The value MUST be a Standard Webhooks symmetric secret: the literal prefix `whsec_` followed by base64 of 24–64 random bytes. Servers MUST reject values that do not satisfy this with `InvalidParams`."

> "`events/subscribe` and `events/unsubscribe` MUST be called with an authenticated principal; servers MUST reject calls without an authorized principal with `-32012 Forbidden`."

> "The subscription key is `(principal, delivery.url, name, arguments)` … `arguments` is compared by canonical-JSON equality."

> "Callback URLs MUST use `https://`. Servers MUST reject `events/subscribe` with a non-`https` `delivery.url` (`-32602 InvalidParams`)."

> "a server MUST NOT begin delivering to a callback URL until the endpoint's intent to receive deliveries is confirmed, by **one of**: (a) a **verification handshake** … which the server compares in constant time"

> "Verification is cached per `(principal, url)` … A server that persists no-expiry subscriptions across restarts … MUST persist their verification status alongside them"

Gateway, in this order (cheapest refusal first, so a bad request costs no
outbound traffic):

1. No authenticated principal → `-32012 Forbidden`. Anonymous and
   auth-disabled deployments cannot use webhook mode, matching the draft.
2. Unknown or invisible `name` → `-32011 NotFound` with `data.kind = "event"`.
   An event the caller may not see is reported as not found, not forbidden, so
   the catalogue cannot be probed (§7.4).
3. `delivery.mode != "webhook"` → `-32014 Unsupported`,
   `data = {"feature": "deliveryMode", "value": <mode>}`.
4. `arguments` invalid against `inputSchema`, URL not `https` or not parseable,
   secret not `whsec_` + 24–64 decoded bytes → `-32602 InvalidParams` naming
   the field, never echoing the secret.
5. Source-level authorization (`EventSource::authorize`, §4) → `-32012`.
6. Quota (`events.max_subscriptions_per_principal`) → `-32013
   ResourceExhausted`, `data.limit = "subscriptions"`. Applies only when
   the key is not already held, so a refresh or secret rotation at the cap
   always succeeds (T26).
7. Identity: `id = "sub_" + hex(sha256(canonical_json([principal, url, name,
   arguments])))[..32]`. `principal` is the gateway's canonical principal
   string (the same key MIK-7116's tenant guard uses). Canonical JSON is
   RFC 8785 (JCS) through `serde_json_canonicalizer`: keys sorted by UTF-16
   code unit, no insignificant whitespace, numbers in ECMAScript form, so
   `{"b":1,"a":1.0}` and `{"a":1,"b":1}` are one key (row T7).
8. Verification: if `(principal, url)` has no live verification record, POST
   the `verification` envelope through the delivery client (§3.5), with a
   32-byte random challenge, `webhook-id = msg_verification_<random>`, a
   5-second timeout and a 4 KiB response cap. Accept only a 2xx whose body
   parses to `{"challenge": <same>}` compared with `subtle::ConstantTimeEq`.
   Failure → `-32015 CallbackEndpointError`, `data.reason` one of the six
   categories. The challenge is single-use: it is generated per attempt and
   held only on the stack of that attempt. The verification record
   (principal, url, verified_at) is persisted and lives while **any** live
   subscription for that `(principal, url)` exists, plus 24 h after the last
   one ends. A new subscription inside that life needs no new challenge; a
   subscription is never left without a recorded opt-in, which is the draft's
   rule for persisted subscriptions (T46).
9. Upsert under the key. On an existing row: secret replaced (old secret kept
   for dual-signing for `events.secret_rotation_grace`, default 10 min), TTL
   re-granted, `active` set true, suspended deliveries resumed.
10. Answer `{id, refreshBefore, cursor: null, truncated: false}` plus
    `deliveryStatus` on a refresh.
    `deliveryStatus.lastError` is a category string, never receiver content:
    `connection_refused`, `timeout`, `tls_error`, `challenge_failed`,
    `http_3xx`, `http_4xx`, `http_5xx`, `http_other`; `audit_unavailable`
    (the audit log refused the attempt's record, nothing was sent);
    `access_revoked` (the access re-check refused the subscription);
    `source_unavailable` (the event's source is not installed yet or is
    switched off: the record is held, not sent and not charged, MIK-7976).

TTL:

> "`refreshBefore` … SHOULD be less than or equal to the suggestion … a server MAY clamp an impractically short suggestion up to its minimum TTL"

> "A server MUST NOT return `null` unless the client suggested `ttlMs: null`"

Gateway: absent `ttlMs` → `events.default_ttl` (1 h). Finite `ttlMs` → clamp to
`[events.min_ttl (60 s), events.max_ttl (24 h)]`; the upper clamp is allowed
because the grant is authoritative and self-announcing. `ttlMs: null` →
`refreshBefore: null` only when `events.allow_no_expiry` is true (default
**false**); otherwise the `max_ttl` grant. The grant becomes a time at the
store's commit, after the callback challenge and any wait, so a slow challenge
cannot shorten it; `refreshBefore` is the stored expiry. Every subscription is persisted
regardless of TTL, which satisfies *OpenAI*'s "Retain subscription state for
the lifetime you grant, including across server restarts."

### 6.4 `events/unsubscribe`

> "`events/unsubscribe` resolves the subscription using the same key as `events/subscribe` … The derived `id` is not accepted as input."

> *OpenAI:* "Stop sending events for the matching subscription and return an empty result … Make unsubscribe idempotent and authorize it against the connected account."

Gateway: same principal rule (`-32012` without one). The key includes the
caller's principal, so a caller can only ever address its own rows. A miss
returns `{}`, not `-32011`: the draft permits `NotFound` but *OpenAI* asks for
idempotency, and `{}` also avoids telling a caller whether a key exists.
Pending outbox entries for the subscription are cancelled in the same
transaction, so nothing is delivered after the answer.

### 6.5 Delivery

> "`webhook-id` carries the `eventId` for event deliveries … Each retry attempt regenerates the timestamp and signature."

> "the server MUST treat `410` as a non-retryable f[ailure]" ; "servers MUST treat `413` as a non-retryable failure for that event."

> "servers SHOULD keep delivery bodies at or under 256 KiB"

> "this validation MUST be performed at delivery time, not only at subscribe time … connects directly to that validated IP (sending the original hostname in the `Host` header / TLS SNI) … Webhook delivery requests MUST NOT follow HTTP redirects"

> "deliveries MUST include `X-MCP-Subscription-Id` (the subscription `id`) so the receiver can select the correct secret without parsing the body."

Gateway: every POST, verification and event alike, carries `Content-Type:
application/json`, `webhook-id`, `webhook-timestamp`, `webhook-signature` and
`X-MCP-Subscription-Id`. The last is the subscription `id`, identical on every
attempt and outside the HMAC input (the draft signs id, timestamp and body
only). Body = `{eventId, name, timestamp, data, cursor: null, _meta}`, serialised
once and stored as bytes in the outbox; every attempt signs those bytes.
`eventId` is assigned once when the event is fanned out to a subscription and
never changes. A body over 262,144 bytes is never sent: it is dead-lettered
with reason `too_large` at fan-out. Retry: 2xx = done; 410, 413 = dead-letter,
no retry; every other non-2xx, timeout, connection and TLS error = retry
(the draft retries "on non-`2xx` responses"; only 410 and 413 are carved out) with exponential backoff and full jitter
(base 10 s, factor 3: about 10 s, 30 s, 90 s, 270 s), at most 5 attempts and
15 minutes, matching the draft's "3–5 attempts spread over no more than 10–15
minutes". `Retry-After` on 429 is honoured up to the window. Exhausted →
dead-letter (§3.8). A subscription whose failure rate exceeds 95 % over the
last 60 min with at least 100 attempts is suspended (`active: false`), per the
draft's guidance; a refresh reactivates it.

Not offered: `events/poll` and `events/stream` answer `-32601` (no descriptor lists `poll` or `push`, so a conformant client never sends them). Not sent: `gap`, `terminated`. When access is revoked or the event type is
removed, the gateway stops delivery and deletes the subscription; the next
refresh then fails with `-32012` or `-32011`, which is the draft's own fallback
("a subsequent refresh is a fresh subscribe and returns `-32012 Forbidden`").

## 7. Security analysis

Threats, in the order an attacker would try them. "Holds because" names the
mechanism and the test row that would catch a regression.

### 7.1 SSRF through the callback URL

| Attack | Holds because |
|---|---|
| `delivery.url` names a private or link-local address or a metadata endpoint (169.254.169.254) | IP literals refused at subscribe by `validate_url_not_ssrf`; names resolved and checked on every connection by `PinningResolver` (T13) |
| DNS rebinding: public at subscribe, private at delivery | check-and-pin happens per connection, inside the resolver reqwest uses, so no second lookup follows the check (T14) |
| 3xx to an internal address | `redirect(Policy::none())`: a 3xx is a non-2xx answer, recorded and retried like any other, never followed (T15) |
| `HTTPS_PROXY` in the environment resolving the name instead | `pinned_client_builder` sets `no_proxy()` |
| `http://` callback | `-32602` at subscribe (T5) |
| Using the gateway as a response oracle for internal services | the endpoint's body is read only for verification (4 KiB cap), and only a category string ever reaches the caller: the draft's `lastError` rule ("MUST NOT include raw response bodies, headers, or status lines") (T16) |

### 7.2 Flooding a third party

Client-supplied HMAC stops forgery, not volume: anyone can subscribe a
victim's URL. The verification handshake proves the endpoint opted in
(T8, T9). Verification is cached per `(principal, url)`, so varying
`arguments` cannot multiply challenge POSTs (T10). Verification POSTs are
rate-limited per destination host (`events.verification_per_host_per_minute`,
default 10, across all principals); the
subscribe over the limit answers `-32013` with `data.limit = "verifications"`,
so many principals cannot challenge-flood one host (T48).

### 7.3 Prompt injection through events

Event data comes from webhooks, backends and task records, all of them
outside the gateway's control, and lands in front of an agent that may
hold write tools. Defences, in order:

- payload minimality (§9: mapped fields only, no raw bodies);
- the response firewall scan, with block or redact (§3.6, T19);
- nothing added by the gateway (T20);
- provenance kept in `_meta` so the client can tell gateway metadata from
  data.

What this does not do: make an injected string harmless to a client that
reads it. The draft puts that responsibility on the client ("Event receipt
does NOT constitute authorization to act"). The gateway reduces the surface;
it does not claim to close it.

### 7.4 Cross-principal and cross-tenant leakage

- The subscription key includes the authenticated principal, so one caller
  cannot address another's subscription. The derived id is not accepted as
  input anywhere (T11, T23).
- `events/list` and `gateway_search` show only descriptors that pass the
  visibility predicate (T3).
- `events/subscribe` reports an invisible event as `-32011`, not `-32012`,
  so a caller cannot use the error code to test whether an event exists
  (T4).
- Fan-out re-checks access per occurrence, so a revoked principal stops
  receiving at the next event, not at the next refresh (T24).
- The tenant guard is applied at fan-out with MIK-7116's existing
  semantics (§3.7, T25). Known limit: the gateway has no per-principal tenant
  entitlement, so "principal P receives only tenant T" is not enforced; the
  guard limits breadth and cross-tenant reads, as it does for tool results.
- Resource-level events from b2 never enter `SubscriptionRegistry`, so a
  `subscriptions/listen` client cannot see a URI that the URI-level
  `authorize` would refuse (§3.3, T39).

### 7.5 Replay and duplication

- **Outbound:** the receiver dedupes on a stable `webhook-id` (§3.6), and
  every attempt carries a fresh timestamp and signature, so the receiver's
  5-minute window accepts retries and rejects captured old requests (T17).
- **Inbound:** one 24 h seen-set per route, keyed on the delivery id where
  the route configures one, on the signed-body hash where it opts in with
  `dedupe: body`, and absent otherwise (§3.6, T34). This is dedupe, not replay
  protection: the upstream HMAC signs the body only and carries no signed
  timestamp, so a captured webhook replayed with a forged fresh delivery id,
  or after 24 h, or on a route without dedupe, becomes a new occurrence. That
  limit predates events (today's notification path has it) and is stated
  rather than claimed away.
- **Verification challenge:** 32 random bytes, one per attempt, never stored
  and never reused, compared in constant time (T9).

### 7.6 Secret handling

- Secrets are accepted only in the `whsec_` form with 24–64 decoded bytes
  (T6).
- Stored owner-only, redacted in `Debug`, and absent from every log, audit
  record, dead-letter listing and error (T21).
- Rotation replaces the secret and dual-signs for a grace window (T18).
- An error from a malformed secret names the field, not the value.
- Known limit: no encryption at rest beyond file permissions, the same as
  the task store and token files beside it.

### 7.7 Denial of service against the gateway

| Vector | Bound |
|---|---|
| subscription flooding | per-principal and global caps → `-32013` (T26) |
| huge `arguments` | the request body cap that already applies to `/mcp`, plus `inputSchema` validation |
| slow or hanging receiver | 10 s total timeout per attempt, `max_in_flight` across subscriptions, one in flight per subscription |
| notification storm from a backend | 1 s coalescing of `list_changed` per backend, bounded source queue, outbox cap (F11) |
| verification amplification | per-host verification limit (§7.2) |
| store growth | caps in §5, expiry and retention sweeps |

### 7.8 Error code space

The draft's `-32011` to `-32015` are new to the gateway; `-32012` and
`-32042` appear nowhere in `src`. One overlap exists: `-32015` is already
`SESSION_NOT_FOUND_CODE` in the **client** transport
(`src/transport/http/mod.rs:148`), where the gateway interprets a backend's
answer. The gateway emits `-32015 CallbackEndpointError` only as a server,
never forwards `events/*` upstream, and never reads `-32015` from a
backend's events method, so the two meanings cannot meet. A test pins that
`events/*` is never proxied (T2).

## 8. Failure modes

| # | Failure | What the gateway does | Visible as |
|---|---|---|---|
| F1 | Gateway restarts with deliveries in flight | Outbox records survive (one file each, §5). On load, every record in `in_flight` returns to `pending` with its `next_attempt_at` set to now and the same `eventId` and body bytes; the receiver dedupes on `webhook-id`. | duplicate delivery at most once per crash, same `webhook-id` |
| F2 | Gateway restarts, subscriptions live | Subscriptions and verification records reload; delivery resumes without a re-subscribe. Expired rows are swept on load. | none |
| F3 | Event arrives while the gateway is down | Webhook sender sees a connection failure and retries on its own schedule; backend notifications and task settles during the outage are lost (emit-only, `cursor: null`). | documented; the draft's emit-only model |
| F4 | Callback endpoint down for a while | Bounded retry, then dead-letter; sustained failure suspends the subscription; refresh reactivates; operator can replay the dead letters (§3.8). | `deliveryStatus.lastError`, DLQ count metric |
| F5 | Callback endpoint answers 410 | That event is dead-lettered with reason `gone`; the subscription stays. | DLQ row |
| F6 | Callback DNS changes to a private address | Connect-time check refuses; counts as `connection_refused`; retried, then dead-lettered. Nothing is sent to the private address. | DLQ row, SSRF refusal audit |
| F7 | Event payload over 256 KiB | Not sent; dead-lettered `too_large` at fan-out. Source adapters are written to emit summaries (§4) so this is rare. | DLQ row |
| F8 | Firewall blocks a payload | Not sent; dead-lettered `firewall_blocked` with the verdict, no payload copy in the audit record. Replay re-scans, so a blocked event cannot be replayed past the firewall. | DLQ row, firewall audit |
| F9 | Principal loses access (role change, tenant change, token revoked) | Re-checked before every attempt against the current policy: nothing more is delivered and the subscription is deleted. | next refresh answers `-32011` when the event is no longer visible, `-32012` when the source refuses the arguments (T24) |
| F10 | Backend disconnects | Its event types leave the catalogue (no notification is sent; clients re-read `events/list`); existing subscriptions to them stay until TTL but receive nothing; if the backend is removed from config they are deleted. | next refresh answers `-32011` |
| F11 | Notification storm from one backend | Per-source coalescing window (`list_changed` collapses within 1 s per backend), per-subscription rate limit, and a bounded fan-out queue; over either outbox cap the new occurrence is dropped and counted; pending records are kept (§5, T45). | `throttled: true` in `deliveryStatus`, drop counter |
| F12 | Store full or unwritable | Subscribe fails `-32603`; fan-out stops accepting new events (counted drops) rather than block intake. Inbound webhook acceptance is not coupled to the events store. | error, metric |
| F13 | Draft spec changes shape | The protocol layer is one module; the fail-fast harness is re-run against the new draft before 4.0.0 is tagged (§11). | — |

## 9. Configuration

```yaml
events:
  enabled: false                   # off: no capability, every events/* method -32601
  store_dir: ~/.mcp-gateway/events
  default_ttl: 1h
  min_ttl: 60s
  max_ttl: 24h
  allow_no_expiry: false           # ttlMs:null gets max_ttl unless true
  max_subscriptions: 10000
  max_subscriptions_per_principal: 100
  queue_depth: 1024
  max_in_flight: 32
  max_outbox: 50000
  max_outbox_per_subscription: 1000
  seen_max_per_route: 100000
  max_verified_tail: 10000
  rate_limit_per_subscription: { per_minute: 60, burst: 10 }
  cost_per_delivery_usd: 0.0       # charged only with cost-governance
  secret_rotation_grace: 10m
  dead_letter_retention: 7d
  dead_letter_max_records: 10000
  dead_letter_max_bytes: 256MiB
  verification_per_host_per_minute: 10
  callback_allow_private: []       # CIDRs; empty = public addresses only
  sources:
    backend_notifications: true    # b1 always; b2 opens upstream only on demand
    task_settled: true
```

Webhook events are opt-in **per route**, in the capability YAML next to the
route they describe, because the payload shape is defined there:

```yaml
webhooks:
  push:
    path: /github/push
    secret: env:GITHUB_WEBHOOK_SECRET
    signature_header: X-Hub-Signature-256
    transform:
      event_type: "github.{action}"
      data: { repo: "{repository.full_name}", ref: "{ref}", sha: "{after}", url: "{compare}" }
    event:                          # new; absent = route emits no MCP event
      description: "A push to a repository the gateway receives webhooks for."
      filters: [repo, ref]          # data keys usable as equality filters in arguments
      delivery_id_header: X-GitHub-Delivery   # or `dedupe: body`; neither = no dedupe
```

A route qualifies only if `transform.data` is non-empty; config validation
refuses an `event:` block on any other route (T42). The event's `data` is
built by the events source from the mapping alone: each mapped key whose
placeholder resolves is included, and a key that does not resolve is omitted.
The legacy notification path falls back to the whole raw body when nothing
resolves (`src/gateway/webhooks/mod.rs:598-603`). The event path never does:
if no mapped key resolves, the occurrence is dropped and counted as
`projection_failed`, because a raw third-party body is neither minimal nor
described by a schema (T42b). The derived event is `webhook.<capability>.<route>.received`.
Its `inputSchema` has an optional `event_type` glob plus one optional string
per declared filter. Its `payloadSchema` is `{event_type: string, fields: {<each
data key>: any, all optional}}`, with `additionalProperties: false` at both
levels. Placeholders use the transformer's `{dotted.path}` syntax.

`EventsConfig` follows the feature-section pattern: `src/config/features/events.rs`,
a `validate()` called from `Config::validate` (`src/config/mod.rs:743`), and an
`"events"` entry in the reload table (`src/config_reload/mod.rs:625`). A
reload that removes an event type deletes its subscriptions (F10); no
`notifications/events/list_changed` is sent (section 19). A reload that keeps a name but removes
a filter or a mapped field is **rejected** (the old config stays live, the
reload error names the event; mapped fields are untyped, so there is no
type change to judge): the draft's
additive-only rule applies to config-derived schemas too, and a breaking
change needs a new route name (T52).

## 10. Test plan

Rules for every row:

- **Failing first, at its own assertion.** Each row drives the gateway
  through a surface that compiles today: the `/mcp` JSON-RPC endpoint, the
  config loader, or an inbound webhook POST. With no events code, `events/*`
  answers `-32601`, so a row goes red at its assertion rather than at a
  missing symbol. CI is the compiler; each row has to be seen red there
  before its implementation lands.
- **Real receiver.** Delivery rows use one in-test HTTPS receiver
  (`tests/support/events_receiver.rs`, a self-signed certificate trusted by
  the test client only) that checks the Standard Webhooks signature with an

## 11. Increments

Each increment ships with `events.enabled: false` as the default and is
releasable alone. The order puts every payload control before any payload
can leave the gateway. **Rows land with their increment, not all up front:**
an increment's PR opens with a commit adding exactly the rows in its Rows
column, plus any fixture those rows need (the HTTPS receiver lands in I1, the
mock backends in I4 and I5); that commit compiles against the previous
increment and is seen red at the rows' own assertions on CI; the
implementation follows in the same PR. A row never lands before the surface
it drives exists, which is why delivery rows sit in I2 and admin rows in
I6. A row whose clauses span increments is written with only the clauses
its increment can drive, and its later clauses join it in the red commit of
the increment named beside them.

## 12. Fail-fast: the operator's ChatGPT step

The question it answers: can ChatGPT reach an MCP endpoint we run, list an
event, subscribe with a webhook callback, pass our verification handshake,
and accept a signed delivery? If not, the 4.0 scope question goes back to
the operator before I1 starts.

The harness is `scripts/dev/mcp_events_failfast.py` (Python, stdlib only).
`selftest` exercises the whole round trip on loopback and exits 0:
discover, list, a short-secret refusal, verification, idempotent subscribe,
persistence across a stub restart, filtering, signature, and idempotent
unsubscribe. It fails if verification is skipped or a delivery is signed
with the wrong key.

**Operator step (about 10 minutes, needs a ChatGPT account with developer
mode / plugin creation):**

1. `python3 scripts/dev/mcp_events_failfast.py selftest --dir "$(mktemp -d)"`
   must print `selftest PASS`.
2. In terminal A, start the stub:
   `python3 scripts/dev/mcp_events_failfast.py serve --port 8765 --dir ~/mcp-events-failfast`.
   It prints an emit URL with a one-time token. Keep it.
3. In terminal B, expose the stub:
   `cloudflared tunnel --url http://127.0.0.1:8765`.
   Note the `https://<random>.trycloudflare.com` URL. It changes on every
   run.
4. In ChatGPT, create a plugin (or a developer-mode connector) whose MCP
   server URL is `https://<random>.trycloudflare.com/mcp`, with no
   authentication. Check that the plugin page lists the event `stub.ping`
   next to the tool `stub_status`.
5. In a new chat: "Subscribe to stub.ping with topic demo, and when one
   arrives, tell me its seq number."
6. In terminal C:
   `curl '<emit URL from step 2 with topic=demo>'`.
   It must print a list with one entry whose `status` is 200.
7. Ask ChatGPT to stop monitoring.
8. Send back `~/mcp-events-failfast/log.jsonl`.

**Verdict, read from `log.jsonl`:**

| Outcome | Condition |
|---|---|
| PASS | the log contains, in order: a `server/discover` (or `initialize`) request; `events/list`; `events/subscribe` with an `https` `delivery.url`; a `verification` entry with `status` 2xx; the subscribe `response` carrying `result.id`; a `delivery` entry with `status` 2xx; `events/unsubscribe`; and ChatGPT replied in the chat with the seq number |
| FAIL: unreachable | no request at all reaches the stub while the tunnel answers `curl https://<random>.trycloudflare.com/mcp` |
| FAIL: no events | `server/discover` and `tools/list` arrive, but `events/list` never does |
| FAIL: handshake | the subscribe answer is an error, or the verification entry is not 2xx |
| INCONCLUSIVE: auth | ChatGPT refuses to connect a server without OAuth. This is not a reachability failure: rerun with `--bearer` if ChatGPT offers a static token, or after I1 against the gateway's OAuth |

The stub pins each connection to the address it checked, refuses non-public
callbacks, and writes its log and store owner-only with signing secrets and
callback paths redacted, so the log is safe to send. Its remaining
simplifications are stated in its code and are not carried into
the gateway:

- a fixed principal when there is no auth (the gateway refuses webhook mode
  without a principal);
- sort-keys JSON instead of JCS;
- an in-memory verification cache.

**Second half (I7):** the same steps 3–8, pointing the tunnel at a built
gateway with `events.enabled: true`, a configured webhook route, and OAuth.
The event is fired by a signed inbound webhook instead of `/emit`.

## 15. Build notes (I1)

Where the I1 build departs from the text above, and why:

- **Config scaffold first.** The loader refuses keys it does not recognise (MIK-7570.CONFIG.1), so an `events:` block stops today's binary at startup. The PR therefore opens with a parse-only `EventsConfig`, then the red rows, then the implementation; the rows fail at their own assertions, not in the startup fixture.
- **Principal.** The subscription principal is the task owner key (`route_task_owner`), not the tenant guard's caller key. It is the one identity both eras share, and `task.settled` (I4) compares against it directly. I2 records the caller key separately for the tenant guard.
- **HTTP only.** Events are served and advertised on the HTTP transport. A stdio session carries no authenticated principal, so webhook mode could only ever answer `-32012` there; stdio keeps `-32601` and advertises nothing.
- **Tail knobs.** `verified_tail_ttl` (default 24 h) and `max_verified_tail_per_principal` (default 100) are config keys, so T46 runs on a short real clock instead of a test clock.
- **Receiver rows on Linux.** The callback client trusts roots through rustls-platform-verifier, which honours `SSL_CERT_FILE` only on Unix other than Apple. Rows that need a verified callback run there, as `tests/task_upstream_recovery_sdk` already does; no test-only trust knob is added.
- **T7 numbers.** Webhook filters are strings, so JCS number canonicalisation is proven by a unit test of the id function; key order is proven end to end.
- **T48 principals.** Two principals over eleven URLs on one host stand in for eleven principals; the limit is per host either way.
- **One page.** `events/list` returns the whole catalogue in one page; a `cursor` it never issued answers `-32602`.
- **Units.** Durations use the config's `s/m/h` form (`168h`, not `7d`); `dead_letter_max_bytes` is a byte count.

## 16. Build notes (I2)

- **Send path.** Every event delivery leaves through one call site
  (`send_event` in `src/events/worker.rs`) on the hardened callback client.
  MIN.2's design row E1 converts that one call to
  `outbound::callback_frame` / `send_callback`; until it does, MIN.2 is not
  gradable for event deliveries. Attribution is taken before the firewall's
  redaction and stored on the outbox record, as E1 requires.
- **T25.** The cross-tenant verdict needs MIN.2's per-principal read history,
  which I2 cannot build without inventing a stub MIN.2 would replace. T25
  lands ignored; MIN.2 test 2v carries the tenant clause and the E1
  conversion un-ignores T25 (release lead ruling, 2026-10-02). SAFETY.3 is
  not graded until then. T25 stays observe-only under operator ruling C3.
- **F9, credentials other than API keys.** Every attempt re-reads an API
  key's expiry, secret digest and backend grant from live config. Other
  credentials have no live entry to re-read in I2, so a subscription made
  with a key-server token, a delegated bearer, the static bearer or a
  dashboard session ends no later than the credential: at the token's `exp`,
  or one dashboard idle timeout from the subscribe, and `ttlMs: null` is
  refused for them (release lead, 2026-10-02). Mid-life revocation of those
  credentials is MIK-7769 (v4.0.0, P1); F9 is not met until it lands.
- **F9, live re-check (MIK-7769).** Every fan-out and every attempt
  re-checks the subscription's credential where it was issued: a key-server
  token by its `jti` in the token store; a delegated bearer by the key-server
  policy (issuer, subject, verified email, groups) still granting the
  event's backend, with `delegated_bearer` still on; the static bearer by the
  running bearer's principal; a dashboard session by the SHA-256 of its
  handle among live sessions (logout revokes server-side). The key server and
  the static bearer are startup-only, as on the request path. Known limit:
  an IdP-side revocation of a raw delegated JWT is not visible to the
  gateway; the token's `exp`, capped at `iat + max_oidc_token_age_secs`,
  bounds it.

## 17. Build notes (I3)

- **Receipt shape.** `_meta["io.github.mikkoparkkola/provenance"]` is the
  `SignedResultProvenance` object (`receipt`, `key_id`, `algorithm`,
  `signature`) when `security.provenance_stamping` is on, and `{receipt}`
  alone when it is off. The receipt is `RuntimeProvenanceReceipt` with
  subject kind `event`, the event name in `tool`, the backend in

  scoring abstains on an event receipt.
- **Signed once.** The receipt is stamped at fan-out, before the outbox write,
  so every retry sends the bytes the first attempt sent.

## 18. I6 contract (operations and discovery)

Fills the places §3.8-3.9 leave open; nothing here changes the protocol.

- **Routes** (authenticated `/ui/api/*`, admin standing, a non-admin caller
  gets the router's usual 403; events off answers 404):
  `GET /ui/api/events/dead-letters?subscription=&reason=`,
  `POST /ui/api/events/dead-letters/{id}/replay` and
  `POST /ui/api/events/dead-letters/replay?all=1&subscription=S`. `{id}` is
  the dead letter's `eventId` (unique per subscription). The router's
  admin-action layer already audits every non-GET call.
- **Listing** answers `{deadLetters: [...]}`; each entry: `eventId`, `subscriptionId`, `name`, `reason`, `deadAt`,
  `sizeBytes`, `attempts`. Never the body, a secret, the callback URL or
  tenant ids. An unknown `reason` value is a 400.
- **Replay** reads the stored body, re-runs the access re-check and the
  firewall over its `data` (what was stored is already redacted; a policy
  tightened since can now block it), keeps the envelope and `eventId`, and
  writes a new outbox record (attempt 0, due now). The dead letter leaves
  `dead/` in the same locked step that places the record. The worker's
  limiter, budget and audit then apply as for any delivery.
- **Refusals**, the dead letter untouched: unknown or swept id 404;
  409 with `reason` `subscription_gone`, `access_revoked`,
  `firewall_blocked`, `too_large` or `already_pending` (the outbox holds
  that event id); 503 `outbox_full`. Bulk replay needs
  both `all=1` and `subscription` (else 400) and answers 200
  `{replayed, refused: [{eventId, reason}]}`, replaying the rest.
- **CLI**: `mcp-gateway events dead-letters list|replay [--all]` is an HTTP
  client of those routes with `dashboard-link`'s rules (token in
  `MCP_GATEWAY_TOKEN`, loopback or https, no proxy, no redirects). It opens
  no store, so a running gateway is never raced.
- **Search**: `gateway_search_tools` and `gateway_search` append one entry
  per visible matching descriptor, `{kind: "event", name, description,
  inputSchema}`, after ranking and the limit; they count in `total` and
  `total_available`. The
  match is a case-insensitive substring of name or description; visibility
  is `events/list`'s predicate. Tool entries and `tools/list` are unchanged.
- **Meta surface**: no new meta-tool; T36 compares `tools/list` with events
  on and off.

## 19. Build notes (I4)

Where the I4 build departs from the text above, and why:

- **Crate-private registration.** `EventsHub::register_source` is `pub(crate)`; `events` is a private module, so a test under `tests/` cannot register a source. T41 is an in-crate row (`src/events/lifecycle_tests.rs`) that drives `subscribe`, `unsubscribe`, `start`, the emit queue and a restart, and one row that delivers a test source's event as a signed POST to an in-test HTTPS receiver (a test-only client constructor trusts the receiver's CA). No public API is added.
- **Trait shape.** `EventSource` is async (`async_trait`) as in §4: `authorize`, `matches(principal, ..)`, `lifecycle_key`, `on_first_subscriber`, `on_last_subscriber`, plus `offers(name)`. `authorize` returns the `RpcError` to answer. `SourceEvent` carries a `scope`; an owner-scoped record sets `owner_scoped` so the per-attempt access check needs a live credential, not a backend grant (a task event names no backend).
- **Refcount.** One async mutex orders every start and stop. It is held across `on_first_subscriber` and the store commit of the subscription that needed it, never across the verification POST. The count is read from the store: a stop is `reconcile_stops` after unsubscribe, revocation, withdrawal and the periodic sweep, so no removal path keeps its own counter. A restart (and a source registered late) runs `replay_starts`.
- **b1 tap.** `backend.<x>.tools_changed` is emitted from `announce_tools_changed`, the one function every tool-set change reaches (§3.3 named a `Listener` on `SubscriptionRegistry`; this is the same producer without a second subscriber). It is debounced per backend (quiet period, then one event with `{}` data). Backends are the registry's plus the capability backend.
- **task.settled tap.** `TaskExecutor::published` calls an installed settled hook with the committed record's id, status and `last_updated_at`; only terminal statuses emit. Ownership is `TaskService::get(principal, id)`, the check `tasks/get` applies. The hook is installed after the task runtime opens; a settlement during startup recovery, before that, is not emitted (emit-only contract).
- **Flags.** `events.sources.task_settled` and `events.sources.backend_notifications` gate registration; with both off and no webhook route, `capabilities.events` stays absent (T1).
- **T38 stimulus.** A backend's own tool-list notification outside a request is dropped today (§3.3), so the producer T38 can drive is the one that exists: a config reload of the backend, which reaches `announce_tools_changed`. The config watcher already merges writes, so the burst clause lives in an in-crate paused-clock row.
- **No catalogue notification (MIK-7803).** `capabilities.events` is `{ "listChanged": false }`: nothing sends `notifications/events/list_changed`, and no 4.0 criterion requires it. Advertising `true` promised what the gateway did not do. `events/list` stays the source of truth; the fail-fast stub already advertised `false`.
- **Task owner rides on the occurrence.** The task publication hook reads the owner digest at the commit seam and `SourceEvent.owner` carries it; fan-out matches on it and skips the source's `authorize` for an occurrence that carries one, so an expired row neither drops the event nor revokes a named-task subscription.
- **Startup backend reconcile.** `reconcile_catalogue` withdraws `backend.*` subscriptions the registry no longer offers, before the partial-scan early return that guards `webhook.*`.
