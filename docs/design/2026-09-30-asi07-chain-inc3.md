## Terms

- Upstream gateway (U): a backend of this gateway that is itself a chain-signing gateway.
- This gateway (D): calls U through `gateway_invoke` or the direct route, and delivers to a client.
- A chain is `_meta["io.mcp-gateway/signature-chain"]`: an array of v1 links, oldest first.
  `verify_chain` (committed) checks size, schema, trusted signers, signatures, no `unverified` hop,
  origin pinning, `prev`/`in`/`out` linkage, last signer, content (`out` == H(received)), nonce,
  staleness and future skew.

## Design

D1. Per-backend policy (config, public widening already approved 2026-09-29):
`backends.<name>.signature_chain: off | verify | require` (default `off`, which is today's
behaviour), `chain_origins: [key_id, ...]`, `chain_signer: key_id`. Keys come from the existing
`security.remote_server_signing.trusted_keys`. Validation at load: `verify`/`require` needs a
non-empty `chain_origins`, a `chain_signer`, every named key present in `trusted_keys`, and
`security.signature_chain` configured, since this gateway must be able to append. Anything else
refuses startup, naming the field.

D2. Outbound nonce. For a `verify`/`require` backend, D mints a fresh random nonce (128 bits, hex)
for each dispatch. It sends the nonce as `params._meta["io.mcp-gateway/chain-nonce"]` next to what
`build_outbound_meta` already writes. That is the one writer of the outbound `_meta`. Never the
client's nonce: U answers D's challenge, and the client challenges D. `off` backends get no nonce,
so their wire bytes are unchanged.

D3. Receipt-time verification, at the single ingress point that increment 2 made the strip point
(`apply_response_gates_effect`, which is shared by the meta route, the direct route and task
recovery). Before the strip, for a `verify`/`require` backend on a live dispatch, D computes
`received = content_digest(result)` on the result as the backend sent it. It then runs
`verify_chain(chain, policy{trusted_keys, chain_origins, chain_signer, replay_window =
message_signing.replay_window, max_links}, received, D's nonce, now)`. The chain is then stripped
from the result, as today. The outcome is server-owned and travels as data, never as payload JSON:

- `Verified(links)`: the verified upstream links. They become the prefix of what D delivers.
- `Unverified(refusal)`: a chain was absent, or failed a rule. Under `verify` the result is
  delivered, and D's own link records `up: unverified`. Under `require` the call is refused with
  `-32001` "upstream signature chain did not verify: <rule>", after the backend was accounted, as
  a post-dispatch gate refusal is today. It names the rule (`ChainRefusal`), never data.

Task recovery reads a stored result with no live nonce. It stays origin-only in increment 3: the
chain is stripped and the result is `NotEligible`. This is a limit, not a verification.

D4. Carrier. Increment 2's `ChainSource::Backend` gains the upstream outcome through a server-owned
`chain_upstream: Option<Arc<UpstreamChain>>` beside `chain_source` on `JsonRpcResponse`
(`#[serde(skip)]`, `pub(crate)`) and on `GuardedValue`. `UpstreamChain` holds the verified links
and `in = received`. The same A3 rules decide eligibility: a gate substitution (`GateEffect::
Enforced`) drops the upstream outcome together with eligibility. A capability dispatch, a cache hit
or a dispatch-error wrapper never carries one.

D5. Append at emission (`emit_origin_link`, finalize, and `finish_direct`), after the firewall and
before the v2 HMAC, as in increment 2:

- no upstream outcome: today's origin link (`prev` null, `in` null, `up: none`);
- `Verified(links)`: deliver `links` unchanged, then D's link with `prev = link_hash(last)`,
  `in = received`, `up: verified`, `out = H(final delivered result)`, `nonce` = the client's
  chain nonce (A1 fallback as in increment 2), `src: live`;
- `Unverified` under `verify`: D's link only, with `prev` null, `in = received`,
  `up: unverified`. A client verifier refuses it (rule 3). D states what it saw and never passes
  off an unchecked hop as checked.

The emission trigger is unchanged (a client chain nonce, or `emit: always`). A chained result whose
client asked for no chain gets no chain: the upstream links are dropped with the strip. The
appended chain must fit `max_links` and the 16 KiB chain cap. Otherwise the call is refused
`-32001`, as for an oversized origin link.

D6. What `out` covers. D's link commits to the final delivered result: gateway_invoke wrapping,
firewall redaction and `resultType` included. That is why `in` (what U delivered) and `out` (what D
delivered) differ, and why the verifier's linkage rule compares `in` to the previous `out`. A
downstream client verifies with origins = `[U's key]` and signer = D's key over the result it
received.

D7. Caches and replays. A `verify`/`require` backend bypasses the response cache: a cached result
cannot answer a fresh nonce. Idempotent replays of a chained result are delivered without a chain,
consistent with increment-2 limit L1: the stored upstream links answered another request's nonce,
and a stored `prev` would bind a stale hop.

D8. Scope limits, stated so the grade can be read against them:

- Chaining covers MCP backends reached through `gateway_invoke` and the direct route.
- Surfaced tools, Code Mode, playbooks and capability backends stay origin-only or unlinked, as in
  increment 2.
- There is no key rotation for chain keys beyond restart, and no revocation list. Trust is the
  static `trusted_keys` map.

## Evidence the row will be graded on (test outline; the full plan comes next)

- CHAIN.1: an end-to-end test starts two real gateway processes, U (origin) and D (`verify`).
  A client calls D with a chain nonce, receives a two-link chain, and verifies it with
  `verify_chain(origins=[U], signer=D)` over the received result. Both signatures verify, U's link
  is identical to what U emitted in RFC 8785 canonical form (the form its signature covers; JSON
  transport does not preserve raw bytes), and D's `prev` is H(U's link).
- CHAIN.2: the same topology with a tampering U (a flipped byte in U's `sig`, or a dropped link, or
  `out` not matching). Under `require` D refuses; under `verify` D's link says `up: unverified`
  and the client verifier refuses. A mutant that skips `verify_chain` in D (always `Verified`) turns
  the test red.
- CHAIN.3: the OWASP matrix ASI07 row is rewritten from those tests, naming the files.
- Unit rows: config validation (D1), nonce injection only for chained backends (D2), `require`
  refusal code and rule name (D3), cache bypass (D7), size cap on append (D5), and that gate
  substitution drops the upstream outcome (D4).

## r2: round-1 findings, all accepted

R1 (replaces the ingress point in D3). Verification runs at raw receipt, not at the gates. For an
MCP backend, raw receipt is the point in `dispatch_to_backend` where `response.result` is taken
(invoke.rs ~3697). That is before `submission.offer`, before `enforce_output_schema`, before any
task-handle capture or continuation, and before the input bridge reads the value. For the direct
route it is the start of `DirectRouteGuards::after_dispatch`, before `gate_payload`. `received`
is the digest of that raw value. `dispatch_to_backend` returns the verification outcome with the
value, and it travels to the live seal as a server-owned field (D4). Interim rounds:

- For a `require` backend, a reply that is not a complete result (`resultType: input_required`,
  or a task handle) is refused `-32001` at raw receipt. The refusal happens before any client
  request, continuation or answer-bearing retry. Chained backends support complete synchronous
  results only in 4.0.
- For a `verify` backend, an interim reply takes the unchained path (strip, `NotEligible`).

A test asserts zero client requests and zero upstream retries after an unsigned interim reply from
a `require` backend. Another asserts that a signed reply still verifies when output-schema
processing later changes the delivered content (`in` = raw digest, `out` = delivered digest).

R2 (replaces the task-recovery sentence in D3). Task execution on a `require` backend is refused at
admission with `-32001` "task execution is not available for a backend that requires a signature
chain". No handle is captured and nothing is recovered. On a `verify` backend a task result is
never chained (`NotEligible`), including a freshly polled completion. Handle-following is never
authorized by a result that raw-receipt verification refused. Tests cover an invalid initial
envelope and a valid synchronous reply beside a task call.

R3 (fixes an off-by-one in `verify_chain`). Terminal verification and append capacity separate.
`ChainPolicy` gains `purpose: ChainPurpose { Forward, Terminal }` (an enum, not a bool).
`Terminal` accepts `len <= max_links`. `Forward` (D verifying before appending) requires
`len < max_links`. Tests: a client verifies a chain of exactly `max_links`, and a forwarding
gateway refuses to append a hop that would not fit.

R4 (nonce). The per-dispatch nonce comes from `ring::rand::SystemRandom` (16 bytes, hex). It is
owned by that one dispatch, never stored or reused, and compared once. A fresh last-hop signature
proves D checked U at that moment. Freshness of earlier hops rests on each trusted hop having
verified its own upstream, which is exactly what `up: verified` asserts under a trusted key.

R5 (scope stated for the grade). Increment 3 meets CHAIN.1 for opted-in (`verify`/`require`)
synchronous MCP-backend forwarding through `gateway_invoke` and direct-route `tools/call`. It covers
requests that carry an explicit chain nonce, and `gateway_invoke` requests that carry the invoke
nonce while message signing is on and `emit` is `always`. The invoke nonce is a fallback value, not
a trigger, so under `emit: on_request` an invoke nonce alone emits no chain; a test pins that case,
which is outside the claim. Only such a chain is challenge-bound and verifiable by `verify_chain`, which
requires the last link to answer the client's nonce. A chain emitted under `emit: always` with no
client nonce carries `nonce: null`. It is signature evidence only: outside the replay-safe CHAIN.1
claim, documented as such, and never accommodated by weakening `verify_chain`. Tests cover
`emit: always` without a nonce on both routes and assert the client verifier refuses it (`Nonce`). The D7/D8 limits (replays, caches, surfaced tools, Code
Mode, playbooks, capabilities, tasks) are recorded in the ledger note and UPGRADING as accepted
limits, not as met conjuncts.

R6 (CHAIN.2 evidence, extended). Beyond a corrupted signature, the tests cover:
- a response from a different request's nonce (swap);
- a replay of a previously valid response (stale nonce);
- a stale `ts`;
- a three-hop chain (U1 -> U2 -> D) with the middle link removed.
All run on both routes where the route applies. The mutant that skips `verify_chain` must turn at
least the tamper, swap and drop rows red.

## r3: seat-2 round-2 findings (two HIGH), both accepted

R7 (direct-route challenge; D2 covered only `gateway_invoke`). The direct route does not use
`build_outbound_meta`: it forwards the caller's `params`, from which increment 2 already removes the
client's chain nonce (`take_chain_nonce_params`). For a `verify`/`require` backend, D writes its own
per-dispatch nonce into `params._meta["io.mcp-gateway/chain-nonce"]`. It creates `_meta` if absent
and keeps every other member. This runs after the client nonce is taken and before dispatch, on
both the sanitized and passthrough arms. That is the second, and only other, writer of the chain
nonce, and the only one for this route. For an `off` backend nothing is written beyond the
existing strip of the client's nonce. Only direct-route `tools/call` is chained; other direct
methods are delivered unchained. Tests, on both routes: the nonce is added only for
`verify`/`require`, existing `_meta` members survive, and `off` makes no write beyond the strip.

R8 (replay suppression, made concrete; D7 was prose). The sync-admission store records a
server-owned `StoredChain` beside the stored body (increment 2). It gains a variant:
`StoredChain::{Backend, ChainedBackend, NotEligible}`.
- `complete_delivery` stores `ChainedBackend` for a response that carried an upstream outcome
  (verified or unverified), or whose backend's mode is `verify`/`require`.
- The replay read maps `ChainedBackend` to `NotEligible`, so the replay carries no chain.
- `Backend` still maps to `Replay`, unchanged for origin-only results.
- A record written before this change deserializes as `Backend` or `NotEligible`, as today. Chained
  backends did not exist before this change, so no old record can hold a chained result.
The direct replay path is already `NotEligible` (limit L1). Red tests: a meta-route idempotent
replay of a chained result carries no chain key, and neither does a direct-route replay. The
backend is called once in each.
