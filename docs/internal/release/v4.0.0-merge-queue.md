# v4.0.0 merge queue

A second burndown, beside the criteria one in
`docs/internal/release/v4.0.0-burndown-tracker.md`. That board counts criteria graded
MET **anywhere**. This one counts the work those grades rest on that the
release line does not carry yet. Both have to reach zero before 4.0.0 ships,
and closing the first does nothing for the second.

The release line is `chore/v4-reconcile-main`. It superseded
`fix/v4-integration-ci-green` — which this document named until 2026-09-15 — by
strictly containing it: 184 commits ahead, 0 behind. `main` is 2246 behind it.

## The number

**19 of the 74 commits cited as evidence in
`docs/requirements/RELEASE-4.0.0-criteria-status.md` are on neither the release
line nor `main`.** Re-derived 2026-09-15 against `chore/v4-reconcile-main`, and
the finding is that it did not move: the 184 commits that took the line past
`fix/v4-integration-ci-green` closed none of the 19. The number is the same
number against a base 184 commits further along, not a number carried forward.
Reproduce it:

```sh
rg -o '`[0-9a-f]{8}`' docs/requirements/RELEASE-4.0.0-criteria-status.md \
  | sed 's/`//g' | sort -u | while read -r s; do
      git cat-file -e "$s^{commit}" 2>/dev/null &&
      git merge-base --is-ancestor "$s" HEAD || echo "NOT-IN-LINE $s"
    done
```

### What the number counts, and what it does not

The command above tests **ancestry**, not content. Two of the cited PRs were
squash-merged (`#473` as `0f04a179`, `#528` as `992b87c3`), and a squash lands
the work under a new identity, so a commit can be absent by ancestry and
present by content. Spot-checked both ways on 2026-09-15:

- `482746c1` — "track server.json version with the 4.0.0 crate version".
  Absent by ancestry; the line's `server.json` reads `"version": "4.0.0"` at
  both sites it touched. That is a match on **end state**, not a provenance
  finding: on a v4 branch any commit bumping the version produces the same
  read. `git log -S'"version": "4.0.0"' -- server.json` attributes the line's
  value to `0f04a179`, the squash of `#473`. **The end state is right; this
  commit is not what put it there.**
- `b7a4a768` — "wire the input bridge into the invoke path". Absent by
  ancestry, and its production wiring is absent by content. **The work is not
  on the line** — see below, where the cause turns out not to be the merge
  queue at all.

So 19 is an upper bound on unlanded work, not a count of it, and a content
check per commit does not exist yet. Do not read 19 as a release blocker of
size 19.

### The bridge wiring did not fail to merge — it merged and was then dropped

`#473` merged on 2026-09-10 as squash `0f04a179`, which **is** an ancestor of
`chore/v4-reconcile-main`, and which **did** carry the production wiring:
`BridgeDispatcher` and its `impl BackendInvoker` at `invoke.rs:834-891`. The
line's `invoke.rs` has neither. The pickaxe finds no commit that removed them,
because the removal is a merge resolution and `git log -S` skips merges by
default:

```sh
git log --full-history -m -S'BridgeDispatcher' \
  0f04a179..origin/chore/v4-reconcile-main -- src/gateway/meta_mcp/invoke.rs
# b3f05fd4  chore(v4): reconcile main into the v4 integration line
```

`b3f05fd4` resolved `invoke.rs` against the `main` side, which had never
carried the v4 bridge work, and 592 further lines across 71 other files went
the same way. One of them, `src/protocol/task_store.rs`, was deleted outright
and is a false alarm: `TaskStore` was consolidated into
`src/gateway/task_service/` and is live there. The bridge is not.

The consequence at the release line's HEAD is that `InputBridge` is
constructed nowhere in production code and the only `impl BackendInvoker` is
`FakeBackend` in `tests/mik_7212_mrtr7_bridge_acs.rs`. The suite is green
because it drives that fake; nothing drives the gateway's invoke path into
the bridge. 25 KB of `src/gateway/input_bridge.rs` is dead code on the branch
4.0.0 ships from.

This changes the remedy. Merging the ten work-package branches cannot fix it,
because the work is not waiting on them — it landed and was lost downstream.
Restoring it means re-applying `0f04a179`'s `invoke.rs` hunks onto the line
and giving the bridge tests a case that runs through the real dispatcher
rather than a fake, so a second reconcile cannot drop it silently again.

One of the 19, `9cf1557b`, is on no merged PR head at all.

## Why this is not worktree clutter

The repository carries 55 worktrees, and the obvious housekeeping reading —
delete the idle ones — is wrong here. Every branch in the table above lives in
one of them, and they hold the only copy of that work. `bin/safe-delete-branch`
refuses an unmerged branch for exactly this reason. Housekeeping for these
worktrees **is** merging them; removal is what happens afterwards.

## Worked example of the consequence

`MIK-7212.MRTR.7a` — "modern backend + legacy client MUST issue the equivalent
legacy elicitation" — is graded MET on `b7a4a768`, which is on four
work-package branches and on no integration line. At the release line's HEAD:

```sh
rg -n 'InputBridge' src/
```

returns the struct definition and two doc comments. There is no construction
site, so `InputBridge` is dead code on the branch 4.0.0 ships from. The grade
is honest about the work and silent about where it lives.

Re-run 2026-09-15 against `chore/v4-reconcile-main`, the line that replaced the
one this example was first taken on: seven hits, all in
`src/gateway/input_bridge.rs` plus one comment in
`src/gateway/server/stdio_channel.rs`, and still no construction site.

The attribution above is wrong, and the correction matters more than the
example. `b7a4a768` is indeed one of the 19, but its content reached the line
through the squash of `#473` and was then dropped by the reconcile merge
`b3f05fd4`. The grade is not silent about where the work lives because the
work is queued; it is silent because the work was merged and lost.

## Re-derived 2026-09-16 against `main`: the queue is one commit, not nineteen

`chore/v4-reconcile-main` was the release line when everything above was
written. It merged as PR #550 on 2026-09-16, so **the release line is now
`main`**, and every ancestry figure above was re-taken against `origin/main` at
`6d033b42`. Reproduce with `scripts/release/check-cited-commits.sh`.

The ledger has grown to 81 SHA-shaped citations, of which **20 are not
ancestors of `main`**. Two further extractions are not commits at all and
should be corrected in the ledger: `34541872175` is a CI run id, and
`a92c36e66a25` matches no object in this repository.

### Ancestry was the wrong oracle, and this run replaces it

The section above already warned that ancestry tests provenance rather than
content but stopped at two spot checks. This run checks all twenty, using the
squash body: GitHub lists the constituent commit subjects when it squashes, so
a `--fixed-strings --grep` of each cited commit's subject against `main`'s log
names the squash that carried it.

| Outcome | Count | Detail |
|---|---:|---|
| Carried into a squash on `main` | 18 | 12 via `992b87c3` (#528), 6 via `0f04a179` (#473) |
| On an open PR | 1 | `469a3eab`, lands with #561 |
| **Unaccounted for** | **1** | `9cf1557b` |

The script prints `unaccounted=2` and exits non-zero: it has no view of open
pull requests, so `469a3eab` counts there too. Subtract it by hand, or land
#561 and re-run.

`git cherry` looks like the tool for this and is not. It compares per-commit
patch ids, and a squash collapses N commits into one patch matching none of
them, so it reported `not-upstream=287` for a branch whose entire content is on
`main`. It cannot distinguish a squash from a missing merge. Do not use it here.

### `task-1-acs-rescued` is resolved, and the earlier reading of it was a query artefact

The branch has no PR of its own — `gh pr list --head task-1-acs-rescued --state
all` returns nothing — which reads as four orphaned evidence commits. It is
not: all four subjects appear in `0f04a179`'s squash body, so they reached
`main` inside PR #473. Searching by `--search` instead of `--head` returns
nothing either, for the unrelated reason that the PR text never names the
branch; that null result is not evidence about the branch.

### The one real gap: `9cf1557b`

"test(sub2b): cover the command-backend leg of S-02" adds 160 lines to
`tests/mik_7272_sub2b_acs.rs` and three test functions. The file exists at
`main`, and **one** of the three is there:

- present: `s02_http_forwards_a_second_notification_with_no_call_between` (`:1731`)
- absent: `s02_progress_from_a_command_backend_reaches_the_client_before_the_result`
- absent: `a_command_backend_notification_with_no_client_token_is_not_forwarded`

The two that are missing are the command-backend leg — precisely what the
commit exists to cover, including its negative control. `MIK-7272.SUB.2b`
(`RELEASE-4.0.0-criteria-status.md:230`) is graded `MET (caveat)` on
`364f4373`, which did land, so the grade does not rest on the missing pair; the
coverage the commit was written to add is nonetheless not on the release line.

### The bridge loss survived the merge to `main`

The finding recorded on 2026-09-15 is unchanged at `6d033b42`, which is the
material point: it is no longer a defect on an integration branch, it is a
defect on the branch 4.0.0 ships from. Scoped to production source at `main`'s
tip, `git grep ... -- 'src/**'` returns zero hits for `BridgeDispatcher` and
zero for `impl BackendInvoker`. `InputBridge` appears in exactly two files: its
own 25,003-byte definition in `src/gateway/input_bridge.rs`, and one doc
comment in `src/gateway/server/stdio_channel.rs:113` that names
`InputBridge::ask` while explaining a cleanup guard. A comment is not a
construction site. This remains the largest single release-readiness gap and
merging branches cannot close it.

### What this retires

Two tracked items were derived from the ancestry oracle and do not survive it:

- "Land the work-package branches holding the cited evidence commits" describes
  a merge queue of one commit, not of ten branches.
- "Adjudicate the declarations `0f04a179` added that have no trace at the
  release tip" rests on `0f04a179` being off the line. It is an ancestor of
  `main`. What has no trace at the tip is the subset `b3f05fd4` dropped, which
  is the bridge finding above and is already tracked as such.
