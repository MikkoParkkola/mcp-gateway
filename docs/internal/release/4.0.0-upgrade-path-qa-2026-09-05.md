> v3.0.0: auth is disabled on this gateway, so the admin UI and config endpoints are reachable by anyone who can reach the port (single-user/local posture assumed). Bind to 127.0.0.1 or a trusted network, or enable `auth.enabled: true`.
> v4.0.0: four changes need your attention. No config was changed automatically.
>     1. OAuth credentials are now stored per issuer. Stored tokens from 3.x are not migrated: re-authenticate each OAuth backend once (`mcp-gateway auth login <backend>`).
>     2. A malformed line in an `env_files` file now FAILS STARTUP instead of being skipped silently. A typo that used to cost one missing variable now costs a refused start, and says which line.
>     3. Protocol version 2024-10-07 is no longer advertised. Clients that only speak it must upgrade; 2025-03-26 and later are unaffected.
>     4. Rate-limited backend responses (HTTP 429 and equivalents) no longer count against the error budgets or the circuit breaker (GH #475). A throttled backend is no longer auto-killed for being busy.

## MIG.4 — FAIL

All four breaking changes are named, and three of the four are genuinely actionable:
item 2 states the new failure mode ("FAILS STARTUP") and that the message "says which
line"; item 3 gives the dropped protocol version and the safe floor; item 4 names the
excluded condition, both affected mechanisms, and the issue (GH #475).

**The one item that hands the operator a command hands them a command that does not exist.**
Item 1 says: re-authenticate each OAuth backend once (`mcp-gateway auth login <backend>`).

Smallest repro — run the notice's own instruction, exactly as printed:

```
$ ./target/debug/mcp-gateway auth login mybackend
error: unrecognized subcommand 'auth'

Usage: mcp-gateway [OPTIONS] [COMMAND]

For more information, try '--help'.
$ echo $?
2
```

There is no `auth` command on the top-level surface. The 23 commands are:
serve, cap, import, kubernetes, ranking, tls, trust, identity, init, stats, validate,
tool, skills, plugin, setup, add, remove, list, get, doctor, upgrade, audit (+help).
The nearest neighbour is `identity`, which is "Identity and local grant administration"
and offers only `identity grants` ("Manage local identity grants") — local grant
administration, not OAuth backend re-authentication.

Why this is a FAIL and not a nit: item 1 is the only one of the four that requires the
operator to *do* something before the gateway works again (3.x OAuth tokens are stated
as not migrated), and the notice's remedy is the sole instruction for doing it. An
operator who follows it literally gets exit 2 and no alternative. The notice is
actionable in form and unactionable in fact on exactly the item that needs an action.

Caveat, stated honestly: this was driven on a **default-feature debug build**. If `auth`
is gated behind a non-default cargo feature, the command may exist in some builds — but
the notice is emitted unconditionally by that same build and names it unconditionally, so
either the notice should name the command that exists in the build printing it, or say
which build exposes it. I did not rebuild to test this (one build per instruction).

## CFG.5 — INVESTIGATE

**An operator can confirm the `error_budget` section is READ and TRACKED. An operator
cannot confirm WHICH VALUES are live.** Those are different claims, and only the first
has a surface.

Probe config: non-default, individually recognisable values —
`error_budget{threshold 0.42, window_size 77, min_samples 3, capability.threshold 0.37}`.

### What DOES exist (found on the last probe, and it is a real surface)

Editing `error_budget.threshold` in a running gateway's config file produces a log line
that names the section by name:

```
./target/debug/mcp-gateway serve -c $S/cfg/reload.yaml &
sleep 6; sed -i '' 's/threshold: 0.42/threshold: 0.91/' $S/cfg/reload.yaml; sleep 8
```

> INFO mcp_gateway::config_reload: Config watcher: config file changed, triggering reload
>
> INFO mcp_gateway::config_reload: Config reload: complete changes=profiles/meta config changed — **NOT YET APPLIED, restart required for: error_budget** restart_required=true

That is correct behaviour and matches `docs/DEPLOYMENT.md`: "The section is read when the
gateway starts, so an edit takes effect on restart, not on reload." It proves the reload
path knows `error_budget` exists and is restart-scoped.

### What does NOT exist — the gap

No surface anywhere echoes the effective **values**. Nothing prints 0.42, 77, 3 or 0.37.

| surface | command | result |
|---|---|---|
| logs, all levels | `serve --log-level debug -c cfg5b.yaml` → 829 lines, searched for budget/threshold/0.42/0.37/77 | **zero matches** |
| metrics | `GET /metrics` | no budget/threshold series |
| status/config endpoints | `GET /config, /status, /api/config, /admin/config, /gateway/config, /.well-known/mcp-config, /v1/config` on :39476 | all **404** (`/health` → 200, so the server was up and answering) |
| stats subcommand | `./target/debug/mcp-gateway stats -c cfg5b.yaml` | no budget/threshold mention |
| config dump | `setup export` | emits *client* config files, not a gateway effective-config dump |

Contrast that with a subsystem that does it: the cache logs its effective configuration
on boot — `Response cache initialized enabled=true default_ttl=60s max_entries=10000`.
Firewall, webhooks and attestation likewise log theirs. `error_budget` is the only major
subsystem I drove that logs no effective-config line at any level.

### Smallest repro

Boot with a value that could not occur by accident, then search the logs for it:

```
./target/debug/mcp-gateway serve --log-level debug -c <cfg with error_budget.threshold: 0.42>
```

Search the output for `0.42`, `threshold`, or `budget` — no output.

### Why this is INVESTIGATE and not PASS

Validation (VAL.1/3/4) proves *a validator* reads the section, and the reload notice
proves *the reload path* tracks it. Neither proves the parsed value reaches the component
that spends the budget. From the operator's chair, a gateway running `threshold: 0.42`
and a gateway running the built-in default are **indistinguishable by observation** — no
log, no metric, no endpoint, no subcommand separates them. That is the gap. It may well
be wired correctly; the point is that nothing available to an operator says so, which
also means a future regression that silently ignored the value would produce no signal.

Cheapest thing that would close it: one boot-time log line in the shape the cache already
uses — `Error budget initialized threshold=0.42 window_size=77 min_samples=3 capability_threshold=0.37`.

## Off-list — things I hit that nobody asked about

### 1. `upgrade --help` promises a backup that is never created

`upgrade --help` states the command "backs up `gateway.yaml`, and runs any registered
migrations." No backup file appeared in either data directory after a successful upgrade.
Listing `$S/n1` and `$S/m1` after their upgrades shows exactly two files each —
`gateway.yaml` and `version.stamp`. No `.bak`, no timestamped copy, no dotfile.

This is benign today precisely *because* MIG.1 holds: the file is byte-identical
afterwards, so there is nothing to restore. It stops being benign the moment a future
migration actually rewrites config, and an operator who read the help text will believe
a rollback exists when it does not. Either the help text or the behaviour is wrong.

### 2. `error_budget` is the only major subsystem with no effective-config log line

This is the mechanism behind CFG.5 rather than a separate defect, but it is worth naming
on its own: cache, firewall, webhooks and attestation each log their resolved
configuration at boot. `error_budget` logs nothing at any level. The house style already
exists; this section just doesn't follow it.

### 3. Config-permissions warning fires on a 644 file (working as intended, noted for noise)

Every `serve` on a scratch config emitted:

> WARN CONFIG READABLE BY OTHER LOCAL USERS: it holds this gateway's credentials. Fix with: chmod 600 <path> path=... mode="644"

Correct and well-worded. Flagging only because a config with no credentials in it at all
still gets the credential warning — it is a mode check, not a content check. Not a defect,
possibly a nuisance for operators running credential-free local gateways.
