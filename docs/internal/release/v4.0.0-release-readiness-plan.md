## Order of work

1. **Integration first.** Merge #550 (green, clean, fast-forward), then #561,
   then land the four branch clusters above. Until the release tip carries the cited evidence, every grade
   below it is provisional and any criterion closed now may have to be regraded
   against the merged tree. This is the single highest-leverage item and it
   subsumes goal rows [31], [36] and [39].
2. **Bucket A in parallel with the merges**, since the missing tests are
   independent of each other. `MIK-6744.STORE.2` and `NFR.CONFORMANCE.1` are
   small and can go first to move the number.
3. **Bucket B on Spark** once the tip is stable, because a latency or workload
   measurement taken against a pre-integration tree has to be retaken.
4. **Bucket D** falls out of step 1 automatically.
5. **Bucket C** as a dedicated live session with backends configured.
6. **Bucket E** as two operator handoffs, stated above with the exact action.

## Regrade after integration

Steps 1 through 4 change the tree the ledgers were graded against. When `main`
carries the v4 line, re-run both scripts and re-run the ancestry sweep. A row
whose evidence commit is still absent from the tip is not MET on the release
line, whatever its status string says.

## Two questions that are not release blockers

**The client tool surface.** Whether 4.0.0 should flip its default from the
classic 9-17 meta-tools to code mode's two, and whether admin operations become
reachable through that pair, was taken to design review before any code. Verdict
recorded in [ADR-015](../../adr/ADR-015-client-tool-surface-4.0.0.md): the classic
surface stays the default, nested meta routing is not added, and the flip is
gated on four entry conditions — a non-colliding meta target, meta-tools indexed
in `gateway_search`, nested calls routed through the central meta-tool gate, and
a real token measurement rather than a tool count. Two of the three blocking
defects were confirmed against source. This closes the question for 4.0.0 and
adds no criteria.

**Multi-user auth.** The identity stack that a multi-user deployment needs is
already built and already graded — OAuth isolation, identity propagation, the
key server and per-agent auth. What is missing is one deployment recipe tying
them together; see the four criteria listed above under bucket A and E rather
than a new workstream. No 4.0.0 scope is added for it.
