# v4.0.0 gap closure — plan to release-ready

Distance to release, re-measured from `docs/requirements/RELEASE-4.0.0-criteria-status.md`
on 2026-09-08 (second measurement, later the same day): **21 rows are not MET** — 5
`UNWIRED`, 9 `ABSENT`, 7 `PARTIAL`. The ledger has grown to 217 table rows as sub-clauses
were split out; the rest are MET or N/A with a reason.

The first measurement that day said 23, counted by `rg -c` over status tokens. That method
counts every occurrence of the word, including the ones in prose and evidence cells, and it
does not count a row whose status cell reads `ABSENT (clause: ...)` or sits in a fourth
column. It over-counted six and under-counted two. Rows are now counted by matching a table
line with a status cell, and the two rows the old method could not see — `NFR.SEC.3` and
`NFR.COMPAT.1`, both `ABSENT (clause: ...)` — are in the 21. A count taken by grepping for a
word is a count of the word.

The 2026-09-07 revision of this plan said 19. That count was taken before the ledger
gained `UNWIRED` as a distinct status, and a status-token count that predates a
vocabulary change undercounts silently rather than failing. Reconciliation of the two
numbers is in the table below; nothing was lost, three rows closed and seven were
regraded out of MET.

## The critical path as of 2026-09-13

Everything below this section is the 2026-09-08 measurement and is left as recorded. This
section is the current path, and it is short because the remaining distance is no longer
made of open engineering rows. Read it with the non-ledger blocker table further down:
that table, not the row count, is where release readiness is actually decided.

**Where the two open core rows stand, and why neither is closable here.** `NFR.SEC.7`
was probed on 2026-09-13 against a listening build of `bd1adbb4` and both controls
refused a foreign origin and a foreign Host with the positive half of each probe still
returning 200. It stays PARTIAL because provenance cannot corroborate before the release
is tagged, and because the install the criterion is about is the deployed
`3.4.0-f30539af`. `NFR.PERF.1` was re-measured the same day; the worst shared-case

reproduce, but the grade does not move, because the row is PARTIAL for a structural
reason — the harness produces no end-to-end percentile — and a second run of the same
harness cannot produce one. **Neither row is waiting on code.** A plan that keeps
scheduling work against them is scheduling work that cannot land.

**What actually gates the release, in order. Each step is blocked by the one above it.**

1. **MIK-7387 step (c), in flight in a peer's worktree, uncommitted.** Steps (a) and (b)
   landed (`416a3319`, `93a77a80`). Step (c) makes stdio dispatch concurrent and routes
   replies before dispatch, and it currently holds 264 uncommitted lines in
   `src/gateway/server/mod.rs` on this shared branch. Nothing below can start while it
   does: a merge into a tree with uncommitted changes in the file most likely to conflict
   is how a peer's work gets destroyed. This also retires the "UNDECIDED" state recorded
   for MIK-7387 below — the deferral's trigger (`MRTR.7a`/`MRTR.7b` MET) has fired and
   the work is being done.
2. **The merge queue.** 19 of the 74 commits this release cites as evidence are absent
   from the release line, spread over the 10 branches inventoried in
   `v4.0.0-merge-queue.md`. Until they land, a row graded MET is a claim about work that
   exists somewhere, not about the branch 4.0.0 ships from — `MIK-7212.MRTR.7a` is the
   worked example: graded MET, and its bridge has no construction site at this HEAD.
3. **Re-cut the scope contract against the merged line.** Most of the 20 pending scope
   criteria are not failing; they are *ungradable* here, because the contract points at a
   tree that predates the merges. This is the step that makes the number able to fall at
   all. Expect `OPEN` to sit near 22 until it happens, and do not read that flatness as
   stalled work.
4. **Make the line testable at all, then get strict CI green on it.** This step was
   badly understated in the first revision of this list, which recorded CI as green since
   `97cb2856` (2026-09-12) and treated the rest as routine. Two things were wrong with
   that, both found on 2026-09-13 by opening a draft PR (#539) to see what would happen.

   First, **nothing on this branch triggers CI.** `.github/workflows/ci.yml` runs on
   `push` only for `main` and `v*` tags, and on `pull_request` only for base `main`,
   `codex/v4-*` or `fix/mrtr2-continuation-handle`. The green run at `97cb2856` came from
   PR #531, whose base was `codex/v4-next-integration`; that PR merged, and every commit
   pushed to the line since — including the MIK-7387 commits `416a3319` and `93a77a80` —
   has been invisible to CI. A branch that cannot run CI does not report red. It reports
   nothing, and "strict CI green" as a release gate was pointing at an instrument that was
   not connected.

   Second, and the reason the draft PR did not fix it by existing: **the line conflicts
   with `main`.** `gh pr view 539` reports `mergeable=CONFLICTING`,
   `mergeStateStatus=DIRTY`, and GitHub skips `pull_request` workflows when it cannot
   compute a merge commit — which is why #539 shows CodeQL jobs and no CI. Measured:
   the line is 2083 ahead of `origin/main` and 15 behind, and `git merge-tree` reports
   about 112 conflicting files — roughly 66 add/add (the same document authored on both
   sides) and 39 content conflicts inside `src/`, plus `Cargo.toml`, `Cargo.lock`,
   `CHANGELOG.md` and three workflow files. The add/add half should be cheap; the 39 in
   `src/` are the real work and are not yet triaged.

   So the order inside this step is: reconcile with `main` first (the conflicts are the
   blocker, not the merge policy), then CI runs on its own through #539, and only then
   does a green run mean anything. Doing this before step 2 would be a mistake — every
   queue merge changes the conflict set, so reconcile once, after the queue, not
   repeatedly during it.
5. **The live acceptance pass.** Still `NOT RUN`, and it is now the largest wholly
   untouched blocker on this list. DoD requires the running thing driven from the
   revision under review, so it cannot be front-run: it has to follow the merges and the
   re-cut, or it certifies a tree nobody is shipping.
6. **Operator cutover of the `3.4.0-f30539af` install, then re-probe it.** This is the
   first half of `NFR.SEC.7` and the row's only remaining work. An earlier revision of
   this section put the tag here instead, reasoning that a tag is what lets the checker
   corroborate provenance — which inverts the criterion. The checker says so itself: *the
   probe decides; build provenance only corroborates.* A deployed build that refuses a
   foreign `Origin` and a foreign `Host`, with the positive half of each probe still
   answering 200, closes the row whether or not a tag exists. Tagging first would mean
   publishing while the release's one blocking row is still blocking.
7. **Tag and publish.** Last, because `NFR.SEC.7` blocks publication until step 6 clears
   it. The tag then also gives the checker its provenance corroboration, which is a
   strengthening of evidence already sufficient, not a precondition for it.

**Operator-only, so that no plan schedules them as work.** The burndown tracker counts
three such rows, and this list must match it or one of them goes unowned: the
`NFR.SEC.7` cutover in step 6, `MIK-6744.STORE.1` (migrate or rewrite), and

## Per-package process — full scope, not abbreviated

Each package runs `rules-source/workflows/development-process.md` end to end: design
reviewed before any code, test plan reviewed, failing tests reviewed as tests,
implementation, self-QA, final review (two code legs plus the functional leg),
documentation, housekeeping. The reviewer pair for this session's authorship is
gpt-review + kimi-review.

Each package closes by rewriting its rows in the criteria file with evidence: what was
done, what pins it, and what is still not pinned.
