# MIK-8513 test plan

Status: FINAL (one review round, gpt SWF + grok SWF, folded; lead ruling: a single round). Design: `2026-10-23-mik-8513-registry-content-and-start.md`
(final, b63ace710). The tests are written on a branch stacked on #4061's head,
4ba529045, where the checker already parses `ServerCatalogEntry`.

## Shape

- **One new offline file,** `scripts/dev/test_check_registry_content.py`, beside
  the existing self-test. Each row is its own function, and a small runner
  calls them all and prints `PASS`/`FAIL <row>: <reason>` for each. A red run
  therefore shows every row failing, rather than stopping at the first missing
  attribute. The runner exits 1 if any row fails.
- **CI wiring:** ci.yml's offline `registry-packages` job runs the new file
  next to the old one. No network or Docker; CONTENT.3.
- **Live rows** are workflow steps in `registry-packages.yml` (L1 to L4 below).
  Their red is "the step does not exist yet"; their proof is the first green
  run plus the falsifier testdata.
- **Network and processes are stubbed in every offline row:** `fetch`, and a
  single `run_container(argv, stdin, caps)` seam the driver uses for every
  Docker call.

## Live rows (registry-packages.yml)

Until each step exists and runs, its row is pending evidence, not a red test.

| row | AC | job | asserts |
|---|---|---|---|
| L1 | C1 metadata | resolve | `registry-integrity.rs` with its sidecar (one wrong value): exit 1, `1/2 registry entries resolve`, exactly one `FAIL <wrong>: … integrity` |
| L2 | C1 bytes | starts | the same testdata under `--start`: exit 1, and exactly one `FAIL <wrong>: … served bytes` naming the wrong entry. FAIL lines of other kinds (integrity, start) for that same entry are allowed |
| L3 | C2 falsifier | starts | `registry-wont-start.rs`: `PASS time`; one `FAIL … exited … before answering initialize` for a named, pinned npm package whose bin exits at once, chosen at implementation, which must itself pass resolve and the byte step; `1/2 eligible entries start`; exit 1 |
| L4 | C2 | starts | the real registry: `PASS` for memory, sequential-thinking, fetch and time; `4/4 eligible entries start`; exit 0 |

The `resolve` job keeps its existing steps and its 10-minute cap. Path filters
gain the sidecar and the testdata files.

## Red-first protocol

1. Write O1–O16 and the testdata on the stacked branch.
2. Run them locally with `python3 -I -B`: they are Python self-tests with no
   cargo and no Docker, so Spark is not needed. `-B` avoids reusing a stale
   `.pyc` of the same size.
3. Expected red: every row FAILs. O4 is a guard: it may pass once the sidecar
   loader exists and is recorded as a guard, not as a red.
4. Each row's failure must be the missing feature, never a typo: the runner
   prints the exception type, and an `AttributeError` or `NameError` on a
   name the design defines is the accepted red.

## Not tested, and why

- **Real Docker isolation:** whether the kernel enforces the flags. O11 pins
  what we ask for; L3 and L4 prove the containers actually run. A hostile
  package test is out of scope.
- **Corrupted bytes under unchanged metadata through a real registry:** too
  costly (design r2). O7 and O8 cover our comparison; the installers'
  verification is upstream behaviour.

- **Extended rows:**
  - O11, the literal isolation flags, environment and volume;
  - O12, cleanup on every outcome;
  - O14, missing `result`, `protocolVersion` or `serverInfo`, and the total

  - O9, single-predicate negatives;
  - O3, split fixtures;
  - O10, a hint-bearing SKIP.
- **Live rows:** L2 requires exit 1; L3 names its package at implementation;
  live steps count as pending evidence until they run.
