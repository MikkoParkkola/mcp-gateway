# v4.0.0 critical-path coverage contract

Covers conjunct **C5** of `NFR.BUILD.1`
(`docs/requirements/RELEASE-4.0.0-scope-update.md:59`):

> Pin supported reference client/backend versions and feature/build
> combinations under the existing license split; current critical-path coverage
> and mutation evidence grades the final integration revision.

## What this document is, and what it is not

**It does not close C5.** Read the criterion's verb: *"current critical-path
coverage and mutation evidence **grades the final integration revision**"* —
one verb, one object, two subjects. C5 carries exactly the same final-revision
dependency as C6, and the final integration revision does not exist yet. Any
number taken today grades a revision that is not the one the criterion names.

What was missing before this document is the other half of the obligation, and
that half does not depend on the final revision at all.
`docs/requirements/RELEASE-4.0.0-scope-tests.md:73` requires coverage on
"final integrated **startup, OAuth, HTTP/stdio dispatch, bridge, tasks and
account paths**" — six named paths with no mapping anywhere to concrete
modules, and no agreed command. "Agreed critical coverage" cannot be run
against a list of six English nouns. This document fixes the mapping, the
command and the baseline now, so that when the final revision lands the
measurement is a re-run rather than a fresh argument about scope.

The prior artifact, `docs/internal/design/2026-09-03-cluster-a-coverage-audit.md`, is
self-scoped "Audit only" and reports Cluster A component rows at `9b0643d4`.
It is not superseded — it answers a different question — but it is not
critical-path coverage and was never claimed to be.

## The mapping

Each row fixes one named path to the modules that implement it. A path whose
module set changes is a change to this contract, made in the same commit.

| Named path | Modules | Tier |
|---|---|---|
| startup | `src/gateway/server/` | Standard (>=80%) |
| OAuth | `src/oauth/` | Standard (>=80%) |
| HTTP dispatch | `src/transport/http/`, `src/gateway/router/` | Standard (>=80%) |
| stdio dispatch | `src/transport/stdio.rs`, `src/gateway/server/stdio_channel.rs`, `src/transport/command_split.rs` | Standard (>=80%) |
| bridge | `src/gateway/input_bridge.rs` | Standard (>=80%) |
| tasks | `src/gateway/task_service/`, `src/gateway/router/handlers/tasks.rs`, `src/gateway/meta_mcp/task_confirmation` | Standard (>=80%) |
| account paths | `src/personal_accounts/`, `src/gateway/server/account_bindings.rs`, `src/config/account_bindings.rs`, `src/identity_propagation/` | Standard (>=80%) |

**Tiers (release-owner ruling, 2026-10-01, for MIK-7324.COV.3).** The floors
are Critical >=95% and Standard >=80% line coverage. The tier follows whether
the code enforces security, the test this release already applied in
`docs/internal/requirements/RELEASE-4.0.0-dod-check.md:634-638` ("protocol
parsing on a security path is Critical rather than Standard"). Startup and
bridge route requests to the enforcement points (admission, firewall, auth);
they are not those points, so both are Standard. A second ruling the same day
applied the same rule to the other five paths: each is Standard.

Inside every path, a function that enforces security is Critical, and is held
to 95% on its own lines. It enforces security when it:

- makes an authentication or authorization decision;
- verifies a token, signature, MAC, PKCE verifier, OAuth state, nonce,
  redirect, issuer or audience;
- enforces tenant or owner scoping;
- refuses a request or input on a security ground. A limit counts when it
  bounds what one principal, or an untrusted peer, provider or disk record,
  can consume (a per-principal quota or rate, a size cap on untrusted input).
  A global capacity budget does not.

A private helper that makes the decision for a Critical function is Critical
itself and has its own row: a wrapper's lines do not include its helper's, so
the helper's refusal could otherwise go untested while the wrapper passes.

Builders and installers whose mistake would silently disable an enforcer are
recorded too, as `standard` rows: they stay at the path floor.

**The inventory is `docs/release/v4.0.0-critical-functions.tsv`**: one row per
function, with its file, name, tier, category and reason. 291 rows are
Critical. It was drawn up by reading every production file in the seven paths
and reviewed once for omissions (2026-10-01); the review added 24 rows,
promoted 14 builders to Critical and moved 7 entries (command quoting,
protocol-era refusals, a forwarding wrapper) to `standard`. Startup's four
and the bridge's four came from reading those files directly. A function added to
one of these paths that meets the definition is added to the inventory in the
same change.

## The command

```sh
cargo llvm-cov --all-features --tests --ignore-run-fail --summary-only --json --output-path cov.json
```

Changed 2026-10-01 from `cargo llvm-cov --lib ...`. `--tests` counts the
integration suite under `tests/` as well as the library's unit tests; `--lib`
alone left bridge at 73.88% when its end-to-end tests
(`tests/mik_7212_mrtr7_bridge_acs.rs`) bring it to 90.61%.
`--ignore-run-fail` keeps the report when a test fails under instrumentation;
every failure is listed with the figure, and a run with a product failure does
not grade anything. Per-function figures come from the same run's
`cargo llvm-cov report --lcov --output-path cov.lcov`, graded by

```sh
python3 scripts/release/critical_function_coverage.py --lcov cov.lcov
```

which reads the inventory, finds each Critical function by name, and takes the
share of its instrumented lines (`DA:` records within its body) with a non-zero
count. It exits non-zero while any Critical row is below 95%, is missing, or
has no instrumented line in any report it was given. Platform-specific
functions (`#[cfg(windows)]`, `#[cfg(unix)]`) are measured only by the run
that compiles them, so the grade takes one report per platform:
`--lcov linux.lcov --lcov windows.lcov`, graded over their union.

One measurement correction, ruled 2026-10-01: a field expression written on
its own line inside a `tracing` macro (`trace!`, `debug!`, `info!`, `warn!`,
`error!`, `event!`, `span!`) is compiled twice, once for the subscriber and
once into tracing's log-fallback branch, and llvm attributes that line to a
region that reads zero even when the event was emitted and asserted. The
grader drops such an argument line only when it reads zero, the macro's own
head line has a non-zero count (so a log call no test reaches still fails), and
the line is a plain field: exactly one field whose value is a literal, a bare
identifier or a field/path access, optionally behind tracing's `%` or `?`,
ending with its comma. A call, parenthesis, operator, postfix `?`, closure or
macro keeps the line graded, so the rule can only fail a function spuriously,
never pass an untested line. It prints every dropped line with its `file:line`
and the head's count.

The reverse case, ruled the same day (MIK-7725): a call in a macro's arguments
on the macro's own head line (`debug!(url = %clean(x), "..")`) shares that
line, so the line's count shows the macro was reached, not that the call ran.
The grader grades such a head line as missed whatever its count and prints it
as unverifiable with its `file:line` and count. The test is one anchored
match on the whole line: indent, an optional `tracing::` path, a level macro
(`trace`, `debug`, `info`, `warn`, `error`, `event`) and `!(`, then
comma-separated plain items (a quote-free string literal, `name = [%|?]value`,
or a bare `[%|?]value`, where a value is an identifier or `::` path or a
numeric literal; no `.` field access, which can run user Deref code), an
optional trailing comma, and an optional `)` and `;`. Every other line that
names a tracing macro (including a `use tracing::<level> as <alias>` alias in
the same file, or a block comment before the `!`) is unverifiable: a call, a second statement, a match-arm
prefix, a char literal, a raw string, a comment, another delimiter, `span!`.
There is no stripping or parsing step to fool. The same principle holds: a
spurious fail is possible, an unrun call passing is not. The fix in the source
is to compute the value into a local before the macro and log the local.

Line coverage per path is then the covered/total line ratio summed over the
files whose path starts with one of that row's prefixes. Test modules are
excluded: re-running the report with
`--ignore-filename-regex '(_tests|/tests)\.rs$'` returns byte-identical totals
and zero excluded files, so the 382 files in the report are production sources
already.

The 2026-09-17 figures below were taken with `--lib` only, which left out the
integration suite under `tests/`; they are kept as the record of that run. The
2026-10-01 figures use the command above.

## The baseline

**The baseline is the `--tests` table under "Measurement, all seven paths,
2026-10-01"**, and nothing else: the no-drop check in step 4 below compares
against it. The 2026-09-17 `--lib` figures (startup 68.78% to tasks 93.84%)
are kept only as the record of that run; they are not a baseline.

This is a **baseline, not a threshold.** Nothing recomputes it. Calling an
unenforced number a rule would be the exact failure this release has already
been bitten by — `docs/release/v4.0.0-supported-matrix.md` spent this same
session replacing a capability count that read as evidence while being a memory
of what was once true, and a floor with no job behind it is that again in a
different file. The numbers above are a measurement with a date and a command,
and they are worth exactly that until something re-runs them.

Turning the baseline into a ratchet — in the shape of
`scripts/ci/check-loc-ceiling.sh`, which the repository already uses for the
file-size deviation — means making an instrumented coverage build a required
job. That is a release-owner decision about CI cost and about which revision it
gates, and this document does not make it.

## What closing C5 requires

1. The final integration revision exists and is named.
2. The command under "The command" runs on it **without** `--ignore-run-fail`,
   on a tree with no uncommitted edits, and exits clean, with no profile
   dropped: an interim probe may discard corrupt profiles from killed children
   (and logs each), the grade may not (#2573). The task-SDK tests
   need the Python task SDK installed (as the `task-sdk-recovery` job does);
   a run without it is not clean. (`--all-targets` was named here before
   2026-10-01; `--tests` is the one command for both the baseline and the
   grade, so the two are comparable.)
3. Every path in the mapping carries a tier. All seven do since the
   2026-10-01 rulings, and none is waived; a path added later blocks the grade
   until it has one, because matching an old baseline is not a floor.
4. The per-path table is re-taken against that revision, and:
   - no row is below its recorded `--tests` baseline (the all-seven-paths
     table, 2026-10-01). The 2026-09-17 figures are `--lib` only and are not
     compared;
   - every path clears its tier's floor (Standard >=80%, Critical >=95%);
   - `critical_function_coverage.py --lcov linux.lcov --lcov windows.lcov`
     exits 0: every Critical row measured by one of the two runs and at or
     above 95%.

Steps 2 to 4 are a re-run of a fixed contract.
Step 1 is the blocker, and it is the same blocker C6 has.
