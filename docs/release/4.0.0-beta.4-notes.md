# mcp-gateway 4.0.0-beta.4

This is the fourth public pre-release of mcp-gateway 4.0. It is here so that people running
3.x or an earlier beta can try 4.0 against their own configurations and clients before the
final release, and tell us what breaks. What 4.0 is as a whole is in
[`docs/whats-new-4.0.md`](../whats-new-4.0.md); this page covers what changed since
[beta.3](4.0.0-beta.3-notes.md).

## New since beta.3

- **A new web UI at `/ui`.** It lists every server with its state and the reason for it
  (running, paused, slow and so on), previews a server before you add it, adds it with only the
  tools you tick, signs an OAuth backend in again, and can adopt a server it finds in another
  app's config file on this host. You can try a tool from it. Activity lists each call with
  the check that decided it and what the gateway did to the answer, including calls an identity
  grant refused, and filters and exports by rule. Admins can create, rotate and revoke API keys,
  read and save settings and policies, and deny an access request. Each key sees only the pages
  and tabs it may open. The UI follows the gateway's live event stream and has a command palette
  (Ctrl+K or ⌘K).
- **More MCP Events sources** (each off by default): a `schedule.tick` timer, a REST watch that
  fires `watch.<capability>.changed`, the gateway's own operational events, and events from
  legacy SSE-handshake and A2A backends.
- **A2A delegation.** An MCP client can hand a whole task to an agent that speaks only A2A 1.0
  (JSON-RPC binding).
- **Secrets in the OS keychain.** `keychain:NAME` references read on Linux, macOS and Windows.
  Secrets the gateway saves (from the web UI, the CLI or discovery) go to the keychain
  by default; `secrets.store: files` keeps them in owner-only files beside the config instead.
  The CLI no longer writes a credential you type into `gateway.yaml`.
- **Firewall rules scoped by backend and key.** A rule can apply to some backends or API keys,
  carry exceptions, and confine a file tool to allowed folders. `backends.<name>.allowed_tools`
  limits a backend to the tools you list.
- **Audit records say why.** Every audit record names the check and rule that decided the call
  and what the tool declared it could change. Delivery records say what happened to the answer.
  `audit verify --anchor` checks the log against an off-host copy, and the log notices when its
  file was rewritten under it. Key-server audit records carry a keyed hash of the email instead
  of the email, and an admin can look up a person's records by email
  (`mcp-gateway audit lookup-email`).
- **Health you can watch.** `/metrics` reports the latency the gateway itself adds, the gateway
  keeps a seven-day record of its own health, and each server keeps a latency history.
- **More settings apply on reload**, with no restart: API keys, firewall rules, credential
  redaction, the tool policy, budgets, input sanitizing, SSRF protection and
  `meta_mcp.surfaced_tools`. API keys rotate without a gap, and a key keeps its rate limit and
  circuit breaker across a rotation.
- **Tasks.** Cancelling a task cancels its upstream task, and a client can cancel its own call.
- **Less work per call.** A repeated `tools/list` re-serialises nothing, and the request path
  copies less.
- **Security fixes.** This beta carries 177 new security entries. Among those that also affect
  3.x: the Windows OAuth login no longer goes through `cmd.exe`; the OAuth callback checks
  `state` before it ends a login; OIDC discovery, JWKS and token-exchange requests no longer
  follow a redirect to another origin; a misspelt action in an agent scope no longer grants
  every action; a backend can no longer forge the gateway's own answer members; the firewall
  audit log no longer records what a scan matched; and tokio moves to 1.53.3
  (RUSTSEC-2026-0386). Each entry in `changelog.d/` in this tag names the versions it affects
  and what an operator has to do.

## Before you upgrade from beta.3

[`docs/UPGRADING-4.0.md`](../UPGRADING-4.0.md) is still the full list, with the action each item
needs. The changes since beta.3 most likely to affect an existing install:

- **Run `mcp-gateway upgrade` once on your config.** Six keys that never had an effect
  (`backends.<name>.idle_timeout`, `backends.<name>.circuit_breaker`, `marketplace`,
  `server.request_timeout`, `server.ws_port`, `cost_governance.currency`) are refused at load
  again. Seven settings the gateway now picks itself (`cache.enabled` and the failsafe
  switches among them) and `meta_mcp.cache_tools` load with a warning and are ignored; if you
  set one of those switches to `false`, read its entry in the upgrade guide. `upgrade` deletes
  all of them and replaces each plaintext API key with its digest. Exit 1 means it left
  something for you to fix by hand.
- **`server.shutdown_timeout` is one total stop budget with a 13 s minimum.** Raise a lower value
  or remove it for the 30 s default. A copy of a shipped container or Kubernetes template needs
  a stop grace of the timeout plus 1 s.
- **An admin key limited to some backends is no longer a gateway-wide admin.** Give a key that
  administers the whole gateway `backends: ["*"]`. An admin key with an empty list stays a
  gateway-wide admin.
- **Identities must name someone.** A certificate or token with no subject, and a grant rule
  that names no one, are refused. `api_key:<name>` grants match only that API key, and per-key
  budgets apply only to API keys.
- **A call with an idempotency key needs a verified caller.** Give such clients a credential or
  have them drop the key.
- **A backend's `secrets:` rules apply on every route**, and a rule the gateway cannot deliver
  safely is refused at load.
- **Back up three new files with the data directory:** `record-principal.key` (records name a
  credential by a keyed digest), `key-server-email-hmac.json`, and each audit log's
  `<log>.sigstart`.
- **Open event subscriptions and watches close once** after the upgrade; reopen them. Each
  subscriber of a passthrough backend sends `events/lease`.
- **Field names.** The gateway's hint, prediction and trace id are `_recovery`,
  `_predicted_next` and `_trace_id`, and a meta-tool's provenance receipt moves to
  `result._meta.provenance`.
- **Library users.** The `mcp_gateway` Rust library is internal and unsupported as of 4.0, and
  several public types were renamed or removed. See the upgrade guide.

## About this beta

**It is a beta, not 4.0.0.** It is not feature complete (see [Known gaps](#known-gaps)),
and it is published only to channels you have to opt in to. Nothing that installs "the
latest version" picks it up: the npm `latest` dist-tag, the `:latest` container tag, the
Homebrew formula and the MCP Registry entry all stay on 3.x, and no `:4.0` tag is created.

Please report problems, and upgrade friction in particular, as
[GitHub issues](https://github.com/MikkoParkkola/mcp-gateway/issues). Include the version
(`mcp-gateway --version`) and the smallest config that shows the problem, with secrets removed.

## Install

Pin the exact version. None of these commands resolves to the beta unless you ask for it.

| Channel | Command |
|---|---|
| crates.io | `cargo install --locked mcp-gateway --version 4.0.0-beta.4` |
| npm | `npm install -g @mikkoparkkola/mcp-gateway@next` (or `@4.0.0-beta.4`) |
| Container | `docker pull ghcr.io/mikkoparkkola/mcp-gateway:4.0.0-beta.4` (`:4.0.0-beta.4-full` adds the Node.js, `uv` and `git` runtimes stdio backends use) |
| Binaries | download from the assets below and check them with `sha256sum -c SHA256SUMS.txt` |

Homebrew is not updated for pre-releases. The container images are signed with cosign and
carry an SBOM attestation, the same as a final release. Verify them by digest as described in
[`docs/release/v4.0.0-prerelease-channel.md`](v4.0.0-prerelease-channel.md), using
`refs/tags/v4.0.0-beta.4` as the certificate identity.

The beta passes the same security and quality gates as a final release: the dependency and
image vulnerability scans, secret-leak lint, formatting, lints and the full test suite. The
one gate a beta does not have to pass is the 4.0.0 acceptance gate, which requires every
release criterion to be met. The open ones are listed next.

## Known gaps

At this beta, 8 release criteria are still open: 4 in the release ledger, which holds 139
criteria (132 met, 3 accepted as shipping unmet), and 4 of the 7 added on 2026-11-06 for a
signed-in CLI. All of the beta.3 gaps not listed here have since been met or accepted.

**Validation**

- The real-backend workload benchmark against 3.5.x has not produced a passing run yet, so
  there is no end-to-end latency comparison with 3.x.
- The client run behind the list of clients 4.0.0 is verified against has not been recorded on a
  4.0.0 build yet.
- The coverage and mutation evidence has to be graded again on the final revision, and every
  shortfall closed with tests or waived in writing.

**MCP Events**

- The automated end-to-end test passes, but the live run with a third-party client (subscribe,
  verify, deliver, unsubscribe over a tunnel) has not been recorded yet.

**Signed-in CLI**

- `mcp-gateway api METHOD PATH` works today with `MCP_GATEWAY_TOKEN`. Still to come:
  `mcp-gateway login` (browser approval or a device code, approved by an admin, stored in the
  OS keychain), CLI credentials that expire and show on the Keys screen and in Activity,
  `mcp-gateway logout` revoking the credential on the gateway, and `mcp-gateway auth status`
  naming where the credential came from.

**Accepted for 4.0.0**

- Tool-discovery ranking is measured against frozen thresholds for selection quality only.
  Discovery turns, invalid tool calls and total tokens per completed task are not measured in
  4.0.0.
- 4.0.0 keeps every MCP protocol revision it accepts (2026-07-28, 2025-11-25, 2025-06-18,
  2025-03-26 and 2024-11-05) and drops none. How widely each older revision is still used is
  not measured in 4.0.0; that measurement, and any decision to retire a revision, moves to a
  later release. Two criteria cover it.

The live list is the release ledger, `docs/requirements/RELEASE-4.0.0-scope-status.json`;
`python3 scripts/release/check_scope_acceptance.py --release` prints what is still open.
