## The 16, grouped by the change that closes them

Grouping is by shared mechanism, not by ticket. Rows in one package share a design,
so splitting them across packages would design the same thing twice.

## Order, and why

A is the largest and two of its rows depend on the first: `PERF.3` soaks the
reclamation `MRTR.8b` introduces, and `OBS.4` counts the events its lifecycle
emits. A is therefore first and internally sequenced.

B, C, D and E touch disjoint code and can run concurrently with A and with each
other. F is measured against the finished tree, so it lands last — but the bench
harness and the 3.5.0 baseline are built early, because a harness written after
the change is a harness written to agree with it.

## Per-package process — full scope, not abbreviated

Each package runs the delivery process in `rules-source/workflows/development-process.md`
end to end: design reviewed before any code, test plan reviewed, failing tests
reviewed as tests, implementation, self-QA, final review (two code legs plus the
functional leg), documentation, housekeeping. The reviewer pair for this session's
authorship is gpt-review + kimi-review.

Each package closes by rewriting its rows in the criteria file with evidence, the
same way `GH475.RL.10` was closed: the row states what was done, what pins it, and
what is still not pinned.

## Honest limits, stated now

- Some of the 16 may prove N/A or already met once read at source. A row's status
  is a claim made when it was written; three RL rows already turned out to be MET
  under a narrower reading. Each package starts by re-verifying its rows against
  source before designing anything.
- `NFR.PERF.1` needs a 3.5.0 baseline that does not exist in this tree yet, and
  the benchmark must run off this machine. Until both exist the row cannot move
  past PARTIAL on evidence, only on assertion — which is what left it PARTIAL.
- The three Codex-owned rows are not tracked to closure here. Release readiness is
  the union of both sides; this plan covers one side of it.
