# v4.0.0 gap closure — plan to release-ready

Distance to release, re-measured from `docs/requirements/RELEASE-4.0.0-criteria-status.md`
on 2026-09-08 (second measurement, later the same day): **21 rows are not MET** — 5
`UNWIRED`, 9 `ABSENT`, 7 `PARTIAL`. The ledger has grown to 217 table rows as sub-clauses
were split out; the rest are MET or N/A with a reason.

The first measurement that day said 23, counted by `rg -c` over status tokens. That method
counts every occurrence of the word, including the ones in prose and evidence cells, and it
does not count a row whose status cell reads `ABSENT (clause: ...)` or sits in a fourth
column. It over-counted six and under-counted two. Rows are now counted by matching a table
line with a status cell, and the two rows the old method could not see — `NFR.SEC.3` and
`NFR.COMPAT.1`, both `ABSENT (clause: ...)` — are in the 21. A count taken by grepping for a
word is a count of the word.

The 2026-09-07 revision of this plan said 19. That count was taken before the ledger
gained `UNWIRED` as a distinct status, and a status-token count that predates a
vocabulary change undercounts silently rather than failing. Reconciliation of the two
numbers is in the table below; nothing was lost, three rows closed and seven were
regraded out of MET.

## Ruling backlog, cleared 2026-09-08

Five of the six lanes were idle and blocked on a decision only the team lead could make,
and the sixth was waiting on one. All six were answered on 2026-09-08 and the answers are
recorded in `docs/release/2026-09-08-team-lead-rulings.md`, not only in the lanes' mailboxes
— a ruling delivered to one agent does not reach the lane that inherits its consequence.

Two of the six were collisions between documents that each read as authoritative: `SUB.4`'s
config gate against an unreviewed design revision, and `CONTROL.4`'s blocking row against
MIK-7291's deletion narrowing. Both existed because a decision was recorded in one file and
its consequence in another. Each ruling therefore names the document to amend, not only the
answer, and the amendments are owned by the lanes.

With the lanes moving again, the remaining unowned work is packages A and F. A is fenced
behind the bridge lane, which holds the same continuation code; F needs a 3.5.0 baseline
that is not in this tree and a machine that is not this one. Neither is startable by
reaching into another lane's files, which is the constraint that keeps them unstaffed rather
than merely unstarted.

## Order, and why

G first, and within G the bridge rows first: they are the only rows where a mechanism
is finished and one wiring change converts it from invisible to done. The era-field
checkpoint is the current critical path and lands as one complete compiling change —
field, all 23 construction sites, and the `WIRE.*` acceptance test together.

A is next and internally sequenced: `PERF.3` soaks the reclamation `MRTR.8b` introduces.

B, D and E touch disjoint code and run concurrently with A. C and H are Codex lanes and
run on their own clock. F is measured against the finished tree so it lands last, but its
bench harness and the 3.5.0 baseline are built early — a harness written after the change
is a harness written to agree with it.

## Per-package process — full scope, not abbreviated

Each package runs `rules-source/workflows/development-process.md` end to end: design
reviewed before any code, test plan reviewed, failing tests reviewed as tests,
implementation, self-QA, final review (two code legs plus the functional leg),
documentation, housekeeping. The reviewer pair for this session's authorship is
gpt-review + kimi-review.

Each package closes by rewriting its rows in the criteria file with evidence: what was
done, what pins it, and what is still not pinned.

## Honest limits, stated now

- Some of the 23 may prove N/A or already MET once read at source — three rows did exactly
  that this week, in both directions. Each package re-verifies its rows against source
  before designing anything. A status is a claim made when it was written.
- `NFR.PERF.1` needs a 3.5.0 baseline that does not exist in this tree, and the benchmark
  must run off this machine. Until both exist the row moves only on assertion.
- Release readiness is the union of both sides. This plan now names the Codex-owned rows
  rather than excluding them, but it does not track them to closure.
- Nothing here is mechanically enforced. The counts came from reading the ledger, and the
  ledger is maintained by hand.
