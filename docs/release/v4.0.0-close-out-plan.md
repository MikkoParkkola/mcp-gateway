## Ordering, and the one reason it matters

Work completed before #550 merges may have to be regraded against the merged
tree. That cost is not uniform:

- **Streams 2 and 3 are merge-independent.** They add tests and production code
  that survive the merge unchanged. Start them now.
- **Stream 4 is not.** A latency or workload number measured against the
  pre-merge tree has to be retaken against the post-merge one. Measuring early
  is measuring twice.
- **Stream 5 is not.** A recorded live run is evidence about a specific build.
- **Stream 1 gates streams 4 and 5** and nothing else.

So the critical path is: merge, then measure, then record. Tests run alongside
all of it.

## Batching detail, stream 4

The three measurement rows are separate criteria but one job. `NFR.PERF.1` needs
end-to-end P50/P99 against a live wire and a real backend — the existing
in-process micro-benchmarks do not answer it, which is why the row is still
open despite having been "measured". `NFR.WORKLOAD.1`'s harness is already built
and has never been run once. `MIK-3274.RANKING.3` needs three more metric
families frozen against an existing corpus. One Spark session with the gateway
deployed serves all three; three sessions would pay the deployment cost thrice.

## Batching detail, stream 5

`MIK-6745.JOURNEY.1` wants a recorded Open WebUI → gateway → Google Workspace
route. `NFR.DEMO.1` wants five recorded scenarios, four of which need the same
running gateway with the same backends attached. Configure once, record six
artefacts, close two rows.

ruling, one needs a merge decision, two need configured live backends. The
