# Design: stdio dispatcher regression rows for keyed execution

Status: draft for review, 2026-09-13. No code written yet.

## Why this exists

An independent non-Claude review of commit `2807d72b` asked for dispatcher-level
coverage that the test landed there does not provide. That test,
`stdio_principal_admits_a_keyed_mutation_and_anonymous_http_still_cannot`, pins the
**admission gate** in isolation: it calls `admit` directly and asserts the stdio
principal is accepted while an anonymous HTTP caller is refused with `-32003`. Its
own doc comment states that limit. The reviewer's point stands: nothing exercises
the **dispatcher** that consumes the gate's verdict, so the wiring between them is
unpinned.

## The construct under test

`src/gateway/server/mod.rs:2981-2994` matches on `admit_meta_sync` and turns four
admission outcomes into four different dispatch behaviours:

| Admission outcome | Dispatcher behaviour |
|---|---|
| `Unprotected` | `execution = None`, call proceeds |
| `Owned(lease)` | `execution = Some(lease)`, call proceeds holding the lease |
| `Replay(response)` | `break 'tool_call response` — the backend is never reached |
| `Err(error)` | `break 'tool_call` with `error.to_rpc_code()` |

Every one of those four arms is a separate branch, and each is currently asserted
only through the gate that produces it, never through the dispatcher that acts on
it. The two arms that matter most are `Replay` and `Err`, because both are early
breaks: a regression that turned either into a fallthrough would still return a
well-formed answer to the caller while silently re-running a mutation.

## Rows proposed

1. **A keyed call reaches the backend exactly once.** Dispatch a keyed mutation and
   assert a backend invocation counter reads 1. This is the control: without it,
   row 2 can pass vacuously against a backend that was never called at all.
2. **A replayed key returns the stored answer and does not reach the backend
   again.** Dispatch the same key twice; assert the second answer is byte-identical
   to the first *and* the counter still reads 1. Both halves are required — equality
   alone is satisfied by a dispatcher that re-runs an idempotent backend.
3. **A conflicting key is refused at the dispatcher, not just at the gate.** Same key,
   different arguments; assert the wire error code, and assert the counter did not
   advance, so the refusal happens before dispatch rather than after.
4. **An anonymous HTTP caller is still refused `-32003` through this path.** The
   existing test asserts this against `admit`; this row asserts the dispatcher
   surfaces it as a JSON-RPC error rather than proceeding.

## Falsification plan

Each row is inverted before it is believed, mutating the **test** file only —
never production source, because peers run `cargo test` against this shared
worktree. The mutation for each row is the specific defect it claims to catch:

- Row 1: assert the counter reads 0 — must fail, or the counter is not wired.
- Row 2: delete the counter assertion — the row must still fail when the `Replay`
  arm is changed to a fallthrough; if it passes, the row was riding on equality.
- Row 3: feed identical arguments instead of conflicting ones — must fail.
- Row 4: feed the refusal half a non-empty principal — must fail, the same
  falsifier already proven for the admission-gate test.

## Explicitly out of scope

Transport wiring, session establishment, and the HTTP principal path at
`src/gateway/router/handlers.rs:1572`. End-to-end stdio proof already exists at
`tests/mik_7272_sub2b_acs.rs`; this work pins the dispatcher's four-arm match and
nothing wider.

## Question for reviewers

Is a backend invocation counter the right instrument, or does the existing fixture
already expose a call record that would make the counter a second source of truth
that can drift from the first?
