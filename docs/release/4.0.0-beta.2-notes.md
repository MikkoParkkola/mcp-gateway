# mcp-gateway 4.0.0-beta.2

This is the second public pre-release of mcp-gateway 4.0. It is here so that people running
3.x can try 4.0 against their own configurations and clients before the final release, and
tell us what breaks.

## Highlights of 4.0

- **MCP 2026-07-28, on by default.** The gateway serves the newest Model Context Protocol
  revision next to 2025-11-25 and earlier, on one endpoint. A 2026 client sends stateless
  `POST /mcp` requests with no `initialize` handshake and gets `server/discover`, mid-call input
  requests it answers by retrying (on HTTP, for a caller with a verified identity), a
  caller-scoped `subscriptions/listen`, the tasks extension and optional idempotency keys.
  While it is on, more than one replica is refused. On stdio,
  `server/discover` lists only the older revisions. `server.modern_protocol: false` turns it off.
- **Per-caller scoping.** A caller sees and invokes only the backends and tools it was granted,
  on every discovery surface. A new backend is reachable by no key until granted. Cached and
  idempotent results, backend notifications and `subscriptions/listen` are kept per caller.
- **SSO admins.** A `control_plane.role_mapping` rule with `role: admin` makes an identity
  provider group or user a full gateway admin, read per request. Key-server OIDC rules need an
  issuer and match only verified emails.
- **Audit with auth.** With auth on, every tool call on `POST /mcp` is logged with who made it,
  the outcome and the credential kind, and a failed write fails the call. In this beta the
  direct per-backend route `POST /mcp/{name}` does not yet write that record.
- **Secrets and keys.** API keys are stored as SHA-256 digests with an optional expiry that is enforced, an
  unresolved secret reference fails the load, and `/metrics` needs its own token.
- **Refuse rather than run unsafely.** Unknown config keys, config files other users can read
  and cleartext HTTP on a network bind with auth on stop the start.
- **A Helm chart that starts** with its default values.

What is still missing for 4.0.0 is under [Known gaps](#known-gaps).

## About this beta

**This is the first beta with container images.** `4.0.0-beta.1` reached GitHub, crates.io and
npm, but its image was never published: the release's container smoke test failed, and the
fix landed after the tag (#1018). `ghcr.io/mikkoparkkola/mcp-gateway:4.0.0-beta.2` is the first
4.0 image. Since beta.1, the tool-call audit log is required with auth on, API keys are
configured as SHA-256 digests, and a `control_plane.role_mapping` rule with `role: admin` now
grants its SSO identity full gateway admin on every admin surface, not only the control plane
(a domain-only admin rule now fails to load); all three are breaking and listed below. `/health`
now answers 503 `degraded` while a backend's circuit breaker is open, matching what the admin
panel already showed (breaking for `/health` monitors, also listed below). A modern-era stdio
caller that asks for input mid-call is now handed a continuation instead of `-32003`. Daily cost
budgets also survive a restart now instead of resetting to zero, and attestation `enforce`,
which beta.1 refused at startup, now enforces (it needs `GATEWAY_ATTESTATION_SIGNING_KEY`).
`webhooks.rate_limit` is now enforced too: each webhook endpoint answers `429` above its
per-minute budget (default 100, `0` for no limit), and most senders do not retry a `429`, so
set it above your busiest sender's peak.

**It is a beta, not 4.0.0.** It is not feature complete (see [Known gaps](#known-gaps)),
and it is published only to channels you have to opt in to. Nothing that installs "the
latest version" picks it up: the npm `latest` dist-tag, the `:latest` container tag, the
Homebrew formula and the MCP Registry entry all stay on 3.x, and no `:4.0` tag is created.

Please report problems, and upgrade friction in particular, as
[GitHub issues](https://github.com/MikkoParkkola/mcp-gateway/issues) with the version
(`mcp-gateway --version`) and the smallest config that shows the problem. Remove secrets
before you paste it.

## Before you upgrade

4.0 changes behaviour that 3.x deployments rely on, and several changes make the gateway
refuse to start rather than carry on with a config it no longer trusts. The full list, with
the action each one needs, is [`docs/UPGRADING-4.0.md`](../UPGRADING-4.0.md). Read it
before pointing the beta at a real deployment. No migration edits your `gateway.yaml`; on the
first start after the upgrade the gateway prints a one-time notice of the changes that need
your attention.

The changes most likely to affect an existing install:

- **An unknown config key fails the load.** A misspelt or retired key is an error that names
  the key, not a silently ignored line.
- **A config or env file that other users can read fails the load** (Unix). `chmod 600` it;
  on Kubernetes keep the chart's `fsGroup` and `defaultMode`.
- **Plain HTTP on a network bind is refused while auth is on**, unless you declare how the
  traffic is protected (`server.cleartext_http`: TLS terminated upstream, host-local publish,
  or cluster-internal).
- **A secret reference that resolves to nothing fails the load** instead of starting with an
  empty credential.
- **With auth on, the tool-call audit log is required.** Set
  `security.transparency_log.enabled: true`; a config without it fails the load, a log that
  cannot open stops startup, and a failed audit write fails the call. New in beta.2.
- **API keys are configured as SHA-256 digests.** A plaintext `auth.api_keys[].key` fails the
  load; put the output of `mcp-gateway hash-key` in `key_sha256`. Clients keep their keys. An
  optional `expires_at` is enforced. New in beta.2.
- **A `role_mapping` rule with `role: admin` grants full gateway admin.** The matching SSO
  identity gets admin on every admin surface (admin meta-tools, `/ui/api/*`), not only the
  control plane, and the mapping is read per request so a reload revokes it at once. A
  `role: admin` rule whose only condition is `domain` now fails to load; header identities never
  confer admin. Review existing `role: admin` rules. New in beta.2.
- **`/health` answers 503 `degraded` while a backend's circuit breaker is open.** Expect it on
  `/health` monitors; the admin panel shows the backend `Down` and `Blocked`. `/livez` and
  `/readyz` are unaffected. New in beta.2.
- **`/metrics` needs its own scrape token.** Set `server.metrics_token` and give it to
  Prometheus through a dedicated scrape job.
- **The inbound WebSocket listener is gone**, and `server.ws_port` fails the load. Connect
  clients over HTTP (`POST /mcp`) or stdio.
- **More than one replica is refused while per-process state is on.** Keep one replica, or
  turn off the modern protocol, the key server and hosted accounts.
- **`server.max_body_size` is enforced on every route, and `server.request_timeout` fails the
  load.** Nothing read the timeout; remove it.
- **API keys need unique, non-empty names, and a key with no `backends` reaches no backend.**
  Add `backends: ["*"]` for the 3.x behaviour.
- **OAuth credentials are stored per issuer**, so each OAuth backend needs to be authorised
  once more.

The same guide covers rolling back to 3.x.

## Install

Pin the exact version. None of these commands resolves to the beta unless you ask for it.

| Channel | Command |
|---|---|
| crates.io | `cargo install mcp-gateway --version 4.0.0-beta.2` |
| npm | `npm install -g @mikkoparkkola/mcp-gateway@next` (or `@4.0.0-beta.2`) |
| Container | `docker pull ghcr.io/mikkoparkkola/mcp-gateway:4.0.0-beta.2` (`:4.0.0-beta.2-full` adds the Node.js, `uv` and `git` runtimes stdio backends use) |
| Helm | the chart in this tag (`deploy/helm/mcp-gateway`) defaults to image `4.0.0-beta.2` |
| Binaries | download from the assets below and check them with `sha256sum -c SHA256SUMS.txt` |

Homebrew is not updated for pre-releases. The container images are signed with cosign and
carry an SBOM attestation, the same as a final release; verify by digest as described in
[`docs/release/v4.0.0-prerelease-channel.md`](v4.0.0-prerelease-channel.md), using
`refs/tags/v4.0.0-beta.2` as the certificate identity.

The beta passes the same security and quality gates as a final release: the dependency and
image vulnerability scans, secret-leak lint, formatting, lints and the full test suite. The
one gate a beta does not have to pass is the 4.0.0 acceptance gate, which requires every
release criterion to be met; the open ones are listed next.

## Known gaps

4.0.0 is tracked against 73 release criteria. At this beta 56 are met, one is accepted as
shipping unmet, and the 16 still open are below in plain terms, grouped by area. Any of them
may change behaviour between this beta and 4.0.0.

**Audit logging**

- Calls through the direct per-backend route do not yet write the same audit record as calls
  through the meta route.
- Grant decisions, refusals included, are not all audited.
- Security-relevant events are not yet all exported as metrics (without identities in labels).

**Authentication and sessions**

- Admins cannot yet be designated through an SSO identity with a verified email.
- Dashboard sessions are not yet held to a 30-minute idle limit or an 8-hour absolute limit,
  so one can stay open longer than 4.0.0 will allow.
- Attestation `enforce` (off by default) now refuses unattested tool calls, but on the direct
  per-backend route it checks only `tools/call`, and multi-step plans are refused under it
  rather than attested.

**Secrets and configuration**

- Secrets cannot yet be referenced from files (a `file:` reference with the same
  fail-closed rules as other references).

**Backends and reliability**

- A stdio backend call that never answers is not yet bounded.
- Per-user backend connection slots are not yet capped.
- Retried input responses are not yet validated against gateway-issued request state before
  being forwarded.
- A personal account whose upstream token is rejected is not yet limited to one forced
  refresh before prompting the user to reconnect.

**Kubernetes**

- The Helm chart cannot yet configure API-key or OIDC auth.

**Documentation**

- The team deployment guide, the backup, restore and key-rotation runbook, a reconciled
  upgrade guide and the supported-client matrix are not finished.
- The published OWASP Agentic AI self-assessment has not been reconciled with the controls
  this build ships.

**Validation**

- The real-backend workload benchmark against 3.5.x has not produced a valid run yet, so
  there is no end-to-end latency comparison with 3.x.
- The list of client and backend versions 4.0 is verified against is not complete.

**Accepted for 4.0.0**

- Tool-discovery ranking quality is not measured against frozen thresholds; this is accepted
  for 4.0.0 and will not block the final release.

The live list is the release ledger, `docs/requirements/RELEASE-4.0.0-scope-status.json`;
`python3 scripts/release/check_scope_acceptance.py --release` prints what is still open.
