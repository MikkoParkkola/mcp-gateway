## The gap the ledgers do not show

A criterion graded MET is graded against evidence, and evidence is a commit.
Of the 81 revisions cited across the core ledger, 79 resolve to commits here.

graded against a tree that is not the default branch. Tagging 4.0.0 off `main`
today would ship a build for which almost no criterion's evidence holds. The
release is not two criteria away from shipping; it is one integration away.

## Order of work

1. **Integration first.** Land the four branch clusters above, then the v4 line
   into `main`. Until the release tip carries the cited evidence, every grade
   below it is provisional and any criterion closed now may have to be regraded
   against the merged tree. This is the single highest-leverage item and it
   subsumes goal rows [31], [36] and [39].
2. **Bucket A in parallel with the merges**, since the missing tests are
   independent of each other. `MIK-6744.STORE.2` and `NFR.CONFORMANCE.1` are
   small and can go first to move the number.
3. **Bucket B on Spark** once the tip is stable, because a latency or workload
   measurement taken against a pre-integration tree has to be retaken.
4. **Bucket D** falls out of step 1 automatically.
5. **Bucket C** as a dedicated live session with backends configured.
6. **Bucket E** as two operator handoffs, stated above with the exact action.

## Regrade after integration

Steps 1 through 4 change the tree the ledgers were graded against. When `main`
carries the v4 line, re-run both scripts and re-run the ancestry sweep. A row
whose evidence commit is still absent from the tip is not MET on the release
line, whatever its status string says.
