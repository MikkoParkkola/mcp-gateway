## MRTR residual — verified at source, and the justification does not hold

The MRTR author reported that `apply_context_integrity` replaces the whole
envelope when `enforcement_applied` is true, dropping `requestState`, and judged
MRTR.2 still satisfied **because the affected path is a withhold path**, where
dropping the field is not observable to the caller.

Two corrections, both verified by reading the function.

**The anchor was wrong.** The function is at
`src/gateway/meta_mcp/invoke.rs:1686`, not `src/gateway/invoke.rs:1434`. The
reported path does not exist. Line anchors reported from an agent worktree are
unreliable; re-locate by symbol before citing one.

**The withhold justification covers only one of three branches.** The kernel
side has now been read, and it changes which branch carries the defect.
`context_integrity_delivered_result` (`src/gateway/meta_mcp/invoke.rs:1550`) has
three exits, not two:

| branch | condition | what the caller receives |
|---|---|---|
| withhold | `delivered` is `None` | an `isError` envelope — the author's justification applies here |
| object passthrough | `delivered.is_object()` | `delivered` returned wholesale |
| **scalar wrap** (`:1568-1576`) | `delivered` is a string or scalar | **a fresh success envelope built from the text alone** |

`Kernel::transform_content` (`src/context_integrity/kernel.rs:494-533`) returns
`Some(Value::Object(..))` only on `Allow`; `Strip` and `Summarize` return
`Some(Value::String(..))`, and `Quarantine`/`Confirm`/`Deny` return `None`.
Enforcement is `policy.effective_mode() == Enforce && decision != Allow`
(`kernel.rs:460`), so `Allow` implies not-enforced and the object-passthrough
branch is unreachable under enforcement. The earlier objection named the wrong
branch.

The defect survives the correction. `Strip` and `Summarize` are enforcement
decisions, they yield a `Value::String`, and the scalar-wrap branch then builds
a brand-new success envelope from that text — discarding the original result
including `requestState`. The caller sees success on an enforced path with the
envelope silently replaced.

**MRTR.2 is open**, on the scalar-wrap exit rather than the object exit.

## Build capacity — a constraint that has eased, and one correction

Root filesystem was the limiter for most of 2026-08-31: 460.4G total, oscillating
between 4.7G and 8.0G free as builds ran. The MIK-4777 guard fails cargo closed
below 5G, and it surfaces as a compile error rather than a disk error, so a drop
below that line stops every agent at once and looks like a code problem.

Measured 2026-08-31 (later): 24.4G free. The constraint is no longer binding.

**Correction — out-of-repo `CARGO_TARGET_DIR` is the cheaper option, not the
expensive one.** This document previously said pointing an agent at an external
target directory discards its warm cache and forces a full cold rebuild of the
workspace. That is wrong, and two agents refuted it with measurements: an
external target directory cost **2.1G**, because cargo builds only what the
branch's test binary needs, not the whole workspace. An in-repo `target/` is the
larger cost *and* is what the Stop hook's H8 sweep deletes mid-run. External
target directories are therefore both cheaper and sweep-immune. Standing rule:
use them.

Reclaiming space: `cargo clean` in an idle worktree. The `rm -rf` guard blocks
direct deletion; the build tool does not. Build artifacts are cache, not state
(DoD H8), so eviction needs no approval. Never evict a live agent's `target/`.
Evicted 2026-08-31 for 3.3G: `gap-header59`, `gap-task-sub4`,
`agent-a21abc33589db8221` (meta-tool-exposure, stopped, tree clean).

The disk guard's own message is stale on two points: it cites a recovery freeze
lifted 2026-08-15, and it implies build caches are protected state. The 5G
threshold is real; that framing is not.

## Release blocker — `exposed_meta_tools` was documented, unenforced — CLOSED

The clippy `dead_code` warnings on `src/gateway/meta_mcp_tool_defs.rs` are not a
lint problem. They are the visible end of a half-built access control.

`MetaMcpConfig::exposed_meta_tools` exists and ships (`src/config/mod.rs:1274`).
Its doc comment makes a specific promise:

> A non-empty list is an allow-list: only the named tools are listed, and a tool
> that is not listed is not callable either. Failing closed is deliberate.

The predicate implementing that promise — `MetaToolExposure` and
`build_meta_tools_filtered`, `src/gateway/meta_mcp_tool_defs.rs:731-816` — is
written, is tested, and **has no caller outside tests**. Verified by search:
every non-test reference is the config field itself and
`src/gateway/meta_mcp_tool_defs_tests.rs`.

So an operator who sets `exposed_meta_tools: ["gateway_invoke"]` gets a gateway
that still lists and still executes every meta-tool. The field reads as a
restriction and enforces nothing. In a release whose security posture is a
shipped differentiator, that is worse than an absent feature: an absent feature
does not tell the operator they are protected.

### Disposition — wire it, do not delete it

Deleting the predicate would leave the config field promising the same thing
with no implementation at all; deleting the field too is a breaking change to a
published config schema. The predicate is complete and tested. The gap is the
call site.

This is a design decision the change did not make, named here per the
development process: the release wires an operator-facing control rather than
removing one, and the behaviour change is that a non-empty `exposed_meta_tools`
starts being honoured — which is what its documentation already claims.

Required to close: the predicate consumed on both the `tools/list` and
`tools/call` paths in `src/gateway/meta_mcp/mod.rs`, with a test proving an
unexposed meta-tool is rejected on **call**, not merely hidden from the list.
Hiding without blocking is the failure mode the predicate's own comment names.

### Closed — evidence

`MetaToolExposure` is now consumed on both paths
(`src/gateway/meta_mcp/mod.rs`: `build_meta_tools_filtered` on `tools/list`,
an exposure check on `tools/call`), wired from the config field in
`src/gateway/server/mod.rs`. The refusal is worded exactly like the
unrecognised-tool fallback, so hiding a tool cannot confirm it exists.

Four tests, `cargo test --lib meta_tool` → 29 passed, 0 failed:

| test | what it pins |
|---|---|
| `unexposed_meta_tool_is_refused_on_call` | refusal on **call**, code `-32601` |
| `exposed_meta_tool_still_runs` | the refusal is not blanket |
| `unexposed_meta_tool_is_not_listed` | the list path still filters |
| `no_allow_list_exposes_everything` | an unconfigured gateway is unchanged |

Falsifier probe run per §P2 (the tests were written before the call-path
gate): with the gate removed, exactly one test failed —
`unexposed_meta_tool_is_refused_on_call`, on its own assertion message, not
on a compile or import error. Source restored and re-run green (29 passed),
which is the restore check, not `git status`.

Residual, stated not fixed: the exposure check sits after the admin gate, so
an unexposed **admin** meta-tool called by a non-admin still answers `-32600
requires admin access` and discloses existence through that door. Reordering
is a separate change with its own review.

### Review finding — the allow-list had an escape hatch

Codex/GPT (`gpt-20260831T212406Z-97201.md`, exit 0, `SHIP-WITH-FIXES`) found
that `gateway_execute` was exempt from the allow-list, verified at source:

`governed_meta_tool_names()` was derived from `build_meta_tools()` alone, while
Code Mode's `gateway_search` and `gateway_execute` come from a second builder,
`build_code_mode_tools()`. `is_exposed` returns `true` for any name outside the
governed set, so an operator who set `exposed_meta_tools: ["gateway_invoke"]`
kept a callable `gateway_execute` — and `gateway_execute` reaches every backend
tool. The predicate's own doc comment asserted Code Mode's two tools "are not
meta-tools"; the dispatcher disagrees, and so does the config field's promise.

Repaired at the derivation rather than at the call site, so a builder added
later cannot escape the same way:

| change | effect |
|---|---|
| `governed_meta_tool_names()` chains `build_code_mode_tools()` | both builders are governed |
| `MetaToolExposure::filter` — one filter, every list path | `tools/list` cannot diverge from `tools/call` |
| both Code Mode list paths filtered, including the URL override | a URL parameter cannot widen what the operator exposed |
| `unexposed_code_mode_tool_is_refused_on_call` | the refusal is on the **call** path, code `-32601` |
| `every_builder_contributes_to_the_governed_set` | a future builder left ungoverned fails this test |

### Second leg, and what died at source

Claude Opus 5 (`rv-claude.log`, exit 0, `SHIP-WITH-FIXES`) reached the same
finding independently — two vendors, one defect, which per the standing lesson
means the fix belongs at the layer that produced it rather than at each sighting.
It also proposed a *different* repair: exempt the Code Mode pair whenever code
mode is on. That was not taken. Exempting them restores the escape hatch for
exactly the deployments that have `gateway_execute` wired, which is the
population the allow-list exists to protect. Governing both builders and
filtering every list path keeps `tools/list` and `tools/call` in agreement
without an exemption.

Two of its supporting claims do not survive inspection, recorded because an
adopted claim is load-bearing and a dead one closes without a round:

| claim | at source |
|---|---|
| a `META_TOOLS` const at `meta_mcp/mod.rs:1400` drifts from the builder | the anchor is wrong — no such const, the dispatcher is a `match` — but the class is real; recorded as residual below |
| the startup warning says an allow-list omitting `gateway_invoke` makes backends unreachable | no such string in `src/`; searched, absent |

Residual, from the half of that first claim which survived: the governed set is
derived from the builders (`governed_meta_tool_names`), while dispatch is a
`match` expression, and nothing asserts the two agree. That is the mechanism
that produced this finding in the first place — `gateway_execute` had a dispatch
arm and a builder the governed set never consulted, so it was ungovernable and
failed open. `every_builder_contributes_to_the_governed_set` covers the
builder-to-governed direction only. The direction that bites is dispatch-arm to
governed, and a `match` cannot be enumerated at runtime, so nothing covers it
short of parsing source. The durable fix is routing dispatch through the same
table the builders feed; that is a separate change.

Recorded as an observation, needing no test: a backend tool surfaced under
`surfaced_tools` is unaffected by a non-empty `exposed_meta_tools`. Surfaced
names are not in the governed set, and `is_exposed` is only consulted for names
that are — so the allow-list neither hides nor exposes them. Naming it because
this change *grew* the governed set, and a disposal recorded is a disposal that
cannot quietly become a default.

Confirmed and fixed in this change:

- **The discovery preamble named four meta-tools unconditionally.**
  `build_discovery_preamble` (`src/gateway/meta_mcp_helpers.rs:197`) hardcoded
  `gateway_search_tools`, `gateway_invoke`, `gateway_list_tools` and
  `gateway_list_servers`, and its output is the `instructions` field of the
  `initialize` response — so it reached every client before any `tools/list`.
  The change spends a comment on refusals not confirming a hidden tool exists,
  while `initialize` announced four of them. It now takes the exposure
  predicate and emits only the exposed lines.
- **The refusal wording had no test.** `the_refusal_does_not_name_the_allow_list`
  asserts the message equals `Unknown tool: gateway_list_tools` exactly. The
  code-only assertion it replaces would have passed for a reworded message that
  discloses the tool was withheld.
- **The config doc now states the list takes effect on restart**, not on
  `gateway_reload_config` — the predicate is captured once in `build_meta_mcp`,
  as `surfaced_tools` already is.

Disposed, not fixed: the destructive-confirmation elicitation in
`src/gateway/router/handlers.rs:1099-1186` runs before the exposure gate, so an
unexposed destructive meta-tool prompts the operator and only then returns
`-32601`. Same class as the admin-gate ordering residual above and the same
disposal — reordering the router's pre-dispatch blocks is a separate change with
its own review. Both are ordering defects in the same pipeline; fixing one
without the other would leave the disclosure open anyway.

### The ordering finding — a residual, not a hole

The exposure gate lives in `handle_tools_call`, the single chokepoint every
`tools/call` reaches, so an unexposed tool is never executed by either path.
What the HTTP router does first is authorise the caller and run the firewall
scan, and those leave audit records for a call that is then refused with the
same wording an unrecognised name gets. That is the same door already recorded
for the admin gate: the refusal is correct, its side effects arrive before it.

Moving the gate ahead of authorisation would require the router to carry the
governed set, which is the typed-registry change the same reviewer files as a
design improvement. Recorded here as residual, not fixed in this change.
