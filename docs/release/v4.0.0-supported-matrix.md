# v4.0.0 supported matrix

Covers the first half of NFR.BUILD.1 (`docs/requirements/RELEASE-4.0.0-scope-update.md:59`):
the concrete clients, backends, feature/build combinations and license availability
that 4.0.0 claims to support. The second half — critical-path coverage and mutation
evidence on the final integration revision — is graded separately in
`docs/release/v4.0.0-burndown-tracker.md`. The coverage half now has a fixed
mapping, command and baseline in `docs/release/v4.0.0-critical-path-coverage.md`;
that document does not close the conjunct, because the final integration
revision it must grade does not exist yet.

A row here is a support claim. Removing a row is a scope reduction; adding one
requires the corresponding build or test to exist.

## Protocol revisions

Two paths, not one. The modern stateless path serves `2026-07-28`
(`MODERN_VERSIONS`, `src/protocol/meta.rs:248`) and is on by default
(`modern_protocol: true`, `src/config/mod.rs:1368`); it is the disable switch
for that surface. The legacy path serves `2025-11-25` by default
(`src/lib.rs:106`) and negotiates downward. A client that sends no
`protocolVersion` is treated as `2024-11-05`.

| Revision | Path | Status |
|---|---|---|
| 2026-07-28 | modern | Served when `modern_protocol` is on; removes the methods listed at `src/protocol/meta.rs:250` |
| 2025-11-25 | legacy | Served by default; tasks, elicitation, audio, tool annotations |
| 2025-06-18 | legacy | Negotiated |
| 2025-03-26 | legacy | Negotiated |
| 2024-11-05 | legacy | Negotiated; the default for an unversioned initialize |

`src/protocol_revision_telemetry.rs:41` additionally admits `2024-10-07` as a
bounded metric label. A label is an observation, not a support claim: a revision
counted there but absent from both tables above is counted, not served.

`2026-07-28` is the newest revision the specification has published
(`https://modelcontextprotocol.io/specification/versioning`, checked
2026-09-13), and it is the one the modern path serves by default. There is no
newer revision this release is behind.

## Reference clients

Each row is a config-export target with a concrete on-disk location
(`src/commands/config_export/mod.rs:388`). Export is behind the `config-export`
feature, which is on by default.

No client version is pinned, and that is a claim in itself: what this gateway
supports is a client's **config contract** — the settings key and file location
below — not a client build. A client that keeps the key and the location is
supported at any version; one that renames either breaks regardless of how
recent it is. Pinning a version here would assert coverage no test produces.

| Client | Config key | Location |
|---|---|---|
| Claude Code | `mcpServers` | `~/.claude.json` |
| Claude Desktop | `mcpServers` | platform-specific (`src/commands/paths.rs:19`) |
| Cursor | `mcpServers` | `.cursor/mcp.json` (workspace-relative) |
| VS Code Copilot | `servers` | `.vscode/mcp.json` (workspace-relative) |
| Windsurf (Devin Desktop) | `mcpServers` | `~/.codeium/windsurf/mcp_config.json` |
| Cline | `mcpServers` | `.cline/mcp_servers.json` (workspace-relative) |
| Zed | `context_servers` | platform-specific (`src/commands/paths.rs:29`): `~/Library/Application Support/Zed/settings.json` on macOS, `~/.config/zed/settings.json` elsewhere |

Windsurf was renamed **Devin Desktop** by Cognition in an over-the-air update on
2026-06-02 (`https://docs.devin.ai/desktop/devin-desktop-faq`). The rename does
not move the contract this row claims: the settings file is still
`mcp_config.json`, the legacy `windsurf` binaries still ship from
`~/.codeium/windsurf/bin/`, and the current changelog still names
`mcp_config.json` by that path. The row keeps both names because what export
writes is the on-disk location, not the product name.

Clients absent from this table are not claimed. JetBrains, Codex CLI, Gemini
CLI, Goose, Continue and Warp all speak MCP and none of them has an export
target in `src/commands/config_export/mod.rs`. Adding one is a feature, not a
documentation fix.

## Backends

The one backend with a pinned version is the one an automated test drives:
`tests/fixtures/task_upstream_sdk/server.py` runs `fastmcp` 4.0.3 +
`fastmcp-tasks` 4.0.3 + `pydocket` 0.25.0, exercised by the `task-sdk-recovery`
workflow. The rest are protocol-conformance claims, not build claims.

| Kind | Transport | Notes |
|---|---|---|
| MCP server | stdio | `src/transport/` |
| MCP server | streamable HTTP | `src/transport/` |
| Capability backend | REST over HTTP | `capabilities/<category>/*.yaml`; SHA-256 pinning rule-governed, see below |
| Composite provider | mixed | `src/provider/` |
| A2A peer | HTTP | `src/a2a/`, `a2a` feature (default on) |
| Upstream task SDK | HTTP | `fastmcp` 4.0.3 fixture, `.github/workflows/task-sdk-recovery.yml` |

SHA-256 pinning is **rule-governed, not universal**: 93 of
the 125 files under `capabilities/` carry a top-level `sha256`, and which 93
is decided by a written rule rather than per-file discretion. That count was
6 when this row was first graded on 2026-09-13; `df7162a7` pinned the
high-privilege catalogue on 2026-09-14. Calling the remainder "opt-in", as
this paragraph did until 2026-09-17, understated it: the rule in
`docs/capability-pin-policy.md` requires a pin on every high-privilege
production capability — one that reaches a credential, an outbound write or a
local process — and declines it for the 6 copy-and-edit templates under
`capabilities/examples/` (a pin there fails closed on the reader's first edit)
and for unauthenticated read-only public `GET`s, where a poisoned file can
return wrong data but has no secret to exfiltrate and no process to spawn.

The rule is machine-checked, not just written down.
`tests/capability_pin_policy.rs` asserts both halves — that no high-privilege
production capability is unpinned, and that every pin still reproduces — and
runs in the `test` job of `.github/workflows/ci.yml`
(`cargo test --all-features`, line 252), whose display name `Tests` is a
required status check on `main`. `scripts/ci/check-capability-pin-counts.sh`
re-checks the drift half without a Rust build and recomputes four published
figures — the pinned count and the file total in this paragraph,
`capability_count` in `benchmarks/public_claims.json`, and the built-in count
in `capabilities/README.md` — failing if any of them stops matching the
catalogue. It does not recompute the rest of this section; those numbers carry
a date and a command instead. It runs as `Capability pin counts and drift`,
which is **not** a required status check, so it reports drift on a pull request
without blocking a merge until a release owner adds it.

Measured on 2026-09-17 at `a68c027d`:

```sh
fd -e yaml -e yml . capabilities | wc -l                              # 125
rg -l '^sha256:' capabilities --glob '*.yaml' --glob '*.yml' | wc -l  # 93
bash scripts/ci/check-capability-pin-counts.sh                        # all 93 reproduce
```

Where a pin is present it fails closed on mismatch; where it is absent there is
nothing to fail on. The hash covers the definition file, not the remote backend
it describes — and there is usually no remote version to cover: 53 of the 125
files address a versioned API path
(`rg -l '^\s*(base_url|url|path|endpoint):.*(/v[0-9]+|v[0-9]+\.)' capabilities --glob '*.yaml' | wc -l`,
measured 2026-09-17), and a REST endpoint behind such a path can change
behaviour without changing the path. A pinned backend *version* is therefore
available for the one backend that ships one — the `fastmcp` task-SDK fixture
above — and unavailable for the REST catalogue. That is a property of those
backends, not a gap in this matrix.

## License availability

Package metadata is `license = "PolyForm-Noncommercial-1.0.0"` (`Cargo.toml:8`) —
one SPDX expression for the whole repository, not a per-file split and not a
per-feature one. Every licensor-owned source file carries a copyright line plus
that identifier as its first two lines; absence is a CI failure, not a default,
and a file carrying any other identifier is an error rather than a carve-out
(`scripts/ci/check-license-headers.sh:7,16-17`, run by the `public-repo-hygiene`
job). Third-party and generated files are out of scope and are listed in
`.license-scope-exclude`.

| Tier | Extent | Boundary |
|---|---|---|
| PolyForm Noncommercial | every licensor-owned source file | the whole repository |

**The MIT core is retired in 4.0.0.** Releases from v3.3.0 shipped a small set of
core files under MIT headers, enumerated by a `.mit-core-allowlist` file; v4.0.0
removes both. `.mit-core-allowlist` does not exist in this tree, and
[ADR-013](../adr/ADR-013-single-noncommercial-license.md) and
[`LICENSES.md`](../../LICENSES.md) record the retirement. Any document still
describing a 51-file MIT core is describing 3.x.

**No feature combination produces a PolyForm-free build**, and under a single
license none could. Of the EE paths in `LICENSE-EE.md:27`, only
`src/security/firewall/` is behind a Cargo feature (`firewall`).
`agent_identity`, `data_flow`, `message_signing`, `policy`, `response_inspect`,
`response_scanner`, `scope_collision`, `tool_integrity`, `transparency_log`,
`src/cost_accounting/` and `src/key_server/` compile unconditionally, including
under `--no-default-features` (`src/security/mod.rs:17`, `src/lib.rs:45`).
Commercial use of any build of this binary requires a commercial license
([`COMMERCIAL.md`](../../COMMERCIAL.md)).

`LICENSE-EE.md:38` lists `src/transparency_log/`; the module lives at
`src/security/transparency_log.rs`. The path is stale, the coverage is not.
