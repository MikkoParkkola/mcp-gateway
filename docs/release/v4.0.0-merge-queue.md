# v4.0.0 merge queue

A second burndown, beside the criteria one in
`docs/release/v4.0.0-burndown-tracker.md`. That board counts criteria graded
MET **anywhere**. This one counts the work those grades rest on that the
release line does not carry yet. Both have to reach zero before 4.0.0 ships,
and closing the first does nothing for the second.

The release line is `chore/v4-reconcile-main`. It superseded
`fix/v4-integration-ci-green` — which this document named until 2026-09-15 — by
strictly containing it: 184 commits ahead, 0 behind. `main` is 2246 behind it.

## The number

**19 of the 74 commits cited as evidence in
`docs/requirements/RELEASE-4.0.0-criteria-status.md` are on neither the release
line nor `main`.** Re-derived 2026-09-15 against `chore/v4-reconcile-main`, and
the finding is that it did not move: the 184 commits that took the line past
`fix/v4-integration-ci-green` closed none of the 19. The number is the same
number against a base 184 commits further along, not a number carried forward.
Reproduce it:

```sh
rg -o '`[0-9a-f]{8}`' docs/requirements/RELEASE-4.0.0-criteria-status.md \
  | sed 's/`//g' | sort -u | while read -r s; do
      git cat-file -e "$s^{commit}" 2>/dev/null &&
      git merge-base --is-ancestor "$s" HEAD || echo "NOT-IN-LINE $s"
    done
```

### What the number counts, and what it does not

The command above tests **ancestry**, not content. Two of the cited PRs were
squash-merged (`#473` as `0f04a179`, `#528` as `992b87c3`), and a squash lands
the work under a new identity, so a commit can be absent by ancestry and
present by content. Spot-checked both ways on 2026-09-15, and the two checks
disagree with each other:

- `482746c1` — "track server.json version with the 4.0.0 crate version".
  Absent by ancestry; `git show chore/v4-reconcile-main:server.json` reads
  `"version": "4.0.0"` at both sites it touched. **The work is on the line.**
- `b7a4a768` — "wire the input bridge into the invoke path". Absent by
  ancestry, and `rg InputBridge src/` on the line returns a definition and
  three comments with no construction site. **The work is not on the line.**

So 19 is an upper bound on unlanded work, not a count of it: some part of it
has already landed squashed and some has not, and nothing here says which
commits fall on which side. Settling that needs a content check per commit,
which does not exist yet. Do not read 19 as a release blocker of size 19, and
do not read a landed squash as evidence that any particular row is covered --
`MIK-7212.MRTR.7a` is graded on `b7a4a768`, whose PR merged, and its code is
still dead on the line.

One of the 19, `9cf1557b`, is on no merged PR head at all.

## Why this is not worktree clutter

The repository carries 55 worktrees, and the obvious housekeeping reading —
delete the idle ones — is wrong here. Every branch in the table above lives in
one of them, and they hold the only copy of that work. `bin/safe-delete-branch`
refuses an unmerged branch for exactly this reason. Housekeeping for these
worktrees **is** merging them; removal is what happens afterwards.

## Worked example of the consequence

`MIK-7212.MRTR.7a` — "modern backend + legacy client MUST issue the equivalent
legacy elicitation" — is graded MET on `b7a4a768`, which is on four
work-package branches and on no integration line. At the release line's HEAD:

```sh
rg -n 'InputBridge' src/
```

returns the struct definition and two doc comments. There is no construction
site, so `InputBridge` is dead code on the branch 4.0.0 ships from. The grade
is honest about the work and silent about where it lives.

Re-run 2026-09-15 against `chore/v4-reconcile-main`, the line that replaced the
one this example was first taken on: four hits, all in
`src/gateway/input_bridge.rs` and `src/gateway/server/stdio_channel.rs`, and
still no construction site. `b7a4a768` is one of the 19.
