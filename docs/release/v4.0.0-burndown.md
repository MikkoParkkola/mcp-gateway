## Why the headline number is slow

It is a lagging measure by construction. A criterion closes when its ledger row carries
evidence, not when the code lands, so delivery work that is real moves it late or not at
all. The decomposition below is what actually converges day to day.

| Bucket | Count | What closes it |
|---|---|---|
| Met on the integration branch, unlanded | 9 | the integration merge |
| Validation against the final revision | 5 | measurement after the merge |
| Deploy probe (`NFR.SEC.7`) | 1 | a probe against the running build |
| Genuine implementation | 13 | code |

Two of the five validation rows carry pre-merge build work rather than measurement:
`NFR.CONFORMANCE.1` needs its matrix widened, `NFR.WORKLOAD.1` needs a harness and a
frozen 3.5.0 baseline that no branch currently measures.

### The eight red jobs are one defect

The `Tests` job log reports `build failed`, and the errors underneath it are not compile
errors — they are the dead-code cluster of §8 of the merge-path note, plus three unused
imports. `.github/workflows/ci.yml:15` sets `RUSTFLAGS: -Dwarnings` for the whole workflow,
so every job that builds dies on the same warnings. The Clippy job is not the only victim of
that cluster; it is the only one whose name says so.

Consequence for the queue: the five un-drafted `MERGEABLE` PRs show exactly these eight
job names and no others, and each of those jobs' logs carries the same dead-code signature.
What that establishes is that the base is red for a known reason, not that any PR is clean.
The `Tests` job dies at compilation, so on every one of those PRs **zero tests executed** —
nothing downstream of the compiler was exercised, including the tests the PR itself adds.
Whether each PR is independently green is therefore unestablished and unmeasurable until the
base builds. That makes the dead-code annotation pass the single unblocker for the whole PR
queue rather than one item in it, and it is owned.

Job-name matching alone would not have settled this. It was checked per job: all eight of
`Tests`, `Public claims`, `Kani`, `Windows check`, `Service template smoke`,
`First-use usability smoke`, `Task SDK recovery` and `Clippy (pedantic)` emit the
`never used` / `never constructed` / `unused import` lines in their own logs, 26 to 44 lines
apiece. `Dependency audit` is the one job that clears `RUSTFLAGS` (`ci.yml:219`) and it is
not among the failures, which is consistent rather than contradictory.

Two of the reported errors are debt rather than scope and must be deleted rather than
annotated: `unused import: DeclaredAccount` (twice) and `unused import: super::super::support::*`.
The verification bar is therefore `RUSTFLAGS=-Dwarnings cargo test --quiet` building clean;
a green `cargo clippy` does not prove the other seven jobs are unblocked.

## The number

`scripts/release/burndown.py [--record]` prints the release-blocking unit count and, with
`--record`, appends a dated row to `docs/release/v4.0.0-burndown.csv`. One unit is one thing
that must reach a terminal state before 4.0.0 ships:

`RBU = scope_pending + baseline_blocking + prs_open`

The first two come from `check_scope_acceptance.py --publish-check` rather than from a second
parser here — that script owns the scope-contract and baseline-ledger formats, and a private
reimplementation would drift from the gate it is supposed to mirror.

Red CI jobs and merge-conflict files are recorded but deliberately **not** summed. Eight red
jobs are one defect, and that defect is already charged to the criterion that owns it;
counting the symptoms as well would inflate the total and make the fix look eight times
bigger than it is. They are tracked because each converges on its own and a rise in either is
a real signal — the integration-into-main conflict count is currently rising, not falling.

| Stream | Meaning | Summed |
|---|---|---|
| `scope_pending` | criteria and decisions not yet `met`/`resolved` | yes |
| `baseline_blocking` | blocking rows in the baseline criteria ledger | yes |
| `prs_open` | open PRs that must land or close | yes |
| `prs_conflicting` | subset of the above needing a rebase first | no |
| `ci_red_jobs` | failing jobs on integration's newest completed run | no |
| `merge_conflict_files` | files conflicting between `main` and integration | no |

### Why two closed criteria did not move the number

`MIK-7332.DISCOVERY.1` and `MIK-7334.CATALOGUE.1` are implemented, tested and committed —
and unpushed, on a branch with no remote ref and no PR, based on a `main` that has since
moved on. A criterion closes when its evidence is on the shipping branch, so neither row can
be graded `met` yet. Both are now owned by the agent that wrote them, with instructions to
rebase, drop the non-source files and open a draft PR.

Two things the split attempt found before anything was pushed. `git checkout <sha> -- <file>`
across a moved base takes whole files, not diffs: it would have reverted 785 lines of
`src/backend/tests.rs` and 133 of `handlers.rs` that landed on `main` after the branch point.
And the DISCOVERY.1 commit carries a `CLAUDE.md` change and a 200-line `PROGRESS.md` rewrite
alongside its source — an instruction-file edit riding inside a criteria fix, which needs the
operator's confirmation rather than a merge.

### The annotation pattern was wrong and is now fixed

The ruling was `#[expect(dead_code, reason = "…")]` per symbol. Run as a falsifier, that
breaks: cargo compiles the crate as two units, and a symbol whose only caller is a
`#[cfg(test)]` module is dead in the `lib` unit but live in the `lib test` unit. The
expectation is fulfilled in one and unfulfilled in the other, so under `-D warnings` the
annotation itself becomes an error. Applied as stated it would have added sixteen errors to
the stronger gate instead of removing them.

The corrected pattern, verified against a full `--all-targets --all-features -- -D warnings`
run, is `#[cfg_attr(not(test), expect(dead_code, reason = "…"))]` — present only in the
non-test build, silent in both units.

`enforce_firewall_challenge` moves from leave-failing to annotate, correcting an earlier
ruling of mine. It is the most precisely routed symbol in the inventory — it *is*
`NFR.SEC.7` — and "reason names the criterion that will wire it" applies to it more clearly
than to anything else in the cluster. Leaving it red also fails on its own terms: it keeps
eight jobs failing, which keeps twelve PRs unvalidatable. `#[expect]` is a tripwire, not a
suppression: the day a caller appears the build breaks and the annotation must come off, so
the signal survives as a build-level assertion instead of a permanently red job nobody can
act on.

### A lint number nobody had measured

Restoring `--all-targets` on integration's `ci.yml:180` surfaces **193 additional lint errors
in test code** on top of the 37 the `--all-features` line reports. They are not optional —
`main`'s gate runs `--all-targets`, so they are what main's CI will demand the moment the
branches meet — but they are not what blocks the queue today. Sequenced third, after the
dead-code cluster greens the eight jobs and after the `ci.yml` line is restored. A red
`--all-targets` until then is expected and is recorded here so it is not read as a regression.
