46 -> >=167 -> 2 -> 0. The middle number was never a regression: it was the local
`--all-targets` view of errors the narrower CI gate could not see. CI's own gate
(`cargo clippy --all-features`, lib only) is now two errors from green.

The gate is being widened to `cargo clippy --all-targets --all-features -- -D
warnings`, because a release gate that never lints test code grades a subset of
what ships. That is a superset of both prior gates, not a restoration of either:
`CLAUDE.md` documents `--all-targets` on default features, CI shipped
`--all-features` on the library alone, and the new line is the union. That raises the CI floor to roughly the local
`--all-targets` number before it falls to zero. Widening the gate and clearing it
are tracked as one step, so the branch is never green against a gate weaker than
the documented one.

The rise from 46 to >=167 is the fail-fast effect being paid off, not a regression:
errors that were always present became visible once the layer above them compiled.

This total is a floor that can RISE, not a burndown ceiling. CI compiles fail-fast:
while the library fails, no integration-test target is built, so its errors are not yet
in any job log. Clearing one layer reveals the next — measured, not predicted: after the
`personal_accounts` dead-code fix let the library compile, `cargo check --all-targets`
surfaced 5 previously invisible errors in `tests/task_upstream_recovery/helper.rs`.
Expect the number to grow before it shrinks.


## Known flake, filed against the release but not blocking it

`x16b_a_dropped_request_future_still_settles_and_releases_its_permit`
(`src/gateway/router/tests/task_execution_adapter/interlock.rs:113`) failed once and passed on
re-run of the same commit. The assertion spins up to 20,000 `yield_now()` calls waiting for a
worker to finish a durable write, then panics. That budget is wall-clock-sensitive, and the
runners moved from self-hosted to GitHub-hosted one commit earlier, so the same budget now buys
less real time. It is a test-harness defect, not a product defect: the code under test settles
correctly, the observer gives up too early. Fix is to wait on a signal with a generous timeout
instead of a fixed yield count.

## How to regenerate this number

```sh
python3 scripts/release/count-release-criteria.py      # core ledger
python3 scripts/release/check_scope_acceptance.py --check   # scope contract
```

The hand-rolled `rg` pair this section used to carry is retired. It counted every
line starting with a criterion-shaped id, which sweeps in the audit **summary**
rows — `MIK-7214.HEADER.7-9`, `MIK-7217.DISCOVER`, `MIK-7246.CONFIRM` and the two
`MIK-7272` rollups are prose summaries of what an audit found on a past date, not
criteria, and they inflate numerator and denominator together. It also has no arm
for the ` (clause: <word>)` suffix the release line uses to split a row, so it
reads a split row as malformed. Use the scripts; they are what CI grades against.

### Why `NFR.PERF.1` is not measurable now (2026-09-12)

An earlier revision of the row above counted `NFR.PERF.1` as measurable and
described a re-measure as "running on `spark`". Nothing is running: the frozen
harness is in place and unfired. Two independent reasons keep it that way, and
the row stays `PARTIAL` and non-blocking under the 2026-09-05 headroom ruling —
this corrects a capacity claim, not a grade.

- **The trigger is half-fired.** `RELEASE-4.0.0-performance-contract.md` R19
  releases the scored run when `MRTR.7a`/`MRTR.7b` are MET *and* strict CI is
  green. The criteria half is satisfied; the CI half is not established on the
  release line.
- **R1 would void the result on arrival.** A4.2 names the scored candidate as
  the HEAD of `fix/mrtr2-continuation-handle`, and R1 holds the evidence only
  while the shipped release commit equals the measured one or diffs empty
  against it over `src/`, `Cargo.toml` and `Cargo.lock`. Measured today:
  `git diff --stat origin/main fix/mrtr2-continuation-handle` over those paths
  reports **90 files, 467 insertions, 6757 deletions**. A scored run against
  that arm expires the moment the release ships from `main`.

Re-pointing the candidate arm at the release line is a contract amendment and an
operator decision; substituting a different branch at reduction time is the same
move as inventing a seventh void condition. The Criterion microbenchmark route
does not substitute either: `dod-check.md:147` records that a Criterion estimate
is not a percentile of served requests, so re-running the `+6.07%`
`session_sandbox/check_tool_denied` set can neither clear nor breach the budget.

## Caveat on the denominator

`criteria-status.md` is **not** the whole authority: none of the scope-update criteria
(`RANKING`, `DISCOVERY`, `CATALOGUE`, `PIN`, `AUDIT`, `NFR.CONFORMANCE/WORKLOAD/UPGRADE/DEMO/BUILD`)
appear in it. Verified: `rg -c 'RANKING.1' criteria-status.md` returns 0 for all ten probes.
Reporting only the core ledger would have understated the remaining work by 30 criteria.
