## Known flake, filed against the release but not blocking it

`x16b_a_dropped_request_future_still_settles_and_releases_its_permit`
(`src/gateway/router/tests/task_execution_adapter/interlock.rs:113`) failed once and passed on
re-run of the same commit. The assertion spins up to 20,000 `yield_now()` calls waiting for a
worker to finish a durable write, then panics. That budget is wall-clock-sensitive, and the
runners moved from self-hosted to GitHub-hosted one commit earlier, so the same budget now buys
less real time. It is a test-harness defect, not a product defect: the code under test settles
correctly, the observer gives up too early. Fix is to wait on a signal with a generous timeout
instead of a fixed yield count.

## The burndown number

One number, defined so it cannot drift with the phrasing of a status cell:

    OPEN = (core criterion rows whose status is neither MET-in-any-qualified-form nor N/A)
         + (scope-contract criteria not yet met)

Both terms come from the scripts, never from a hand count:

```
python3 scripts/release/count-release-criteria.py     # core rows, met-or-non-blocking, blocking
python3 scripts/release/check_scope_acceptance.py --check   # scope criteria, pending
```

The first term of OPEN is the `Core open:` line of the first script, never its
`Coverage:` line. `Coverage:` counts BLOCKING rows; `Core open:` counts rows
neither MET-in-any-qualified-form nor N/A, and the two differ by every row that
is PARTIAL and non-blocking. Reading the wrong one under-reported the headline
for eight entries — see `2026-09-15l`.
