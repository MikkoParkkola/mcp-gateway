# v4.0.0 — release-readiness plan

Companion to `v4.0.0-merge-queue-state.md`, which records *state*. This
records *what closes each gap and in what order*. Update in place.

## The shape of the problem

Measured 2026-09-01, replacing the 2026-08-31 reading that said every branch
sat at step 0.

Two branches have moved. `fix/mrtr2-continuation-handle` is at step 4: pushed,
PR #473 open, DoD comment posted, both vendors returned SHIP on the
confirmation pass, CI still running. `feat/MIK-7320-golden-fixture-fix` is at
step 2. PRs #464, #465, #466 and #473 are open; none is merged.

The rest of the picture got worse, not better, because the earlier inventory
counted the `gap/*` fan-out and nothing else. The true figure:

**33 branches carry roughly 350 commits that exist on exactly one disk.**

| cohort | branches | commits | what it is |
|---|---|---|---|
| yesterday's fan-out (`gap/*`, 08-31) | 17 | ~35 | the v4.0.0 gap agents' output |
| security and admin cluster (08-26..29) | 8 | ~256 | `authorize-at-dispatch` alone is 152 |
| stale (07-20..26) | 5 | 48 | five weeks old, superseded or abandoned |
| release-publishing fixes (08-28..29) | 3 | 8 | npm and registry selection |

`fix/authorize-at-dispatch` is the single largest exposure in the repository:
152 commits, no remote ref, one disk failure from gone.

So the release has three kinds of gap, not two, and the third dominates:

| kind | what it is | how it closes |
|---|---|---|
| **content gaps** | code or criteria wrong, missing, or claimed-but-unenforced | engineering, per branch |
| **chain gaps** | reviewed work that has not reached main | PR, DoD comment, dual review, merge |
| **unbacked work** | ~350 commits on no remote | one push each — cheap, reversible, and first |

Unbacked work is not a release blocker in the sense that it stops a version
number being cut. It is worse: it is invisible. A content gap is something
someone can see and argue about. A branch on one machine cannot be reviewed,
cannot be inherited, and disappears without a trace.

## Content gaps — ordered

### 1. `exposed_meta_tools` documented but unenforced — CLOSING

A config field promising an allow-list ("a tool that is not listed is not
callable either") whose predicate had no caller outside tests. An operator
setting it got a gateway that still listed and still ran everything.

Closed by consuming `MetaToolExposure` on both the `tools/list` and
`tools/call` paths in `src/gateway/meta_mcp/mod.rs`, wired from
`MetaMcpConfig::exposed_meta_tools` in `src/gateway/server/mod.rs`.

Both review legs then found the same second defect: the governed set was
derived from one of the two builders, so Code Mode's `gateway_execute` — which
reaches every backend tool — stayed callable under any allow-list. Repaired at
the derivation, with one shared filter on every list path, so a builder added
later is governed by construction. The preamble fix follows from the same
review: `initialize` was naming four meta-tools regardless of exposure.

Design decision named per §P3: the refusal is worded exactly like the
unrecognised-tool fallback. An operator hiding a tool must not receive a
reply confirming the tool exists and was deliberately withheld.

Residual, stated rather than fixed: two ordering defects in the same
pre-dispatch pipeline. The exposure check sits *after* the admin gate, so an
unexposed **admin** meta-tool called by a non-admin answers `-32600 requires
admin access`; and the router's destructive-confirmation elicitation
(`src/gateway/router/handlers.rs:1099-1186`) fires before the gate, prompting
an operator about a tool the deployment removed. Both disclose existence
through a door the refusal wording closes. Reordering that pipeline is a
separate change with its own review; fixing either alone leaves the disclosure
open.

### 2. MRTR.2 — closed, and MRTR.3 opened in its place

Closed on `fix/mrtr2-continuation-handle`, PR #473. The enforced transform now
rebuilds the delivered result so an unfinished round keeps its discriminator
and its handle, and refuses a round whose `resultType` or `isError` carries the
wrong type rather than dropping or cloning it. Five tests, both vendors SHIP on
the confirmation pass.

Two things it deliberately did not settle, both now disclosed in the release
notes and both needing an operator, not an engineer:

- **MRTR.3.** The sealed continuation envelope (`src/protocol/continuation.rs`
  — AES-256-GCM, caller-bound, single-use) has no production caller. Every
  interim round forwards the backend's own `requestState`, so a
  backend-controlled blob crosses to the caller uninspected. Shipping a feature
  whose summary says "sealed, bound, single-use" while the sealing half is
  unwired is the kind of claim a reader will take as a security property.
  Recommendation: wire it before 4.0.0, or rename the claim.
- **`inputRequests` under enforcement.** The repaired path withholds the
  structured questions while the question text still reaches the caller inside
  sanitized content. Whether enforcement should carry the questions, refuse the
  round, or keep the current split is policy.

### 3. Unverified branches

`gap/mrtr-cluster-v2`, `gap/control-confirm`, `gap/discover-schema`,
`gap/cache-v2`, `gap/cache-otel-v3`, `gap/header59` carry work that has had no
review and, for the last three, no queue position. Each needs the same
treatment: read the diff, check the criteria it claims, then the chain.

`gap/order2`, `gap/cache34`, `gap/task-sub4` point at the fan-out base and

## Chain gaps — the same five steps, per branch

```
1 PUSHED       git rev-list --count <branch> --not --remotes  == 0
2 PR OPEN      gh pr view <n> --json state,headRefName,commits
3 DoD PASSED   §1-§13 + H1-H11 + D-gates verdicts posted as a PR comment
4 REVIEWS      dual-vendor verdict recorded + CI green on the PR head
5 MERGED       gh pr view <n> --json state,mergedAt == MERGED
```

Two standing hazards on step 4, both measured on this queue:

- **Verdict authority is the run file plus the process exit status.** Ledger
  rows here all carry `label: null`, so a row proves *a* review ran, never
  *what* was reviewed. Re-runs must pass a label.
- **Never scrape a verdict from body text.** The review payload quotes the
  verdict template, so a text match finds all three verdict words inside the
  echoed prompt.

`gap/order2-profiles` is the only branch with labelled verdicts: `SHIP` from
one leg, `SHIP-WITH-FIXES` from the other. `SHIP-WITH-FIXES` does not
authorise a merge — the confirmation pass that terminates a review has not
run.

## Order of work — five phases, each with an exit test

The old list said "push every branch, open one PR per branch, review each".
At 33 branches that is 33 dual-vendor reviews, and it will not finish. The
phases below separate what must happen to **all** the work from what only the
release needs.

### Phase 1 — make the work survivable (all 33 branches)

One `git push -u origin <branch>` each. No PR, no review, no merge. A plain
push of a local-only branch creates a new remote ref: it destroys nothing, and
it is reversible by deleting the ref.

Two constraints. The push hook demands a ratification stamp; for a backup push
on a branch that is not asking to merge, `RATIFY_BYPASS=1` exported is the
audited path and every use of it gets recorded here. And a branch belonging to
another live session is pushed, never rebased, renamed or force-pushed.

*Exit test:* `git rev-list --count <branch> --not --remotes` returns 0 for all
33. Nothing in this repository then exists on one disk.

**Done, 2026-09-01.** 43 local branches carried unpushed commits, not 33. 34
pushes covered all of them: pushing a branch retires the count on every
ancestor branch, so the remaining 9 needed no push of their own. `main` was
excluded deliberately — its two local commits are reachable from
`fix/mrtr2-continuation-handle`, so they are backed without pushing a trunk
that no review has seen. The ratification stamp was never needed; no push was
refused, so `RATIFY_BYPASS` went unused. Exit test re-run over every local
branch, `main` included: `git rev-list --count <branch> --not --remotes`
returns 0 for all 44. Nothing in this repository now exists on one disk.

### Phase 2 — triage, before any more engineering

Every branch gets one of four dispositions, recorded in the branch inventory:

| disposition | test |
|---|---|
| **in 4.0.0** | the release notes claim it, or it fixes something they claim |
| **after 4.0.0** | real work, not claimed by this release |
| **superseded** | its content is already on main — verify by file content, not by `git branch --merged`; this repo squash-merges |
| **dead** | abandoned, and saying so is cheaper than carrying it |

The five branches from 07-20..26 are the likeliest supersededs, and the
152-commit `fix/authorize-at-dispatch` the likeliest to be genuinely
load-bearing. Both readings are guesses until the diffs are read.

*Exit test:* every branch has a disposition and a one-line reason. No branch
is left unclassified.

### Phase 3 — close the content gaps that 4.0.0 claims

Only the "in 4.0.0" set. Per branch: read the diff, check the criteria it
claims are actually enforced, fix what is not. The two operator decisions
(MRTR.3, `inputRequests`) are answered here or the release notes carry them as
stated limitations — one of the two, never neither.

*Exit test:* no claim in the release notes is unenforced in the code that
ships, and every accepted limitation is written where a user reads it.

### Phase 4 — the delivery chain, batched

One PR per coherent cluster, not per branch. The security-and-admin cohort is
one integration branch; the `gap/*` fan-out groups by subsystem. Each PR gets
its DoD comment and its dual-vendor review; a `SHIP-WITH-FIXES` gets a
confirmation pass. Merge in dependency order, integration branches last.

Reviews run on the artifact — the PR diff — never on a whole worktree; a
1.9 MB tree diff has already voided one run and killed two of three vendors.

*Exit test:* every "in 4.0.0" branch is at step 5, verified by content on main.

### Phase 5 — cut the release, then housekeep

Tag, publish, then delete merged branches through `bin/safe-delete-branch`,
prune worktrees, and delete the three empty fan-out branches (`gap/order2`,
`gap/cache34`, `gap/task-sub4`) that carry no commits and read as pending work.

*Exit test:* `git branch` lists only live work, and every deleted tip is
archived under `refs/archive/by-tip/`.

## What this plan does not decide

Whether 4.0.0 waits for all of it. Phases 1 and 2 are unconditional — they cost
little and they stop work disappearing. Phase 3 onward is scoped by what the
release notes claim, and cutting that scope is the operator's call, not the
engineering sequence's.
