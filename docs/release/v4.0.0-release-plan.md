# v4.0.0 — release-readiness plan

Companion to `v4.0.0-merge-queue-state.md`, which records *state*. This
records *what closes each gap and in what order*. Update in place.

## The shape of the problem

Every branch in the queue is at **step 0 of the five-step delivery chain**
(DoD D18): nothing pushed, no PR open, no DoD comment posted, one partial
review, nothing merged. Local base-branch merges do not move any of the five.

So the release has two distinct kinds of gap, and they need different work:

| kind | what it is | how it closes |
|---|---|---|
| **content gaps** | code or criteria that are wrong, missing, or claimed-but-unenforced | engineering, per branch |
| **chain gaps** | work that exists only on this disk | push, PR, DoD comment, dual review, merge |

Chain gaps are the larger risk. A content gap is visible and someone can fix
it. A branch that exists on one machine is invisible, unreviewable, and a
disk failure loses it with no trace.

## Content gaps — ordered

### 1. `exposed_meta_tools` documented but unenforced — CLOSING

A config field promising an allow-list ("a tool that is not listed is not
callable either") whose predicate had no caller outside tests. An operator
setting it got a gateway that still listed and still ran everything.

Closed by consuming `MetaToolExposure` on both the `tools/list` and
`tools/call` paths in `src/gateway/meta_mcp/mod.rs`, wired from
`MetaMcpConfig::exposed_meta_tools` in `src/gateway/server/mod.rs`.

Design decision named per §P3: the refusal is worded exactly like the
unrecognised-tool fallback. An operator hiding a tool must not receive a
reply confirming the tool exists and was deliberately withheld.

Residual, stated rather than fixed: the exposure check sits *after* the admin
gate, so an unexposed **admin** meta-tool called by a non-admin still answers
`-32600 requires admin access` and discloses existence through that door.
Ordering the two the other way is a separate change with its own review.

### 2. MRTR.2 — open, on the scalar-wrap exit

The kernel side has been read, and it moves the finding rather than closing
it. `context_integrity_delivered_result`
(`src/gateway/meta_mcp/invoke.rs:1550`) has three exits, not two: withhold,
object passthrough, and a scalar wrap at `:1568-1576`.

`Kernel::transform_content` (`src/context_integrity/kernel.rs:494-533`)
returns an object only on `Allow`, and enforcement requires `decision !=
Allow` (`kernel.rs:460`) — so the object-passthrough branch is unreachable
under enforcement, and the earlier objection named the wrong branch.

`Strip` and `Summarize` are enforcement decisions and return
`Some(Value::String(..))`. The scalar-wrap branch then builds a fresh success
envelope from that text alone, discarding the original result including
`requestState`. Same defect, different door: the caller sees success on an
enforced path with the envelope replaced.

Closes by preserving the original envelope's non-content fields when wrapping
a transformed scalar, with a test on the `Strip` path.

### 3. Unverified branches

`gap/mrtr-cluster-v2`, `gap/control-confirm`, `gap/discover-schema`,
`gap/cache-v2`, `gap/cache-otel-v3`, `gap/header59` carry work that has had no
review and, for the last three, no queue position. Each needs the same
treatment: read the diff, check the criteria it claims, then the chain.

`gap/order2`, `gap/cache34`, `gap/task-sub4` point at the fan-out base and
carry nothing. Delete them at housekeeping; they read as pending work.

## Chain gaps — the same five steps, per branch

```
1 PUSHED       git rev-list --count <branch> --not --remotes  == 0
2 PR OPEN      gh pr view <n> --json state,headRefName,commits
3 DoD PASSED   §1-§13 + H1-H11 + D-gates verdicts posted as a PR comment
4 REVIEWS      dual-vendor verdict recorded + CI green on the PR head
5 MERGED       gh pr view <n> --json state,mergedAt == MERGED
```

Two standing hazards on step 4, both measured on this queue:

- **Verdict authority is the run file plus the process exit status.** Ledger
  rows here all carry `label: null`, so a row proves *a* review ran, never
  *what* was reviewed. Re-runs must pass a label.
- **Never scrape a verdict from body text.** The review payload quotes the
  verdict template, so a text match finds all three verdict words inside the
  echoed prompt.

`gap/order2-profiles` is the only branch with labelled verdicts: `SHIP` from
one leg, `SHIP-WITH-FIXES` from the other. `SHIP-WITH-FIXES` does not
authorise a merge — the confirmation pass that terminates a review has not
run.

## Order of work

1. Land the `exposed_meta_tools` wiring (gap 1) — tests, clippy, commit.
2. MRTR.2 is settled as **open** — the kernel read moved it from the object
   branch to the scalar-wrap branch. Fix the envelope preservation there, or
   record it as accepted residual risk with the criterion unstamped. What is
   not available any more is stamping it MET on the recorded reasoning.
3. Push every branch that carries work. This is cheap, reversible, and it is
   what makes the work survivable. Do it before any further engineering.
4. Open one PR per branch with its DoD comment.
5. Run the labelled dual-vendor review per PR; confirmation pass on any
   `SHIP-WITH-FIXES`.
6. Merge in dependency order, integration branch last.
7. Housekeeping: delete the three empty fan-out branches, prune worktrees.

Steps 3-5 are not optional polish. They are four of the five things that make
the release real to anyone but this session.
