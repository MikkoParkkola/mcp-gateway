# v4.0.0 gate-day procedure: NFR.BUILD.1 C6 mutation evidence

The C6 ranking header (`docs/release/v4.0.0-c6-mutation-ranking.tsv:4`) and
the #2689 description both point to "the gate-day procedure". It was written
as "NFR.BUILD.1 C6 proposal REV 2" plus "C6 REV 2.1 addendum" in a

copied verbatim into the appendix below, so the procedure now lives in the
repository. **[R:n]** cites line n of that file. The appendix keeps the line

## Consequences outside C6

G1 and G10 together mean that a survivor fix lands as a commit, which moves
FROZEN. The maintainer release plan (`.git/release-plan-4.0.md:36-37`,
maintainer-local) reads: "Candidate = one immutable SHA. Any
commit after freeze invalidates tip evidence (COV.3, WORKLOAD.1, BUILD.1,
grading) and re-runs it." A survivor therefore also re-runs C5, WORKLOAD.1,
the BUILD.1 verified-against list and the release grading.

[COV3] allows a written waiver for a mutation floor miss. REV 2 allows none
for C6 (G10, G11). The procedure is the stricter of the two, and that does
not conflict with the criterion.

## Killer-gap table

`docs/release/c6-gap/v4.0.0-c6-gap-table.tsv` holds one row per SAMPLE row:
its fail-open patch (`docs/release/c6-gap/patches/<path>/`), its declared
killer (cargo arguments) and assertion, whether that assertion can go red,
and the proposed test where it cannot. Drawn on `2848618a8`; every patch
applies at `0270539a4`. Nothing in it is graded. Two review seats read every
row for intent, in two batches; their fixes are in the table.

- `can_kill`: every one of the 68 obligations has a killer. Eleven were
  added by #2877, #2879 and #2880; each failed at its own assertion under
  its patch before merging. Startup rank 1 is replaced by understudy rank 9
  under G11 (below).
- OAuth rank 8 (`OAuthClient::authorize`): the ranking names
  `src/oauth/client/mod.rs`; the function moved to
  `src/oauth/client/grants.rs:341` (#2770). It stays an obligation (G4).
- Startup rank 1 (`PeerCertIdentityAcceptor::accept`): two seats found that
  no non-equivalent fail-open mutant of it exists (G11, 2026-10-04). The
  evidence is the guard from #2884: no client leaf that webpki accepts is
  rejected by `CertIdentity::from_der`. Two leaf kinds were not tried, a
  negative serial and an unusual signature-algorithm encoding, because each
  needs a hand-re-signed TBS. The row falls through to startup understudy
  rank 9, `Gateway::response_firewall` (G2, rank order). This is the startup
  path's one equivalence.

Run notes for gate day:

- Bridge ranks 3 and 4 go RED only after the bridge's 30-second prompt
  timeout; the harness allows 20 minutes per test.
- Startup rank 6 and stdio rank 3 leave an unused binding. They compile with
  warnings and go VOID only if a run both denies warnings and drops the
  harness's `--cap-lints=warn`.
- Several declared assertions fail inside a helper (`refused()`, an
  `unwrap_err`) rather than at the assert line. The table names both, for
  the G7 log check.

## Freeze-day command sheet

Every step takes one input, the frozen commit. Run from a checkout of the release
line in the repository root. Work directories and branches are named after the commit
and a per-attempt stamp, so a rerun or a moved FREEZE_SHA (G1) gets fresh ones, and
earlier attempts are kept.

```sh
FREEZE_SHA=<40-hex frozen commit>
git fetch origin && git cat-file -e "$FREEZE_SHA^{commit}"
S=${FREEZE_SHA:0:9}; A=$(date -u +%y%m%d%H%M%S)
W=$(cd .. && pwd)/freeze-$S-$A; mkdir -p "$W"
```

Nothing below merges, tags or publishes. Each step either runs locally or pushes a
`throwaway/` branch, whose own workflow then runs on that push.

### Order on freeze day

1. Merge #2469, then #2380 (version and packaging, labelled `no-changelog`).
2. On `docs/v4.0.0-changelog-fold`, rebased onto the line, fold the changelog as
   RELEASING.md step 1 describes. Run
   `python3 scripts/release/changelog_fragments.py assemble`, then make the manual
   edits listed there. Also point the `[4.0.0]` compare link at `v4.0.0`. In the same
   PR, mark every UPGRADING row still reserved as never assigned:

   ```sh
   grep -n 'Reserved: lands' docs/UPGRADING-4.0.md   # must print nothing after the edit
   ```

   This PR merges last. Its merge commit is FREEZE_SHA, the commit that gets tagged.
3. Run the gates below on FREEZE_SHA, then the C5, C6 and client steps.

### Open: where the grade records live

Grading writes files: scope-ledger flips, the verify record, and the C5 and C6
evidence. If they are committed after FREEZE_SHA, the tag commit is not the graded
commit. If they are committed before it, nothing has been graded yet, and
`check_scope_acceptance.py --release` cannot pass on FREEZE_SHA. The lead's ruling
decides between two options:

- (a) Tag FREEZE_SHA plus one evidence-only commit. That commit must change nothing
  outside `docs/`, and `git diff --stat FREEZE_SHA <tag commit> -- . ':!docs'` must
  print nothing.
- (b) Record the evidence in the PR descriptions and the tracker, and keep it out of
  the tree.

### Release gates (RELEASING.md steps 1 and 2)

```sh
git worktree add -q --detach "$W/gates" "$FREEZE_SHA"
(cd "$W/gates" && git status --short &&                 # must print nothing
  python3 scripts/release/check_tag_manifest.py --tag v4.0.0 &&
  python3 scripts/release/count-release-criteria.py --check &&
  bash scripts/release/check-cited-commits.sh HEAD)
```

`check_scope_acceptance.py --release` exits 0 only after every row is graded. It
runs last, on the commit to be tagged, as the ruling under "Open: where the grade
records live" decides.

Step 2 is the exact-commit CI run and the container rehearsal. `ci.yml` does not run on
pushes to the release line, so this dispatch is the full suite on FREEZE_SHA:

```sh
[ "$(git rev-parse origin/docs/ranking-1-release-line)" = "$FREEZE_SHA" ]   # the line tip is the frozen commit
gh workflow run ci.yml --ref docs/ranking-1-release-line -f rehearse_manifest=true
gh run list --workflow ci.yml --event workflow_dispatch --branch docs/ranking-1-release-line \
  -L3 --json databaseId,headSha,createdAt   # take the run whose headSha is FREEZE_SHA
gh run watch <databaseId>
```

The run passes when its `headSha` is FREEZE_SHA and every job is green, including
`Docker (amd64)`, `Docker (arm64)`, and `Docker manifest list` through `Assert the
list carries both platforms`. `release-criteria` may be red in this run.

Security tickets: in the tracker, list the open mcp-gateway issues labelled security
with priority Urgent or High. The list must be empty. This is a manual check; no gate
automates it.

Step 3, deploying the release build to the listening gateway (NFR.SEC.7), is an
operator step. No agent restarts the live gateway.

### C5 and COV.3: coverage on Linux and Windows

The grade workflow is on `throwaway/coverage-grade-template` (commit `9ceffa4d8`); keep
that branch until the grade is recorded. It runs the command under "The command" in
`docs/release/v4.0.0-critical-path-coverage.md`: the pinned task SDK in its own
single-threaded pass, then every other target, with no `--ignore-run-fail`. It writes
`cov.json` and `linux.lcov` on Linux, and `windows.lcov` on Windows. The frozen commit
gets this one file and nothing else:

```sh
B=throwaway/coverage-freeze-$S-$A
git worktree add -q -b "$B" "$W/coverage" "$FREEZE_SHA"
git -C "$W/coverage" checkout 9ceffa4d8 -- .github/workflows/coverage-cov3.yml
git -C "$W/coverage" commit -q -m "ci(throwaway): C5 coverage grade on $S ($A)"
git -C "$W/coverage" push -q origin "$B"
gh run list --workflow "Coverage probe" --branch "$B" -L1 --json databaseId,headSha   # headSha = the commit above
gh run watch <databaseId>
gh run download <databaseId> -D "$W/cov"
(cd "$W/coverage" && python3 scripts/release/critical_function_coverage.py \
  --lcov "$W/cov/coverage-linux/linux.lcov" --lcov "$W/cov/coverage-windows/windows.lcov")
```

Both jobs must be green. Neither runs `--ignore-run-fail`, so any failed test fails
its job. The grader runs in the frozen tree, against that tree's inventory and
sources, and must exit 0. The per-path table is then re-taken from
`$W/cov/coverage-linux/cov.json`, using the mapping and the 2026-10-01 baseline, as
step 4 of "What closing C5 requires" describes.

### C6: the three mutation batches

The batches come from the gap table (`docs/release/c6-gap/`) at the frozen commit.
Every row except the G11 row is dealt, in table order, to three hosted batches: the
first two get 23 rows and the third gets 22.

| Batch | Rows |
|---|---|
| 1 | HTTP 1, 4, 7, 10, 13, 16; accounts 3, 6, 9, 12, 15; OAuth 2, 5, 8; bridge 3; startup 2, 5, 8; stdio 3, 6; tasks 1, 4, 7 |
| 2 | HTTP 2, 5, 8, 11, 14; accounts 1, 4, 7, 10, 13, 16; OAuth 3, 6; bridge 1, 4; startup 3, 6; stdio 1, 4, 7; tasks 2, 5, 8 |
| 3 | HTTP 3, 6, 9, 12, 15; accounts 2, 5, 8, 11, 14; OAuth 1, 4, 7; bridge 2; startup 9, 4, 7; stdio 2, 5, 8; tasks 3, 6 |

Build all three locally. The block checks that every patch applies and that the
harness's `plan` check passes. It also prints the sha256 of each manifest and patch,
which G6 records. Branch numbers come from the attempt stamp:

```sh
STAMP=$A
FREEZE_SHA="$FREEZE_SHA" OUT="$W/c6" STAMP="$STAMP" bash <<'BUILD'
set -euo pipefail
T=docs/release/c6-gap/v4.0.0-c6-gap-table.tsv
for b in 1 2 3; do
  n=$STAMP$b; wt=$OUT/batch-$b
  git worktree add -q --detach "$wt" "$FREEZE_SHA"
  (
    cd "$wt"; git switch -q -c "throwaway/mutants-$n"; mkdir .mutants
    printf 'head_sha\t%s\n' "$FREEZE_SHA" > .mutants/manifest.tsv
    awk -F'\t' -v b="$b" 'NR>1 && $8!="G11" { i++; if ((i-1)%3+1==b) print }' "$T" |
    while IFS=$'\t' read -r rank npath file fn mutant args assertion rest; do
      case "$npath" in
        "HTTP dispatch") d=http ;; "account paths") d=acct ;; OAuth) d=oauth ;;
        bridge) d=bridge ;; startup) d=startup ;; "stdio dispatch") d=stdio ;; tasks) d=tasks ;;
        *) echo "unmapped path: $npath" >&2; exit 3 ;;
      esac
      p=$(basename "${mutant%%:*}")
      cp "docs/release/c6-gap/patches/$d/$p" ".mutants/${d}_$p"
      id=$(printf '%s_%02d' "$d" "$rank" | tr '[:lower:]' '[:upper:]')
      printf '%s\tlinux\t%s\t%s\n' "$id" "${d}_$p" "$args" >> .mutants/manifest.tsv
    done
    for f in .mutants/*.patch; do git apply --check "$f"; done
    echo "batch $b (throwaway/mutants-$n): $(($(wc -l < .mutants/manifest.tsv) - 1)) rows"
    shasum -a 256 .mutants/*
    git add .mutants; git commit -q -m "test(mutants): C6 gate batch $b on ${FREEZE_SHA:0:9}"
    GITHUB_REF="refs/heads/throwaway/mutants-$n" GITHUB_OUTPUT=/dev/null \
      python3 scripts/ci/mutants/run_mutants.py plan
  )
done
BUILD
```

Under G6, two seats review the three manifests for intent, and the printed hashes are
recorded, before anything is pushed. Then push each batch and find its own run:

```sh
for b in 1 2 3; do
  br=throwaway/mutants-$STAMP$b; git -C "$W/c6/batch-$b" push -q origin "$br"
  echo "$br $(git -C "$W/c6/batch-$b" rev-parse HEAD)"
done
gh run list --workflow Mutants --branch "throwaway/mutants-${STAMP}1" -L1 --json databaseId,headSha   # and ...2, ...3
```

For each branch, the run's `headSha` must equal the batch commit printed above. Its
`Mutants (linux)` job prints one line per row: RED, SURVIVED, VOID or ERROR. Each RED
is then checked against the row's declared assertion in the log (G7).

### BUILD.1: the verified-against client run

This repeats the 2026-09-23 run (`docs/release/verify/2026-09-23-claude-code-2.1.280.md`)
on the frozen commit. It runs on the operator's machine, where the `claude` CLI is
installed, and starts its own gateway on port 39477. It does not touch the listening
gateway.

```sh
git worktree add -q --detach "$W/verify" "$FREEZE_SHA"
cd "$W/verify"
cargo build --release --locked --bin mcp-gateway
BIN=target/release/mcp-gateway; "$BIN" --version; shasum -a 256 "$BIN"
mkdir -p verify-run
printf '%s\n' 'server:' '  host: 127.0.0.1' '  port: 39477' 'meta_mcp:' '  enabled: true' \
  'capabilities:' '  enabled: true' '  directories: [./capabilities]' > verify-run/gw.yaml
chmod 600 verify-run/gw.yaml
printf '%s\n' '{"mcpServers":{"gw4":{"type":"http","url":"http://127.0.0.1:39477/mcp"}}}' > verify-run/claude-mcp.json
! curl -fsS -m 2 -o /dev/null http://127.0.0.1:39477/health || { echo "port 39477 already serves a gateway" >&2; exit 1; }
RUST_LOG=info,mcp_gateway=debug "$BIN" --config verify-run/gw.yaml > verify-run/gw.log 2>&1 & GW=$!
up=no
for i in $(seq 60); do
  curl -fsS -m 2 -o /dev/null http://127.0.0.1:39477/health && { up=yes; break; }
  kill -0 "$GW" 2>/dev/null || break
  sleep 1
done
[ "$up" = yes ] || { tail -20 verify-run/gw.log; kill "$GW" 2>/dev/null; exit 1; }
claude --version | tee verify-run/claude-version.txt
claude -p "Load the schema of mcp__gw4__gateway_list_servers, call it, quote the raw result, then list every gw4 tool." \
  --mcp-config verify-run/claude-mcp.json --strict-mcp-config \
  --allowedTools mcp__gw4 ToolSearch --model haiku --output-format json > verify-run/client.json
kill "$GW"
jq .is_error verify-run/client.json          # false
grep -c 'server/discover' verify-run/gw.log  # at least 1
grep -c 'tools/call' verify-run/gw.log       # at least 1
```

Record the run as a new `docs/release/verify/<date>-claude-code-<version>.md`, in the
shape of the 2026-09-23 file. It needs the client and gateway versions, the binary's
sha256 prefix, the date and owner, the method counts, and what the run does not cover.
Then add its row to the `Verified against` list in
`docs/release/v4.0.0-supported-matrix.md`.
