# v4.0.0 gate-day procedure: NFR.BUILD.1 C6 mutation evidence

The C6 ranking header (`docs/release/v4.0.0-c6-mutation-ranking.tsv:4`) and
the #2689 description both point to "the gate-day procedure" for the C6 pass
rules. That document was never committed. This file records those rules, and
each rule cites the line it comes from. A rule that no source states is listed
under **Open** and is not applied until it is ruled.

Sources:

- **[NFR]** `docs/requirements/RELEASE-4.0.0-scope-update.md:63`, the NFR.BUILD.1 criterion
- **[COV3]** `docs/requirements/RELEASE-4.0.0-scope-update.md:147`, the MIK-7324.COV.3 criterion
- **[TSV]** `docs/release/v4.0.0-c6-mutation-ranking.tsv`: the header (lines 1-4) and the published rows
- **[PR]** #2689 description (merged as `fef196e05`), the pass-rule sentence: "fail-open mutants approved and hashed before the run, RED only by the declared killing assertion, no VOID allowance, survivors fixed and re-run RED on FROZEN, one FROZEN"
- **[TEST]** `scripts/release/test_c6_mutation_sample.py`
- **[LEDGER]** the `MIK-7324.COV.3` note in `docs/requirements/RELEASE-4.0.0-scope-status.json`: "closing them is test work, no waivers" (said of the coverage misses)

## Rules

| # | Rule | Source |
|---|---|---|
| G1 | Mutation evidence that grades C6 comes from the final integration revision. | [NFR] "mutation evidence grades the final integration revision"; [COV3] "on the final revision" |
| G2 | There is one FROZEN revision, and every run counted as gate evidence is on it. | [PR] "one FROZEN" |
| G3 | The obligations are the 68 `SAMPLE` rows of the ranking: account paths 16, HTTP dispatch 16, startup, OAuth, stdio dispatch and tasks 8 each, bridge 4. | [TSV:4] "SAMPLE rows are the gate's obligations"; [TEST] `test_sample_quotas` |
| G4 | The sample is not redrawn. The nonce `8edb1c00edf8571ffabc3e492341e347` is the first and only draw. The frame is frozen at sha256 `76d59ee3…`, and an inventory edit cannot move the draw. | [TSV:1-3]; [TEST] `test_the_frame_is_frozen`, `test_the_draw_ignores_the_live_inventory` |
| G5 | An understudy replaces a SAMPLE row only in rank order, within the same path. | [TSV:4] "understudies replace a row only in rank order"; [TEST] ranks are drawn per path |
| G6 | The mutants are fail-open, and they are approved and hashed before the run. | [PR] "fail-open mutants approved and hashed before the run" |
| G7 | A mutant counts as killed (RED) only when its declared killing assertion fails. | [PR] "RED only by the declared killing assertion" |
| G8 | A VOID result never counts toward the pass. | [PR] "no VOID allowance" |
| G9 | A surviving mutant is fixed with a test. The test is re-run and must turn the mutant RED on FROZEN. | [PR] "survivors fixed and re-run RED on FROZEN" |

G7 to G9 point to a gate that passes only when every approved mutant ends RED
by its declared assertion on FROZEN. [COV3] also allows "a written waiver
naming the module and the reason" for a mutation floor miss. O8 settles which
of the two governs, and until it is ruled, neither does.

## Open

Each item below needs a ruling before the gate runs. None is applied until it
has one.

**O1. How a survivor fix meets "on FROZEN".** G9 needs a new test, and a new
test is a new commit. The maintainer release plan (`.git/release-plan-4.0.md:36-37`,
maintainer-local and not in the tree) says any commit after the freeze
invalidates the tip evidence (COV.3, WORKLOAD.1, BUILD.1, grading).
- (a) The fix lands and becomes a new FROZEN, and all of that evidence is
  re-run on it: C5, every C6 row, WORKLOAD.1, the BUILD.1 verification and
  the release grading. The sources stay consistent, but each survivor costs
  the full freeze tail.
- (b) Graded C6 rows carry over. Everything else in (a) is re-run on the new
  SHA, but only the fixed C6 rows. This is cheaper, but no source permits a
  carry over.
- (c) Mutants are run before the freeze, on a candidate, to find survivors.
  Only the FROZEN run counts (G2). This finds survivors before the freeze
  instead of after it.

**O2. Mutants per SAMPLE row.** No source states a count.
- (a) One mutant per refusal branch. This covers the most, and the run is
  longer.
- (b) One mutant per function. This is the cheapest, and a function with
  several refusals is only partly graded.

**O3. Who approves the mutant set (G6), and what the approved record holds.**
[PR] says the pass rules were reviewed by two seats. It records no mechanism
for approving mutants.
- Approver (a): two review seats on a committed manifest, with its sha256 in
  the ledger row. Approver (b): the operator approves the manifest, which
  takes the most operator time.
- Content (a): the patch hashes only, with G7 settled under O9. Content (b):
  the patch hashes plus each row's declared killing assertion, so what must
  fail is fixed before the run.

**O4. Equivalent mutants.** No source covers a mutant that cannot change
behaviour.
- (a) It is withdrawn before the run and replaced. After the run it cannot be
  withdrawn.
- (b) A written waiver, under O8.

**O5. When an understudy replaces a SAMPLE row (G5), and what happens when a
path has none left.** No source states the trigger. Bridge and stdio dispatch
have no understudies, startup has 4 and OAuth has 5.
- (a) Replace a row only when the function no longer exists at FROZEN, or no
  fail-open mutant of it can be written (O7). This is the narrowest, and it
  resists cherry picking.
- (b) Also replace a row that is VOID twice. This is looser, and lets a flaky
  row drop out.
- For a path with no understudy left: either the row blocks the gate until it
  is graded, or it takes a waiver under O8.

**O6. A VOID result (G8).** No source says whether a VOID row may be re-run.
- (a) A VOID row is re-run on FROZEN until it is RED or SURVIVED, and VOID
  never passes.
- (b) Any VOID fails the gate outright.

**O7. What "fail-open" means for a row.** [PR] uses the word without defining
it. Some SAMPLE rows enforce integrity, scrubbing or expiry rather than an
allow-or-refuse decision.
- (a) A mutant that makes the function allow what it should refuse. This is
  the narrowest, and rows with no such decision fall to O5.
- (b) Any mutant that weakens the security property the row's inventory
  reason names. This covers every row, but it needs judgement at approval
  (O3).

**O8. Waivers against an all-RED gate.** [COV3] allows a written waiver for a
mutation floor miss. [LEDGER] says "no waivers" for the coverage misses only.
- (a) No waivers for C6: every miss is closed with a test. This is the
  strictest, and survivors drive O1.
- (b) [COV3] waivers are allowed, each naming the module and the reason, and
  recorded in the ledger row. This is faster, and the operator owns each one.

**O9. How a RED is attributed to its declared assertion (G7).** The batch
harness (`scripts/ci/mutants/run_mutants.py`) classifies RED from cargo's
summary and keeps 15 evidence lines per row. It does not check which
assertion failed.
- (a) Pin each row's cargo arguments to the one declared test, and require
  the panic message in the kept evidence lines to match the declared
  assertion. This needs no harness change.
- (b) Extend the harness to match a declared assertion string per row. This
  is stronger, and it changes reviewed CI code before the freeze.
