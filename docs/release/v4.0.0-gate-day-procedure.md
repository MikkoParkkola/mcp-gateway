## Rules

| # | Rule | Source |
|---|---|---|
| G1 | The whole gate runs on one FROZEN sha, the final integration revision. If FROZEN moves, the complete manifest re-runs on the new FROZEN. A row that SURVIVED earlier stays an obligation, and it must be RED on the final FROZEN. | [R:101]; [NFR] |
| G2 | The obligations are the 68 SAMPLE rows of the published ranking: account paths 16, HTTP dispatch 16, startup, OAuth, stdio and tasks 8 each, bridge 4. Later ranks are understudies, used only in rank order. Bridge (4/4) and stdio (8/8) are full census, with no understudies; OAuth has 5 understudies and startup 4. | [R:99], [R:114], [R:130]; [TEST] `test_sample_quotas` |
| G3 | The draw is fixed. The nonce `8edb1c00edf8571ffabc3e492341e347` is the first and only draw, and the draw comes from the frozen frame, not the live inventory. [R:99]'s "added rows join the ranking by the same hash" is superseded: after [2756], an added inventory row cannot enter the sample. Its "a removed row is replaced by the next-ranked understudy" is narrowed by G4: an inventory edit alone removes nothing. | [R:99]; [2756]; [TEST] `test_the_draw_ignores_the_live_inventory` |
| G4 | A sampled row stays an obligation through file moves and renames. It leaves the sample only when two seats verify that its security decision no longer exists in FROZEN. Enforced by `scripts/release/c6_resolve.py` (MIK-8245): it finds each obligation by identity, re-targets its patch, requires the patch to change only that function and to apply, and fails naming any it cannot resolve. It runs on every pull request and release-line push (`.github/workflows/c6-obligations.yml`). A decision that survives in another function is re-bound there by two seats, recorded in `docs/release/c6-gap/v4.0.0-c6-replacements.tsv` as `G4-successor`; an unresolved row is never VOID and never uses G9. | [R:112]; MIK-8245 |
| G5 | There is one fail-open mutant per SAMPLE row. It removes the row's security decision, per its reason column, and keeps valid-input behaviour unchanged. | [R:100] |
| G6 | Mutants are written and approved before the run. Each row records its patch, its cargo test args and the security assertion expected to kill it. The manifest and patches are committed to `throwaway/mutants-<n>` with their sha256 recorded, and two seats review them for intent. After the run, a patch may change only to fix a VOID, and that change is reviewed for unchanged intent. Every attempt's outcome is kept. | [R:100] |
| G7 | A RED counts only when the failed test is the row's pre-declared killer and its declared security assertion failed, as checked in the log. Any other RED is VOID for that row. | [R:111] |
| G8 | ERROR = 0. | [R:103] |
| G9 | Every SAMPLE row is judged. A VOID gets one patch repair. If it is still VOID, the row is replaced by its path's next understudy. A path that cannot fill its quota after two understudies per row fails C6. There is no VOID allowance. This replacement is the one exception to G4: the still-VOID row leaves the sample, and its two VOID attempts stay in the evidence (G6, G12). A VOID that is not a patch defect, from a runner timeout or a red baseline, gets one re-run of its batch on the same FROZEN, which consumes the row's one repair; if the row is still VOID, it follows the rule above. Ratified by the release lead on 2026-10-05 (delta-6 bot review of #2870): "A timeout VOID or a red-baseline VOID is an infrastructure outcome, not a product verdict. One batch re-run that consumes the row's single repair is the narrowest fix, and G4 still governs everything else." | [R:104] |
| G10 | SURVIVED = 0. A survivor passes only when a killing test is merged and the row is re-run RED on FROZEN. "Equivalent" is not a pass. | [R:105] |
| G11 | An equivalent mutant is replaced by a non-equivalent mutant of the same function. It falls through to an understudy only after two seats find that no non-equivalent fail-open mutant exists, at most once per path. Otherwise the path fails. | [R:105], [R:113] |
| G12 | Evidence on the NFR.BUILD.1 row: run ids, the nonce, the manifest sha256, and for each row RED, VOID or SURVIVED with the killing test name, the assertion, and which security decision was mutated. | [R:106], [R:115] |
| G13 | Before gate day, a pilot covers all seven paths, one row each. It measures cold build, baselines and per-row time, to size the batches. It runs on the trusted runner when `vars.MCPGW_TRUSTED_RUNNER == ready`; otherwise batches are sized to the hosted 360-minute job. | [R:107], [R:116] |
| G14 | A sample bounds, it does not prove. The C5 coverage floors remain the census. | [R:108] |
| G15 | Standard rows are out of scope. The house harness `scripts/ci/mutants/run_mutants.py` and its classifier are used, not cargo-mutants. | [R:109] |

## Consequences outside C6

G1 and G10 together mean that a survivor fix lands as a commit, which moves
FROZEN. The maintainer release plan (`.git/release-plan-4.0.md:36-37`,
maintainer-local) reads: "Candidate = one immutable SHA. Any
commit after freeze invalidates tip evidence (COV.3, WORKLOAD.1, BUILD.1,
grading) and re-runs it." A survivor therefore also re-runs C5, WORKLOAD.1,
the BUILD.1 verified-against list and the release grading.

[COV3] allows a written waiver for a mutation floor miss. REV 2 allows none
for C6 (G10, G11). The procedure is the stricter of the two, and that does
not conflict with the criterion.

## Freeze-day command sheet

Every step takes one input, the frozen commit. Run from a checkout of the release
line in the repository root. Work directories and branches are named after the commit
and a per-attempt stamp, so a rerun or a moved FREEZE_SHA (G1) gets fresh ones, and
earlier attempts are kept.

```sh
FREEZE_SHA=<40-hex frozen commit>
git fetch origin && git cat-file -e "$FREEZE_SHA^{commit}"
S=${FREEZE_SHA:0:9}; A=$(date -u +%y%m%d%H%M%S)
W=$(cd .. && pwd)/freeze-$S-$A; mkdir -p "$W"
```

Nothing below merges, tags or publishes. Each step either runs locally or pushes a
`throwaway/` branch, whose own workflow then runs on that push.

### Publish the Helm chart pinned to the image digest (MIK-6684, after the release build)

The committed chart keeps `image.digest` empty, since the digest exists only after the image is
built and rule (a) allows no non-docs change after FREEZE_SHA. The tag run publishes the chart:
`ci.yml`'s `helm-chart-publish` job runs `scripts/release/publish_pinned_chart.sh` after
`docker-manifest` has signed the image and named `:4.0.0` (MIK-7952). It injects the digest into
the packaged chart only, takes the chart's own version from `Chart.yaml` (0.2.0, not 4.0.0),
packages it reproducibly, stops on any failed step, cosign-signs the pushed chart by its digest
(RFC-0133 HELM.6) and verifies the digest by pulling the published chart back. The signature is
keyless from the workflow, so chart and image carry one identity,
`https://github.com/MikkoParkkola/mcp-gateway/.github/workflows/ci.yml@refs/tags/v4.0.0`, issuer
`https://token.actions.githubusercontent.com`; the job also checks that a verify under any other
identity is refused. No step runs from your shell.

GHCR has no `charts/mcp-gateway` package before the first tag. The job's first `helm push`
creates it, owned by this repository with its Actions write access, so there is no operator step.
Never push `charts/mcp-gateway` by hand: a package created from a personal token is not linked to
this repository, and the tag run's push to it then fails. After the tag run, check that the
package exists, is linked to this repository, and is public. The rehearsal dispatch (run
37503276254) created `charts-rehearsal/mcp-gateway` that way: public and linked, with no manual
step. If GHCR created it private, set it to
Public in the package settings (Danger Zone, Change visibility) before announcing the chart:
consumers pull it anonymously.

The pass record is the image digest, the chart version, the signed chart reference, the signer
identity and issuer, and the publish check line. The job writes all of them to its `chart-notes`

### C6: the three mutation batches

The batches come from the gap table (`docs/release/c6-gap/`) at the frozen commit.
Every row except the G11 row is dealt, in table order, to three hosted batches: the
first two get 23 rows and the third gets 22.

| Batch | Rows |
|---|---|
| 1 | HTTP 1, 4, 7, 10, 13, 16; accounts 3, 6, 9, 12, 15; OAuth 2, 5, 8; bridge 3; startup 2, 5, 8; stdio 3, 6; tasks 1, 4, 7 |
| 2 | HTTP 2, 5, 8, 11, 14; accounts 1, 4, 7, 10, 13, 16; OAuth 3, 6; bridge 1, 4; startup 3, 6; stdio 1, 4, 7; tasks 2, 5, 8 |
| 3 | HTTP 3, 6, 9, 12, 15; accounts 2, 5, 8, 11, 14; OAuth 1, 4, 7; bridge 2; startup 9, 4, 7; stdio 2, 5, 8; tasks 3, 6 |

Build all three locally. The block checks that every patch applies and that the
harness's `plan` check passes. It also prints the sha256 of each manifest and patch,
which G6 records. Branch numbers come from the attempt stamp:

```sh
STAMP=$A
FREEZE_SHA="$FREEZE_SHA" OUT="$W/c6" STAMP="$STAMP" bash <<'BUILD'
set -euo pipefail
# G4 (MIK-8245): every obligation resolves on FREEZE_SHA, or nothing is built. The
# batches take the resolver's re-targeted patches, never the drawn ones.
python3 scripts/release/c6_resolve.py --tree "$FREEZE_SHA" --manifest "$OUT/resolved"
for b in 1 2 3; do
  n=$STAMP$b; wt=$OUT/batch-$b
  git worktree add -q --detach "$wt" "$FREEZE_SHA"
  (
    cd "$wt"; git switch -q -c "throwaway/mutants-$n"; mkdir .mutants
    printf 'head_sha\t%s\n' "$FREEZE_SHA" > .mutants/manifest.tsv
    # The resolver's manifest is the batch plan: its rows, in killer-gap order, cut
    # round robin. Each row's patch is the re-targeted one it wrote beside them.
    awk -F'\t' -v b="$b" 'NR>1 { i++; if ((i-1)%3+1==b) print }' "$OUT/resolved/manifest.tsv" |
    while IFS=$'\t' read -r id platform patch args; do
      cp "$OUT/resolved/$patch" ".mutants/$patch"
      printf '%s\t%s\t%s\t%s\n' "$id" "$platform" "$patch" "$args" >> .mutants/manifest.tsv
    done
    for f in .mutants/*.patch; do git apply --check "$f"; done
    echo "batch $b (throwaway/mutants-$n): $(($(wc -l < .mutants/manifest.tsv) - 1)) rows"
    shasum -a 256 .mutants/*
    git add .mutants; git commit -q -m "test(mutants): C6 gate batch $b on ${FREEZE_SHA:0:9}"
    GITHUB_REF="refs/heads/throwaway/mutants-$n" GITHUB_OUTPUT=/dev/null \
      python3 scripts/ci/mutants/run_mutants.py plan
  )
done
BUILD
```

Before anything else, check that every row's test filter still names a test at
FREEZE_SHA. Cargo runs only the tests whose path contains the filter, so a test moved
to another module matches nothing, and the row comes back `VOID (baseline-no-tests)`
instead of judging its killer. The arguments are the manifest's own, run the way the
harness runs them:

```sh
W="$W" bash <<'FILTERS'
set -euo pipefail
cd "$W/c6/batch-1"
for b in 1 2 3; do
  m="$W/c6/batch-$b/.mutants/manifest.tsv"
  [ -f "$m" ] || { echo "STOP: no manifest $m" >&2; exit 4; }
  while IFS=$'\t' read -r id plat patch args; do
    read -r -a argv <<< "$args"
    # The last argument must be a test filter: not a flag, and not the name a
    # target selector takes. Non-negative indexes: macOS ships bash 3.2.
    k=${#argv[@]}
    if [ "$k" -lt 2 ]; then echo "STOP: $id has no test filter" >&2; exit 4; fi
    case "${argv[k-1]}" in -*) echo "STOP: $id has no test filter" >&2; exit 4 ;; esac
    case "${argv[k-2]}" in --test|--bench|--bin|--example) echo "STOP: $id has no test filter" >&2; exit 4 ;; esac
    if ! cargo test --all-features "${argv[@]}" -- --list > "$W/c6/list-$id.txt" 2> "$W/c6/list-$id.err"; then
      echo "STOP: $id could not be listed; see $W/c6/list-$id.err" >&2; exit 4
    fi
    n=$(grep -c ': test$' "$W/c6/list-$id.txt" || true)
    echo "$id $n"
    [ "$n" -ge 1 ] || { echo "STOP: $id lists no test" >&2; exit 4; }
  done < <(tail -n +2 "$m")
done
FILTERS
```

Every row must list at least one test. A row that cannot be listed means the tree does
not build: stop and fix that first. If a row lists no test, stop as well: push
nothing, repoint that row's filter and declared assertion in the gap table through a
docs PR, then rebuild the batches.
