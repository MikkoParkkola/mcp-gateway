# Prerelease channel: how to stage a v4.0.0 release candidate

Cutting `v4.0.0-rc.1` reaches only the channels a user has to ask for. This is what the
D21 CANARY gate asks for on a client-installed binary: exposure that can be staged and
observed before every `brew upgrade` and every untagged `docker pull` gets the new code.

## What a prerelease tag does, per surface

Three workflows fire independently on a `v*` tag and none can read another's job outputs,
so each runs `scripts/release/check_tag_manifest.py` itself. The script refuses to publish
when the tag disagrees with `Cargo.toml`/`Cargo.lock`, and classifies the channel.

| Surface | Where | On `v4.0.0-rc.1` | On `v4.0.0` |
|---|---|---|---|
| GitHub release | `release.yml` `release` | Marked prerelease; the "Latest" pointer does not move | Latest release |
| crates.io | `release.yml` `publish` | Publishes `4.0.0-rc.1`; Cargo will not resolve it for `^4`, so `cargo install mcp-gateway --version 4.0.0-rc.1` is the opt-in | Resolvable by `^4` |
| npm | `release.yml` `npm-publish` | `@mikkoparkkola/mcp-gateway@next` | `@latest` |
| Homebrew tap | `release.yml` `homebrew-update` | Skipped — the tap has one stable formula | Formula bumped |
| ghcr, signed publisher | `ci.yml` `docker` | Pushes `:4.0.0-rc.1` only; `:latest` withheld. cosign signature and SBOM attestation run on both channels | Also moves `:latest` |
| ghcr, metadata publisher | `docker.yml` `build` | Pushes `:4.0.0-rc.1` only: `latest=auto` withholds `:latest`, and a prerelease semver makes the action compile `{{version}}` in place of the `{{major}}.{{minor}}` row, so no `:4.0` appears. Signs and attests its own digest | Pushes `:4.0.0`, `:4.0` and `:latest` |
| MCP Registry | `docker.yml` `publish-mcp-registry` | Skipped — a discovery surface nobody opts in to | Listed |

Both ghcr publishers push `:VERSION` from the same commit, and neither workflow can
depend on the other, so the name is owned by whichever pushed last. Both sign and attest
what they push: the image behind `:4.0.0` carries a signature from `ci.yml` or from
`docker.yml`, at the pushed tag. A consumer pinning `--certificate-identity` accepts
either.

Which of the two signed the digest a given pull resolves to is not knowable in advance,
so a consumer checks both identities and accepts the first that verifies:

```bash
DIGEST=$(crane digest ghcr.io/mikkoparkkola/mcp-gateway:4.0.0)
BASE=https://github.com/MikkoParkkola/mcp-gateway/.github/workflows
for wf in ci docker; do
  cosign verify \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com \
    --certificate-identity "$BASE/$wf.yml@refs/tags/v4.0.0" \
    "ghcr.io/mikkoparkkola/mcp-gateway@$DIGEST" && exit 0
done
echo 'unsigned by both publishers' >&2; exit 1
```

The SBOM attestation is checked the same way, with `cosign verify-attestation --type
spdxjson`. Verify by digest, not by tag: `:4.0.0` is a mutable pointer that either
publisher can move, and a signature is over the digest.

Every gate a final release passes, a prerelease passes too: `security-gate`,
`secret-leak-lint`, `release-criteria`, clippy, fmt, the test suite, trivy and the OSV scan
are unchanged. A channel that skips gates is not a canary.

## Staging one

1. Bump `Cargo.toml` to `4.0.0-rc.1` and run `cargo update -p mcp-gateway` so the lockfile
   agrees. The tag/manifest gate fails the run otherwise, in all three workflows — this is
   deliberate: `cargo publish` takes its version from the manifest, not the tag, so a
   mismatch would publish the candidate to crates.io as the final `4.0.0`.
2. Verify locally before pushing anything:
   `python3 scripts/release/check_tag_manifest.py --tag v4.0.0-rc.1` → exit 0, `prerelease`.
3. Commit, tag `v4.0.0-rc.1`, push the tag.
4. Confirm the five stable pointers have **not** moved: the `releases/latest` redirect, the
   npm `latest` dist-tag, the tap formula's version, `ghcr.io/mikkoparkkola/mcp-gateway:latest`
   by digest, and the MCP Registry entry.
5. Observe. Promotion criteria and the observation window are the operator's call and are not
   encoded here; record what was observed against them before step 6.
6. Promote: bump the manifest to `4.0.0`, tag `v4.0.0`, push. The same workflows now take the
   stable path on every surface.

## What this does not close

The mechanism existing and being validated is not the same as exposure having been staged.
D21 stays **OUTSTANDING** until an rc has actually been published and observed; claiming MET
off a workflow edit is the fabrication the gate exists to catch.

Both publishers push first and sign second, so a run that fails or is cancelled between the
two steps leaves `:VERSION` public and unsigned. The run goes red and the verify snippet
above returns non-zero, so the state is detectable rather than silent, but it is not
prevented. Closing it means pushing by digest and promoting the tag only after signing —
a rework of both publishers' push architecture, whose correctness depends on
`docker buildx imagetools create --prefer-index=false` preserving the digest (the default
`--prefer-index=true` does not carbon-copy a single source) and cannot be tested without a
registry. Tracked as #529. Out of scope here, and worth knowing that the cheaper-looking
alternative pulls the other way: moving signing into a tag-only job to narrow the
`id-token` grant would put the push and the signature in different jobs and widen this
window, not close it.
