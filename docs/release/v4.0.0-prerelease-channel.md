# Prerelease channel: how to stage a v4.0.0 release candidate

Cutting `v4.0.0-rc.1` reaches only the channels a user has to ask for. This is what the
D21 CANARY gate asks for on a client-installed binary: exposure that can be staged and
observed before every `brew upgrade` and every untagged `docker pull` gets the new code.

## What a prerelease tag does, per surface

Three workflows fire independently on a `v*` tag and none can read another's job outputs,
so each runs `scripts/release/check_tag_manifest.py` itself. The script refuses to publish
when the tag disagrees with `Cargo.toml`/`Cargo.lock`, and classifies the channel.

| Surface | Where | On `v4.0.0-rc.1` | On `v4.0.0` |
|---|---|---|---|
| GitHub release | `release.yml` `release` | Marked prerelease; the "Latest" pointer does not move | Latest release |
| crates.io | `release.yml` `publish` | Publishes `4.0.0-rc.1`; Cargo will not resolve it for `^4`, so `cargo install mcp-gateway --version 4.0.0-rc.1` is the opt-in | Resolvable by `^4` |
| npm | `release.yml` `npm-publish` | `@mikkoparkkola/mcp-gateway@next` | `@latest` |
| Homebrew tap | `release.yml` `homebrew-update` | Skipped — the tap has one stable formula | Formula bumped |
| ghcr, the publisher | `ci.yml` `docker-build` + `docker-manifest` | Publishes `:4.0.0-rc.1` only; `:latest` and `:4.0` withheld. cosign signature and SBOM attestation run on both channels | Also moves `:latest` and `:4.0` |
| ghcr, branch and PR builds | `docker.yml` `build` | Builds, scans and starts the image; pushes nothing on a tag | Same |
| MCP Registry | `ci.yml` `publish-mcp-registry` | Skipped — a discovery surface nobody opts in to | Listed |

One publisher owns every release tag. `ci.yml` builds the index under a provenance-only
`sha-<commit>` tag, signs and attests it by digest, verifies both, and only then copies that
verified digest onto `:4.0.0` — and, for a stable release, `:latest` and `:4.0`. A release tag
therefore never resolves to an image that is not already signed, and the signature over it comes
from `ci.yml` at the pushed tag:

```bash
DIGEST=$(crane digest ghcr.io/mikkoparkkola/mcp-gateway:4.0.0)
: "${DIGEST:?tag did not resolve — a registry error, not an unsigned image}"
REF="ghcr.io/mikkoparkkola/mcp-gateway@$DIGEST"
ID=https://github.com/MikkoParkkola/mcp-gateway/.github/workflows/ci.yml@refs/tags/v4.0.0
ISSUER=https://token.actions.githubusercontent.com
cosign verify --certificate-oidc-issuer "$ISSUER" --certificate-identity "$ID" "$REF" \
  && cosign verify-attestation --type spdxjson \
       --certificate-oidc-issuer "$ISSUER" --certificate-identity "$ID" "$REF" \
  && { echo "verified $REF"; exit 0; }
echo "no publisher identity verifies $REF" >&2; exit 1
```

Resolving the tag is separated from verifying it on purpose: a registry error and an
unsigned image are different failures, and the guard above stops the first from reading as
the second. Verify by digest, not by tag — `:4.0.0` is a mutable pointer, and a signature
is over the digest.

A prerelease runs every gate a final release runs: `security-gate`, `secret-leak-lint`,
clippy, fmt, the test suite, trivy, the OSV scan, the tag/manifest match and the
`release-criteria` job's scope-ledger checks.

One requirement is lifted. On `4.0.0` itself, `check_scope_acceptance.py --publish-check`
exits 1 until every 4.0.0 criterion is met or waived. On a `4.0.0-beta.N` or `4.0.0-rc.N`
(manifest and tag both), it only checks that the ledger is consistent. Any other suffix, such
as `4.0.0-hotfix`, still needs full acceptance. This follows the owner decision of 2026-09-25
to cut a beta before the scope is complete so 3.x users can start testing 4.0; the criteria
still open ship as known gaps in the beta's release notes.

## Staging one

1. Bump `Cargo.toml` to `4.0.0-rc.1` and run `cargo update -p mcp-gateway` so the lockfile
   agrees. The tag/manifest gate fails the run otherwise, in all three workflows — this is
   deliberate: `cargo publish` takes its version from the manifest, not the tag, so a
   mismatch would publish the candidate to crates.io as the final `4.0.0`.
2. Verify locally before pushing anything:
   `python3 scripts/release/check_tag_manifest.py --tag v4.0.0-rc.1` → exit 0, `prerelease`.
3. Commit, tag `v4.0.0-rc.1`, push the tag.
4. Confirm the five stable pointers have **not** moved: the `releases/latest` redirect, the
   npm `latest` dist-tag, the tap formula's version, `ghcr.io/mikkoparkkola/mcp-gateway:latest`
   by digest, and the MCP Registry entry.
5. Observe. Promotion criteria and the observation window are the operator's call and are not
   encoded here; record what was observed against them before step 6.
6. Promote: bump the manifest to `4.0.0`, tag `v4.0.0`, push. The same workflows now take the
   stable path on every surface.

## What this does not close

The mechanism existing and being validated is not the same as exposure having been staged.
D21 stays **OUTSTANDING** until an rc has actually been published and observed; claiming MET
off a workflow edit is the fabrication the gate exists to catch.

The push-before-sign window this section used to describe is closed (#529). `ci.yml`
`docker-manifest` builds the index under a provenance-only `sha-<commit>` tag
(`Create the manifest list under a provenance tag`), signs and attests it by digest,
verifies both, and only then copies that verified digest onto `:VERSION`
(`Publish the release tags (copy the verified index by digest)`). `Assert the release tag
resolves to the signed digest` fails the run if that copy produced a different digest. A
run that fails or is cancelled before promotion therefore leaves no unsigned `:VERSION`
public, only the provenance tag. `docker.yml` pushes nothing on a tag.
