## Highlights

### MCP 2026-07-28, on by default

The gateway serves the newest Model Context Protocol revision, 2026-07-28, alongside
2025-11-25 and earlier, on the same endpoint. Older clients keep the `initialize` handshake
and see no change.

- **Stateless requests.** A 2026 client skips the handshake. It states its revision on each
  `POST /mcp` request, in the `MCP-Protocol-Version` header and in
  `io.modelcontextprotocol/protocolVersion` in the request's `_meta`.
- **`server/discover`** tells a client what the gateway speaks before it calls anything.
- **Mid-call input by retry.** When a backend asks the user a question, the gateway returns
  it as a result, and the client answers by retrying the call. On HTTP this needs a verified
  caller identity; an anonymous caller is refused.
- **`subscriptions/listen`** streams change notifications, scoped to the caller that opened it.
- **Tasks.** `server/discover` advertises the `io.modelcontextprotocol/tasks` extension. A
  long `tools/call` can run as a task that the client polls with `tasks/get` and cancels with
  `tasks/cancel`. Cancelling marks the task cancelled and the gateway stops waiting for its
  result; the backend is not sent a cancellation, so a call it already received may still
  run. A task belongs to the caller that created it, and its handle still resolves after a
  restart within the retention window. In 4.0.0 a task does not accept input responses; the
  rest of the task lifecycle on both routes is still landing (#1530).
- **Idempotency keys** (`io.mcp-gateway/idempotency-key` in `_meta`) stop a retried call from
  running twice. They are optional by default, but creating a task always needs one.
  `server.idempotency_key: required` enforces them on `POST /mcp` and stdio for any other modern
  call to a tool not marked read-only. It does not cover the direct per-backend route
  `POST /mcp/{name}`.

Limits: while the modern protocol is on, the gateway refuses to start when `server.replicas`
declares more than one replica, because each process keeps its own task store. The Helm chart
keeps `server.replicas` equal to `replicaCount`; the gateway cannot detect replicas started any
other way. `key_server.enabled` and `accounts.enabled` force one replica on their own. On
stdio, `server/discover` lists only the
older revisions. `server.modern_protocol: false` turns the modern protocol off.

### Built for teams

- **Each caller sees and reaches only what it was granted.** Every discovery surface
  (tool lists, search, server lists, the direct per-backend route) shows a caller only the
  backends and tools it could invoke. A newly added backend is unreachable until a key is
  granted it, and a key with no `backends` reaches nothing.
- **Per-caller state.** Cached results, idempotent results, backend change notifications and
  `subscriptions/listen` streams are kept per caller.
- **Admins from your identity provider.** A `control_plane.role_mapping` rule with
  `role: admin` makes a single sign-on (SSO) group or user a full gateway admin on every admin
  surface. The mapping is read on every request, so removing the rule revokes admin at once. An
  admin rule that names only an email domain is refused. Proxy headers and mTLS certificates
  never confer admin.
- **OIDC rules bound to an issuer.** Key-server OIDC rules must
  name the issuer, and email and domain rules match only an email the provider has verified.
- **Identity headers need a proven source.** Caller identity headers count only when they
  arrive from a source you configured: listed proxy addresses or Cloudflare Access.
- **A revoked account token is caught on the first refusal.** When a backend answers 401 to a
  managed personal account, the gateway forces one token refresh. A revoked grant turns into a
  reconnect prompt; otherwise the caller is told whether a retry can help.

### An audit trail you can rely on

- With auth on, the tool-call audit log is required, and it fails closed: a failed write
  fails the call instead of letting it through unrecorded.
- Each record says who made the call (credential kind, key fingerprint, verified issuer and
  subject), with its outcome and error code. Refused calls are recorded too.
- Calls on the direct per-backend route `POST /mcp/{name}` write the same record as calls
  through `POST /mcp`.
- Admin actions (admin meta-tool calls and admin-panel changes, control-plane edits included)
  write an `admin_action` record naming who acted. With auth on, an admin meta-tool call is
  refused when its record cannot be written. An admin-panel change is refused when the log is
  already failing; if the write fails after the change ran, the change stands and its response
  is withheld with 503.

### Keys and secrets handled as secrets

- API keys are configured as SHA-256 digests (`mcp-gateway hash-key` makes one), with an
  optional expiry that is enforced. Clients keep their keys.
- `file:/absolute/path` reads a secret from a file wherever `env:NAME` is accepted.
- A secret reference that resolves to nothing stops the load instead of sending an empty
  credential. The one exception is `server.metrics_token`: it logs a warning and `/metrics`
  answers 401 until the token is set and the gateway restarted.
- `/metrics` needs its own scrape token.
- Session ids are always minted by the gateway, and logs carry an 8-hex fingerprint instead
  of the id.

### A gateway that refuses to run unsafely

- The gateway refuses to start, with an error that names the problem, on an unknown config
  key, a config or env file that other users can read (on Unix), or plain HTTP on a network
  address with auth on.
  `server.cleartext_http` declares how the traffic is protected when TLS ends elsewhere.
- On Unix, keys, tokens and credential files that other users can read, and trust files they
  can change, are refused. Windows gets no permission check in 4.0.0.
- Attestation `enforce` (off by default) applies to every forwarded method on the direct
  per-backend route, not only `tools/call`; `initialize`, `ping` and notifications are exempt.

### Also new in 4.0

- **WebSocket backends.** A backend with `ws_url` connects over WebSocket, bounded by the
  backend `timeout`, with in-flight calls failed at once when the socket drops. It speaks the
  legacy handshake only: a `protocol_version` of 2026-07-28 or later on `ws_url` refuses the load.
- **A Helm chart that starts.** The Kubernetes chart installs and serves with its default
  values, runs as the image's own non-root user, and defaults to one replica. Besides a shared
  bearer token and a service mesh, it renders API-key auth (each key's digest in a Secret) and
  OIDC through the key server. Backend secrets come in through `extraEnv`/`envFrom`, which
  refuse `MCP_GATEWAY_*` names, and `persistence` keeps task and control-plane state on a claim.
- **Honest capabilities.** The gateway advertises only the change notifications it actually
  delivers.
- **Clearer failure reporting.** A refusal by the gateway's per-backend rate limiter (`failsafe.rate_limit`) is reported as
  `RateLimited`, not as an open circuit breaker, and counted by
  `mcp_backend_rate_limited_total{backend}`. A backend that fails to start counts toward its
  circuit breaker on every transport. `/health` reports an open circuit breaker.
- **Error results are never served from a response cache.**

## Breaking changes

Several 4.0 changes make a 3.x config refuse to start instead of running on settings the
gateway no longer trusts. No migration edits your `gateway.yaml`, and the first start after the
upgrade prints a one-time notice of the changes that need your attention. The full list, with
the action each change needs and how to roll back to 3.x, is
[`docs/UPGRADING-4.0.md`](../UPGRADING-4.0.md). By area, with its item numbers:
