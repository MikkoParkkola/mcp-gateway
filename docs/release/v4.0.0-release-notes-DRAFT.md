## Breaking changes

Seven, ordered by how likely they are to bite an existing install.

1. **Protocol `2024-10-07` is no longer advertised.** `SUPPORTED_VERSIONS` is
   2025-11-25 / 2025-06-18 / 2025-03-26 / 2024-11-05. **Action needed: none for
   conforming clients.** `2024-10-07` was never a real MCP revision, and nothing is
   rejected that was previously accepted: `negotiate_version("2024-10-07")` returns
   `"2025-11-25"` — the same fallback any unrecognized version string gets, before and
   after this release. Only what `server/discover` *claims* changed. See
   `docs/UPGRADING-4.0.md` §3. (**V** — `src/protocol/mod.rs:54`,
   `tests/integration.rs:26,37`)
2. **Response caching now requires an identifiable protocol revision.** The cache is
   keyed by the revision a request was served under, and a request whose revision cannot
   be identified is not cached at all — the skip is deliberate and fail-closed. A modern
   request carries its revision in the body; a legacy request needs the
   `MCP-Protocol-Version` header or a session that completed `initialize`. **Action
   needed: send the header on stateless requests, or reuse an initialized session.** A
   bare stateless `POST` that does neither loses caching entirely and puts that traffic
   on your backends, where the default rate limit (100 rps, burst 50) then applies to
   calls that never reached it before. Nothing errors; throughput and backend load move.
   3.x cached such requests, which meant one entry could be served across revisions. See
   `docs/UPGRADING-4.0.md` §6. (**V** — `src/protocol/meta.rs:514,523,550`)
3. **OAuth credentials are keyed by issuer.** 3.x tokens are not migrated: expect one
   re-authentication per OAuth backend on first use. No config change required. (**I**)
4. **A malformed line in an `env_files` file now fails startup** (previously skipped
   silently). The error names the offending line. (**I**)
5. **Error budgets / circuit breaker no longer count HTTP 429 and equivalents**
   (`too many requests`, `rate limit`, `RESOURCE_EXHAUSTED`, `throttled`).
   Suppressions are counted by `mcp_error_budget_suppressed_total` (GH #475). If you
   alert on budget samples, your signal changes. (**I**)
6. **One licence: PolyForm Noncommercial 1.0.0 across the whole repository.** The MIT
   core carve-out and the MIT core allowlist file are removed (ADR-013);
   `LICENSE-EE.md` is marked SUPERSEDED. Commercial use now requires a commercial
   licence. (**I**)
7. **`server.modern_protocol` defaults to `true`** — the 2026-07-28 stateless/modern
   path is served by default. Note `2026-07-28` is deliberately *absent* from
   `SUPPORTED_VERSIONS`: it is reached per-request via `_meta`, not via `initialize`.
   Opt out with `server.modern_protocol: false`. (**V** —
   `src/gateway/router/handlers.rs`, `MODERN_VERSIONS` gate)

## Upgrading from 3.5.x

Four items, the same four the binary prints on the first `serve` after the upgrade.
Only the second one can refuse a start; the rest are advisory.

1. **Re-authenticate each OAuth backend once.** Credentials are now keyed by issuer
   and 3.x tokens are not migrated. No config change.
2. **Check your `env_files`.** A malformed line now fails startup instead of being
   skipped; the error names the line. Fix or remove it before upgrading a running
   install.
3. **Protocol `2024-10-07`: no action.** It is no longer advertised, but it is still
   negotiated exactly as before — to the `2025-11-25` fallback. The startup notice's
   advice to upgrade such a client is advisory only; see `docs/UPGRADING-4.0.md` §3.
4. **Re-point rate-limit alerting.** HTTP 429 and equivalents no longer consume the
   error budget or trip the circuit breaker; watch
   `mcp_error_budget_suppressed_total` instead.

If you need the pre-4.0 stateless behaviour, set `server.modern_protocol: false`.

### MIK-3274.RANKING.3 — ships UNMET: the ranking baseline covers selection quality only

The frozen discovery baseline floors **one** family, selection quality: five floors at
section 4 of the freeze document, measured and enforced in-window. Three families named
by the criterion are **unfloored in 4.0.0** — discovery turns, invalid invocations, and
total completed-task tokens. Nothing in this release constrains them, and no number in
these notes should be read as doing so.

This is a decision, not an oversight. A rewrite of the criterion and a descope were both
declined; the three unmeasured families carry to a release where a fresh freeze window
can be opened. That window must open **before** the next change to `src/ranking/`, not
after — sequencing the corpus behind the implementation is exactly what cost the measure
here.

### The latency claim is not end-to-end

Release material must not describe 4.0.0's performance as an end-to-end latency
result, because no such measurement exists at any version of this repository.

What was measured: 56 micro-benchmarks on the `bench-host` host, 2026-09-03, comparing
`v3.5.0` (`32f135a6`) against `5c29494a` over the 47 cases the two versions share.
The worst shared regression is `session_sandbox/check_tool_denied` at +6.07% by
criterion's own comparison, against a 10% bound; the largest movement in the set
is a 67% improvement. Full report: `docs/requirements/RELEASE-4.0.0-performance.md`.

What was not measured: a P50 or a P99. The repository's only bench target,
`benches/gateway_benchmarks.rs`, measures in-process component work — no wire, no
backend, no queue — so there is no latency distribution to take percentiles from.
A bootstrap confidence interval is not a P99.

The release owner accepted this residual on 2026-09-16 on the headroom argument,
with the carrier named above. A client-to-backend harness that would settle the
criterion at its own wording was considered for 4.0.0 and deferred to 4.1.0.
Quote the micro-benchmark result, the host and the date; never the word
"end-to-end".
