## 1. Absence claim re-verification (step 1)

Commands run against this commit, `src/ranking/` on this branch (identical
to `main` at `8ab4bc5d` -- `src/ranking/` has not changed there):

```
$ rg -ni "levenshtein|damerau|jaro|edit_distance|trigram|ngram|fuzzy" src/ranking/
(no output -- zero matches)

$ rg -n "split_whitespace" src/ranking/
src/ranking/mod.rs:373:        let words: Vec<&str> = query_lower.split_whitespace().collect();
src/ranking/mod.rs:580:    let words: Vec<&str> = query_lower.split_whitespace().collect();
src/ranking/scoring.rs:188:/// `words` must be `query.split_whitespace().collect()`; passed in to avoid

$ rg -c "contains" src/ranking/scoring.rs
16

$ rg -i "levenshtein|fuzzy|edit.distance|strsim|jaro" Cargo.toml
(no output -- zero matches)
```

`mod.rs:373` and `:580` split the query into whitespace-delimited tokens
purely so multi-word queries can be matched token-by-token against
`.contains()` substrings and `[keywords: ...]`/`[schema: ...]` tags (see
`mod.rs:360-368` doc comment on `rank()`); this is tokenization for exact
substring matching, not word-boundary regex matching or fuzzy tolerance.
The 16 `contains` hits in `scoring.rs` are substring matching plus a
synonym table (`text_contains_with_synonyms`, `scoring.rs:109-124`); two of
the 16 are doc-comment prose, the rest are `.contains(` calls.

**Verdict: absence claim holds.** No edit-distance, trigram/n-gram, or
regex word-boundary matching exists anywhere in `src/ranking/`, and no
fuzzy-matching crate is a dependency. The current ranker is
substring-`contains` + a synonym table. The `RANKING.3` ordering window
(threshold freeze before fuzzy ranking lands) is open.

## 2. Held-out corpus

`benchmarks/ranking-baseline/corpus.json`, generated by
`benchmarks/ranking-baseline/gen_corpus.py` from `capabilities/*.yaml`
(119 production capabilities, `capabilities/examples/` excluded per
`capabilities/README.md`'s own stated count).

114 queries via six mechanical rules, each keyed to a `derivation` field on
every case (full detail is per-case in `corpus.json`, not restated here):

| rule | n | how derived |
|---|---|---|
| `name_phrase` | 30 | tool name, `_` -> space, every 4th tool alphabetically |
| `description_lead` | 24 | first 5 words of the YAML `description`, tools at index%5==2 |
| `tag_query` | 20 | a single `metadata.tags` entry typed verbatim, every 3rd tag alphabetically |
| `abbreviation` | 15 | tags <=4 alphabetic chars (tts, stt, ocr, uuid, waf, jql, ...) -- the acronyms a user actually types |
| `shared_prefix_ambiguous` | 13 | leading `name` segment shared by >=3 tools (gmail, video, linear, ...), typed alone |
| `typo` | 12 | one adjacent-letter transposition on the first word of a `name_phrase` tool |

No query was chosen, tuned, or filtered by running it against the ranker
first -- the generator only reads `capabilities/*.yaml`. Re-running
`gen_corpus.py` against an unchanged `capabilities/` tree reproduces
`corpus.json` byte-for-byte.

Gold labels (`gold_tools`) are the tool(s) that mechanically produced the
query; for `tag_query`, `abbreviation`, and `shared_prefix_ambiguous`,
multiple tools legitimately share a query and all are listed as acceptable
gold -- this is real corpus-derived ambiguity, not injected.

## 3. Measured quantities

Harness: `tests/mik_3274_ranking_3_baseline.rs` (`cargo test --test
mik_3274_ranking_3_baseline`). It builds the full 119-tool candidate pool
via the production `CapabilityLoader` (server label `"fulcrum"`, neutral
`RankingSignals::default()` throughout so ranking is driven by text
relevance alone), calls the unmodified `SearchRanker::rank()` for every
corpus query, and records where the best-ranked gold tool landed. Full
per-case output is in `benchmarks/ranking-baseline/results.json`.

### Selection quality -- MEASURED

| metric | value |
|---|---|
| top1_hit_rate (overall) | 84/114 = 0.736842 |
| top3_hit_rate (overall) | 98/114 = 0.859649 |
| top5_hit_rate (overall) | 0.904 (103/114) |
| mean reciprocal rank (overall) | 0.807 |

By derivation (weakest first):

| derivation | n | top1 | top3 | MRR |
|---|---|---|---|---|
| `typo` | 12 | 0.333 | 0.583 | 0.505 |
| `tag_query` | 20 | 0.600 | 0.600 | 0.633 |
| `name_phrase` | 30 | 0.700 | 0.967 | 0.829 |
| `abbreviation` | 15 | 0.800 | 0.867 | 0.828 |
| `shared_prefix_ambiguous` | 13 | 0.923 | 1.000 | 0.962 |
| `description_lead` | 24 | 0.958 | 1.000 | 0.979 |

`typo` is the weakest category by a wide margin, consistent with step 1:
there is no edit-distance tolerance, so a one-letter transposition is
scored purely as a failed substring match unless the untransposed
remainder of the query still happens to hit. `tag_query` is next weakest --
several tags are shared across many tools (e.g. `google`, `workspace`),
so "the" gold tool is frequently outranked by an equally-valid sibling
under plain substring scoring, which is the ambiguity this rule exists to
surface, not a ranker bug.

### Discovery turns, invalid invocations, total completed-task tokens -- NOT MEASURABLE from this corpus alone

These three are properties of an *agent* working a *task* across a
multi-turn tool-use loop (search, maybe reformulate, invoke, maybe retry
after an error, complete). A static (query -> ranked list) corpus has no
loop, no reformulation behaviour, no tool execution, and no token
accounting -- it cannot produce these numbers without inventing agent
behaviour that was never observed.

What a real measurement needs, concretely:

- A live-agent trial harness that, for each corpus query (or a task built
  around it), runs an actual agent against the real MCP gateway/capability
  set and records: number of search/reformulation turns before a correct
  tool is selected (**discovery turns**); count of tool invocations against
  a tool outside `gold_tools` or that fails schema validation
  (**invalid invocations**); and total input+output tokens for trials that
  reach task completion (**total completed-task tokens**).
- `benchmarks/live_agent_tool_selection.py` (existing, MIK-6977) is the
  closest in-repo precedent -- it already runs real Codex/MCP trials and
  records `tool_calls`, `extra_turns`, `input_tokens`/`output_tokens`/
  `total_tokens`, and `selection_correct` per trial. It is not a drop-in
  fit: its candidates are synthetic (`archive_case_NNN`) and its task is
  pure selection, not completion. It would need adapting to run against
  the real 119-tool capability set with this ticket's 114 held-out queries
  as prompts, and to define "task completion" (not just "tool selected")
  for invalid-invocation and token accounting to mean anything.
- Running it costs live LLM API calls and wall-clock time per trial x
  114 queries x however many repeats are needed for stable statistics --
  explicitly out of scope for the baseline-and-freeze half of this ticket.

No number is given for these three. Do not treat their absence as zero.

## 4. Proposed thresholds

Frozen **before** `RANKING.1` (fuzzy ranking) lands, per the criterion's
ordering clause. Two tiers: **floor** (fuzzy ranking must not regress
below current baseline) and **target** (what fuzzy ranking is supposed to
buy, informed by which categories are weakest today).

Comparison rounding: a floor is written to 3 decimals **truncated toward
zero** from the exact measured fraction (never rounded to nearest), so the
frozen baseline itself always clears its own floor. Compare candidate
values to the exact fraction, not the truncated display value, when in doubt.

| metric | floor (= measured baseline, truncated down) | target |
|---|---|---|
| overall top1_hit_rate | >= 84/114 (0.736) | >= 0.85 |
| overall top3_hit_rate | >= 98/114 (0.859) | >= 0.95 |
| overall mean reciprocal rank | >= 0.807 (0.8071325...) | >= 0.90 |
| `typo` category top1_hit_rate | >= 4/12 (0.333) | >= 0.70 (this is what edit-distance tolerance is *for*) |
| `tag_query` category top1_hit_rate | >= 12/20 (0.600) | >= 0.75 |
| discovery turns | not set -- baseline not measured (see section 3) | to be set once a live-agent baseline run exists, before `RANKING.1` lands |
| invalid invocations | not set -- baseline not measured (see section 3) | to be set once a live-agent baseline run exists, before `RANKING.1` lands |
| total completed-task tokens | not set -- baseline not measured (see section 3) | to be set once a live-agent baseline run exists, before `RANKING.1` lands |

The floor values are the measured baseline (truncated toward zero per the
rounding convention above, so the baseline always clears its own floor) --
clearing them is a non-regression bar, not an aspiration. Target values are judgment calls
informed by the baseline's weakest categories (stated as such, not
measured); they are for the `RANKING.1` implementer to hit, not this
ticket's deliverable.
