---
change: API keys accept three optional rotation fields, principal, previous_key_sha256 and previous_expires_at
action: None unless you downgrade; remove the three fields before downgrading below 4.0.0
---
## API key rotation fields

**Startup:** no notice; an existing config loads unchanged

An `auth.api_keys[]` entry can carry `previous_key_sha256` and `previous_expires_at`, so a rotated key accepts its old secret until the grace ends, and `principal`, so the key keeps its identity (and its sessions, grants and tasks) under the new digest. The gateway cannot pick these values itself: they record a rotation, which only an operator decides, and gateway.yaml is the only state that could hold them. Key rotation writes them; you set them by hand only to rotate without the UI or to recover. A key without them behaves exactly as before.

- What you lose: nothing. No configuration that loaded before is refused now: two keys sharing a digest, or a key equal to the bearer token, were already refused as sharing a principal.
- What you gain: rotating a key without breaking the agent that holds it, and without orphaning what the key owns.
- What you do: nothing, unless you downgrade.

Before downgrading below 4.0.0, remove `principal`, `previous_key_sha256` and `previous_expires_at` from every key: an older release refuses them as keys nothing reads. The key's secret keeps working, but a key that was ever rotated then takes its identity from its current digest again, so the sessions, grants and tasks it owned under its `principal` are no longer its own.

For code that embeds the gateway as a library: `ResolvedAuthConfig::api_keys` is no longer a public field. Read the list through `ResolvedAuthConfig::api_keys()`, which returns it read-only; nothing outside the gateway can replace it any more.
