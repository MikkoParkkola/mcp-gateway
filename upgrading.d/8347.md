## An unconfirmed upstream cancel is retried; task records may be version 8

**Startup:** no notice

**What changes.** When an owner cancels a recoverable task, the gateway sends the upstream job one `tasks/cancel`. If the peer did not answer (a timeout, a backend that was not ready, or a login in progress), it was never sent again and the job kept running. Now the cancel stays pending and is retried. It is retried when that backend next starts successfully, and by the expiry sweep. A cancel that cannot be delivered stops after 6 failed sends or 24 hours, and an ERROR log names the backend and the task handle.

**Upgrading.** Nothing to do, and nothing is migrated.
- Existing task records are read as they are. A row a 4.0.0 pre-release already claimed (version 7) counts as sent, and is not sent again.
- Only a cancel claimed from now on writes a version 8 record.
- 3.x has no task store and is not affected.

**Rolling back.** A 4.0.0 pre-release reads records up to version 7 and refuses to open a task store holding a version 8 record, so that gateway does not start.
- Back up `tasks.store_dir` (default `~/.mcp-gateway/tasks`) before upgrading, and restore that backup to roll back.
- Clearing the store to start a pre-release abandons every task and every task idempotency key. It is not a migration.
