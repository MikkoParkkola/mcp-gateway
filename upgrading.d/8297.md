## A lost question and its idempotency key

**Startup:** no notice

**What it is.** A keyed call can come back with a question (the backend asks the user something before it finishes). If that answer never reaches the client (a dropped connection, a stream read halfway), the client may retry under the same key. In 4.0 the gateway answers that retry in one of three ways:

1. **A question nested in a playbook result** (`gateway_run_playbook`, HTTP or stdio) is replayed under its key. The playbook's earlier steps already ran, so replaying is what keeps the call from running them twice.
2. **A top-level question on `/mcp`** (`gateway_invoke`) **or stdio** is not kept. A same-key retry is refused with 409 "Secured execution result is unavailable", and the backend is not called again. The key stays refused for up to 24 hours. A retry under a fresh key reaches the backend again and gets the question again.
3. **A top-level question on the direct route `/mcp/{name}`** releases the key, so a same-key retry reaches the backend again. This is deliberate: the direct route does not settle a key on a question.

**What to watch for.** In cases 2 (with a fresh key) and 3, the backend call runs again. A backend can take side effects before it asks its question, and those would then happen twice. On the direct route, do not treat the idempotency key as protection for a call that asks a question.

**What you do.** Nothing to upgrade. A client that retries lost questions should handle the 409 on `/mcp` and stdio by retrying under a fresh key, and should only retry calls whose backend is safe to run again.

**Later.** 4.1.0 is planned to replay a top-level question under its key as well (MIK-8622). These outcomes will then change.
