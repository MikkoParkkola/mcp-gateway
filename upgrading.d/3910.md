## A keyed call needs an execution principal before it reaches a backend

**Startup:** no notice

**What you lose.** A keyed call (one carrying an idempotency key) from a caller with no
execution principal is refused `-32003` "A verified execution principal is required" with
HTTP 400 before the gateway looks the backend up. On `/mcp/{name}`, such a call to a backend
that does not exist now answers `-32003` instead of `404 -32001`, and one whose backend is down
answers `-32003` instead of a `500` transport error. With authentication on, a keyed task
submit from a caller with no principal (for example an anonymous caller on a public `/mcp`)
now answers `-32003` instead of `-32602` "no such task"; no task is created either way.

**What stays.** Auth-off gateways keep pooled anonymous task ownership: an anonymous keyed task
submit there is still admitted under the shared anonymous owner. Sync keyed calls without a
principal were already refused there; they are now refused earlier.

**What you gain.** An anonymous keyed call no longer makes the gateway list a backend, read a
tool schema or exchange a token for a call it will refuse, and its answer no longer tells the
caller whether a backend exists or is up. A call refused because its backend needs identity
propagation and the caller has none still answers as a missing name (`-32601`), and the server
logs a WARN naming the backend, at most once per backend and caller key every 10 minutes while
fewer than 1024 such pairs are tracked.

**What you do.** Give callers that send idempotency keys a principal: an API key, a
trusted-proxy subject (`security.caller_identity`), an OIDC identity or an agent token. Keep the
key; it is what makes a retry safe. For a plain keyed call with no task, dropping the key
restores the old unkeyed path (unless `server.idempotency_key: required`), at the cost of retry
safety. Dropping the key does not help a task submit: task creation refuses a submit with no
key (`-32602` "task creation requires an idempotency key").
