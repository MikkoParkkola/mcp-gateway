## API keys apply on reload

**Startup:** no notice

**What changes.** Adding, removing, editing or expiring a key under `auth.api_keys` and reloading
the config changes the next request: a new key works, a removed or expired one is refused, and an
edited key's scope, admin standing, rate limit and expiry apply. A request already in flight keeps
the table it started with. A dashboard link, sign-in code or session opened with an API key ends at
its next use once a reload removes that key, demotes it from admin, moves its expiry into the past
or replaces its secret; one opened with the bearer token is unaffected. A task created with an API key
is re-checked against the key table when it first dispatches and when an input round continues
it: if a reload removed, expired, re-issued or demoted the key, it is refused before anything
reaches the backend, and if the reload narrowed the key, the narrower scope judges it. Usage already spent under a key's rate limit carries over. Before 4.0.0
a key edit waited for a restart.

**Still restart-only.** Every other `auth` setting (`enabled`, `single_user`, `public_paths`,
`bearer_token`, OIDC, `client_circuit_breaker`) still applies only at a restart, except
`dashboard_session`, whose limits already applied on reload and still do; a reload that
changes one of them together with a key applies the key only. The reload report still lists
`auth` as needing a restart after any `auth` edit, a key-only edit included: the key has applied,
and the report does not yet tell the two apart.

**Refused reloads.** The whole reload is refused, and the running keys keep working, when the new
key list:

- would make the gateway multi-user, or single-user again, judged on the running `enabled`,
  `single_user`, bearer and OIDC settings. Multi-user status is fixed at startup, so restart to
  apply such an edit;
- gives a key the same digest or principal as the running bearer token, including one generated
  for `bearer_token: auto`;
- names an `env:` or `file:` secret reference that does not resolve. This is new for a reload on
  stdio as well: before 4.0.0 a stdio reload never read `auth.api_keys`.
