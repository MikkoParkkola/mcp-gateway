## Admins create API keys through the web UI's API, and the key list carries its revision

**Startup:** no notice

What you gain: an admin adds a key through `POST /ui/api/keys` without
editing `gateway.yaml` by hand. The bundled web UI's screen for it ships
separately; this release adds the API. The secret is returned once, with
`Cache-Control: no-store`, and only its digest reaches the file. Every create
needs the audit log: the write is recorded there before the file changes,
naming who created which key, and with no audit log the create is refused.

What changes:

- `POST /ui/api/keys` takes `name`, `backends`, optional `allowed_tools`,
  `denied_tools`, `admin`, `rate_limit` and `expires_at`, and the `revision`
  of the list it read. An `expires_at` is kept to the whole second, as
  `gateway.yaml` stores it, and must be later than now. It answers 201 with
  the secret, or a fixed refusal that writes nothing: no `gateway.yaml`, a
  `gateway.yaml` that does not load or reload switched off, a name already in
  use, a revision that is no longer current, an invalid field, a key that
  would turn the gateway multi-user (restart required), a key list the
  gateway cannot edit in place (the answer gives the `mcp-gateway hash-key`
  steps to add it by hand), or an audit log that cannot record the write. A
  refusal names a field at most, never a value.
- When the gateway cannot tell whether the write happened, the create answers
  500 `state_uncertain` and returns no secret. Read `GET /ui/api/keys` before
  creating the key again. If the key is listed, its secret was never shown,
  so it cannot be used: remove it from `gateway.yaml`, reload, then create it
  again.
- `GET /ui/api/keys` answers `{revision, keys}`. Each entry lists the file's
  key in file order with its `last_used` (empty after a restart, until a call
  matches) and whether it is `live`. No entry carries a secret, digest or
  principal. With no `gateway.yaml`, or one that does not load, it lists the
  running gateway's keys with `revision: null` and `file: absent` or
  `file: unloadable`, and every create is refused.

What you keep: a key you wrote by hand in `gateway.yaml` loads and reloads as
before. The route is private to the bundled web UI and was never released in
its earlier shape, so there is nothing to migrate for a released client.
