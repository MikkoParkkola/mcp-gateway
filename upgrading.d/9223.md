## The web UI creates API keys, and the key list carries its revision

**Startup:** no notice

What you gain: an admin adds a key from the web UI without editing
`gateway.yaml` by hand. The secret is shown once, with `Cache-Control: no-store`,
and only its digest reaches the file. The write is recorded in the audit log
before the file changes, naming who created which key; with no audit log it
is refused where the gateway requires one.

What changes:

- `POST /ui/api/keys` takes `name`, `backends`, optional `allowed_tools`,
  `denied_tools`, `admin`, `rate_limit` and `expires_at`, and the `revision`
  of the list it read. It answers 201 with the secret, or a fixed refusal: a
  name already in use, a revision that is no longer current, a key that would
  turn the gateway multi-user (restart required), or an audit log that cannot
  record the write. A refusal names a field at most, never a value.
- `GET /ui/api/keys` answers `{revision, keys}`. Each entry lists the file's
  key in file order with its `last_used` (empty after a restart, until a call
  matches) and whether it is `live`. No entry carries a secret, digest or
  principal.

What you keep: a key you wrote by hand in `gateway.yaml` loads and reloads as
before. The route is private to the bundled web UI and was never released in
its earlier shape, so there is nothing to migrate for a released client.
