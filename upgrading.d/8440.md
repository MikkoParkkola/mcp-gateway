## A stored result is served only under the binding that produced it

**Startup:** no notice

What you gain: output stored for one account or credential is never handed to
a request that would run under another one.

- On the direct route `/mcp/{backend}`, a passthrough backend's keyed retry
  that forwards a different credential than the first call did is refused
  (-32603, HTTP 200), instead of being served the first credential's output.
  The same credential is still served the stored result. The call is not run a
  second time: the key keeps its one execution. To run it under the other
  credential, send it with a new idempotency key. A retry that forwards no
  credential keeps its existing refusal.
- If a backend's `account:` (applied at a restart) or a capability's
  `auth.account` (applied on reload) now names a different account, or that
  account's descriptor changed (issuer, resource, client, scopes or mode),
  then a keyed retry, a repeated task call and a task read of a result
  produced before the change are refused with -32603. Nothing is sent.
  One exception: a backend whose `account:` names a `mode: shared`
  descriptor runs under the gateway's static credential, the same for every
  caller, and records no account. Moving it from one shared descriptor to
  another is not refused, as changing any static credential is not. A
  capability's shared `auth.account` is recorded, and that change is refused.

What changes for stored tasks:

- A task row written by an earlier 4.0 beta records no binding. Its stored
  backend output is refused with an error that says the result predates
  credential binding. The row and its idempotency key stay held, so the call
  is never run again under that key. Re-run it with a new key.
- Every task row this release creates is written at a new record version
  (9), from creation on, so the first task created after the upgrade sets the
  rollback boundary. A row a beta wrote keeps its old version, and its
  unrecorded status, whatever this release later does to it.

**Rollback:** an earlier 4.0 release refuses to open a task store that holds
a version-9 row, as it refuses the version 5 to 8 rows described in the 4.0
guide's Rollback paragraph, so an HTTP gateway does not start. A 4.0 beta.3
stdio gateway falls back to serving without its task store, whether it finds
the current store or the backup made below. In that mode a task-augmented call
runs live again, so a completed task call can run twice: that fallback is not
a way around these steps. Earlier betas keep no stdio task store, and 3.x has
none. Rolling back from this release therefore requires clearing the stored
task results first.

Clearing abandons every stored task and every task idempotency key. The
restart also drops the idempotency keys of synchronous calls, which are held
in memory only. After the rollback, a call repeated with an old key runs
again, external effects included. In order:

1. Stop the clients that send keyed calls, task calls and synchronous calls
   alike, or make sure none of them retries a call it sent before the
   rollback. A queued or retried pre-rollback call is exactly the call that
   would run twice.
2. Let running tasks settle (`tasks/get` shows each one finished or
   cancelled), or record which ones are still running, so you can reconcile
   their effects by hand.
3. Stop every gateway that writes under `tasks.store_dir` (default
   `~/.mcp-gateway/tasks`; a beta.3 stdio gateway uses `<tasks.store_dir>/stdio`
   inside it).
4. Move the directory aside, keeping it as a backup rather than deleting it.
   Use your configured `tasks.store_dir` in place of the default. The move
   refuses to run if the backup path already exists, because `mv` onto an
   existing directory would nest the store inside it:

   ```sh
   test ! -e ~/.mcp-gateway/tasks.4.0.0-backup && mv ~/.mcp-gateway/tasks ~/.mcp-gateway/tasks.4.0.0-backup
   ```

5. Start the older gateway. It creates an empty task store. Let clients send
   new calls only now.

Why a wipe and not a migration: a version-9 row records the account or
credential each result ran under, and an older gateway cannot judge that
record. If it kept the row, it would serve the result to whoever asks under
the key. Do not delete individual rows: a removed row frees its key, and a
retry could repeat a completed write.

**Returning to this release** after a rollback: the backup holds the task
idempotency keys from before the rollback, and the older gateway's own store
holds the keys from after it. Neither store knows the other's keys. Fence
clients as in step 1 and stop every gateway first. Then:

- If the older gateway accepted no task work, move its store aside and then
  restore the backup onto the freed path. Each move refuses to run if its
  destination exists:

  ```sh
  test ! -e ~/.mcp-gateway/tasks.rollback-interim && mv ~/.mcp-gateway/tasks ~/.mcp-gateway/tasks.rollback-interim
  test ! -e ~/.mcp-gateway/tasks && mv ~/.mcp-gateway/tasks.4.0.0-backup ~/.mcp-gateway/tasks
  ```

- If the older gateway did accept task work, do not restore either store
  over the other. Keep both directories and reconcile those tasks' effects
  before any of their calls is sent again.

Not covered by a full gateway-restart test: the restart path is pinned by a
task-store reopen (the binding is read back from the reopened store) and by
a backend swap under a running gateway.
