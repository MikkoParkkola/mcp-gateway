## A settings save is audited before and after

**Startup:** no notice

- What changes: before a web UI settings save writes gateway.yaml, it appends an intent record to the audit log: who saved, the file revision it started from, and the fields it changes. With auth on, a save whose intent cannot be written is refused and nothing is written.
- The outcome: the save's admin action record carries `save_outcome` (`applied`, `unchanged`, `refused`, `stale`, `rolled_back` or `indeterminate`) and the same intent id. An intent with no admin-action record means the write was not confirmed: the gateway stopped between the two, so read gateway.yaml to see which bytes stand.
- Not audited while auth is off: with auth off and no audit log open, a save proceeds without an intent record, and its answer says so with the notice `NOT_AUDITED`.
- New answer member: a saved answer always carries a `notices` list, empty when there is nothing to say; a refused save's answer does not. `OUTSIDE_CHANGE_APPLIED` means the save changed no bytes itself but its reload loaded edits someone made to gateway.yaml outside the UI; such a save is not reported as `unchanged`.
- Turning auth on: a save that turns auth on from an auth-off gateway is refused with 409 `AUDIT_LOG_REQUIRED`, nothing written, unless the audit log the next start opens (`security.transparency_log`) is enabled and its path is writable. The check reads permissions only and creates nothing; off Unix it always allows, and the next start's own open refuses an unwritable log there.
