## The request firewall checks stdio calls before admitting them

**Startup:** no notice

What you gain: a stdio call meets the same request firewall an HTTP call
does, at the same point: before any task, idempotency key or lease is taken.

What changes:

- The content scan (on by default: `security.firewall.enabled` and
  `scan_requests`) already refused blocked arguments on stdio, but only at
  dispatch, after the call was admitted. It now refuses them first, with the
  codes HTTP uses: `-32600` "Firewall blocked: ...", or `-32002` "Anomaly
  detection blocked: ..." for an anomaly block. A refused task call over
  stdio no longer leaves a failed task behind. With
  `security.firewall.audit_log` set, each stdio call now also writes a
  request audit row.
- Three per-caller controls that never ran on stdio now do, each only where
  you configured it. All stdio calls of one process count as one caller,
  named `stdio`:
  - anomaly detection (`security.firewall.anomaly_detection`) scores stdio
    call sequences and can refuse (`-32002`);
  - the tenant guard (`security.firewall.tenant_guard`, off by default)
    checks the tenants a stdio call names;
  - the call budget (`security.firewall.budget`) counts stdio calls.

With those three unset, the only change is that refusals come earlier.

What to do:

- Nothing, if none of the three controls is configured.
- Otherwise, review the thresholds you set for HTTP callers: a stdio
  process now spends the same budget and builds the same anomaly history,
  as one caller.
