## A key's backend list bounds Activity and status in the web UI

**Startup:** no notice, a log warning per admin key whose `backends` names some backends but not `"*"`

What you gain: Activity and status answer a backend-scoped key the way the gateway
already does on `/mcp`. A key limited to `alpha` no longer reads `beta`'s
calls in Activity or learns from the status counts how many backends exist,
whatever role its identity maps to.

What you keep: unscoped keys (`backends: ["*"]`), the static bearer and the
dashboard session read everything they read before. An admin key with
`backends: []` stays a UI-wide admin that calls no backend (see the item on
keys with no `backends`).

What changes:

- Activity list, export and receipts show a scoped key only calls on its
  backends, intersected with its role: an Auditor or Admin role reads all of
  them, a Developer its own. Grant and policy changes and admin actions are
  gateway-wide, so a scoped key sees none of them. A receipt it may not read
  answers as one that does not exist. Use an unscoped key for the full audit
  trail.
- Status counts (`server_count`, `healthy_count`, `degraded_count`) count only
  the key's backends. The full status view, with every server row, needs an
  unscoped admin credential.
- An admin key whose `backends` names some backends reads only them in
  Activity, status and the control-plane snapshot's backend list. It can no
  longer mint a dashboard link (a session is unscoped), and a session it minted ends on the reload that narrows it. The
  gateway logs one warning per such key at each load, naming it. If the key
  is meant to administer the whole gateway, set `backends: ["*"]`.
- A scoped key's control-plane snapshot (`/ui/api/control-plane`) shows no
  identity grants, local policies or store audit events, whatever its role:
  each is gateway-wide. Its decision queue holds no grant or policy item, and
  its `coverage.grants`, `coverage.policies` and `coverage.audit_events` flags
  read false. The shadow radar is not run for it: `shadow_radar.scan_status`
  is `"out_of_scope"`, a new value for `control_plane.api.v1` consumers, and
  every radar count is zero. The web UI shows "Outside your backend scope".
  Its `authorizations.read_all_principals` reads denied with reason code
  `CONTROL_BACKEND_SCOPE`, since it is shown no other principal's rows.
- The live status stream (`/ui/api/stream`) follows the same scope. A
  scoped key, admin or not, gets status counts of its own backends only, and
  never the full view. Its stream sends no status update when only backends
  outside its scope change, and the status part of its event ids counts the
  updates it was sent, so it no longer moves with changes elsewhere. A reload
  that changes the key's backend list closes its stream; the browser
  reconnects and is judged afresh. Reordering or repeating the same backends
  is no change and keeps the stream open.
