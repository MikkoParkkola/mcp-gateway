## A key's backend list bounds what it reads in the web UI

**Startup:** no notice, a log warning per admin key whose `backends` names some backends but not `"*"`

What you gain: the web UI answers a backend-scoped key the way the gateway
already does on `/mcp`. A key limited to `alpha` no longer reads `beta`'s
calls in Activity or learns from the status counts how many backends exist,
whatever role its identity maps to.

What you keep: unscoped keys (`backends: ["*"]`), the static bearer and the
dashboard session read everything they read before. An admin key with
`backends: []` stays a UI-wide admin that calls no backend (see the item on
keys with no `backends`).

What changes:

- Activity list, export and receipts show a scoped key only calls on its
  backends, intersected with its role: an Auditor or Admin role reads all of
  them, a Developer its own. Grant and policy changes and admin actions are
  gateway-wide, so a scoped key sees none of them. A receipt it may not read
  answers as one that does not exist. Use an unscoped key for the full audit
  trail.
- Status counts (`server_count`, `healthy_count`, `degraded_count`) count only
  the key's backends. The full status view, with every server row, needs an
  unscoped admin credential.
- An admin key whose `backends` names some backends reads only them in
  the web UI. It can no longer mint a dashboard link (a session is
  unscoped), and a session it minted ends on the reload that narrows it. The
  gateway logs one warning per such key at each load, naming it. If the key
  is meant to administer the whole gateway, set `backends: ["*"]`.
