## Reloads wait for a config write; a crashed write is undone

**Startup:** no notice, unless a replace journal is pending beside gateway.yaml and cannot be resolved: then the gateway does not start, and the error names the journal and the step

**What changes.** A reload now takes the config lock (the `.gateway.yaml.lock` file beside the
config) after the reload lock, so it never loads a file mid-way through a write that is about to
be undone. A lock another process holds past the reload's wait makes that reload skip; the next
change to the file retries it, and the log says which lock was held.

**Read-only and root-owned config directories.** Where the lock file cannot be created because the
filesystem is read-only (a Kubernetes ConfigMap or Secret mount) or this account cannot write the
directory (a root-owned `/etc` config under an unprivileged gateway), reloads read the file
without the lock, as they always did, and log that once.

**A crashed write.** A write from the web UI or a configuration restore keeps the original in
`.gateway.yaml.replace-original` and records the write in `.gateway.yaml.replace-journal` until
the reload accepts it. If the gateway stops in between, the next writer, or the next start, puts
the original back (or keeps the new file, when its reload had already accepted it) and removes
both files. A start that finds a journal it cannot act on (unreadable, its original missing, or
beside a file this account cannot lock) refuses to start rather than serve either version.

- What you do: nothing, normally. If a start refuses, follow the step in its error: run the
  gateway or any config command from an account that can write the config directory, or copy
  the staged original over gateway.yaml and delete the journal.
