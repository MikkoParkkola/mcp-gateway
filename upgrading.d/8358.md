## A capabilities name shared with a backend, and a non-mapping input schema, are refused

**Startup:** refuses to start, only when `capabilities.name` equals a registry backend name; fails a capability file, when its `schema.input` is a string, number, boolean or list, with a CAP-003 error in the log

What you gain: the gateway tells a capability from a registry backend's tool
by the backend name, so one name used for both made it judge a capability as
the backend's tool. A capability without a schema could be withheld, and a
block on the registry backend applied to the capability as well. That config
is now refused at load, naming both sides. A capability whose input schema is
not a mapping was advertised to callers with a schema no client can build a
call against. It is now refused the way a wrong `type` already was.

What changes:

- `Config` validation fails with `capabilities.name = "X" is also backends.X`
  when the two names are equal. This also applies when the capabilities
  section or that backend is disabled, so enabling one later never meets the
  rule for the first time.
- CAP-003 reports `schema.input must be a YAML mapping (object), got a
  string` (or a number, a boolean, an array) as an error. The loader skips the
  file, `cap validate` fails it, and the web UI refuses to save it.
- `cap discover --write-config` skips a discovered server whose name is
  `capabilities.name`, with a warning, and writes the rest. The default
  `setup export` entry is named `gateway`, so a re-discovered export of this
  gateway is no longer imported as a backend of itself. `cap discover
  --shadow` no longer reports that entry as unmanaged.

What stays the same: an input schema that is missing, `null` or `{}` still
loads (webhook-only capabilities), and so does an object schema without
`type`.
