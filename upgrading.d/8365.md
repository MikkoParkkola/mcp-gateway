## The transparency-log key is resolved, and must be 32 bytes or more, not all zero

**Startup:** refuses to start, only while the transparency log is on and its `shared_secret` is under 32 bytes or all zero bytes (literal or resolved), a reference that does not resolve, or a reference to an empty variable

What you gain: `shared_secret` takes `${VAR}`, `${VAR:-default}`,
`env:NAME`, `file:PATH` or a literal, as documented. Before this release a
reference was never resolved: the key was the reference's own text, which
anyone reading the config knows, so the entry signatures proved nothing. A
`file:` key is tracked for reload like every other secret file. An empty
`shared_secret` still means unsigned entries, protected by the hash chain
alone.

What you lose: while the log is on, the gateway refuses to start when the key
is under 32 bytes or all zero bytes, literal or resolved, or a reference that
is unset, empty or names a missing file. The error names the field and never the value. With the log
off, the gateway starts, but `audit verify` refuses until the key resolves; it
never verifies with an empty key or with the reference's text.

What to do:

- Generate a key: `openssl rand -base64 48` (64 characters). Put it in an env
  file and set `shared_secret: "env:NAME"`.
- Segments written before this release with a reference were signed with that
  reference's text. Verify them with the release that wrote them and its
  original config; this release cannot take the text as a key.
- Library users: `Config::audit_verify_config(path)` is new. It returns the
  key and key id `audit verify` checks a log with, or an error when the config
  does not load or the key did not resolve. The `mcp-gateway audit verify`
  command uses it.
- If `shared_secret` was a reference, upgrading changes the key: the old
  release signed with the reference's text, this one signs with its value.
  Treat the upgrade as a key change, below, before starting this release.
- To change the key, stop the gateway and move each log set signed with it
  aside, for verification: the log file and every file beside it named after
  it (its sealed segments, `.hwm` and, with SIEM export on, its
  `.export-cursor.json`). Each log then starts a fresh chain.
  That is the transparency log at `security.transparency_log.path` and, with
  auth on, the governance log, `audit.jsonl` in the control-plane directory
  (`control_plane.store_dir`, by default `<config name>-control-plane` beside
  the config file). Grants and policies live in `store/` beside it and are
  untouched; the admin audit view starts empty. Set a new `key_id` and the new
  key, then start. Writing a new key into an old log set mixes signatures
  from two keys and breaks its high-water mark.
