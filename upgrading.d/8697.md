## Records name a credential by a keyed digest

**Startup:** no notice

**What you gain.** A record no longer carries the stored credential principal,
so a leaked audit log, event stream or delivery record cannot be matched
against the gateway's credential store. Within one key, one credential still
maps to one value, so per-caller queries keep working.

**What happens automatically.** On its first 4.0.0 start the gateway creates
`<data dir>/record-principal.key` (owner-only) and keys every record with it.
Nothing needs configuring. With several replicas, each pod keeps its own key
in its own data directory, so one credential's records carry a different value
on each pod (docs/DEPLOYMENT.md, replica table).

**What you lose.** The values change. Owner and caller-key fields that came
from a credential (`caller_key` in tenant-read and delivery records, the events
`principal` and `who.account` fallbacks, settlement `who.account`, the firewall
`caller`) read `credential:rp:<12 hex>`, never `credential:<p>` or
`credential:<len>:<p>`. `who.principal` is 12 hex, or empty for a caller with
no credential. A watch poll's record (`who.principal` of a REST watch event's
poll) carried the subscription's raw owner string (`credential:<p>`); it now
carries the 12-hex keyed principal of the API key the poll runs as, and the
firewall session it names reads `watch:<12 hex>`, not `watch:<owner>`. Records written before the upgrade keep the old form, so a query
spanning the upgrade sees two values for one credential. Losing the key file
changes every value from then on.

**What you do.** Update SIEM and log queries that matched the old forms, and
back up `record-principal.key` with the rest of the data directory.

**Override, for two cases only.** Set `security.record_principal_key` (for
example `env:RECORD_PRINCIPAL_KEY`, at least 32 bytes) when you need one
credential's records to match across replicas, or values that survive the loss
of a data directory. The gateway cannot pick a shared value for you: no secret
every deployment has is held by the gateway alone (a bearer token is also held
by every client).

**Event subscription handles are keyed too.** A subscription's handle (the `id` an `events/subscribe`
answer returns, the `x-mcp-subscription-id` header on deliveries and on the
verification challenge, and `subscription_id` in event records) is now a keyed
alias of the stored id, 16 hex, not the stored `sub_…` id. A new event's
`eventId` (and `webhook-id`) is derived from that alias. The admin dead-letter
listing names a subscription as `subscriptionAlias`; `subscriptionId` is gone. Event
warnings (an unwritten attempt record, a suspension, a full outbox) name the
subscription by the same alias; a skipped store record names its directory.

**For events, what happens automatically.** `events/unsubscribe` and refresh never took a
handle: they recompute the subscription from your own arguments, so they keep
working across the upgrade unchanged. Repeating the same `events/subscribe`
returns the current handle. Deliveries already queued at the upgrade keep the
`eventId` they were queued with until they are delivered, dead-lettered or
expire (at most `events.max_ttl`, 24 h by default); only new events use the new
form. The events store records which record key it was written under
(`record-key.id` beside the store); if that key changes, the store adopts the
new one at startup with one warning naming the store, and every handle and
`eventId` changes again. Deleting `record-key.id` raises the same warning,
but handles change only if the key itself changed.

**For events, what you lose.** Every handle and `eventId` changes once at the upgrade, and
again whenever the record key changes. A receiver that deduplicates on
`eventId` or `webhook-id` can see a retried pre-upgrade event as new.

**For events, what you do.** Learn the new handle from the next delivery's header or by
repeating your subscribe. Across the upgrade, deduplicate by subscription and
upstream event, or drain deliveries first; for event types whose upstream id is
not delivered, drain before upgrading. Change admin scripts that read
`subscriptionId` from the dead-letter listing to read `subscriptionAlias`; its
`subscription` filter still accepts a stored id. Back up the record key with
the data directory, or set `security.record_principal_key`, if handles must
survive the loss of a data directory.
