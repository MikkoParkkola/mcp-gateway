## A per-user tool's error-rate cooldown is checked after the credential step

**Startup:** no notice

What you gain: a caller with no connected account on a per-user backend can no
longer learn that a tool exists because other callers pushed it into
error-rate cooldown. Before, its `gateway_invoke` answered "temporarily
disabled due to a high error rate" and named the tool, while a missing name got
the account's connect offer. Both now get the connect offer, and nothing is
sent.

What changes for a caller who can see the tool, on a per-user backend:

- The cooldown refusal comes after the credential step. On a managed account
  the call may mint, refresh or lease its credential first.
- On `/mcp` the refusal is the dispatch's: HTTP 200 with JSON-RPC error
  -32000, not HTTP 400. The text is unchanged.
- A task for a tool in cooldown is accepted, then fails in the worker.
- A signed call refused for the cooldown keeps its nonce spent. Retry with a
  fresh nonce.
- A stored task read of the tool answers retryable while the cooldown lasts,
  and serves once it ends.
- An idempotency key refused for the cooldown stays usable: the same key is
  sent fresh once the cooldown ends.

What stays the same: `/mcp/{name}` already checked the cooldown after the
credential. Shared backends still check it in the invocation policy; the one
change there is that a tool that enters cooldown after admission and before
the send is now refused at dispatch, and not sent.

What to do:

- Nothing, to keep working.
- If a client branches on the HTTP status of a `/mcp` cooldown refusal, read
  the JSON-RPC error code instead.
- Send a fresh nonce when you retry a refused signed call.
