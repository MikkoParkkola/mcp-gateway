## A backend name shared with the running capability backend is refused, not re-routed

**Startup:** no notice

**What you gain.** A config cannot load with `capabilities.name` equal to a registry backend name, but a reload could still create that pair: a `capabilities` change applies only at restart, so the capability backend keeps its old name, while a reload's backend changes apply at once. A reload that renamed `capabilities.name` and added a backend under the old name passed validation and registered it. The gateway then judged calls to that name against the registry backend and dispatched them to the capability backend. Such a call is now refused before anything is sent, and the reload that would create the pair is refused.

**What changes.**

- A call to the shared name is refused with `-32001`, message `Backend name '<name>' is both a configured backend and the capability backend; ...`, and `data`: `{"reason": "ambiguous_backend", "server": "<name>", "routes": ["backend", "capability"]}`. It is refused before an idempotency key is reserved and before the response cache is read. A call for a tool that only the configured backend exposes is still refused as a tool that is not found, as before.
- A config reload that adds or changes a backend named like the running capability backend is refused: `backends.<name> has the name of the running capability backend, and a capabilities.name change applies only at restart. Restart first, or rename the backend.` Nothing is started, stopped or published.

**Library callers.** `mcp_gateway::Error` gains a variant, `AmbiguousBackend { server, rule }`. `Error` is not `#[non_exhaustive]` in this release, so a `match` on it that lists every variant without a wildcard arm needs one more arm.

**What stays the same.** A capability call with no same-named backend, and a backend call with no same-named capability, are served as before.
