---
change: A key-server token now counts against its identity's cap from the moment its mint starts, and becomes valid only when the mint finishes; TokenStore lost insert and gained reserve, activate and abort
action: Nothing for configuration. Library users who implement TokenStore or build InMemoryTokenStore move to the API below
---
## Key-server mints reserve their slot first

**Startup:** no notice, nothing changes at startup

**What changed.** The per-identity token cap (`key_server.max_tokens_per_identity`) used to be checked by counting active tokens and then inserting the new one, two separate steps. Mints for one identity arriving together could each see room and each insert, ending above the cap. A mint now reserves a slot under the cap first: active tokens plus mints in progress never exceed it. The reserved token is not valid (lookup and revocation-liveness checks do not see it) until the mint activates it. A mint that ends early, including a client that disconnects mid-mint, gives its slot back. A slot left pending longer than 30 seconds is reclaimed by the next mint for that identity.

**Answers.** The cap refusal is still `429 too_many_tokens`, and nothing is evicted. Revoking an identity (or a token's JTI) while its mint is in progress cancels that mint: the minter gets `403 access_denied` and no token. A mint whose reservation outlived its 30 seconds gets `503 temporarily_unavailable` with `Retry-After: 1`. Revocation counts include cancelled in-progress mints: `DELETE /auth/token/{jti}` answers 204 for one, and the bulk `revoked` count includes them.

**Library API.** For code built against `mcp_gateway`:

- `TokenStore::insert` is removed. A token becomes active only through `TokenStore::reserve(ReservationRequest, now)` and then `TokenStore::activate(&ReservationId, TemporaryToken, now)`; `TokenStore::abort(&ReservationId)` releases a slot. `reserve` refuses with `ReserveError::CapReached` when the identity's active plus pending tokens fill the cap. `activate` refuses (`ActivateError::Revoked`, `Expired`, `Mismatch`, `Timestamps`, `Missing`) unless the token matches the reservation's issuer, subject and JTI and runs from `now` for the store's lifetime.
- `InMemoryTokenStore::new` takes the per-identity cap and the token lifetime in seconds; both are fixed for the store's life. `InMemoryTokenStore` no longer implements `Default`.
- `count_for_subject` still counts active tokens only; it no longer decides admission.

**Rollback.** No stored state changes: tokens stay in memory, so a rollback drops them as any restart does.
