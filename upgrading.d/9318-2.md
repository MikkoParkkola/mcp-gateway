## `audit verify` pairs config-write records

**Startup:** no notice

What you gain: `audit verify` now checks that every config write the gateway
settled into the audit log is accounted for. Each intent pairs with its
outcome or abandonment by token, and a deferral or a stopped delivery names
an intent that exists. These checks run only on records the chain check
already verified.

What changes in the output:

- A pairing failure exits non-zero with the headline "Pairing verification
  FAILED: <rule> at counter <n> (token <token>)". A chain failure keeps its
  own headline, and pairing findings then print as "unverified:" warnings.
- New warnings name an intent that was interrupted or left to recovery, and a
  record that is not a settle record.
- New `info:` lines name records whose intent retention deleted. A log
  written before 4.0 gets one line counting its config intents: they were
  written before outcome records existed and are not paired.
- No payload value is printed; tokens are escaped like other log text.

What to do:

- If a script parses `audit verify` output, let it accept `info:` lines.
- `VerifyResult` now has fields only the crate can set, so code outside it
  can no longer build one as a struct literal: start from
  `VerifyResult::default()` and set its public fields. Read the new
  findings with `failed_check()` and `notes()`.
