## A task's settlement refusal is recorded on the task's own record

**Startup:** no notice, applies only with a transparency log

**What you gain.** A task-augmented call runs its worker in the background, and the worker inspects the backend's answer once more when it settles the task. Before, a refusal or a redaction at that point reached no record: the worker's dispatch record had already been written with `outcome: ok`, and the task read that returns the outcome deliberately carries no delivery facts. Now the settlement writes a record of its own, before the task is committed:

- `route: "task_settlement"`, with `server` and `tool` as the task was inspected, and the gateway `task_id`;
- `correlation_source: "task_id"`, and `session_id` holds the task id;
- `trace_id` is the trace of the worker's dispatch record, so the settlement record and the dispatch it settles join by that one key; when no dispatch record exists it holds the task id;
- `response_effect` (`refused` or `rewritten`) and `response_findings` (what the scan found, by kind, severity and part, never content);
- `outcome: denied` with the committed code for a refusal; a redacted answer that completes keeps the class a live call would give it;
- `request_hash` is the hash of `{"task_id": <id>}`, as on `task_recovery`.

A recovered upstream task (section 113) adds the same `response_effect` and `response_findings` to its `task_recovery` record when the recovery's gates refuse or rewrite the answer.

**What stays the same.** A task whose answer passes the settlement unchanged writes no new record, and a clean recovery's `task_recovery` record is unchanged. Task reads (`tasks/get`, `tasks/result`) still carry no delivery facts.

**Fail-closed.** The record is written before the task is committed. Under `FailClosed`, a failed write settles the task `-32005` with no backend content, as section 113's record does. The record describes the settlement the gateway decided; if another writer commits the task first, the committed task is that writer's.

**What you do.** Add `task_settlement` wherever you list audit routes.
