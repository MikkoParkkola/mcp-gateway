## Audit logs carry a stable `log_id`, named by an `audit_log_identified` record

**Startup:** no notice

What you gain: each audit log has one id, kept across restarts and rotations,
so a record kept elsewhere can name the log it belongs to. Every segment's
`audit_segment_opened` record carries the id as `log_id`. When the active file
is lost and the gateway starts a new log, the new log's open record names what
survived of the old one (its id, if the running gateway held it, and the last
high-water mark, if `.hwm` survived) in a `predecessor_missing` field, and
`audit verify` prints that as a warning.

What changes in the log: a new log now begins with the `audit_segment_opened`
record at counter 1, then an `audit_log_identified` record at counter 2 that
names the log's id; the first caller record is counter 3. A log written before
4.0 has no id: the first open under 4.0 mints one and appends one
`audit_log_identified` record to it. The id is not written to `.hwm`, whose
layout is unchanged.

The record is signed and chained like any other, so every consumer that
follows the chain gets it: SIEM export and the NDJSON file sink forward it,
the export metrics count it, and `audit verify` counts it in
`entries_checked`. Readers that select records by session or kind
(`audit show`, the dashboard's governance view) never show it.

What to do:

- Where a SIEM rule, export consumer or script matches caller events, skip
  records whose `event` is `audit_log_identified`, as for
  `audit_segment_opened`.
- Chain and counter checks need no change.
