## Sessionless legacy calls get a short-lived, capped session

**Startup:** no notice

What changes: a 2025-era client that calls anything other than `initialize`
without a session id of its own used to be given a new session kept for
`streaming.session_ttl` (30 minutes by default), one per call, with no limit on
how many. That session is now provisional:

- It is kept while a request runs under it or a GET stream holds it open, and
  reaped once it has been idle for 60 s after that (or for `session_ttl`, if
  that is set shorter).
- Presenting its id again, on `/mcp` or the direct route, makes it an ordinary
  session that lives for `session_ttl` as before.
- At most 10,000 provisional sessions are live at once. A new sessionless legacy
  call past that is refused before anything runs: HTTP 503, `Retry-After: 60`,
  JSON-RPC error -32603 with `data.reason` set to `session_capacity`.

What stays the same: `initialize` opens an ordinary session and is never refused
by the cap. A caller resuming its own live session is never refused. Requests
that declare the 2026 era by header open no session, as before. Under
`security.posture: hardened` nothing changes.

Who shares the cap: with authentication off, or with `/mcp` listed in
`auth.public_paths` (which the `mcp-gateway init` starter config does), every
anonymous sessionless legacy caller draws on the same 10,000 slots. One caller
sending about 167 such requests a second can keep them full, and other new
sessionless legacy callers then get the 503 above. Before this change the same
traffic grew memory without bound for `session_ttl`.

The cap is gateway-wide, not per caller: authenticated sessionless legacy callers
share the same 10,000 slots too. Enabling authentication and keeping `/mcp` out of
`public_paths` stops anonymous callers from taking slots; it does not give each
authenticated caller slots of its own. A client that sends `initialize`, or presents
the session id it was given, never needs a provisional slot.

The 60 s idle limit and the 10,000 cap are fixed values, not configuration keys; a shorter `streaming.session_ttl` shortens the 60 s.
