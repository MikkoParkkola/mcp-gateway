## Sessionless legacy calls get a short-lived, capped session

**Startup:** no notice

What changes: a 2025-era client that calls anything other than `initialize`
without a session id of its own used to be given a new session kept for
`streaming.session_ttl` (30 minutes by default), one per call, with no limit on
how many. That session is now provisional:

- It is kept while a request runs under it or a GET stream holds it open, and
  reaped once it has been idle for 60 s after that (or for `session_ttl`, if
  that is set shorter).
- Presenting its id again, on `/mcp` or the direct route, makes it an ordinary
  session that lives for `session_ttl` as before.
- At most 10,000 provisional sessions minted by POST are live at once. Past
  that, a sessionless legacy POST is still answered, but without a session:
  its answer carries no `mcp-session-id`, so there is no id to adopt until
  slots free. A client that calls fast and never presents its id is therefore
  never refused.
- The three session tools need a session. Called that way past the POST cap,
  `gateway_set_state`, `gateway_set_profile` and `gateway_get_profile` refuse
  and say to send `initialize`, which is never capped, then retry with its id.
- A sessionless `GET /mcp` stream needs a session to deliver anything, so it
  has its own share: at most 1,000 live at once. Past that it is refused:
  HTTP 503, `Retry-After: 60`, JSON-RPC error -32603 with `data.reason` set to
  `session_capacity`. POST traffic cannot use up the stream share.

What stays the same: `initialize` opens an ordinary session and is never refused
by the cap. A caller resuming its own live session is never refused. Requests
that declare the 2026 era by header open no session, as before. Under
`security.posture: hardened` nothing changes.

Memory: the caps bound provisional sessions at about 11 MB for POST and about
31 MB for streams at the default `streaming.buffer_size`; larger buffers and
large queued notifications add to that. `initialize` itself is not capped
(unchanged; tracked as MIK-8534).

The 60 s idle limit and both caps are fixed values, not configuration keys; a
shorter `streaming.session_ttl` shortens the 60 s.
