## A withheld surfaced tool answers as a missing name

**Startup:** no notice

What you gain: a caller cannot learn that a surfaced tool exists when it may
not use it. Before this release, some paths (a task call, a chained task, a
continuation, a listing) answered differently for such a tool than for a
name that matches nothing.

What changes: every call by the name of a surfaced tool the caller may not
see answers exactly as the same call by a name that matches no tool: the
same code, message and HTTP status, whichever check answers first. The
refused call keeps no idempotency key and spends no signing nonce.

One exception to a fail-closed audit log: with the transparency log set to
fail closed, the grant-decision record of such a refused call is written on
a best-effort basis. If that write fails, the gateway logs the warning "The
audit record of a withheld surfaced call could not be written" and still
answers as a missing name, because answering `-32005` would tell the caller
the tool exists. The call itself is refused and runs nothing. Every other
audit record still refuses the request when its write fails.

One limit: for a backend that keeps a separate tool catalogue per user, a
schema that is invalid only in one user's catalogue hides the tool from that
user's listings and suggestions, but a call by its name is still judged on
the shared catalogue's schema. That case is tracked as MIK-8356.

What to do: nothing, unless you detect audit-log failures by watching for
`-32005` answers. Then also alert on that warning, which is the only sign
that a refused withheld call's record is missing.
