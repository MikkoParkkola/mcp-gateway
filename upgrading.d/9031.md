## UI role checks use the role mapping a request arrived under

**Startup:** no notice

What changes: a reload that changes `control_plane.role_mapping` applies to
UI requests that arrive after it. A request that arrived before it, even one
whose body is still being read, is judged by the mapping it arrived under on
Activity (list, export, receipts), the control-plane export status, the
grant, policy and decision writes, and the `access` report on
`GET /ui/api/status`. Before, those checks read the mapping current when the
handler ran, so a request that arrived before a reload was judged by the new
mapping: a role the reload removed was refused, and a role it added was
admitted. Now that request keeps the mapping it arrived under, and the reload
applies from the next request on.

Not covered here: the admin flag the key server sets for an OIDC caller at
authentication still reads the current mapping, and a stream's recheck judges
each delivery by the mapping current then.
