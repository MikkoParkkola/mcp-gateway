## Backend panel credentials go to the secret store; mixed template values are refused

**Startup:** no notice

**Who is affected.** Operators who add or edit backends in the web UI or adopt a discovered server there, and anyone using `mcp-gateway add` with a value that mixes literal text and a `${...}` template.

**Before.** The panel wrote each env value, and a registry server's token spliced into its `Authorization` header, into gateway.yaml exactly as typed, so a secret typed into the panel sat in gateway.yaml as plaintext. A value such as `sk-${SUFFIX}` or `${TOKEN:-fallback}` was written as given.

**After.** On add or update in the panel, a value that is not empty, not a secret reference (`env:`, `file:`, `keychain:`) and not a template is saved in the secret store chosen by `secrets.store` when it is a header value (a registry server's token) or an env value whose name marks a credential. A name is split into parts at `_`, `-` and where a lower-case letter or digit meets an upper-case one (`authToken` is `auth`, `Token`). It marks a credential when a part, in any letter case, is `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD`, `PASSPHRASE`, `CREDENTIAL`, `CREDENTIALS`, `APIKEY`, `PAT` or `DSN`, or when `API`, `ACCESS`, `PRIVATE`, `SECRET`, `SIGNING` or `ENCRYPTION` comes directly before `KEY` (`X_AUTH_TOKEN`, `DB_PASSWORD`, `GITHUB_PAT`, `OPENAI_API_KEY`). Parts that also name ordinary settings (`AUTH_TYPE`, `SESSION_TIMEOUT`, `COOKIE_SECURE`, `SORT_KEY`) do not. gateway.yaml then holds the store's reference (`keychain:NAME` or `file:PATH`), and the answer lists each stored field with its reference under `secrets_stored`, so you can see which entry a backend names. Every other env value (`DEBUG=1`, `LOG_LEVEL=debug`) is written as typed, as before: a stored value is redacted from tool results wherever it appears, so storing an ordinary setting would damage results. A secret under a name the rule does not recognise is written as typed too; keep its key and write an `env:` or `keychain:` reference as its value instead. Adopting a discovered server applies the same rule: its credential-named env values, its header values, and any env value that reads as a secret reference (`file:/x`, stored as its bytes so it is not read as a reference) go to the store; its other env values are written as found. A registry server's header is stored as one whole value. An update stores only the values it sets; every other value is left as it is. A value with literal text beside a template, or a template with a non-empty default, is refused with `literal_in_value`, naming the field and never the value; `mcp-gateway add` refuses the same values. Plain values given to `mcp-gateway add` are still written as given.

**Values saved before 4.0.0** stay in gateway.yaml as they are; nothing is migrated. To move one, write an `env:` or `keychain:` reference as its value in gateway.yaml under the same key; an env value under a recognised name can also be typed again in the panel, which stores it.
