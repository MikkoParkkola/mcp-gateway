## Backend panel credentials go to the secret store; mixed template values are refused

**Startup:** no notice

**Who is affected.** Operators who add or edit backends in the web UI or adopt a discovered server there, and anyone using `mcp-gateway add` with a value that mixes literal text and a `${...}` template.

**Before.** The panel wrote each env value, and a registry server's token spliced into its `Authorization` header, into gateway.yaml exactly as typed, so a secret typed into the panel sat in gateway.yaml as plaintext. A value such as `sk-${SUFFIX}` or `${TOKEN:-fallback}` was written as given.

**After.** On add or update in the panel, a value that is not empty, not a secret reference (`env:`, `file:`, `keychain:`) and not a template is saved in the secret store chosen by `secrets.store` when it is a header value (a registry server's token) or an env value whose name marks a credential. A name is split into words at `_`, `-` and camel-case boundaries (`authToken` is `auth`, `token`), and only its last words count: it marks a credential when it ends in `password`, `passwd`, `passphrase`, `token`, `secret`, `credential(s)`, `pat`, `dsn` or `apikey`, or in `key` after `api`, `secret`, `private`, `signing`, `session`, `cookie`, `auth`, `access` or `encryption`, in any letter case (`X_AUTH_TOKEN`, `DB_PASSWORD`, `GITHUB_PAT`, `OPENAI_API_KEY`, `SESSION_KEY`). A name that only contains such a word is a setting and stays text (`TOKEN_LIMIT`, `PASSWORD_MIN_LENGTH`, `API_KEY_TIMEOUT`, `SORT_KEY`), and so are pagination names (`next_page_token`). Rails' `SECRET_KEY_BASE` is a credential too. A credential-named value or a header value shorter than 8 bytes is written as typed (`HF_HUB_DISABLE_IMPLICIT_TOKEN=1`, `AUTHORIZATION=none`): a stored value is redacted from tool results at any length, and one that short would blank ordinary text. A name written as one glued word (`PGPASSWORD`) is not recognised; write a reference for it by hand. gateway.yaml then holds the store's reference (`keychain:NAME` or `file:PATH`), and the answer lists each stored field with its reference under `secrets_stored`, so you can see which entry a backend names. Every other env value (`DEBUG=1`, `LOG_LEVEL=debug`) is written as typed, as before: a stored value is redacted from tool results wherever it appears, so storing an ordinary setting would damage results. A secret under a name the rule does not recognise is written as typed too; keep its key and write an `env:` or `keychain:` reference as its value instead. Adopting a discovered server applies the same rule: its credential-named env values, its header values, and any env value that reads as a secret reference (`file:/x`, stored as its bytes so it is not read as a reference) go to the store; its other env values are written as found. A registry server's header is stored as one whole value. An update stores only the values it sets; every other value is left as it is. A value with literal text beside a template, or a template with a non-empty default, is refused with `literal_in_value`, naming the field and never the value; `mcp-gateway add` refuses the same values. Plain values given to `mcp-gateway add` are still written as given.

**Values saved before 4.0.0** stay in gateway.yaml as they are; nothing is migrated. To move one, write an `env:` or `keychain:` reference as its value in gateway.yaml under the same key; an env value of at least 8 bytes under a recognised name can also be typed again in the panel, which stores it.
