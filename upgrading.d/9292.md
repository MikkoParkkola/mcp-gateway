## Backend panel secrets go to the secret store; mixed template values are refused

**Startup:** no notice

**Who is affected.** Operators who add or edit backends in the web UI, and anyone using `mcp-gateway add` with a value that mixes literal text and a `${...}` template.

**Before.** The panel wrote each env value, and a registry server's token spliced into its `Authorization` header, into gateway.yaml exactly as typed, so a secret typed into the panel sat in gateway.yaml as plaintext. A value such as `sk-${SUFFIX}` or `${TOKEN:-fallback}` was written as given.

**After.** On add or update in the panel, each value that is not empty, not a secret reference (`env:`, `file:`, `keychain:`) and not a template is saved in the secret store chosen by `secrets.store`, and gateway.yaml holds the store's reference (`keychain:NAME` or `file:PATH`). The answer lists each stored field with its reference under `secrets_stored`, so you can see which entry a backend names; the file shows the same reference. This covers every plain value, including ones that are not secrets (`LOG_LEVEL=debug`): to keep such a value in gateway.yaml as text, edit gateway.yaml directly. A registry server's header is stored as one whole value. An update stores only the values it sets; every other value is left as it is. A value with literal text beside a template, or a template with a non-empty default, is refused with `literal_in_value`, naming the field and never the value; `mcp-gateway add` refuses the same values. Plain values given to `mcp-gateway add` are still written as given.

**Values saved before 4.0.0** stay in gateway.yaml as they are; nothing is migrated. To move one, type it again in the panel (an env value), or write an `env:` or `keychain:` reference in gateway.yaml by hand (a header value, which the panel's update does not edit), or remove the backend and add it again.
