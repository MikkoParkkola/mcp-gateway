## Keyed playbook runs complete; retry fields on a run are refused

**Startup:** no notice

**A keyed playbook run runs every step.**
- What you gain: a client that sends an idempotency key, as retry-safe clients do,
  can run a playbook with two or more steps. Before, the second step to complete was
  refused 409 because every step reused the client's key for its own entry.
- What stays the same: the key identifies the run. Repeating the same call with the
  same key returns the run's stored result without running any step again; reusing
  the key for a different run is refused 409. A step that `on_error: retry` repeats
  inside one run is still served its stored outcome, so a step whose backend ran
  and then failed does not run again.

**A playbook run carrying retry fields is refused.**
- What you lose: `gateway_run_playbook` with `requestState` or `inputResponses`
  (in any form, including `{}` or `""`) is refused -32602 "a playbook run has no
  continuation to resume". A playbook never asks its client a question at top level,
  so there is nothing to resume; such a call used to start a new round that ran every
  step again.
- What you do: send playbook runs without those fields. Operators do nothing.
