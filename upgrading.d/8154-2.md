## One sanitize step on every route; keyed direct calls need a principal

**Startup:** no notice

**Sanitization is one step, on the whole request, on every route.**
- What changes: with `security.sanitize_input` on (the default), `/mcp`,
  `/mcp/{name}`, stdio and task submits sanitize the whole request (method,
  params and `_meta`, not only the tool arguments) before signing, authorization
  and the request firewall read it. A string holding a NUL is refused -32600;
  control characters are stripped. The request `id`, the signing nonce and the
  chain nonce are checked by the same rule but never rewritten, so a NUL or a
  control character in one of them is refused.
- What changes on `/mcp/{name}`: the direct route now honours the setting.
  Before, it sanitized the tool arguments even with the setting off, and
  answered a refusal with HTTP 403; it now answers 400, as `/mcp` does.
- What changes for passthrough: a backend with `passthrough: true` is exempt
  from sanitization on every route. A call whose every backend target is
  passthrough is forwarded as sent; authorization, the request firewall and
  the response scan still run. A call that reaches any other backend, or names
  a tool the caller cannot see, is sanitized.
- What you do: nothing, unless a passthrough backend relied on the gateway
  stripping control characters on `/mcp` or stdio. It no longer does; remove
  `passthrough: true` from that backend to keep them stripped.

**A keyed direct call needs a verified execution principal.**
- What you lose: a keyed `tools/call` on `/mcp/{name}` from a caller with no
  execution principal is refused -32003 "A verified execution principal is
  required", HTTP 400, and the backend does not run. `/mcp` already refused
  it. This hits a gateway with auth off and no proven subject, and a gateway
  with auth on reached through an unauthenticated public path.
- What stays the same: an unkeyed call runs on both routes as before.
- What you do: keep the key only with a verified execution identity: a
  credential on a gateway with auth on, or a proven agent or certificate
  subject. Otherwise drop the key. Sending an API key to a gateway with auth
  off does not help.
