## A backend with per-user sessions only has no gateway shared session

**Startup:** no notice

A backend whose identity binding is required with `session_mode: per_user`, or that is bound to a managed account or an external account with per-user sessions, is no longer reached through a shared session of the gateway's own. In 3.x the gateway opened one to it: warm-start listed its tools, the health loop probed it, and a restart from the dashboard rebuilt that session. In 4.0.0 all of these are refused before anything is sent.

- What you lose: the shared tool list that warm-start filled, health data for these backends, and the dashboard restart. Their status reads `per_user` ("starts on each user's first call") instead of up, down or not started.
- What you gain: no request reaches the backend through a gateway session, and a caller never sees a tool list fetched under that shared session.
- Each subscriber's own session to the backend starts with that subscriber's credential (see the item on required bindings' per-user sessions).
- What you do: nothing. A backend that may share (a binding that is not required, or `session_mode: stateless`) keeps its gateway session as before.

`tools/list` for surfaced tools on such a backend changes too. In 3.x it answered at once from the cache: with the shared list on a single-user gateway, or without the tool on a multi-user one. In 4.0.0 a caller whose own list is not yet held waits for it to be fetched under their own credential, at most the backend's `timeout` plus a short grace and never more than 30 s (half the MCP TypeScript SDK's 60 s default request timeout). Tools that arrive later are announced with `tools/list_changed`, and later listings answer from the caller's own cached list.
