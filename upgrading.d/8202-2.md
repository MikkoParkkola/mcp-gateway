## A clock before 1970: undated firewall and segment records, fallible task and TrustLab calls

**Startup:** no notice

What you gain: on a host whose clock reads before 1970 (a dead RTC, an unsynced VM), the gateway no longer stops when a firewall audit row, a transparency-log segment, a personal-account dispatch, an identity-grant change or a `TrustLab` evaluation reads the clock. Each is refused, or written undated, and none is dated 1969 or 0.

What changes:
- Firewall audit rows (`request`, `response` and `dispatch`) are still written, with `"timestamp": null` and `"clock_invalid": true`. A `dispatch` row on such a host used to carry the epoch (`1970-01-01T00:00:00Z`); it is now `null` like the other two. On a correct clock the rows are unchanged.
- A transparency-log segment opened on such a host has `"segment_opened_at": null` in its open record. An undated segment is never rotated by age, only by size; size rotation never depends on the clock. Existing records with a numeric `segment_opened_at` still restore dated.
- A personal-account dispatch on such a host is refused ("managed account credential not issued: the gateway clock reads before 1970") before custody refreshes or releases anything. An `identity grants` change is refused with nothing written.
- Tasks on such a host: a running task's result is kept. The worker waits for a readable clock, bounded by the task's `ttlMs`, and then stores the result. If the clock is still unreadable when the `ttlMs` runs out, the result is stored dated at the task's own last change, never 1969 or 0. An owner's `tasks/cancel` always succeeds: it never waits for the clock and is dated at the task's last change. Stated limit: while a worker waits for the clock to store a followed upstream job's result, a `tasks/get` of that one task queues behind it, for at most the task's `ttlMs`. This keeps a task from being queried twice upstream or recorded twice in the audit log.
- Library users:
  - `Task::create(tool)` returns `Result<Task, TaskModelError>`.
  - `Task::complete(&mut self, result: &Value)` and `Task::fail(&mut self, error: &JsonRpcError)` return `Result<(), TaskModelError>` and take the outcome by reference. On `Err(TaskModelError::ClockUnreadable)` nothing is applied and the caller still holds the outcome; a caller that holds a time uses `transition(.., at)`. A late outcome on a terminal task is still `Ok(())` and ignored.
  - `complete` with a result that is not a JSON object now returns `Err(TaskModelError::InvalidInput)`; it used to be ignored silently.
  - `TaskModelError` is `#[non_exhaustive]` and gains `ClockUnreadable`. An exhaustive `match` on it needs a wildcard arm; later variants will then break nothing.
  - `CatalogTrustLab::evaluate_card(card)` returns `crate::Result<TrustLabEvaluation>`: `Err(Error::Internal(..))` naming the clock on such a host. A caller that holds a time uses `evaluate_card_with_baseline_at`.
  - `EraObservation::from_outcome(outcome, trigger, probed_at)` takes `probed_at: Option<DateTime<Utc>>`; pass `Some(at)` for the old behaviour.
