## The response cache answers only for tools declared read-only

**Startup:** no notice, a log warning per capability file that enables `cache:` without `read_only: true`, and no shipped file does

What you gain: a repeated call is never answered from the cache unless the
backend said the tool only reads. Before, any tool's result was stored, and an
identical call within the cache's lifetime was answered with it without
reaching the backend. For a write that meant a call reported as done that never
ran: a second "mark these emails as read" returned "Successfully marked" and
left the mail unread.

What you lose: caching for every tool whose backend does not declare
`readOnlyHint: true` for it. That covers:

- a tool with no annotations, even one whose name reads as a getter, such as
  `get_status`;
- a tool declared `idempotentHint: true` but not read-only. It may still be
  retried, since a retry runs the call again, but a cache answer runs nothing;
- a backend whose tools the gateway has not listed yet for that caller;
- a capability not declared `read_only: true` in its YAML, even one that
  enables `cache:` (a `ttl` above 0). The gateway logs one warning when it
  loads such a file, naming the file, and does not cache it. A `cache:` block
  that is already off stays quiet.

Those calls now reach the backend each time, which is slower but correct.

What to do:

- Nothing, to keep working.
- To keep caching for a backend you run, have it annotate its read-only tools
  with `readOnlyHint: true` in `tools/list`.
- If the load warning names a capability you wrote and it only reads, add
  `read_only: true` under its `metadata:`. Every shipped capability that caches
  already declares it.
