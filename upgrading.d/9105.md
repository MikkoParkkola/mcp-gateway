## Configured header and env credentials no longer come back through a backend

**Startup:** no notice, a log warning naming each `env:` field whose `${VAR}` value is too short to be treated as a secret, and each referenced value under 8 bytes

**What you gain.** A backend that echoes a credential its configuration gave it (an `Authorization` header it received, or a variable from its environment) no longer hands it to the client, to the response cache or to the logs. Each occurrence, verbatim or percent-encoded, becomes `[redacted]`, as for values injected by `secrets:` rules.

**Which values count as secret.**

| Written as | In `headers:` | In `env:` |
|---|---|---|
| `env:NAME`, `file:/path` or `keychain:name` | yes, at any length | yes, at any length |
| `${VAR}` | yes, the variable's value, at any length | only when the value is nothing but `${VAR}` references, and 8 bytes or longer |
| text mixed with `${VAR}` (`${HOME}/bin`) | yes, the variable's value | no |
| a `${VAR:-default}` whose default was used | no | no |
| a literal | no | no |

**What changes.**

- Text in a backend's answers that equals one of those values is replaced, even inside unrelated words. A `${VAR}` in a header that is not a credential (for example `${LOG_LEVEL}`) is redacted too if the backend echoes it.
- A short value written as a reference is still redacted and is named in one warning; a short `${VAR}` in `env:` is left as it is and named in one warning.
- A value a reload removes stays redacted for the redaction grace, so an echo of a just-rotated credential is still removed.
- Changing whether a value counts as secret (writing a pasted value as a reference, or a reference back as a literal) restarts that one backend on reload, as any change to its configuration does: its sessions end and its cached tool lists and catalogues are rebuilt, so nothing cached before the change carries the value.
- A stored answer (a cached response, an idempotent replay or a stored task result) is checked against the current values each time it is sent, so one recorded before a value counted as secret comes back redacted. If that check cannot complete, the stored answer is withheld: a cache entry is treated as a miss, a replay or a `tasks/get` read is answered with the redaction refusal, and a task notification is sent with its status only. A backend whose injected `secrets:` values rotate faster than the redaction grace fills its set (1,024 values); stored answers are then refused for every backend until that set has room again and the grace of the last value it refused has passed: a refused value is held nowhere, so the refusal lasts at least one grace (24 hours or more) after that value was sent, even once older values age out. A `headers:` or `env:` value counts toward it only once a reload replaces it, until its grace passes, so frequent credential rotation through reloads can fill it too.
- Load refuses a backend that configures more than 64 secret values in `headers:` and `env:`, naming the backend and the count, and a secret value that contains `[redacted]`, `<removed>` or `{hidden}` (the markers a redaction is written as), naming the field. Neither message prints a value.
- A stored answer in which removing one backend's value would form another backend's value (a value that overlaps a redaction marker, next to a value that is removed) is refused whole, with a warning that names no value.

**What stays the same.** How values resolve and what the backend receives. A literal credential pasted into `headers:` or `env:` is not redacted: write it as a reference to have it treated as a secret.

**Limits.** The same as for injected values: a value encoded twice, mixed-case hex within one value, and base64 inside a composite value (such as a Basic auth header) are not matched.
