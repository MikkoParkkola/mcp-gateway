## Configured header and env credentials no longer come back through a backend

**Startup:** no notice, a log warning naming each `env:` field whose `${VAR}` value is too short to be treated as a secret, and each referenced value under 8 bytes

**What you gain.** A backend that echoes a credential its configuration gave it (an `Authorization` header it received, or a variable from its environment) no longer hands it to the client, to the response cache or to the logs. Each occurrence, verbatim or percent-encoded, becomes `[redacted]`, as for values injected by `secrets:` rules.

**Which values count as secret.**

| Written as | In `headers:` | In `env:` |
|---|---|---|
| `env:NAME`, `file:/path` or `keychain:name` | yes, at any length | yes, at any length |
| `${VAR}` | yes, the variable's value, at any length | only when the value is nothing but `${VAR}` references, and 8 bytes or longer |
| text mixed with `${VAR}` (`${HOME}/bin`) | yes, the variable's value | no |
| a `${VAR:-default}` whose default was used | no | no |
| a literal | no | no |

**What changes.**

- Text in a backend's answers that equals one of those values is replaced, even inside unrelated words. A `${VAR}` in a header that is not a credential (for example `${LOG_LEVEL}`) is redacted too if the backend echoes it.
- A short value written as a reference is still redacted and is named in one warning; a short `${VAR}` in `env:` is left as it is and named in one warning.
- A value a reload removes stays redacted for the redaction grace, so an echo of a just-rotated credential is still removed.

**What stays the same.** How values resolve and what the backend receives. A literal credential pasted into `headers:` or `env:` is not redacted: write it as a reference to have it treated as a secret.

**Limits.** The same as for injected values: a value encoded twice, mixed-case hex within one value, and base64 inside a composite value (such as a Basic auth header) are not matched.
