## Init stores the admin token and writes a reference

**Startup:** no notice

`init` now saves its generated admin token in the store selected by `secrets.store`
and writes only the returned `keychain:NAME` or `file:PATH` reference into
`auth.bearer_token`. Neither the config nor the sample configs contain the literal
token. The default `auto` prefers the OS keychain and uses owner-only files under
`<config-dir>/secrets` when the keychain probe fails. A failed write in the chosen
store fails init; there is no literal fallback.

Existing configs keep working, and a literal `auth.bearer_token` still loads.
There is no automatic migration. To move an existing literal without changing
the credential clients use, make its value available as `MCP_GATEWAY_TOKEN` in
the gateway process environment, replace the field with
`bearer_token: "env:MCP_GATEWAY_TOKEN"`, and restart. Keep that environment
available on subsequent starts. Do not rerun init over an existing config.

For a client, retrieve the value named by doctor's `admin-token` reference and
export `MCP_GATEWAY_TOKEN`; the reference itself is not a bearer credential.
See the [per-store retrieval recipes](../docs/QUICKSTART.md#read-the-admin-token-for-a-client),
including the documented Windows CI limitation.

**Deployments that copy `gateway.yaml`:** the reference is a path or keychain entry on the
machine where `init` ran, so a config copied into a container, a systemd unit or a
launchd daemon no longer carries a token that works there. The gateway refuses to
start on a reference it cannot read; it does not run without authentication. Pick one:

- **Environment variable (containers, Compose):** in the deployment copy set
  `bearer_token: "env:MCP_GATEWAY_TOKEN"`, read the token with the recipe for
  your store, and pass it to the process (`docker run -e MCP_GATEWAY_TOKEN`, or
  Compose `environment:`). See `docs/DEPLOYMENT.md` and `deploy/single-node/README.md`.
- **Token file (systemd, launchd):** copy the stored file (`file:PATH` on doctor's
  `admin-token` line) next to the deployed config, owner-only and owned by the
  service user, and set `bearer_token: "file:/etc/mcp-gateway/secrets/NAME"`.
- A `keychain:` reference cannot be used by a service running as another user;
  use one of the two above.

Helm and the Kubernetes manifests do not run `init` and are unchanged: they already
take the token from a Secret through `env:` references.

A crash can leave an orphan store entry or a config without its samples. Remove
the orphan entry, delete the partial config and any samples left by that attempt,
then re-run init; it refuses an existing config. See
[init recovery](../docs/QUICKSTART.md#recover-an-interrupted-init).

**Library API:** `cli_support::write_init_files` creates the config and samples,
stores the generated credential, and returns only its reference.
