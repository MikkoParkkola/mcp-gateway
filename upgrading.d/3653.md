## CLI capabilities: a new `Error` variant, templates checked at load, the child in the audit record

**Startup:** no notice

Three changes, each visible to a different reader.

**The library's `Error` gains `CliCredentialRefused`.**
- What you lose: code built against the `mcp-gateway` library that matches `Error` exhaustively
  no longer compiles until it handles the new variant. A CLI capability's refusal of its
  credential used to arrive as `Error::JsonRpc` with code 401.
- What you gain: only the gateway builds this variant. A backend that answers with its own
  JSON-RPC error code 401 no longer triggers a managed account's forced refresh or reconnect
  offer. A backend that refuses with HTTP 401, whatever its body, now does. Callers still see
  code 401 for a CLI refusal.
- What you do: add an arm for `Error::CliCredentialRefused { message }` where you match `Error`
  exhaustively. Gateway operators do nothing.

**A malformed CLI argument template is refused when the capability loads.**
- What you lose: a CLI capability whose `args`, `each`, `json` or `stdin` template breaks a rule
  used to load, be listed and searchable, and then fail every call. Now it is refused when it
  loads or is registered, and it is left out of the registry index. Your existing config can
  stop loading that capability.
- The rules are the ones a call already enforced:
  - one placeholder per argument;
  - a parameter only as the value of a fixed option (`--to={to}`) before `--`;
  - an `each` as one bound `--x={item}`;
  - one placeholder per JSON or stdin string.
- What to look for: a load error that names the capability, its provider and the template,
  with the same rule text the first call would have returned.
- What you do: fix the template it names. For example, bind the value to an option
  (`--to={to}`), or move it after a `--` element. No shipped capability is affected.

**The invocation audit record says how a CLI child ended.**
- What you gain: a record of a call that ran a CLI child carries `process`, a list with one
  entry per child. Each entry has:
  - `ended`: `exited` with `exit_code`, `signalled`, `timed_out`, `output_overflow` or
    `observation_failed`;
  - `duration_ms`, from spawn;
  - `stdout_bytes` and `stderr_bytes`, null when the output was not kept.
- The field holds counts only, never output. It keeps at most 16 entries, with `process_total`
  when more children ran. A record of a call that started no child is unchanged.
- What you do: nothing, unless a tool that reads the audit log refuses keys it does not expect.
  Then allow `process` and `process_total`.
