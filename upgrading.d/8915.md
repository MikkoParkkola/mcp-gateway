## Per-server latency history

**Startup:** no notice

**What you gain.** The web UI can show which server got slow and when: a p95 backend latency per server for each half hour (two days) and each local day (30 days), and the slowest server of the last hour on the Overview.

**What changes.** `counters.json` gains an optional `latency` field. Its format version stays 1, so an older gateway still reads the file and ignores the field.

**What stays the same.** The call counts, their retention and their caps. A server without calls has no latency.

**Limits.**

- Rolling back to a release without this field drops the latency history the next time the older gateway saves `counters.json`; upgrading again starts it empty.
- Latency of direct-route requests other than `tools/call` (for example `resources/read` and `prompts/get`) is not shown: those requests are not counted, and a latency sample follows a counted call.
- Latency is not shown for calls through the stdio transport, which keeps no call counters.
- A p95 is reported in whole milliseconds, from a histogram whose bins are 25% wide: from about 10 ms up it is within about 12% of the real value; below that the whole-millisecond rounding dominates (a 1.5 ms p95 reads 1 ms).
