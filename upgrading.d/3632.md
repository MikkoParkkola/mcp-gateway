## Durations above 100 years, and zero timer periods, are refused

**Startup:** refuses to start, only when a duration is longer than 100 years or a running timer's period is 0

**What you lose.** A config that loaded on 3.x is refused at startup (and by `mcp-gateway
validate`) if it sets a duration longer than 100 years, or a 0 period for a timer that runs.
Such a value could crash the gateway the first time it was used, and a release build aborts on
that crash. A capability file with a `timeout` of 0 or above 100 years, or a `cache.ttl` above
100 years, is refused when it loads instead of when it is called.

**What you gain.** No setting can crash the gateway through a duration. A value the gateway
writes back (a dashboard edit, say) always loads again.

**What you do.** Set the value to 100 years or less (`3155760000s` or `876600h`), or give the
timer a positive period. A 0 under a feature that is off still loads. The error names the
value:

- `duration "<value>" is longer than 100 years, the most any duration may be`: any `5m`-style
  duration, for example `cache.default_ttl`, `backends.<name>.timeout` or `events.max_ttl`.
- `<n> seconds is longer than 100 years, the most any duration may be`: whole-second settings
  such as `auth.dashboard_session.idle_timeout_secs`, `key_server.token_ttl_secs`,
  `backends.<name>.oauth.token_refresh_buffer_secs` and the firewall `window_secs`.
- `<n> ms is longer than 100 years, the most any duration may be`: `tasks.default_ttl_ms` and
  `tasks.poll_interval_ms`.
- `streaming.session_reaper_interval is 0; a timer needs a positive period`, and the same for
  `key_server.cleanup_interval_secs` with the key server on and `failsafe.health_check.interval`
  with health checks on.
- A capability `timeout: 0` reads `a duration of 0 seconds`.

No shipped example, capability file or doc sets a duration above 100 years.
