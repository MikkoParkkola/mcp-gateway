## SIEM export refuses a signed entry it cannot authenticate

**Startup:** no notice

What you gain: SIEM export and `audit verify` now agree. A signed entry is
only exported when the key that signed it is configured, so a forged entry
with a recomputed hash chain cannot reach your SIEM. The refusal applies to
entries that still carry their `sig` field.

What you lose: with SIEM export on and `shared_secret` empty, export stops at
the first signed entry (for example one written while a key was set). It logs
a warning naming `security.transparency_log.shared_secret` and counts the
failure on the export status. Unsigned entries before that point still export,
and an unsigned log exports as before.

What to do:

- Set `security.transparency_log.shared_secret` to the key the pending entries
  were signed with and restart. A refused poll delivers nothing and does not
  move the export cursor, so export resumes at the halted entry, with the
  usual at-least-once delivery. Retention keeps running during a halt, so
  segments it expires before you restart are not exported.
- If the pending entries were signed with different keys, or with none, export
  stops again at the first one the configured key cannot authenticate. Keep
  that log set and start a fresh log (see the MIK-8365 note on changing the
  key).
- If the key is gone, those signed entries cannot be authenticated by any
  release. Keep the log set in case the key is recovered, and start a fresh
  log.
