## Every backend send is checked against the request firewall

**Startup:** no notice: nothing is printed at startup; read the item before upgrading. A refused send names the firewall in its error and writes one `dispatch` row to the firewall audit log.

What you gain: the request firewall's pattern scan covers every send to a
backend, not only the outer call. Playbook steps, `gateway_execute` chain
steps, task workers, continuation retries (the client's answers) and bridged
input rounds are scanned on the bytes they send, and authorization is
checked again at that moment. A `gateway_invoke` whose `arguments` arrive as a
JSON string is judged as the object the string parses to, which is what the
backend receives.

What you keep: the per-tool firewall rules (`Allow`, `Warn`), the free-text
skip keys (`MCP_GATEWAY_FIREWALL_SKIP_KEYS`) and `scan_requests: false` work
on these sends exactly as on the outer call. Detector counts (anomaly,
tenant, budget) are unchanged: a send is not counted twice.

What you lose:
- A step argument, retry answer or string-form argument carrying a pattern
  the firewall blocks is refused with -32600 ("Firewall blocked: ...")
  where it used to be sent. A refused playbook step reports the neutral
  "step not permitted for this caller"; the audit row says why.
- Retry answers (`inputResponses`) that are not a JSON object are refused
  with -32602 when the firewall is on.
- String-form `arguments` that parse to an array or a number were and stay
  refused with -32602 ("expected object or JSON object string"); nothing
  is sent.

How to tell: each refused or warned send writes one firewall audit row with
`"event": "dispatch"`, its `action` (`block` or `warn`) and its `source`:
`invoke`, `step` (a playbook step), `retry` (a client's answers) or `bridged`
(an input round on a legacy client). Arguments appear only as a hash.
