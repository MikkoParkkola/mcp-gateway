## Startup recovery of a crashed config write: recorded first, refused when it cannot be

**Startup:** no notice; refuses to start, only when a crashed write's recovery cannot be recorded

**Who is affected.** Operators whose gateway crashed or was killed during a config save (the web UI, discovery adopt, a configuration-history restore), leaving a `.gateway.yaml.replace-journal` beside the config, and who then restart it.

**Before.** The start recovered the write, putting back the original or keeping new bytes a reload had accepted, and recorded nothing in the audit log. A 3.x gateway always recovered and started.

**After.** The start first works out which config the recovery leaves: the staged original for a write no reload accepted, the file on disk for one a reload accepted. It loads that config and appends a `config_recovery_intent` record to its audit log, then recovers. A config with no audit log and auth off recovers as before, unrecorded. The start refuses and changes nothing when the record cannot be written: the surviving config has auth on and no audit log, it does not load, or its audit log cannot be opened (whatever the auth setting). The message names the journal and the steps to finish by hand.

**What you do.** Nothing, unless a start is refused naming a pending journal. Then fix the cause it names and start again. To recover by hand instead: if the journal's state is `staged`, restore the staged original over the config only if its SHA-256 matches the journal's `original_revision`, then delete the journal; if it is `all_renamed`, only delete the journal. Record the recovery yourself.

**Library path.** The bundled binary's startup recovery entry moved: `mcp_gateway::config_persistence::recover_before_start` → `mcp_gateway::config_reload::recover_before_start`, same signature (`fn(&Path) -> Result<(), String>`); the old path is crate-private. Both modules are hidden library surface with no stability promise; code calling the old path calls the new one.
