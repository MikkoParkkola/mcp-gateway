## The first API key in the UI waits for a restart

**Startup:** no notice

A gateway with a single credential (the starter's bearer token) is single-user,
and a running gateway never turns multi-user (see 97 for why a second
credential makes it multi-user). So creating the first API key from the web UI
used to be refused with 409 `restart_required`, and the key had to be added by
hand.

Now the key is created:

- **It is written to gateway.yaml** and its secret is shown once, as for any
  key. The answer says the key takes effect at the next restart
  (`pending_restart: true`).
- **It does not work before the restart.** Until then the bearer token is the
  only credential, and the new secret is refused. The next start applies the
  key, and from then on the gateway is multi-user.
- **gateway.yaml is frozen until the restart.** Any other change that keeps the
  waiting key, from the UI or by hand, is refused: the UI answers 409
  `restart_pending`, which names the waiting key, unless the change has a
  fault of its own, which is refused for that fault as before. The gateway
  status (`GET /ui/api/gateway`) lists the waiting keys and, if a start from
  the file would succeed, the start command where the platform has one;
  otherwise it says why a start would be refused.
- **To cancel it,** revoke the key before restarting: the file goes back to
  one credential and the freeze ends.
- A file that a start would refuse is never kept: such a create is refused and
  nothing is written.

What to do: restart the gateway when you are ready to use the key; a client
that scripted the old 409 `restart_required` reads 201 with
`pending_restart: true` instead.
