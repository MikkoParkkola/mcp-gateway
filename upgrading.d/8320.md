## OAuth backends use only metadata that names them

**Startup:** an OAuth backend whose server publishes metadata for another resource fails to start, naming both

What changed: when a backend uses gateway-level OAuth, the gateway reads the
server's RFC 9728 protected-resource metadata to find the authorization server,
the scopes and the token audience. It used to read only the origin's document
(`https://host/.well-known/oauth-protected-resource`) and use it whatever
resource it described. It now:

- asks the backend first, and reads the metadata URL a `401` names in
  `WWW-Authenticate: Bearer resource_metadata="..."` (MCP 2025-11-25);
- otherwise tries `https://host/.well-known/oauth-protected-resource/<path>`,
  then the origin's document;
- uses a document only if its `resource` is the backend URL you configured
  (the same URL, or the same URL as written by a URL parser, so `https://h`
  and `https://h/` match). A document naming another resource, including one
  naming just the origin for a backend with a path, is refused, not skipped.

What you gain: tokens are requested for the backend's own URL. For an endpoint
at `https://mcp.linear.app/mcp`, the gateway used to send the origin
`https://mcp.linear.app` as the RFC 8707 resource, because that is what Linear's
origin document names; it now sends `https://mcp.linear.app/mcp`. Linear,
Notion, exa and kapa.ai all publish metadata for their endpoint (checked
2026-10-10).

What can stop loading: a server whose only metadata names the origin while the
backend URL has a path. The error names the document, the resource it names,
and the backend URL (passwords, queries and fragments removed). Set the
backend URL to the resource the server's metadata names, or ask the server to
publish metadata for its endpoint.

A library caller that builds its own `OAuthClient` (not through a backend)
keeps its HTTP client's redirect policy for the first request.
