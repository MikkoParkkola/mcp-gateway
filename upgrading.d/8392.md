## Stored task reads follow the caller's current access

**Startup:** no notice

**A stored result is withheld once access is withdrawn.**
- What changes: `tasks/get` (HTTP and stdio) and the task-status frame judge each
  recorded target against the reading caller now. A tool the caller can no longer see,
  or a personal account revoked or awaiting reconnect, answers `-32601`, exactly as an
  absent tool name does; a frame carries the status without the output. A policy
  refusal (a kill switch, an attestation challenge) keeps the error a live call gets.
- What you do: nothing as an operator. A client treats `-32601` on a read as "this
  result is no longer yours to see".
- An account the gateway cannot read without minting a credential (an external
  or token-exchange account) is not judged on a stored read; its stored result
  follows the tool's catalogue only, as the E7 residual states for live views.
- A stored read can serve a shared backend's tool for up to one catalogue TTL after
  the tool is withdrawn upstream: the read refreshes a shared catalogue only once it
  is past its TTL. A withdrawn grant, key scope or descriptor block applies at once.
- A stored read of a `gateway_invoke` task whose personal account has no view (revoked,
  or awaiting reconnect) answers `-32601`, where a live call by the same caller is offered
  the account connect instead. A per-user backend whose caller has no principal answers
  "retry" while its catalogue is stale.

**A read can answer "retry" while a per-user view is re-established.**
- What changes: after a per-user slot was evicted for idleness, the first read
  re-establishes it with one credential resolution; other reads meanwhile answer
  `-32603` with `data.retryable: true` and `data.retry_after_ms`, the time left on that
  attempt. A custody that is busy or unavailable answers the same way. The message is
  `temporarily unavailable, retry` (earlier builds of this change said
  `task result temporarily unavailable, retry`); match on the code and
  `data.retryable`, not on the text.
- What you do: a client retries after `retry_after_ms`. No output is ever carried in
  that answer.

**A live call whose managed account's custody is busy now answers the same retryable error.**
- What changes: a live call whose managed account's custody is busy used to get
  HTTP 200 with a non-retryable answer: `-32601` when it named the tool, or `-32603`
  with no retry data (a configuration refusal) when it named the backend. It now gets
  JSON-RPC `-32603` with `data.retryable: true` (no `retry_after_ms`: no lease runs
  on this path), the same answer a task read gets in the same state. One `idp_refuse`
  audit record per call names the transient busy custody.
- What you do: retry the `-32603` after a short backoff.
- A task-augmented call (`task` in the request) that meets the busy custody gets the
  same `-32603` at once: no task is created and no idempotency key is held, so the same
  keyed request re-sent after recovery runs normally. A kill-switched, disabled or
  otherwise policy-refused target keeps its refusal on a task call: the retryable answer
  is given only to a call the policy admits.
- Not yet covered: when the account's view reads fine but custody turns busy at the
  moment the credential is minted, the live call still answers the non-retryable
  configuration refusal, once per call; MIK-8428 makes it retryable. In one request, a
  later call to the same target after an early refusal may repeat that call's stale
  answer instead of resolving again (a repeated refusal, never an unauthorised answer);
  MIK-8428 (Case C) tracks it.
