## Logging never waits on stderr

**Startup:** no notice

**What you lose.** When whatever reads the gateway's stderr stops reading (a full pipe under a supervisor or container that no longer drains it), log lines past a bounded queue (8192 lines, 8 MiB) are dropped instead of waited for. The key-server token audit and the OAuth agent tool-invocation audit lines are among them: they are tracing lines too. A dropped line is counted, and once stderr takes writes again the gateway writes one line of its own, `dropped N log lines while stderr was not draining`. Audit records with their own file (the transparency log, the control-plane `audit.jsonl`, the firewall audit file and the identity-grant journal) are not affected. When the firewall cannot open its audit file it writes its audit entries to stderr directly, as before, so those writes still wait on a stderr nobody reads.

For code that embeds the library: `mcp_gateway::setup_tracing` now returns a value that must be kept for the life of the process. Dropping it flushes the queue, waiting at most 2 s. A caller that discards it early loses lines still queued at that point, and lines logged after it may be lost at exit.

**What you gain.** A stderr nobody reads can no longer stall requests: before, a blocked log write held the thread that wrote it, and with it every request waiting on a lock that thread held.

**What you do.** Keep the gateway's stderr drained. If you see the dropped-lines line, whatever reads stderr fell behind. Library callers bind the value: `let _logs = setup_tracing(level, format)?;`.
