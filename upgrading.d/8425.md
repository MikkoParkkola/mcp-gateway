---
change: `ImportedSkill.extra` values are now `serde_json::Value`, with tags as one-entry maps
action: Rust callers of `ImportedSkill.extra` switch to `serde_json::Value`; CLI users: nothing
---
## `ImportedSkill.extra` values are JSON values

**Startup:** no notice

What changes for Rust API users: `ImportedSkill.extra` values are
`serde_json::Value` instead of the YAML parser's own tree type. A YAML tag
`!t v` is no longer a tagged value: it is the one-entry map `{"!t": v}`,
which cannot be told from a map keyed `"!t"`. A non-string key is no longer
a YAML key: scalar keys become strings (booleans to `"true"`/`"false"`,
integers to decimal, finite floats to `serde_json`'s float text: `1.0` to
`"1.0"`, `1e3` to `"1000.0"`, `-0.0` to `"-0.0"`), and null, non-finite float,
sequence, mapping and tagged keys drop their entry. When two keys end up
as the same string (`1:` and `"1":`), the later one in the document wins.
This field type changes in 4.0.0 as its own change, not as part of the
later YAML backend swap.

What changes for CLI and registry users (a behaviour fix): a skill whose
frontmatter has a null, non-finite float, sequence, mapping or tagged key
inside an extra field can now be registered, with that entry dropped.
Before, saving the registry failed with "key must be a string" ("float key
must be finite" for a non-finite float key), so such a skill could not be
registered at all.

What stays the same: `skills.json` holds the same JSON values as before,
compared after parsing, and files written by earlier versions load with the
same values. Two textual differences inside an extra value: keys are now
written in sorted order, where before they kept document order, and two
keys that stringify the same are written once. Before, both were written,
and the registry then failed to load (`duplicate entry`); a registry file
that already holds such a duplicate is still refused on load.

## YAML errors no longer quote the offending value

**Startup:** no notice

What changes: outside the config loader (capability files, grants, skills,
imports, CLI readers) a YAML type, value or variant error no longer quotes the
offending value, often a secret typed into the wrong field (CWE-532). The error
keeps the key path, the expected type and the line and column, as the config
loader has since MIK-8375. Scripts matching the old wording must match the new
wording instead:

- `providers.primary: invalid type: string "abc", expected u64 at line 9 column 14`
  -> `providers.primary: invalid type: string, expected u64 at line 9 column 14`
- ``unknown variant `forever`, expected `online` or `offline` ``
  -> ``unknown variant, expected `online` or `offline` ``
- `<N>s is longer than 100 years, the most any duration may be`
  -> `this duration is longer than 100 years, the most any duration may be`
  (a too-long duration the gateway writes)

What stays the same: key paths, expected types, line and column, key names in
`unknown field` / `duplicate entry` errors, and syntax messages.
