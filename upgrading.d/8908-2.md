## `secrets.store`: where saved secrets go

**Startup:** no notice

Secrets saved through the gateway (the web UI's settings and adopt flows) are written to a fresh entry and gateway.yaml is pointed at it; an old entry is never edited or deleted. `secrets.store` picks that store: `auto` (the default), `keychain` or `files`. It is a setting because the choice is the operator's: some hosts want secrets in the OS keychain, others in owner-only files they back up with the config (ADR-028).

- `files` writes each secret to a new owner-only file under `<config dir>/secrets/` and references it as `file:/abs/path`.
- `keychain` writes each secret to a new OS keychain entry (macOS Keychain, Linux Secret Service, Windows Credential Manager) and references it as `keychain:NAME`. A save is refused, with nothing written and a message naming `secrets.store: files`, when the keychain is locked, missing or does not answer. It never switches to files on its own.
- `auto` probes the keychain when the store is chosen and uses it when the probe passes, otherwise `files`. A fallback is logged as a warning naming the reason, and `mcp-gateway doctor` shows it on the `secret-store` row. On Linux the keychain needs `libsecret-tools` and `libglib2.0-bin`.
- Old entries are never deleted. The `secret-store` doctor row counts the entries no config names; removing them is up to you.

Existing `env:`, `file:` and `keychain:` references keep resolving whatever the setting says.
