## Grant rules that name no one are refused

**Startup:** no notice; refuses to start, only for a grants file holding a rule that names no one

What changes: a grant matches a caller on its exact authority and subject. A
rule whose subject or owner has an empty authority or subject, or one made only
of spaces, matches no caller and so grants nothing. The grants file now refuses
to load with such a row in it, naming the file and each rule.

What to do: delete each named rule from the grants file. Startup names every
such rule with its id and the empty field, and `mcp-gateway upgrade` runs the
same check on the grants file the gateway would load (the config found as
startup finds it, environment overrides included), on every run whatever the
installed version, and fails naming the same rules. Nothing edits the file for
you: such a rule matched no caller, so deleting it changes no decision,
unless another rule uses the same id. The gateway kept the last rule per id,
so a rule naming no one may have been hiding an earlier one with its id;
the refusal says when, because deleting it may make that rule active.
Values are kept exactly as written: `" admin "` stays a different subject
from `admin`.

Sign-in: the same check applies to OIDC. A provider that returns a `sub` or
`iss` made only of spaces is now refused at sign-in, as an empty one already
was: the token exchange answers 401 with no token, and the error names the
missing `sub` claim. If sign-in starts failing after the upgrade, check the
provider's subject claim mapping.

In the library: `GrantSubject::new` returns `Result<GrantSubject, EmptyIdentity>`
and is the only constructor; `GrantSubject::checked` is removed. The fields are
private; read them through `authority()`, `subject()` and `label()`.
