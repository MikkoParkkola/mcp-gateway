## Seven settings are now the gateway's own choice

**Startup:** no notice, a config that sets one of the keys logs one warning per key at load

A setting stays only where the gateway cannot decide for itself. These seven
reached 4.0.0 pre-releases without such a reason, so 4.0.0 retires them. A
config that still sets one loads. On start and on reload it logs one warning
that names the key, says what the gateway does instead, and says what to do.
The value is not honoured: there is no hidden override. `mcp-gateway upgrade`
deletes each key and keeps every other line and comment.

- What you lose: a value you set for one of these keys. Where you set a switch
  to `false`, the mechanism is now on.
- What you gain: a shorter config, and behaviour that does not depend on a
  value someone had to guess.
- What you do: delete the keys, or run `mcp-gateway upgrade`. Each entry below
  names the hatch that remains for an incident.

**`capabilities.stale_check_secs`.** The gateway re-checks the watched
capability directories every 60 s by itself, so a silent file watcher still
heals. There is no off switch. The check walks a bounded tree, and a tree past
the walk bounds is skipped with a warning.

  `` `capabilities.stale_check_secs` is ignored since 4.0: the gateway re-checks the watched capability directories every 60 s by itself, so a silent file watcher still heals. Delete it, or run `mcp-gateway upgrade`. ``

**`cache.enabled`.** The response cache is always on. It stores only the
results of tools whose annotations mark them read-only, so a tool with side
effects is never served from it. If a cached answer is wrong in an incident,
it lives at most `cache.default_ttl` (60 s unless you set it), and a restart
clears the cache. `cache.max_entries` caps its size; `0` means no cap.

  `` `cache.enabled` is ignored since 4.0: the response cache is always on and stores only results of tools their annotations mark read-only; `cache.default_ttl` sets how long an entry lives and a restart clears it. Delete it, or run `mcp-gateway upgrade`. ``

**`failsafe.retry.enabled`.** Retry is always on for calls a tool's
annotations permit to resend (`readOnlyHint` or `idempotentHint`, ADR-012),
and never for others. To stop retries in an incident, set
`failsafe.retry.max_attempts: 1`, which means one attempt.

  `` `failsafe.retry.enabled` is ignored since 4.0: retry is always on for calls a tool's annotations permit to resend (`readOnlyHint` or `idempotentHint`) and never for others; `failsafe.retry.max_attempts: 1` means one attempt. Delete it, or run `mcp-gateway upgrade`. ``

**`failsafe.circuit_breaker.enabled`.** The backend circuit breaker is always
on. A breaker held open on a healthy backend closes with
`gateway_revive_server`, and the health probe, which bypasses the breaker,
closes it when the backend answers again.

  `` `failsafe.circuit_breaker.enabled` is ignored since 4.0: the backend circuit breaker is always on; `gateway_revive_server` closes one held open on a healthy backend, and the health probe closes it on recovery. Delete it, or run `mcp-gateway upgrade`. ``

**`auth.client_circuit_breaker.enabled`.** The `auth.client_circuit_breaker`
section's presence is the switch, as it already was when the section was
absent. A section that still says `enabled: false` now turns the client
breaker ON. To keep the breaker on with no other key in the section, write
`client_circuit_breaker: {}`: a bare `client_circuit_breaker:` line is empty
YAML and turns it off. To turn it off, delete the section. `upgrade` never
deletes this key when it is the only one in the section; it keeps it and says
which of the two edits to make.

  `` `auth.client_circuit_breaker.enabled` is ignored since 4.0: the `auth.client_circuit_breaker` section's presence turns the client breaker on, whatever this key says. To keep it on with no other key, write `client_circuit_breaker: {}`; to turn it off, delete the section. ``

**`security.signature_chain.max_links`.** A chain holds at most 8 links. That
is a constant every hop agrees on: with a per-deployment value, a chain one
gateway builds could be refused by the next. 8 links fit inside the 16 KiB
chain cap. A misspelled key under `security.signature_chain` is still refused
at load, by its full path.

  `` `security.signature_chain.max_links` is ignored since 4.0: a chain holds at most 8 links, a constant every hop agrees on. Delete it, or run `mcp-gateway upgrade`. ``

**`server.protocol_revision_window`.** The RFC-0060 U1 measurement window is
the operator's instrument for their own deployment, so it leaves the config.
Start the gateway with `--protocol-revision-window record`, a flag hidden from
`--help`, or set `MCP_GATEWAY_PROTOCOL_REVISION_WINDOW=record`. Both work with
no subcommand and before `serve`. On Helm, set the variable through `extraEnv`.
The old overlay spelling, `MCP_GATEWAY_SERVER__PROTOCOL_REVISION_WINDOW`, is
ignored with no warning: it was a config overlay, and the key it set is gone.
A hot reload does not stop a recording window.

  `` `server.protocol_revision_window` is ignored since 4.0: the measurement window is an operator instrument: start the gateway with `--protocol-revision-window record` or `MCP_GATEWAY_PROTOCOL_REVISION_WINDOW=record`. Delete the key, or run `mcp-gateway upgrade`. ``

**Set through the environment.** A retired key set as an `MCP_GATEWAY_*`
overlay variable is ignored with no warning, because the unknown-key check
reads the config file only. The same holds for a misspelled overlay under
`security.signature_chain`, which a strict refusal no longer catches.

Copy-paste check: `mcp-gateway upgrade --dry-run` names every retired key the
file still sets, and the line it would remove.
