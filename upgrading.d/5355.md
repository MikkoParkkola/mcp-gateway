## The library's reload entries ask the restart gate

**Startup:** no notice

- What changes: `ReloadContext::reload` and `ReloadContext::reload_outcome` take the restart gate's admission before they reload gateway.yaml, as the web UI's reload route and the admin reload tool already did. While a restart is being prepared, restarting or stopping, they return the gate's refusal text and leave the running config as it was. No method is removed.
- What changes for writes: `ReloadContext::write_and_reload_outcome` and `ReloadContext::mutate_and_reload_outcome` (and their `_within` forms), which the library's `write_config_and_reload_outcome` and `mutate_config_and_reload` use when given a live context, take the gate's admission before any lock. While a restart is being prepared they write nothing and answer "a restart is being prepared; retry"; restarting or stopping, the gate's own text.
- What stays: `ReloadContext::reload_identity_grants` stays ungated, so a revoked grant applies while a restart is being prepared. The gateway binary's own reloads and its CLI config writes, which pass no live context, are unchanged.
