## Allowed folders for file tools

**Startup:** no notice, a log warning when a folder rule's root does not resolve, when a folder rule covers the capabilities backend, or when a secret rule injects into a declared path argument

**Why a setting.** A tool's input schema says what type an argument has, but no schema marks a path, so the gateway cannot tell on its own which argument names a file. A folder rule says which arguments hold paths (`path_args`) and which folders they may name (`allowed_roots`).

```yaml
security:
  firewall:
    rules:
      - match: "read_text_file"
        servers: ["filesystem"]
        action: block
        reason: "files stay in the project folder"
        allowed_roots: ["/srv/data", "~/projects"]
        path_args: ["path"]
      - match: "read_multiple_files"
        servers: ["filesystem"]
        action: block
        allowed_roots: ["/srv/data", "~/projects"]
        path_args: ["paths[]"]
      - match: "move_file"
        servers: ["filesystem"]
        action: block
        allowed_roots: ["/srv/data", "~/projects"]
        path_args: ["source", "destination"]
```

Write one rule per tool, naming that tool's own arguments: a declared argument a tool lacks is refused as missing, so a glob such as `*_file` that also covers `move_file` refuses the tools it does not fit.

**The `path_args` grammar.** `name` is a string argument, `name[]` an array of strings, `a.b` a nested key. A trailing `?`, as in `name?` or `name[]?`, marks an argument a call may omit; without it, a call that omits the argument is refused.

**What a folder rule decides.** Its `action` is `warn` or `block` (`allow` is refused at load), its `scan` stays empty, and it decides only its own findings: a warn folder rule never softens a credential or injection finding. A path outside every root is a `path_outside_root` finding its own rule decides. Anything the check cannot judge is a forced block whatever the action, a `root_refused` finding with a reason code. docs/FIREWALL.md lists the codes.

**Limits.**

- Only an argument named in `path_args` whose whole value is a path is confined. A path inside a command, file contents or a JSON-encoded string is not.
- A stdio backend that runs in a container or on another host (`command: docker run ...`, `command: ssh host ...`) sees its own filesystem; the gateway resolves against the host's, so the two views can differ.
- A symlink swapped between the gateway's check and the backend's open defeats the check. Keep the backend's own folder check as a second line.
- Under a folder rule only normalised absolute native paths are accepted. A backend that accepts relative paths, `..` or URIs gets a refusal for them.
- Remote backends (Http, WebSocket, A2a) are refused, not checked, under a folder rule.
- A root rule refuses capability calls; confine CLI capabilities with `capabilities.files`.
- A missing path whose Unicode-equivalent spelling exists in its folder is refused. A backend that respells a missing path by other rules of its own (case folding, other normalisations) can still defeat the check. An allowed root should hold no symlink that leads out of it.
- A folder with more than 10,000 entries refuses every path through it, a new file included.
- On Windows a trailing dot or space and an 8.3 short name are refused, since Windows resolves them to another name; a file really named with `~1` is refused there.
- On a filesystem whose canonical form keeps the spelling given while matching case-insensitively, such as a Linux case-folding mount, a differently cased spelling of an inside path is refused. It is a refusal, never a wrong allow.

**For code that uses the gateway as a library.** `ScanType` is now `#[non_exhaustive]`: a match on `mcp_gateway::security::firewall::ScanType` outside the gateway needs a wildcard arm (`_ => ...`), so new scan types can arrive in a minor release. It gains `PathOutsideRoot` and `RootRefused`, and `FirewallRule` gains the `allowed_roots` and `path_args` fields.

**Audit format.** A `root_refused` finding's row carries a new optional `reason` field holding its code. Rows for every other finding are unchanged. A reader that refuses unknown fields needs updating before it reads rows from this version.
