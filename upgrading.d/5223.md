## A served start settles crashed config writes before it serves

**Startup:** no notice; refuses to start, only for leftovers of a crashed config write that cannot be finished

What you gain: no start serves on a half-finished config write. `mcp-gateway
serve` locks the config before reading it. If another process holds the lock,
the start waits for up to 30 seconds and then gives up. A dead writer's journal
or abandoned config-write file is finished and recorded in the audit log this
gateway will serve with, and only then do backends start. A retired manifest,
which this release cannot read, stops the start instead. With the audit log
turned off, an abandoned file is left where it is for a later start that has
the log.

What you keep: with nothing left over, a start behaves as before. Hot reloads
already followed the same rule.

What changes:

- When the leftovers cannot be settled, the start stops and prints one fixed
  sentence that tells you what to do. For a write made by an older release
  (a v1 journal), the error logged right before that sentence lists the
  journal file, the saved original and the manual recovery steps. If finishing
  that write would put back a config that fails to load, the start now says so
  directly.
- The lock is a small hidden file beside the config, `.gateway.yaml.lock`
  (the name follows your config file's name). A start creates it now, even when
  the config is never written; in a folder no writer can use (a read-only one,
  say) the start finds nothing pending and reads the config without a lock. The file is empty and harmless to keep. The
  gateway does not delete it: removing it while someone holds the lock would let
  a second writer lock a fresh file. With no gateway and no CLI write running,
  deleting it is fine, and the next start recreates it. If your config sits in
  a git repository, list the file in `.gitignore`.
- For library code: `Gateway::new`, `Gateway::new_with_path` and
  `Gateway::new_evaluated` now open the configured transparency log during the
  build and keep its writer lease for the gateway's lifetime. Building a second
  gateway on that log while the first still exists fails straight away, with
  the log named in the error. Drop the old gateway first. A constructor given a
  config path (`Gateway::new_with_path`, `Gateway::new_evaluated`) also checks
  beside that config for an unfinished write, so it can wait up to 30 seconds
  for the config lock before it refuses; a long pause there is that wait, not a
  hang.
- With auth off, the audit log is opened once, as the gateway is built. If that
  open fails (say its folder is not mounted yet), the gateway warns and serves
  without a log, and it does not try again later: once the folder is there,
  restart the gateway to get audit records. The exception is a config whose
  folder still holds work a crashed write left behind, an abandoned file or a
  journal that owes audit records: those records need that log, so the start
  refuses instead of serving. Mount the log's folder, then start again.
