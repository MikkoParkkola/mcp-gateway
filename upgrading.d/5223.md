## A served start settles crashed config writes before it serves

**Startup:** no notice; refuses to start, only for leftovers of a crashed config write that cannot be finished

What you gain: no start serves on a half-finished config write. `mcp-gateway
serve` locks the config before reading it. If another process holds the lock,
the start waits for up to 30 seconds and then gives up. A dead writer's leftovers
(its journal, an abandoned config-write file, or a retired manifest) are
finished and recorded in the audit log this gateway will serve with, and only
then do backends start.

What you keep: with nothing left over, a start behaves as before. Hot reloads
already followed the same rule.

What changes:

- When the leftovers cannot be settled, the start stops and prints one fixed
  sentence that tells you what to do. For a write made by an older release
  (a v1 journal), the error logged right before that sentence lists the
  journal file, the saved original and the manual recovery steps. If finishing
  that write would put back a config that fails to load, the start now says so
  directly.
- The lock is a small hidden file beside the config, `.gateway.yaml.lock`
  (the name follows your config file's name). Every start creates it now, even
  when the config is never written. The file is empty and harmless to keep. The
  gateway does not delete it: removing it while someone holds the lock would let
  a second writer lock a fresh file. With no gateway and no CLI write running,
  deleting it is fine, and the next start recreates it. If your config sits in
  a git repository, list the file in `.gitignore`.
- For library code: `Gateway::new`, `Gateway::new_with_path` and
  `Gateway::new_evaluated` now open the configured transparency log during the
  build and keep its writer lease for the gateway's lifetime. Building a second
  gateway on that log while the first still exists fails straight away, with
  the log named in the error. Drop the old gateway first.
