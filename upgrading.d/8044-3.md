## `mcp-gateway upgrade` exits 1 when it leaves a key that blocks loading or cannot read the file

**Startup:** no notice

- What you lose: `upgrade` used to exit 0 in both cases below. It now exits 1, under
  `--dry-run` and `--quiet` too; with `--quiet` it prints one line.
  - A removed key or a plaintext API key stays in the file because upgrade could not change it
    alone. It names each one. The version stamp and data migrations still run first, so a rerun
    after the hand fix has nothing left to do.
  - The file cannot be parsed as a config (not YAML, or its top level is not a mapping of keys,
    `~` included). Upgrade changes nothing, runs no migration, and says where: a line and a
    column, never text from the file, which may hold a secret.
- What stays the same: an empty or comments-only file passes. A `meta_mcp.cache_tools` that
  stays still exits 0: it loads. A config that parses but needs something from the host that
  runs the gateway (an env var, a file) is checked by the gateway's own load, not by upgrade.
- What you gain: a script or CI job that runs `upgrade` sees that the config needs a hand fix,
  instead of finding out when the gateway does not start.
- What you do: when `upgrade` exits 1, fix what it names, then run it again.
