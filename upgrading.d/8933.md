## Windows lock files and lock directories

**Startup:** no notice; refuses to start

**What you lose.** Nothing that worked before, unless a lock directory lets Everyone, Anonymous or a specific other account create files in it: that directory is now refused, and the gateway does not use it until its permissions are tightened.

**What you gain.** Another local account can no longer hold one of the gateway's lock files and stall its writes to the grant journal, the audit log, OAuth registration and refresh, the control-plane store or protocol telemetry. The gateway creates each lock file owner-only. An existing lock file that is not owner-only (every one an earlier version created) is replaced on first use, once nothing has it open. A lock file another process still holds, for example an older gateway during the upgrade, is waited out up to the lock's usual deadline and then refused with the file and what to do.

**Lock directories.** A directory that only `BUILTIN\Users` or Authenticated Users may create files in is common outside the user profile (another drive, `C:\ProgramData`), so it is used, with one warning per directory naming it, the group and the repair; `mcp-gateway doctor` shows the same finding as a `lock-directories` warning. Another local account could still place a lock file there before the gateway does. A directory that Everyone, Anonymous or a named other account may create files in, has no access list, or sits behind a link is refused.

**What you do.** Usually nothing. For a refused lock file, stop the process holding it. For a refused or warned directory, follow the message: disable inheritance on the folder, keep full control for the gateway's account, and remove the other accounts' rights to create, delete or change files in it.
