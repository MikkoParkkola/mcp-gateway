## Verified identities and gateway tokens can no longer be read from bytes

**Startup:** no notice

**Who is affected.** Code that links the `mcp-gateway` library and deserialized `key_server::oidc::VerifiedIdentity` or `key_server::TemporaryToken`, possible since 3.x. Operators who only run the gateway binary are not affected.

**Before.** Both types derived `Deserialize`. Any bytes that parsed, for example `{"subject":"","email":"","issuer":""}`, became a `VerifiedIdentity` without an OIDC token ever being verified. That includes one naming nobody, which the gateway's own checked constructor refuses.

**After.** `serde_json::from_str::<VerifiedIdentity>(..)` and the same call for `TemporaryToken` fail to compile (`E0277`, the trait `Deserialize` is not implemented). Serializing either one still works, so audit output is unchanged. The gateway itself never read either back: its token store is in memory, and a subscription row it writes to disk now stores the identity in its own form and checks it again on every read (an identity naming nobody is refused; the check is not a new verification).

**What you do.** Stop deserializing these types. A `VerifiedIdentity` stands for a verification the gateway made, and reading one from bytes skipped that verification. Removing `Deserialize` closes that path only. In this release its fields are private as well (see the item on verified identities no longer being built or changed outside the gateway), so outside code can no longer build or change one either. Do not treat a `VerifiedIdentity` your own code built or read back as verified. If your code kept one to read back later, store the fields in a type of your own and treat what you read back as an unverified claim.
