## Stored answers: served without public provenance signatures while a secret is held

**Startup:** no notice

**Who is affected.** Clients that verify `public_signature` (see `docs/provenance-public-key.md`) on stored answers: response-cache hits, idempotency replays, `tasks/get` results and task notifications, on a gateway with any secret value held (a backend with a configured or sent secret).

**Before.** A stored answer was scrubbed against the secret values held when it was served, but kept the `public_signature` made before that scrub. Its payload carried the digest of the unredacted result, so a client could test guesses of a removed value offline, and the reference verifier answered `ResultMismatch` for any answer the scrub changed.

**After.** While any secret value is held, every `public_signature` in a stored answer is removed before the scrub, at any depth and in chain and playbook steps carried in `content[0].text`. The receipts stay. A fresh delivery is sealed as before, and with no secret value held stored answers keep their seals. A stored answer the scrub redacted whose text names `public_signature` without parsing as JSON is refused with the fixed refusal.

**What you do.** Nothing on the gateway. A verifier that requires a public signature treats a stored answer with a receipt but no `public_signature` as unsigned, and asks for a fresh call when it needs one.
