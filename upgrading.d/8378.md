## A control character no longer renames a key the gateway reads

**Startup:** no notice

What you gain: with `security.sanitize_input` on (the default), a client can no
longer reach a gateway field, or switch on a gateway directive, by hiding a
control character inside a key. Stripping used to turn `ser\u0007ver` into
`server` and `_fu\u0007ll` into the `_full` directive (which turns off response
projection). Such a key is now refused with `-32600` ("Input contains control
characters which are not allowed in a protocol field"), and nothing is
dispatched.

What you lose: on `/mcp` and stdio, these requests are refused where they used
to run:

- a meta tool's own argument key with a control character, whether the
  arguments are an object or a JSON string; for `gateway_execute`, also a chain
  step's own key;
- a key with a control character under `gateway_invoke`'s `arguments._meta`
  (trace context, prompt cache key);
- in any tool arguments the gateway reads directives from, a key that becomes
  `_full` or `_claim` once the control character is stripped. That means
  `gateway_invoke`'s and `gateway_execute`'s inner `arguments`, each chain
  step's `arguments`, and a surfaced tool's own arguments.

A call to a passthrough backend is refused too: the exemption still spares the
values, but no longer the keys the gateway reads, as on intake already. A task
stored by a gateway with `sanitize_input` off and resumed by one with it on is
refused at re-admission instead of being stripped or sent as stored.

Unchanged: any other key inside tool arguments is the tool's own data, and its
control characters are still stripped. `/mcp/{name}` is unchanged; there a
`_full` is the tool's own parameter. With `sanitize_input` off, nothing is
refused.

What to do:

- If a client hits the new `-32600`, have it send the key without the control
  character. A client sending ordinary keys sees no change.
