## With auth on, the audit log is on by default

**Startup:** no notice

What you gain: an authenticated config needs no audit-log line. This replaces
item 43's rule that `enabled: true` must be written. With `auth.enabled: true`
and no `security.transparency_log` section, the log is on at its default path,
`~/.mcp-gateway/transparency/transparency.jsonl`. A section that sets only
`path` turns it on at that path.

```yaml
auth:
  enabled: true
  bearer_token: "env:MCP_GATEWAY_TOKEN"
# no security.transparency_log section: the audit log is on
```

What you keep: the rule from item 43. With auth on the log is required, so
`security.transparency_log.enabled: false` with auth on still fails the load,
and so does a blank `path`. With auth off, nothing changes: the log is off
unless you turn it on. `mcp-gateway add`, `remove` and the other commands that
rewrite the config do not add an `enabled` line you did not write.

What you lose: nothing in a config file.

Library users: `config.security.transparency_log.enabled` on an
`mcp_gateway::config::Config` changes from `bool` to `Option<bool>`, where
`None` means "on exactly when auth is on".
Code that sets it writes `enabled = Some(true)`; code that reads it calls
`is_enabled(config.auth.enabled)`, which applies the default. The
`From<&TransparencyLogConfig>` conversion into the runtime logger config is
gone: an unset switch means nothing without the auth setting, so the gateway
builds that config internally.

What to do:

- Nothing, for a config file. You may delete `enabled: true` from an
  authenticated config.
- In library code, replace `enabled = true` with `enabled = Some(true)`, and
  read the switch through `is_enabled`.
