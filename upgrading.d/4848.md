## Look up issuance rows by email

**Startup:** no notice

`POST /ui/api/key-server/audit/lookup-email` takes `{"email", "limit"?, "from"?, "to"?}` for a first page, or `{"cursor", "limit"?}` for a next page (never both, and no window beside a cursor), and answers the retained `token.issued` rows whose keyed email hash matches, newest first, with `next_cursor`, `scan_exhausted`, `cursor_reset` and `scope: "retained"`. It needs gateway-wide admin standing: a backend-scoped admin, an auditor, an ordinary key and an anonymous caller are refused. The email is hashed for the one request and is never stored, logged or echoed; there is no hash-to-email table. `next_cursor` is an opaque sealed token: it carries the keyed hash and the window, bound to the credential that got it (a dashboard session binds to its own session), valid for five minutes, a chain of pages for fifteen, and good for one page; a token that does not open for any reason is one fixed 400 (`the page token is not valid; run the lookup again`). Tokens end when the gateway restarts, as key-server tokens do, and a page response lost on the wire has already spent its token: run the lookup again.

An empty answer proves nothing about the past: only rows still retained are searched, mints under best-effort audit may have written no row, and rows from before this release carry no issuance record. Legacy plaintext records are never searched by email.

Every authorized attempt, including a malformed one, is charged to one budget per process: two lookups at once, then one every six seconds (`429` with `Retry-After`). With several replicas the capacity is per replica. The counters `mcp_key_server_lookup_attempts_total` and `mcp_key_server_lookup_throttled_total` carry no labels; the `McpKeyServerLookupVolume` alert fires on sustained volume. A stolen admin credential can still guess candidate emails at the allowed rate; the budget limits that, it does not prevent it.
