## Backend protocol directives are scoped to where the protocol puts them

**Startup:** no notice

What you gain: a backend could put a task handle, a continuation or cache
hints on any answer, for example a cache hint on a prompt or on an interim
answer, or a task handle on a call that asked for none, and a client or the
gateway's caches could act on it. Now each one reaches the client only where
the protocol lets a backend send it.

What changes:

- `requestState` is kept only on an `input_required` answer to `tools/call`,
  `resources/read` and `prompts/get`.
- `cacheScope` and `ttlMs` are kept only on a final, non-error answer to
  `tools/list`, `prompts/list`, `resources/list`,
  `resources/templates/list`, `resources/read` and `server/discover`. The
  gateway no longer adds its own cache hints to an interim answer either.
- `taskId` and `ttlMs` are kept on a task handle answering a task-augmented
  `tools/call` the gateway sent, and on a `tasks/get` answer. A task
  envelope's stored `result` loses all four.
- A task handle (`resultType: "task"`) answering a call that did not declare
  the tasks extension is refused. Through `gateway_invoke` or a surfaced
  tool name the call answers a tool error: `isError: true`,
  `_recovery.error_code: "INVALID_PARAM"`, and a text that names the backend
  and says it answered with a task handle to a call that did not declare the
  tasks extension. With signature chains in `require` mode this answer used
  to be a `-32001` error naming `interim`.
- One warning per answer names the backend, the method and the removed
  members, never their values. A signature chain from an upstream gateway
  still verifies.

What you do: a client that keyed on `-32001` for an unrequested task handle
reads the tool result instead: `isError: true` and `_recovery.error_code:
"INVALID_PARAM"`. Through `gateway_invoke` that tool result is the JSON text
in the answer's `content[0].text`; through a surfaced tool name it is the
answer's `result` itself.
