## The capability editor saves only what you loaded

**Startup:** no notice

The capability routes used to write whatever text arrived, unlocked and not
atomically, with no check that the file was still the one the editor loaded.
A pinned file saved that way no longer matched its pin, and the loader then
dropped the capability on the next reload.

What changes:

- **`PUT` and `DELETE` need `If-Match`.** Send the `ETag` that `GET
  /ui/api/capabilities/{name}` answers (the SHA-256 of the file's bytes,
  quoted or bare). Without it the answer is 428 and nothing is written. If
  the file changed since you read it, the answer is 409 `stale` with a patch
  from the current file to your text and the current hash; nothing is
  written. A save answers the new `sha256` (and `ETag`): send that as the
  next `If-Match`, because the bytes written can differ from the text sent.
- **A save keeps the pin valid.** A pinned file's `sha256:` line is
  rewritten in place for the bytes written; comments, order and line endings
  stay. Removing the pin line is refused (409 `unpin`): unpin with the `cap`
  command or by hand. A file whose bytes no longer match its pin cannot be
  edited (409 `pin_mismatch`); review it, then run `cap pin`, restore a
  version, or delete it.
- **What a save accepts is what loads.** The editor runs the loader's own
  checks, including the account binding, so a saved file is never dropped on
  reload. Errors name their line and column, or their field.
- **`PUT` to a name with no file answers 404.** Create with `POST
  /ui/api/capabilities`.
- **A capability file that is a symlink is refused** for every change (409
  `symlinked`, naming where the file lives). A symlinked capability
  directory works as before.
- **New: `POST /ui/api/capabilities/{name}/validate`** answers whether the
  text would load, the diff a save would make and the pin before and after.
  It writes nothing and is not recorded in the audit log.
- **`cap pin` waits for the capability directory's lock** and writes
  atomically, so it never lands between an editor's check and its write.
- **Windows: a save writes the file owner-only.** Keeping the directory's
  permissions could widen a private file that holds a token; owner-only
  never widens. The gateway reads the file as its owner. A file you had
  shared with other accounts must be shared again after a save.

What you gain: a save never erases a change you did not see, never breaks a
pin, and never writes a file the gateway would refuse to load.
