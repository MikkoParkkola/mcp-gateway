## Cancelling a task cancels its upstream task

**Startup:** no notice

**What you gain.** When a task's backend accepted the call as an upstream task (the
`tasks.recovery_adapters` path), the owner's `tasks/cancel` now reaches that backend: the
gateway sends it a `tasks/cancel` naming the backend's own task id, through the same trusted
adapter and gateway credential its `tasks/get` reads use. Any answer from the backend
confirms it, and its content is not acted on. A cancel the backend does not answer (a timeout, a backend that
was not ready, or a gateway stopped between the claim and the send) stays pending and is sent
again when that backend next starts and by the expiry sweep, until 6 failed sends or 24 hours
(#3808; see the note on unconfirmed upstream cancels). This holds whether the gateway is still
following the job, has stopped following it, or learns the handle only as the cancel lands.

**What stays the same.** A backend the adapter does not claim is never sent anything. A task
whose upstream task id the gateway never received (the cancel won before the backend's reply
arrived) cannot be cancelled upstream: the gateway closes its stream, which is all the
specification allows. That case is not retried.

**What you do.** Nothing. Before rolling back to a beta, back up `tasks.store_dir`: a cancelled
task whose upstream cancel was sent is recorded as version 7, which a beta refuses.
