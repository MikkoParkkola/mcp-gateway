## `api_key:<name>` grants match only that API key

**Startup:** no notice; refuses to start, for a `key_server.oidc` provider whose `issuer` is `mtls`, `agent_oauth` or `api_key`

**What you gain.** An `api_key:<name>` grant subject names one API key, and now
only that key matches it. Before this release the grant fallback read the
caller's display name whatever the credential was, so the static bearer (named
`bearer`), the dashboard session (`dashboard`), auth-off callers (`anonymous`)
and public-path callers (`public`) each matched a grant written for an API key
of that name.

**What you lose.** Four subjects stop matching their accidental callers:
`api_key:bearer` no longer admits the static bearer, `api_key:dashboard` no
longer admits the dashboard session, `api_key:anonymous` no longer admits
auth-off callers, and `api_key:public` no longer admits public-path callers.
Admin standing never satisfies a Personal grant, so the static bearer and the
dashboard session, though admin, lose any personal capability those grants gave
them. A `key_server.oidc` provider whose `issuer` is `mtls`, `agent_oauth` or
`api_key` is now refused at startup and on reload: its tokens would otherwise
arrive as verified subjects under an authority the gateway mints itself.

**What you do.**

- Turn auth on (`auth.enabled: true`) and give each affected caller a named API
  key in `auth.api_keys` whose name the grant names.
- Point a reserved `key_server.oidc` issuer at the provider's real https issuer
  URL.
- A search of shipped configs, fixtures and docs at `c01cfbfd3` found 0 uses of
  these four subjects and of those three issuers, so only an operator's own
  grant files or config can be affected.
