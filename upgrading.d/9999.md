## One email hash on every build

**Startup:** the key server refuses to start on a build that normalizes differently

The keyed `email_hash` used to lowercase with the compiler's own Unicode tables,
so two builds could hash one address differently and an admin lookup would miss
silently. Normalization version 1 now uses tables the crate owns (frozen at
Unicode 17.0.0, reproducing the old output exactly, final-sigma rule included)
and exact versions of the NFC crates. When the key server starts it checks 21
known answers before it reads or creates any key, and refuses to start with the
mismatching answer named. A normal release binary passes; a source build that
resolves other dependency versions does not.

**Surrounding white space is trimmed.**

An address is trimmed of Unicode White_Space at both ends before it is hashed,
at issuance as well as at lookup. An address that arrived padded (spaces, a
no-break space, an ideographic space) now hashes like the clean address.
Whitespace inside the address, and characters that only look blank (zero-width
space, byte-order mark), still count as part of it.

**`subject_hash` is its own value.**

The warning for an email-shaped OIDC subject logs the subject's keyed hash under
its own domain (`subject-v1`) and exactly as given (no case folding). It no longer
equals the `email_hash` that issuance records for the same address. The retained
rows carry the subject itself, so no lookup depended on the match.
