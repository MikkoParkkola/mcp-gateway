## A backend's allowed_tools

**Startup:** no notice

**What you gain.** `backends.<name>.allowed_tools` names the only tools that backend offers, to every caller. It uses the grammar of an API key's `allowed_tools`: an exact name or a trailing `prefix*`, matched on `tool` or `server:tool`. A tool outside the list is left out of every tool list and refused by name on every route, as an absent tool. That includes a tool the server adds later. The web UI's add and edit API (`POST`/`PATCH /ui/api/backends`) take the list, and a preview marks which tools can be ticked (`selectable`); the screens that tick them come with the web UI redesign. Leave the key out and the backend offers every tool, as before.

It narrows; it never widens. A call must pass all three tool scopes: the API key's `allowed_tools` and `denied_tools`, this list, and the global `security.tool_policy`. An `allow` in one of them does not bring back a tool another leaves out. Like the other scopes, the list is judged when a call is admitted: a call admitted before you narrow the list finishes its own retries.

**What you lose.** Nothing for a config without the key.

**What you do.**
- A `BackendConfig` struct literal in your own crate needs `allowed_tools: None` (or a list).
- **Before a rollback:** an older binary ignores `allowed_tools` and exposes every tool. On 3.5.x the key is ignored without a word, so a backend you limited offers everything again. Before rolling back, disable each backend that sets `allowed_tools`, and enable it again only once you have checked what the target version offers. A 4.0 pre-release without the key refuses to start on it instead.
