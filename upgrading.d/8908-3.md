## Backend `env` and `headers` are secret slots

**Startup:** no notice; refuses to start, only for an enabled backend's reference that does not resolve

A backend's `env` and `headers` values used to pass through as text, apart from `${VAR}` expansion. In 4.0.0 a value that is a whole `env:NAME`, `file:/abs/path` or `keychain:NAME` reference resolves to the secret, as stored (a `file:` value drops one trailing newline, as in every slot), for every enabled backend. This is the same grammar as every other secret slot (ADR-028).

- What changes:
  - A value spelled `keychain:x`, `env:x` or `file:/x` is now a reference.
  - A value that only contains one, such as `Bearer keychain:x`, stays text.
  - `${VAR}` expansion is unchanged.
- Refusals: a reference that does not resolve fails the load, naming the field and the entry. Saves through the web UI (answering 422), `mcp-gateway add`, `discover --write` and the setup import refuse it before writing anything.
- Rotation: a rotated `file:` or `keychain:` backend secret is picked up at the next reload (`gateway reload`, a config edit or the web UI), and that backend restarts with it.
- What you do: if a backend value must literally start with `env:`, `file:` or `keychain:`, put it in an env file and write `env:NAME`, or in an owner-only file and write `file:/abs/path`. The resolved value is used as stored and never read again as a reference.
- Response codes: POST `/ui/api/backends` with a reference that does not resolve answered 201 and wrote the text; it now answers 422 and writes nothing. PATCH `/ui/api/backends/{name}` answered 200; it now answers 422.
