## Key-server audit records hash the email

**Startup:** no notice; refuses to start, when `key_server.enabled` is true and no audit log is open, or when the hash key file is missing but the audit log shows a key existed

**What changed.** Every key-server audit line (`token.issued`, `token.used`, `token.revoked`) used to carry the verified identity in full, email included. It now carries the subject, the issuer and `email_hash`, a keyed hash of the email, with `email_hash_version` (the normalization and hash version, 1) and `email_hash_key_id` (SHA-256 of the key, which names the key without being it). The name and groups are no longer written. Policy and refusal log lines name the issuer and subject instead of the email.

The same email always gives the same `email_hash` on one installation, so one person's records still correlate; two installations give different values. Version 1 normalizes the address with NFC, then Unicode lowercase, then NFC again, so `Ada@X.org` and `ada@x.org` meet; both tables are Unicode 17.0.0 (lowercase from the Rust standard library, NFC from ICU 78 data). The domain part is not IDNA-converted: an address with an `xn--` domain and the same address with the Unicode domain hash differently.

**The hash key.** The key is 32 random bytes kept in `key-server-email-hmac.json` in the gateway data directory, owner-only, created on the first enabled start. To provide your own key instead, set `key_server.audit_email_hmac_secret_ref` to a secret reference (`env:`, `file:` or a keychain name) holding exactly 64 lowercase hex digits; generate one with `openssl rand -hex 32`. The file then records only that a configured key is in use, and its id; back up both the file and the secret. Moving the same key from the file to a reference is allowed; a different key is refused, since every earlier record would stop matching.

**Back it up.** Losing `key-server-email-hmac.json` loses the link between earlier records and any later lookup. The gateway records each new key in the audit log, so a start that finds the file missing while the log shows a key existed refuses instead of making a new key:

```text
<data dir>/key-server-email-hmac.json: missing, but retained audit records carry an email_hash; restore the file from backup (a new key would make every earlier record unfindable)
```

Restore the file from backup. An unreadable audit log segment also refuses the start.

**The key server requires the audit log.** With auth on, the audit log is already required. With auth off, a start with `key_server.enabled: true` and no audit log now refuses:

```text
key_server.enabled needs the audit log: set security.transparency_log.enabled: true with a writable path (the log records the email-hash key, so a lost key file is refused, never replaced silently)
```

Set `security.transparency_log.enabled: true` with a writable `security.transparency_log.path`.

**Subjects that are email addresses.** Some identity providers use the email as the OIDC subject. The subject is the stable identifier tokens and revocation key on, so it is still logged as it is. The gateway logs one WARN per provider that sends email-shaped subjects; the warning carries only the subject's `email_hash`. A later release may replace email-shaped subjects with a pseudonym.

**Library API.** For code built against `mcp_gateway`:

- `key_server::audit::AuditEvent::identity` is now `Option<SafeIdentity>` (subject, issuer, `email_hash`, `email_hash_version`, `email_hash_key_id`) instead of `Option<VerifiedIdentity>`.
- `AuditEvent::issued` and `AuditEvent::used` are crate-internal; they need the installation key. `AuditEvent::expired` is removed: the gateway never emitted a `token.expired` record. `AuditEvent::revoked` takes `Option<SafeIdentity>`.
- `KeyServer::new` is crate-internal and takes the installation key; `KeyServer` can no longer be built with a struct literal outside the crate.

**Rollback.** After a rollback, an older release writes the email into audit lines again. Keep `key-server-email-hmac.json`: rolling forward again reuses it, and records written in between stay matched.

**Each key mint now writes an audit row.** A mint appends a `token.issued` row (subject, issuer, `email_hash`, `email_hash_version`, `email_hash_key_id`, the token id and scopes; never the email, name or groups) to the audit log and waits for it to reach disk before the token becomes valid. With `security.transparency_log` set to fail closed, a mint whose row cannot be written, synced or confirmed in time answers `503` with `Retry-After: 1` and issues no token; a late row can still land for a token that was never issued. With best-effort, the mint goes on, logs a fixed warning and counts `mcp_key_server_issuance_rows_total{status}` (`not_attempted`, `failed` or `unconfirmed`). Use a durable audit volume (`audit.existingClaim` in the chart, a persistent path elsewhere): on an `emptyDir` the issuance rows are lost with the pod.
