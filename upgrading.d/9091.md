## A backend's own error is the backend's

**Startup:** no notice

**What changes.** `mcp_gateway::Error` gains `BackendJsonRpc { code, message, data }` (the enum is `#[non_exhaustive]`, so this is not a breaking change). A backend's JSON-RPC error carried on a non-retry HTTP status, in an in-band answer on the meta route, or on a list page arrives as `BackendJsonRpc`, with the same Display text and code `JsonRpc` had.

- `mcp_gateway_errors_total` counts a backend's error as `backend`, including a meta-route dispatch failure the gateway answers as an `isError` tool result (not counted before) and a playbook or chain step failure it reports or ends on.
- An audit record files a backend's -32001 or -32004 as `error`, not `denied`.
- A backend's error no longer forwards the gateway's recovery keys (required capabilities, elicitation mode, tool text) or its removed-method mark.
- A backend's error shaped like the gateway's account refusal is answered as the backend's failure: HTTP 500 with its own text on the direct route, a tool error on the meta route, never the 403 account refusal.

**What you do.** Nothing, unless you match `mcp_gateway::Error` yourself: add a `BackendJsonRpc` arm wherever you read a backend's code from `JsonRpc`. An audit query that counted a backend's -32001 as a denial now sees it as an error.

**Rollback.** Reverting this change restores the old counting and the old reading of a backend's codes; nothing stored depends on it.
