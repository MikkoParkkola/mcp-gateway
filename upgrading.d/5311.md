change: The OpenAPI import binds to its preview by a digest, and the import and capability create routes refuse when no capability directory is configured

## An OpenAPI import writes only what was previewed

**Startup:** no notice, nothing changes at startup

The preview (`POST /ui/api/import/openapi/preview`) answers a `digest` beside `tools`: the SHA-256 of the
document text it parsed. An import by `url` must send that digest back; without it (or with a blank one) the
import answers 422 before fetching anything. When a sent digest no longer matches the document's text, the import
writes nothing and answers 409. An import with an inline `spec` may send the digest and is then checked the same
way. The classic page does this for you.

With capabilities switched off, or on with no directory, both import routes and the capability create route
answer 409 before fetching or writing anything. Before, they wrote into a `capabilities` folder relative to the
gateway's working directory, which nothing loaded. This check comes before the route looks at what the body
asks for: with no directory, a body with no `url` and no `spec`, both, or an empty `spec` answers 409 where it answered 422
before, and an
import by `url` with no digest answers 409, not the 422 it gets when a directory is set. A body that is not JSON (400) or not the request's shape (422) is refused as
before. Turning capabilities on means editing gateway.yaml and
restarting; no settings field changes it.

A document with several security schemes of equal preference, a request body with several media types that are
neither JSON nor form, or two operations whose tool names are equal, now converts the same way every time (the
name that sorts first wins, then the path, then the method). A re-import of such a document may name a
different scheme or keep a different operation than a 3.x import happened to.
