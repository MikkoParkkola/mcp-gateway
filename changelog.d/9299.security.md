- **Every rewrite of gateway.yaml reads it through the same mode and owner check as every loader.** The web UI's config writer, the locked text editor behind `mcp-gateway init` and `mcp-gateway upgrade` (and its backend URL-key migration), the locked config writer behind the web UI and reload-API writes (which fell back to a plain read when the checked load refused the file), and the writer's crash recovery each reread gateway.yaml with a plain read, then wrote it back owner-only; crash recovery also restored a staged original, checked only against its journal's digest, as gateway.yaml. If another local account could write the file (group or world write), could read it (group or world read on a file the gateway owns), or owned it, that account's edit could be rewritten as a trusted owner-only file and loaded on the next start or reload. Each of these, and recovery's read of the journal and staged original, now refuses such a file before it records an intent, creates a secret entry or writes anything, and leaves the file's bytes and mode as they were. The discovery adopt route answers that refusal with 503 "gateway.yaml could not be loaded", naming no path, and logs the reason on the server; a gateway.yaml removed while an adopt runs answers 409 `no_config_file` instead of a 500. (MIK-9299)
  Affects: an admin using the web UI adopt route or other web UI and reload-API config writes, or an operator running `mcp-gateway upgrade` or `init`, on a gateway whose gateway.yaml another local account can write or owns.
  Operator action: none for an owner-only gateway.yaml (chmod 600); a command or write that now refuses the file names it and the fix, the same refusal the gateway gives at start, so fix the file's mode or owner and run it again.
