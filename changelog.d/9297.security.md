- **A gateway starting after a crashed config write now records the recovery in its audit log before it recovers.** A save that crashed mid-write leaves a journal beside `gateway.yaml`, and the next start puts the right file back. Until now that recovery wrote nothing to the audit log. The start now works out which config the recovery leaves (the original for an unfinished write, the new file for one a reload accepted), loads it, and appends a `config_recovery_intent` record to that config's audit log, then recovers. If the record cannot be written, the start refuses and recovers nothing: the config has auth on and no audit log, the config does not load, or its audit log cannot be opened (with auth on or off). The message names the journal and the steps to finish the recovery by hand. A 3.x gateway would have recovered and started. (MIK-9297)
  Affects: an operator whose gateway crashed or was killed during a config save, then restarts it with a config that names an audit log or turns auth on.
  Operator action: if a start is refused with a pending journal, fix the cause it names (usually the audit log's path or permissions) and start again, or finish the recovery by hand as the message describes.
