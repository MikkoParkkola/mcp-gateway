- **A reload or a config write can no longer put a firewall rule the firewall-on load refuses into a running firewall.** `security.firewall.enabled` and `auth.enabled` take effect only on a restart, but a reload's rules join the running firewall at once. A reload or write whose file said `enabled: false` skipped the rule checks, so it could publish a rule with an empty scope list, an exception setting no field, an invalid glob or a bad folder rule (which then blocked its scan types on every call), or a key reference no running caller could carry. While the firewall runs, such a reload or write is now refused, naming `security.firewall.rules[i]`, and the running rules stay; a key reference is also refused while the running gateway has no API-key authentication. A write that adds or changes such a rule is refused whether or not the firewall runs. `init` and `upgrade` keep an existing one byte for byte and warn. A firewall-off load warns once for each such rule, and the Policies screen's read model marks it with the load's message and how it compiles meanwhile. (MIK-9343)
  Affects: an operator whose `security.firewall.rules` hold a rule the firewall-on load refuses, or who reloads key-scoped rules before restarting with `auth.enabled`.
  Operator action: fix or remove each rule a warning names; to add a key-scoped rule while auth is off, restart with `auth.enabled` first.
