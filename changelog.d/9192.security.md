- **A grant subject that names no one cannot exist.** `GrantSubject::new` is the one constructor and returns `Result<_, EmptyIdentity>`, refusing an empty authority or subject; `GrantSubject::checked` is removed, the fields are private behind read-only accessors, and every deserialization goes through the same check, wherever the subject is nested. A grants file with a rule whose subject or owner names no one is refused at load, naming the file and every such rule; such a rule matched no caller, so it granted nothing; but the gateway kept the last rule per id, so a rule naming no one that shares its id with another rule may have been hiding it, and the refusal says so, because deleting it makes that rule active. `mcp-gateway upgrade` runs the same check on the grants file the gateway would load and fails naming the same rules; it edits nothing. (MIK-9192)
  The same check now treats a value of only whitespace as naming no one: an OIDC provider that returns a blank `sub` or `iss` is refused at sign-in as a token missing its required `sub` claim (401, no token issued), as an empty one already was.
  Affects: grants files with an empty or blank subject or owner; OIDC providers returning a blank `sub` or `iss`; library users who built `GrantSubject` with a struct literal or read its fields directly.
  Operator action: if startup or `mcp-gateway upgrade` names a grant rule naming no one, delete that rule from the grants file.
