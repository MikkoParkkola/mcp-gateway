- **A firewall rule's `scan` list now limits the findings it decides.** The list was documented but never read: a rule whose `match` covered the tool decided every finding in the call. An `allow` rule written for `scan: [credentials]` therefore also allowed a shell injection or path traversal in the same call, and a `warn` rule softened a high-severity injection to a warning. Each finding is now decided by the first rule whose `match` covers the tool and whose `scan` list holds that finding's type (an empty list holds every type), or else by its severity default, and the call or answer takes the most restrictive result. A rule with no `scan` list behaves as before. (MIK-8932)
  Affects: every release since 2.6.0 with `security.firewall.enabled` on and an `allow` or `warn` rule that sets `scan`. Operator action: none for configs without `scan` lists; where a rule sets one, check that calls it used to allow or warn on for other finding types are meant to be blocked by their severity default.
