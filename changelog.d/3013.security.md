- an OAuth backend no longer sends its client secret, authorization code or refresh token over cleartext `http://` to a host off this machine. The authorization server, token endpoint and registration endpoint that discovery returns, and every redirect from an OAuth request, must be `https://` or `http://` on a loopback host, under every destination policy. A loopback `http://` authorization server is reached directly, never through `HTTP_PROXY`/`ALL_PROXY`. A capability that sends a credential (`auth.required`) is held to the same rule: at load for a literal `base_url`/`endpoint`, and at send time for REST, GraphQL, JSON-RPC and its OAuth refresh (#3013)
  Affects: every release before 4.0.0, for OAuth backends whose authorization server or its advertised endpoints are `http://` off this machine, and for capabilities with `auth.required: true` whose API URL is `http://` off this machine. Operator action: such a backend now fails at connect, and such a capability file now fails to load (the warning names `providers.<name>.config.base_url` or `endpoint`). Move it to `https://`, or serve it on a loopback host (`localhost`, `127.0.0.1`, `[::1]`; `localhost.` with a trailing dot is not loopback). `allow_cleartext_credentials` does not cover either. If one ran over cleartext before, rotate the client secrets, refresh tokens and API keys it sent. See UPGRADING-4.0 item 146.
