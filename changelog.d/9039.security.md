- **A backend's notifications can no longer carry members only the gateway may write.** A notification a backend sends during a call (progress, a log message, a list change) reached the client with whatever members the backend put in it, including the gateway's own (`_security_findings`, `_meta["io.mcp-gateway/..."]` and the rest of the reserved set), which an answer already loses. Every notification on its way to a client now passes one ingress, whatever transport carried it: gateway-only members are removed, a signature chain or listen subscription tag in `_meta` is removed, and an MCP notification also loses the protocol members the protocol places elsewhere (`taskId`, `ttlMs`, `requestState`, `cacheScope`). A vendor's own notification keeps its fields. A task notification a backend sends (`notifications/tasks`, `notifications/tasks/status`) is withheld, since the gateway reports tasks under its own ids. Removals are logged with the backend, the method and the member names, never the values. (MIK-9039)
  Affects: 4.0.0 pre-release builds; no released version forwards in-call notifications. Operator action: none.
