- **A non-ASCII `agent_id` query parameter now decodes as UTF-8.** The query-string
  label decoded each byte as a separate character, so `agent_id=caf%C3%A9`, and a
  raw `café`, became the label `cafÃ©`. It now decodes as UTF-8. A value that is not
  valid UTF-8 (such as `%FF`, or `a%FFz`) yields no declared label, so the request is
  treated as if it sent no `agent_id`. `+` and a malformed `%` escape still stay
  literal. (MIK-8498)
  Affects: clients that send a non-ASCII `agent_id` in the query string. Where
  `agent_identity.known_agents` is set, also clients that send an `agent_id` that is
  not valid UTF-8 (for example `%FF`) without proving an identity: they were refused,
  because the garbled label could not satisfy `known_agents`, and are now admitted as
  unlabelled, the same as a client that sends no `agent_id` (which `known_agents` has
  never refused).
  Operator action: if `agent_identity.allow_unverified_agent_identity` is on, check
  `known_agents` for `declared` entries written in the garbled form (such as `cafÃ©`)
  and change them to the real id. With that setting off, a declared label never
  satisfies `known_agents`, and nothing needs changing.
