- **A non-ASCII `agent_id` query parameter now decodes as UTF-8.** The query-string
  label decoded each byte as a separate character, so `agent_id=caf%C3%A9`, and a
  raw `café`, became the garbled label `cafÃ©` (U+00C3 U+00A9 in place of `é`). It
  now decodes as UTF-8. A value that is not valid UTF-8 (such as `%FF`, or `a%FFz`)
  yields no label from the query, as if the query carried no `agent_id`; a readable
  `x-agent-id` header still supplies the label as before. `+` and a malformed `%`
  escape still stay literal. (MIK-8498)
  Affects: clients that send a non-ASCII `agent_id` in the query string. Where
  `agent_identity.known_agents` is set and `require_id` is off, also clients that send
  an `agent_id` that is not valid UTF-8 (for example `%FF`) without proving an
  identity: they were refused, because the garbled label could not satisfy
  `known_agents`, and are now admitted as unlabelled, the same as a client that sends
  no `agent_id`. With `require_id` on they are still refused.
  Operator action: look for agent ids written in the garbled form (such as `cafÃ©`)
  and change them to the real id. In `agent_identity.principal_labels` this matters
  in every configuration: a proven caller whose decoded label no longer matches a
  garbled entry is now refused as a contradiction. In the `declared` entries of
  `known_agents` it matters only when `allow_unverified_agent_identity` is on.
