- **A non-ASCII `agent_id` query parameter now decodes as UTF-8.** The query-string
  label decoded each byte as a separate character, so `agent_id=caf%C3%A9`, and a
  raw `café`, became the garbled label `cafÃ©` (U+00C3 U+00A9 in place of `é`). It
  now decodes as UTF-8. A value that is not valid UTF-8 (such as `%FF`, `a%FFz`, or a
  Latin-1 escape like `%E9`) yields no label from the query, as if the query carried
  no `agent_id`; a readable `x-agent-id` header still supplies the label as before.
  `+` and a malformed `%` escape still stay literal. (MIK-8498)
  Affects: clients that send a non-ASCII `agent_id` in the query string without a
  readable `x-agent-id` header. Where `agent_identity.known_agents` is set and
  `require_id` is off, an unproven client sending an `agent_id` that is not valid
  UTF-8 (for example `%FF`) was refused, because the garbled label could not satisfy
  `known_agents`, and is now admitted as unlabelled, the same as a client that sends
  no `agent_id`; with `require_id` on it is still refused. A client that sent a
  Latin-1 escape matching an allowlisted label (for example `%E9` for `é`) now sends
  no label instead. For a proven caller, an undecodable query `agent_id` no longer
  counts as a contradicting label.
  Operator action: look for agent ids written in the garbled form (such as `cafÃ©`)
  and change them to the real id, in `agent_identity.principal_labels[].labels` and
  in the `declared` entries of `known_agents[].id`. A garbled `principal_labels` entry
  can now refuse a proven caller as a contradiction, in any configuration, unless the
  label equals the caller's proven id or `allow_unverified_agent_identity` admits it
  as a `declared` entry. The `known_agents` entries matter only when
  `allow_unverified_agent_identity` is on.
