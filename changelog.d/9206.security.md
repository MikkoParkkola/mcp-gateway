- **A client certificate that names no one is never a certificate identity.** `CertIdentity::from_der` now answers `None` for a certificate that parses but has no SAN URI and no CN; production reaches it only from the TLS acceptor's verified peer chain. `CertIdentity` fields are private (read them through the accessors) and it no longer implements `Default`. The TLS identity layer still refuses such a certificate exactly as before (401, JSON-RPC -32000, before any route runs, `/health` included); it is never treated as "no certificate". (MIK-9206)
  Affects: library users of `CertIdentity::from_der`; mTLS deployments see no behaviour change.
  Operator action: none.
- **A blank SAN URI or CN in a client certificate is skipped.** A value of only whitespace names no one, like an empty one, so the gateway takes the first SAN URI that is not blank, else a non-blank CN: a certificate whose first SAN URI is blank now presents its next SAN URI (or its CN) as its identity, for grants, the firewall key and the agent check alike, and one left with no name is refused (401, JSON-RPC -32000). Any other value is kept exactly as written. (MIK-9206)
  Affects: mTLS deployments issuing client certificates with a whitespace-only SAN URI or CN.
  Operator action: grants for such a certificate must name the value it now presents; reissue a certificate whose only names are blank.
